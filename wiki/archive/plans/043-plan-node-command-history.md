# Immutable Node command history and submission ordering

Status: Complete — implemented and verified on 2026-10-06.

## Problem and evidence

1. A Node currently assigns `journalIndex` to a command row, `nodeIndex` to a local submission, and `changeIndex` to each mutation of that row. Execution usually overwrites the staged row. Sessions retain the same `sessionIndex` while replacing staging with execution. These overlapping identities obscure the distinction between retaining a record and submitting a command.
2. The mutable synchronization stream has a demonstrated ordering defect. Accept A and B, retain execution A at `executedIndex = 1`, retain execution B at `executedIndex = 2`, then retry acceptance of A or process its late admission receipt. Updating A's `changeIndex` moves its execution behind B. A subscriber starting before both executions receives execution 2 before execution 1, and the session importer rejects the gap.
3. Read-only diagnostic runs reproduced that defect using the actual AggregateNode and ServiceNode and their actual session importers with in-memory SQL.js databases. Both control cases imported `[1, 2]`; both retry cases and both late-admission cases delivered `[2, 1]` and rolled back with the corresponding session command-index-gap failure. These diagnostics are evidence for the design, not completed verification of this plan.
4. Current receivers and fixtures permit multiple executions of the same command ID in one bound execution stream. The traced server producers do not require that behavior: chain admission deduplicates command IDs, and execution advances through previously unexecuted admitted input. Separate aggregate versions are separate streams. The agreed invariant is at most one staged record and one executed record per command ID in a bound Node/session history.
5. Relevant current implementation: [AggregateNode](../../../packages/core/src/AggregateNode/AggregateNode.ts), [ServiceNode](../../../packages/core/src/ServiceNode/ServiceNode.ts), [aggregate importer](../../../packages/core/src/aggregateSession/importAggregateNodeCommands.ts), [service importer](../../../packages/core/src/serviceSession/importServiceNodeCommands.ts), [Node fixtures](../../../packages/core/src/Node/fixtures/commandOutcomes.ts), [aggregate admission](../../../packages/system-worker/src/AggregateChain/admitAggregateCommands/admitAggregateCommandsTx.ts), and [service admission](../../../packages/system-worker/src/ServiceChain/admitServiceCommands/admitServiceCommandsTx.ts).
6. [ADR 002](../../adrs/002-browser-node-journals-and-worker-routing.md) records the existing design. This plan changes its history/index decisions while retaining its AggregateNode/ServiceNode ownership and worker-routing decisions. [Plan 041](041-plan-session-command-index.md) is background for session row identity, not an implementation of this redesign.

## Agreed scope

1. Apply the redesign to both AggregateNode and ServiceNode, their session databases, subscription/recovery code, and the client/server submission protocol.
2. Replace the superseded design outright. Remove `journalIndex`, `changeIndex`, `afterJournalIndex`, `afterChangeIndex`, and the old session-command `pushIndex` alias for server admission. Do not add compatibility fields, alternate decoders, migrations, or dual protocols. Changed fixed schemas require empty storage; do not automatically delete user storage.
3. Preserve synchronous local staging, optimistic replay, resource checkpoints, command failure notifications, authentication, manual push/pause, and recovery after interruption. Preserve `AggregateNode` and `ServiceNode` ownership, SharedWorker routing, and existing storage/runtime lifetimes.
4. Update existing direct producers, including agent sessions, where the shared command schemas, importers, or websocket protocol change. Preserve their current ownership and lifetime; do not introduce SharedWorkers or a durable background agent runner.
5. History pruning, general event infrastructure, application redesign, and unrelated Explorer layout changes are outside scope. Update schema-derived views and in-scope consumers only as needed to reflect the implemented fields.
6. Preserve unrelated work already present in staging validation, tests, fixtures, and architecture documentation. Re-read those files before implementation and integrate the required changes without reverting other edits.

## Terms and ownership

| Term                               | Meaning after this cutover                                                                                                                                                                                                  |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                               | Command identity across staging, submission, and execution. A retry retains this ID.                                                                                                                                        |
| `nodeIndex`                        | Stable local primary key and append position of one record in one Node database. Every staged or executed record has its own position.                                                                                      |
| `pushIndex`                        | Dense outbound submission position for one originating `nodeId`. Assigned once when the Node durably accepts a new staged command; reused by every submission retry.                                                        |
| `sessionIndex`                     | Stable local primary key and retention position of one record in one session database. A staged record and its executed record have different positions.                                                                    |
| `admissionIndex`                   | Existing server admission position. It is not a local record key or a replication cursor. Keep its existing name where the protocol supplies it.                                                                            |
| `admittedThroughPushIndex`         | One durable Node metadata value, initially zero: the highest consecutive submission prefix known to have been admitted. It is delivery bookkeeping, not another allocated sequence.                                         |
| `outcomeIndex`                     | Existing contiguous completion watermark, now measured in `pushIndex`: every originating submission through this position has a retained executed result. It is not the maximum local record index or the admission prefix. |
| `executedIndex` and execution hash | Existing checkpoint for the bound server execution stream; retain the aggregate/service-specific hash and owner watermark meanings.                                                                                         |
| `afterNodeIndex`                   | A session's committed cursor into one Node's immutable record stream. Advance only after importing the corresponding ordered page successfully.                                                                             |

1. The Node owns allocation of `nodeIndex` and `pushIndex`. A Node-backed session owns only its `sessionIndex` allocator and its imported Node cursor. The server checks submission continuity using `(nodeId, pushIndex)`; gaps between submitted `nodeIndex` values are irrelevant because Node record positions are not submission positions.
2. Staged Node records have `pushIndex`; executed Node records do not allocate or inherit it. Relate the two records by command ID within the bound history. Preserve execution provenance already carried by server command contracts without confusing it with the retaining Node's local row identity.
3. Remove the obsolete `pushIndex` property from the public session command returned by synchronous staging and its decoder alias from `admissionIndex`. A command has not acquired a Node submission position when synchronous staging returns. Accepted Node records and actual server submission contracts use the new, precise `pushIndex` meaning.
4. Direct producers that currently submit without a SharedWorker continue to own their own submission sequence under their existing `nodeId`. Adapt their delivery state to the same `pushIndex` wire meaning; never substitute `sessionIndex` or assign fictitious Node history positions to their records.

## Record lifecycle

1. A successful local stage creates one staged session record and its optimistic operations atomically. Its `sessionIndex` is stable.
2. New Node acceptance atomically appends one staged Node record and allocates its `nodeIndex` and consecutive `pushIndex`. Failed/rolled-back acceptance consumes neither position. A retry returns the retained record and allocates nothing.
3. A session receiving that staged record attaches the known Node coordinates to its existing local staged record, or creates one staged record if it has not retained it before. This acknowledgment may enrich the session record; it does not modify the immutable Node record or create a second staging record.
4. Server admission changes only private delivery metadata. It neither rewrites the staged Node record nor appends a command-history record. Sessions receive admission details with the executed record. Existing state notifications continue to report connection, authentication, protocol, or delivery failures.
5. First retention of an executed command appends a distinct Node record with a new `nodeIndex`. This applies equally to locally submitted commands and commands submitted elsewhere. Retention, resource application when appropriate, execution checkpoints, and originating completion progress commit together before publication.
6. Each session appends a separate executed record with a new `sessionIndex`. The original staged row remains intact. Replay and pending-command queries exclude staged records that have an executed counterpart; `executedIndex IS NULL` alone no longer means a command is pending.
7. Exact redelivery reuses the existing executed row and does not reapply resources, allocate positions, or repeat completion/failure notifications. A second conflicting execution for the same ID, or an execution position claimed by another command, is a synchronization error. Preserve storage and block synchronization on such conflicts.
8. Enforce at most one row per command ID for each phase, in addition to row primary keys and unique execution positions. Use database uniqueness/constraints and transactional checks appropriate to the existing schema facilities. Staged and executed rows are distinguishable by their existing phase fields; do not introduce a generic event hierarchy.
9. Preserve the original staged result and input on the staged record. Executed records hold the executed result and server fields. Update readers that previously expected one combined row to join the two records when they need the full lifecycle; do not copy execution fields back onto staging merely to preserve old reads.

For example, other commands can interleave without consuming submission positions:

| `nodeIndex` | Command                | Record   | `pushIndex` |
| ----------- | ---------------------- | -------- | ----------- |
| 1           | A                      | staged   | 1           |
| 2           | X, submitted elsewhere | executed | null        |
| 3           | B                      | staged   | 2           |
| 4           | A                      | executed | null        |
| 5           | B                      | executed | null        |

1. A's staged and executed session records likewise have distinct `sessionIndex` values, independently allocated by that session. They need not equal 1 and 4 or be adjacent.
2. Admission of B can advance `admittedThroughPushIndex` to 2 without changing any of these five Node records. Retrying A changes none of their indexes or contents.

## Private admission and submission delivery

1. Retain one durable `admittedThroughPushIndex` on each Node. Do not add a per-command receipt table or publish mutable admission fields through the command stream.
2. Keep the existing serialized outbound submission discipline. Select the next staged submission beyond the known admitted prefix in `pushIndex` order. A retained result for a matching originating submission also establishes its admission; account for execution arriving before its receipt so completed submissions are not pushed again unnecessarily.
3. Validate admission replies against the current pending command ID and `pushIndex`, and retain existing validation of the server admission result/index. A valid reply for push 5 proves admission through pushes 1–5 because the server accepts only consecutive positions for that Node. Persist prefix advancement transactionally. Duplicate or late valid replies must not regress it or publish another command record.
4. Both successful and failed domain admission results consume the server's accepted submission position when the server has durably retained them. A transport failure or rejected, unretained submission does not advance the prefix. Preserve this distinction and the existing failure notification paths.
5. Keep server reconciliation for an `expectedPushIndex` mismatch. A valid response can reset the private admission prefix to `expectedPushIndex - 1` so the same retained submissions are retried. Validate it against allocated positions and retained completion evidence; a response contradicting already retained completed submissions is a history conflict. No command rows are rewritten and no new indexes are allocated.
6. Continue rejecting replies from stale connection generations. Reopen/reconnect resumes from durable metadata and retained records. Do not treat an in-memory send as proof of admission.
7. Derive `outcomeIndex` by relating staged submission rows to executed rows by command ID and walking the contiguous `pushIndex` prefix. An admission acknowledgment alone cannot advance it. Retain this watermark for the existing server outcome-recovery contract.

## Immutable subscription and retry recovery

1. Page immutable rows in ascending `nodeIndex`, using the existing bounded page delivery and one cursor per subscriber. Deliver one record for each row, including the retaining Node coordinates needed for session deduplication. There is no mutable-row ordering counter.
2. A fresh subscription atomically captures resources, unresolved staged records, execution checkpoints, and the current Node append position while registering the subscriber. An existing subscription resumes `afterNodeIndex` without replacing its resources or history.
3. Capture the initial catch-up boundary and preserve readiness semantics: attachment becomes ready only after the subscriber commits through that boundary. Writes can continue while a subscriber is slow; never hold a SQLite transaction or the Node's serialized operation across a session callback.
4. A page import commits its rows, resource effects, optimistic replay, session allocations, execution checkpoints, and Node cursor in one transaction. A failed import leaves them all unchanged. Advance the sender's cursor only after callback success. A recovered record already present in the session must not prevent the page cursor from advancing when its ordered page later arrives.
5. Node `accept` and its browser RPC return the retained records needed by that command: its staged record and any already-retained executed record. Use the domain records directly; remove the current ID-only acceptance receipt and the retry-driven `changeIndex` bump. A lookup/retry never appends or renumbers history. An ID already known only as executed must not be turned into a new outbound submission merely to answer a retry.
6. Route acceptance replies through the same session import rules, serialized with subscription imports. Verify the expected command identity and current attachment before clearing an uncertain handoff. Import reply records transactionally without advancing `afterNodeIndex`; point lookup does not establish observation of intervening history.
7. If a returned executed result is at or below the session's execution checkpoint, retain it as history and settle its staged counterpart without applying its resource delta again. This recovers completed commands omitted from a fresh resource snapshot. Import the related records together so a completed command is not briefly replayed as pending.
8. If a returned result is ahead of the session's execution checkpoint, leave its execution application to normal ordered stream delivery. The Node has already appended that result; the subscriber's cursor will reach it. The acceptance reply may acknowledge/import staging, but it must not skip intervening executions, advance either cursor, or need a separate persisted recovery queue.
9. Historical outcome recovery from the server remains supported. A previously unretained execution already covered by the Node's resource baseline can append a local history row without reapplying its delta or regressing execution checkpoints. New execution progress must remain contiguous. Local append order therefore records observation order, including legitimate late recovery of older outcomes.
10. Test both races: subscription delivery before the acceptance reply and the reply before subscription delivery. Each retains one record per phase and produces one lifecycle notification. A lost reply remains recoverable by retrying the original command ID.

## Alternatives and rationale

1. Reuse `sessionIndex` for submission continuity: rejected because sessions independently retain staged and executed records, including commands received from elsewhere. Those local row positions do not describe what one shared Node submitted.
2. Keep submission-only `nodeIndex` plus `journalIndex`: rejected because `nodeIndex` should identify records in the Node table. The necessary consecutive submission sequence has the direct name `pushIndex`.
3. Keep mutable Node rows plus `changeIndex`: rejected because it conflates current row state with an ordered command stream and demonstrably reorders executions after late mutations. Sorting an individual delivery page cannot repair an earlier execution displaced into a later page.
4. Append an admission event for every acknowledgment, or maintain individual private admission receipts: not selected. Sessions do not need those intermediate records; a single private admitted prefix is sufficient under the server's consecutive submission contract, with full admission details on executed results.
5. Republish retained command history to answer a retry: rejected. Explicit retained-record recovery handles lost replies and snapshot omissions without changing immutable history or advancing a subscription cursor incorrectly.
6. Preserve arbitrary repeated-ID executions: rejected for the bound streams in scope. Command retries and executed redelivery are idempotent; conflicting second execution is an error. This does not merge distinct versioned server streams or redefine their execution checkpoints.
