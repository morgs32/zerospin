# Agent command callbacks, selected views, and pending wakes

**Status:** Historical plan. Selected-row wake rules supersede the exposed-command callback design, owner-computed Agent deltas and delivery retention on replacement. See [current Agent execution](../../architecture/server/AgentExecution.md) and [ADR 029](../../adrs/029-independent-agent-command-callbacks.md).

## Problem and scope

1. Replace state/query-driven Agent automation with authored callbacks for specific exposed commands and explicit durable pending wakes. The owner release evaluates the Agent's selections and supplies selected changes; the Agent executes callbacks against its selected view.
2. Preserve the intended behavior independently of today's machinery. Existing modules are implementation starting points, not architectural constraints. Replace superseded behavior rather than retaining compatibility paths.
3. Implement both Aggregate and Service Agents. One Agent binds one exact owner release. No cross-owner selected views or joins. An Aggregate Agent retains the owning Aggregate instance context.
4. This plan establishes selection, callback, scheduling, replacement and initialization semantics. It does not claim to solve independent Worker packaging, routing, registration protocols, or physical Agent deployment. Those deployment mechanisms were not designed in this interview. Do not retain owner-local embedding as an inherited constraint. Resolve independent Agent declaration/registration before changing the factories; do not silently introduce a global Agent-name namespace.
5. Calendar notifications were illustrative only. Notification timing, late-work eligibility and business idempotency belong to application authors; do not introduce calendar-specific framework policy.
6. The user authorized implementation directly on main. No deployment, publication, storage reset, dependency release or consumer reinstall is authorized. Preserve unrelated and concurrent work.

## Agreed selection model

1. Agent selections support structured conditions only. Reject `where.RAW` and other opaque condition paths whose model/field dependencies cannot be validated. Do not ban `RAW` globally for Actors or unrelated queries.
2. Validate all condition dependencies against the Agent's explicitly declared model and field view. Fields omitted from that view cannot influence selection membership. Relation predicates are subject to the same validation; banning `RAW` alone is insufficient.
3. Cross-model conditions evaluate against the other model's selected rows, not all of its owner rows. For example, if the Agent selects only unpaid invoices, an order condition cannot match a paid invoice excluded from that selection.
4. Reject cycles between model selections. Derive a dependency graph and evaluate in dependency order. A condition on a model's own candidate-row fields is ordinary filtering, not a recursive dependency on its own selected result. Reject actual self-recursion through a selected relation.
5. The exact owning Aggregate or Service release evaluates the selection over its command-derived materialization. Agent callbacks read only the selected result. Do not copy every owner model into the Agent execution Repo to evaluate authored predicates there.
6. Preserve command/replay ownership of parallel models: callback reads and initialization must not populate or repair owner domain models. Installing selected resources is materialization of owner output; pending wakes and current operational status are private execution bookkeeping.

## Agreed callback interface and command visibility

1. Register at most one authored callback per exact exposed-command name and version in each Agent release. Several authored actions belong in that callback's one transaction, not in independently ordered handlers.
2. Pass the whole exposed command, not only its payload. Preserve its canonical command identity, exact declared name/version and payload, applicable owner context and logical position, `dispositionChainHash`, selected delta and full `outcome` as applicable to the exposed representation. Do not substitute the private underlying owner command.
3. Deliver both successful and failed command executions to the same subscribed callback. `outcome` is `{ result: Success | Failure, finalizedAt }`; use `outcome.result._tag`. Failed executions may have no selected-resource delta but must remain observable to the matching subscription. Do not confuse observed command failure with failure of the Agent callback.
4. Amend Agent-specific exposure, retained Chain publication and codecs as needed to preserve that data. Do not widen Actor/browser visibility or expose private claims, credentials, unrelated payloads or private completion fields merely by reusing a shared wire type. Validate subscriptions against contracts actually declared by the bound owner release.
5. Each callback reads the selected view immediately after its exposed command's changes, before the next exposed command is applied. Do not catch up the whole view and then run old command callbacks against the final view.
6. Callbacks may read the selected view, set/cancel wakes and record declared commands. They may not perform external requests, mutate domain models directly or define arbitrary persistent Agent models. External work proceeds through declared commands.
7. Callback reads do not grant access to all owner data. Command emission is a separately validated exact contract grant; it does not implicitly enlarge the Agent's selected view.
8. Apply the exposed-command delta, callback wake changes, complete emitted-command delivery rows and processing position in one synchronous transaction. Preserve duplicate/gap/hash validation. An acknowledged processing position proves durable local processing, not execution of an emitted command at its destination.

## Agreed wake interface and ownership

1. Provide authored `setWake(key, at, payload)` and `cancelWake(key)` operations backed by durable pending-wake rows owned by the stable logical Agent Repo. They use the current callback or initialization transaction; they are not RPCs to another Durable Object.
2. A repeated `setWake` replaces the pending deadline and payload for that key. It does not create duplicate pending wakes. Cancelling a missing key does nothing. Keys are scoped to the logical Agent; replacement semantics remain consistent across releases even though release replacement rebuilds the pending set.
3. Only pending-wake bookkeeping is added, not arbitrary author-defined persistent state. A pending-wake query/list interface was explicitly deferred as YAGNI; do not add one to the authored interface. Internal deadline reads necessary for WakeRegistry are implementation responsibility.
4. The registered Agent wake operation reads committed pending state and supplies its earliest deadline to WakeRegistry. WakeRegistry coordinates the physical Durable Object alarm and recovery. The physical alarm is outside the SQL transaction; reconcile it after commit and recover from interruption using committed bookkeeping.
5. Before running due wakes, capture the owner-history position and process exposed commands through that position. Then invoke due wake callbacks against that selected view. Do not require a continuously advancing global freshness barrier, and do not fire midway through the captured backlog.
6. A due wake invokes authored Agent code. The author inspects the selected view and decides which declared commands, if any, to record. Eligibility and overdue behavior belong to the author.
7. A wake callback may set/cancel wakes, including scheduling its own key again. On success, consume the invocation's pending wake, install any replacement or other wake edits, and record complete emitted commands atomically. Consuming the old wake must not delete a replacement scheduled by that same callback.
8. Scheduling idempotency is not an exactly-once external-side-effect guarantee. Complete pending command delivery rows survive restart and Agent release replacement, retain their frozen identity/version/payload, and are deleted only after durable receiver acknowledgement. Destination execution and retained `outcome` are separate facts.

## Agreed failure semantics

1. Both exposed-command and wake callbacks support authored `onFailure`. It catches all callback failures, including thrown exceptions, not just anticipated business errors. An observed command's Failure outcome is ordinary callback input.
2. Discard partial wake edits and command emissions from the failed normal callback before invoking its failure handler. Preserve the callback's required read context. Collect-then-apply or an equivalent local transaction scope must prevent partial effects from leaking.
3. A successful failure handler records its declared failure-handling command. Atomically commit that complete pending delivery with advancing the exposed-command processing position or consuming the wake. For exposed commands, commit the selected-view delta as well. Actual creation of an application failure row happens through execution of that declared command, not direct Agent writes.
4. If `onFailure` also fails, discard partial effects from both callbacks, log/report the failure, and move on. For an exposed command, commit its selected-view delta and processing position; for a wake, remove the pending wake. Do not recursively invoke a failure handler, endlessly retry a callback defect, or add durable execution/failure history to the materialization Repo.
5. Storage failure, transaction commit failure and interruption before durable completion are different from a callback failure handled by this policy. They cannot be treated as successful advancement. Roll back/recover and retry from the last committed processing position or pending wake.
6. Initialization has the separate error-state policy below. The earlier tentative rules to retry every callback failure, or block forever after failure-handler failure, were superseded by the decisions in this section.

## Agreed initialization, replacement and retry

1. Initialization captures the current selected view and rebuilds pending wakes. It does not invoke newly added callbacks over all historical exposed commands. Existing selected rows can therefore acquire wakes without replaying historical business actions.
2. Initialization can only rebuild pending wakes; it cannot directly record commands. An author can schedule due work whose wake callback later decides what command to record.
3. On Agent release replacement, discard the old pending schedule and rebuild with new initialization. Do not interpret old-release wake payloads through new-release callbacks. Preserve complete command delivery already durably emitted by the previous release, including its original identities and bindings.
4. Successful initialization atomically installs the selected snapshot, its processing position and `dispositionChainHash`, rebuilt wakes, active release binding and successful operational state. Start subsequent command callbacks after that snapshot position.
5. If initialization fails, discard its partial scheduling changes and persist a current initialization error with the attempted release identity on the Agent Repo. Pause exposed-command and wake callbacks. Old-release wakes must not execute through new-release callbacks. The error is current operational state, not append-only failure history.
6. Continue delivery of previously committed commands while initialization is failed. Do not drop delivery just because callback execution is paused or the configured release changed.
7. Retry initialization only through the existing `zerospin dev` and `zerospin deploy` lifecycle, or through replacement by another release. No separate admin/dev retry command and no automatic initialization-error retry loop. Ordinary alarm dispatch and Durable Object reactivation preserve the pause.
8. A successful deploy or accepted development startup/reload attempts initialization for new or initialization-failed Agents. Healthy Agents do not rebuild their schedules on every reload or activation. Existing declaration immutability/version-bump rules still apply; accepting code is not permission to silently rewrite immutable declarations.
9. Every retry captures a fresh selected view. On success atomically install that fresh view, processing position and rebuilt wakes, clear the current initialization error and resume callbacks. Commands predating that new snapshot are represented through initialization, not retroactively invoked as historical callbacks.
10. Surface initialization error status through the existing CLI/readiness reporting path so a paused Agent is observable. Do not add a new status dashboard, automation or failure-history subsystem.

- Owner VersionRepos read Agent selections on both sides of execution and retain `agentSelectedChanges` in the evaluated command. ## Browser and Agent Node replacement policy

1. **Use the same durability rule.** A selected view and its checkpoint can be rebuilt from an authoritative snapshot for the exact receiving definition. A command already durably recorded for delivery is an outstanding obligation until the destination owner Chain durably acknowledges admission. Preserve the original identity and binding across replacement. Retry uncertain admission with the same command identity. Destination execution and retention of its `outcome` remain separate. A command already admitted belongs to the destination owner Chain regardless of which definition is now active.
2. **Use the same materialization boundary.** Derive typed model tables from the declared view. Verify the snapshot's definition binding and decode its resources against that schema. Install the model tables, selected resources and matching checkpoint, including `dispositionChainHash`, before the new definition can process changes. Storage or transaction failure cannot publish a partially installed view. The source checkpoint is the boundary for subsequent selected changes.
3. **Browser Nodes today.** The [Aggregate Node definition](../../../packages/browser/src/AggregateNode/makeAggregateNodeDefinition.ts) and [Service Node definition](../../../packages/browser/src/ServiceNode/makeServiceNodeDefinition.ts) hash their session locks. The resulting identity selects a [browser storage namespace](../../../packages/browser/src/Node/nodeStorageNamespaces.ts). An unchanged identity can resume its retained queue after a refresh. A changed definition can select a different namespace. The new Node does not automatically reopen and drain the previous namespace, so work awaiting admission can remain stranded. The existing [connected storage upgrade path](../../architecture/browser/bootstrapBrowserSession.md#connected-storage-upgrade-preflight) handles schema upgrades within a retained identity. Cross-definition draining is a browser lifecycle gap relative to the shared durability rule. Address it separately with the original Node identity, authority and command format, without moving or re-authoring the commands in the new Node.
4. **Agent Repo design.** Use a stable Repo identity with a persisted installed definition hash. On a hash change, capture a fresh snapshot and rebuild the disposable model tables inside that Repo. Install the schema, snapshot, checkpoint, definition hash and initialized wake schedule in one synchronous transaction. A failed initialization leaves callbacks paused under the current error policy. Keep the existing `WakeRegistry` instance per Repo and preserve pending command delivery, producer position and original authority bindings. Do not re-key the Repo by definition hash. Compute the hash from the declaration and the executable behavior that determines initialization and callbacks. The CLI embeds a SHA-256 digest of the bundled Worker executable. The binding combines the exact owner/Agent versions with that digest. Imported callback and initialization helpers contribute their bundled code. A change elsewhere in the bundle may also refresh an Agent. The Agent Repo keeps model replacement in `makeAgentViewMaterialization` and installation in `makeAgentNodeRuntime`.
5. **Physical storage can differ.** Browser Nodes currently open separate IndexedDB namespaces for different definitions. An Agent Repo can replace its model tables in place because it owns its SQLite transaction and operational tables. Reuse the model schema compiler, resource codecs and snapshot invariants where they fit. Preserve fixed operational schema validation and read-only deployment preflight. Any Repo helper for rebuilding tables must be limited to the installed materialization's owned tables and leave operational tables intact. This policy does not require a shared Repo builder, choose its name, or authorize a storage reset.
6. **Verification.** Prove that replacing an Agent definition installs the new schema and snapshot together and that a previously recorded command still reaches admission under its original identity. Use the same two invariants for future browser cross-definition recovery coverage. Keep browser implementation work outside this Agent cutover and reconcile the runtime docs with verified behavior after implementation.
