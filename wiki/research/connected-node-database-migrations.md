# Migrating the connected Node database

The [current worker startup and migration example](../architecture/browser/bootstrapBrowserSession.md#opening-a-connected-node-database) shows the adopted API. This research records the alternatives considered on November 19, 2026. Source reviewed at [Zerospin PR #175, `41b548a`](https://github.com/morgs32/zerospin/commit/41b548a019ff1e08f65f60c9459e0908a80c64f5).

**Agreed behavior.** A task moved while offline keeps its original command ID, payload, ordering, release binding and execution rules across a change in how SQLite stores it. The new worker can migrate it locally and send it on reconnect. If the server already admitted the move and the reply was lost, the Node must recover the original outcome. A planner read-table change can rebuild confirmed rows and replay unresolved originals independently. An authenticated `dev --clean` selects a fresh history. [MOR-486](https://linear.app/morganatwork/issue/MOR-486) · [Immutable Node command history](../adrs/003-immutable-node-command-history-and-submission-order.md)

## Where a database migration belongs

Mentor Mailbox’s worker entry supplies the authored session and the SQLite WASM URL. Zerospin selects the family, acquires the session’s storage lease, opens the SQLite file and constructs the Node. The sequence below follows the personal planner. Service sessions use the corresponding Service constructors. The **SharedWorker host** listens for tabs. An **owner** holds one session’s Node, database connection, synchronization and exclusive lease. The **connected Node database** is the proposed name for the SQLite database managed by an AggregateNode or ServiceNode. It contains durable Node metadata and command records, and rebuildable read tables. A migration declaration belongs beside the owning Node’s durable tables. The browser transport can keep opening the file and closing it under its existing lease. In Zerospin’s glossary, **Repo** already names a Durable Object class. ## What the Durable Object factory does

`ServiceChain` declares `makeMigratableDORepoConfig({ migrations: [], ...serviceChainName, dbConfig: serviceChainDbConfig })` and passes it to `makeMigratableDORepo` when defining its class. The latter installs schema initialization in the existing activation path. A migration author supplies `{ id, name, sql }`. Fresh storage gets the current tables and stamps together. On reopen, the initializer verifies that the stored migration IDs and checksums match a prefix of the declarations, applies the remaining SQL in order and validates the resulting tables. Each step commits with its stamp. `ServiceAgentNodeRepo` also supplies separately installed model tables for validation. ## PR #175 before the offline migration amendment

Browser migration declarations include `id`, `name`, `fromVersion`, `toVersion`, ordered SQL and the destination table definitions. Every supported source and destination also needs a registered storage format. Aggregate V24 currently spreads V22’s tables, readers and writers and changes its `version` to `24`. Aggregate and Service both have empty general migration lists on this head. The older shipped Aggregate database has a separate adoption path. For a pending general migration the browser imports saved tab commands, freezes the latest submission position, starts synchronization and waits for every earlier submission’s final outcome. Offline or paused synchronization can block a change as small as a column rename. Core checks the same condition again before applying SQL. The underlying SQL procedure already runs inside a caller-owned transaction without network calls. ## Proposed developer API

The concrete browser opener is `openWaSqliteNodeStorage` in the local PR worktree. It loads the async WebAssembly build of `wa-sqlite`, constructs the SQLite API with `SQLite.Factory(module)`, and opens the database using the package’s IndexedDB-backed `IDBBatchAtomicVFS`. Drizzle wraps the open connection. The proposed `makeMigratableNodeDatabase` owns the tables and migrations applied to that connection. [Pinned browser dependency](https://github.com/morgs32/zerospin/blob/41b548a019ff1e08f65f60c9459e0908a80c64f5/packages/browser/package.json#L78) · [SQLite and VFS setup](https://github.com/morgs32/zerospin/blob/41b548a019ff1e08f65f60c9459e0908a80c64f5/packages/browser/src/Node/openNodeStorage.ts#L54) · [Drizzle connection](https://github.com/morgs32/zerospin/blob/41b548a019ff1e08f65f60c9459e0908a80c64f5/packages/browser/src/Node/openNodeStorage.ts#L128)

A framework developer edits the current Drizzle table and appends its migration in one family-owned database declaration. For example, suppose `commands.payload` is renamed to `encodedPayload` in the current table declaration, retaining the exact encoded bytes. The example uses the existing names for the current table objects. The migration and factory are illustrative. The proposed editor location is `packages/core/src/AggregateNode/aggregateNodeDatabase.ts`. Define `aggregateNodeDatabase` once at module initialization and reuse it when a connected Node opens its file. The current list lives in `storage/aggregateNodeStorageMigrations.ts`. The table definitions in `aggregateNodeTables.ts` also describe the shipped layout 22. Preserve that historical definition and its Standalone callers before editing the current connected declaration. [Current Aggregate tables](https://github.com/morgs32/zerospin/blob/41b548a019ff1e08f65f60c9459e0908a80c64f5/packages/core/src/AggregateNode/aggregateNodeTables.ts#L18) · [SQLite column renames](https://www.sqlite.org/lang_altertable.html#alter_table_rename_column)

```ts
// In the current connected commands table, keep the TypeScript key:
// payload: text('encodedPayload')
export const aggregateNodeDatabase = makeMigratableNodeDatabase({
  tables: [aggregateNodeMetadata, aggregateNodeCommands],
  migrations: [{
    id: 1,
    name: 'rename-command-payload',
    sql: ['ALTER TABLE commands RENAME COLUMN payload TO encodedPayload'],
  }],
})

// Inside connected Node initialization, with the existing leased connection.
await aggregateNodeDatabase.initializeSchema(db)
```

`initializeSchema` names the work performed on an already-open SQLite connection. On a fresh database, schema and ledger provisioning belong in the existing transaction that initializes the producer metadata. On an existing database it would verify ownership and supported source storage with the Node, apply outstanding migrations, validate the resulting schema and record progress atomically with the SQL. Retrying picks up from the last committed step. Skipping worker releases applies any missing steps on the next open. The current Node readers then operate on current tables. The example requires no code change in Mentor Mailbox’s worker entry. [Existing Node initialization](https://github.com/morgs32/zerospin/blob/41b548a019ff1e08f65f60c9459e0908a80c64f5/packages/core/src/AggregateNode/AggregateNode.ts#L211) · [Current ledger](https://github.com/morgs32/zerospin/blob/41b548a019ff1e08f65f60c9459e0908a80c64f5/packages/core/src/Node/nodeMigrationLedger.ts#L23) · [SQLite transactions](https://www.sqlite.org/lang_transaction.html)

A migration ID identifies one authored change. A checksum detects edits to a previously distributed change. A package version identifies a build, and SQLite’s `user_version` is an integer controlled by the application. Future migration authors could supply just the ID, name and SQL. Existing files still need their exact published checksums and baseline stamps recognized: the browser historically hashed version bounds as well as the SQL, while the DO hashes the ID, name and SQL. Recomputing historical checksums with the DO algorithm would strand existing files. [DO history](https://github.com/morgs32/zerospin/blob/41b548a019ff1e08f65f60c9459e0908a80c64f5/packages/system-worker/src/makeMigratableDORepo/migrationHistory.ts#L30) · [Browser history](https://github.com/morgs32/zerospin/blob/41b548a019ff1e08f65f60c9459e0908a80c64f5/packages/core/src/Node/nodeMigrationHistory.ts#L42) · [SQLite `user_version`](https://www.sqlite.org/pragma.html#pragma_user_version)

## What can be removed, and what still has a job

- **Remove network coordination from ordinary schema migrations.** A representation-preserving step can drop the migration-only online/paused checks, frozen submission cutoff, outcome subscription, timeout, explicit `resume`/`push` and duplicate final-outcome guard. Normal delivery still owns reconnect, admission and outcome recovery. A new schema step can use SQL to read old rows without supplying a full historical Node runtime for every intermediate format. Trace users of the V22/V24 adapters before deleting them, including Standalone and shipped-format adoption. [Browser drain](https://github.com/morgs32/zerospin/blob/41b548a019ff1e08f65f60c9459e0908a80c64f5/packages/browser/src/AggregateNode/prepareAggregateNodeStorage.ts#L256) · [Core guard and step](https://github.com/morgs32/zerospin/blob/41b548a019ff1e08f65f60c9459e0908a80c64f5/packages/core/src/AggregateNode/AggregateNode.ts#L475) · [Standalone storage selection](https://github.com/morgs32/zerospin/blob/41b548a019ff1e08f65f60c9459e0908a80c64f5/packages/core/src/AggregateNode/AggregateNode.ts#L356)
- **Keep the two shipped Aggregate formats identifiable.** Both reported `24`. The older one could retain uploads or a predecessor a command depended on. Validating the recorded history, tables, pending prerequisites and journal lets the Node either preserve the old behavior or leave the work intact for a compatible reader. A SQL rename alone cannot give a command new execution semantics. [Published-format adoption](https://github.com/morgs32/zerospin/blob/41b548a019ff1e08f65f60c9459e0908a80c64f5/packages/core/src/AggregateNode/storage/adoptPublishedAggregateCommandStorageTx.ts#L135) · [Accepted storage policy](../adrs/027-connected-browser-node-storage-upgrades.md)
- **Keep journal recovery and original command identity.** A tab can close after saving an original in `localStorage` and before SQLite retains it. Recovery must read the matching identity and producer, retain the original once, then acknowledge it. Retrying after a lost acknowledgement must find the existing submission. This responsibility can outlive the migration-only drain. [Journal keys](https://github.com/morgs32/zerospin/blob/41b548a019ff1e08f65f60c9459e0908a80c64f5/packages/browser/src/stagedCommandJournal/makeStagedCommandJournal.ts#L29) · [Acknowledgement](https://github.com/morgs32/zerospin/blob/41b548a019ff1e08f65f60c9459e0908a80c64f5/packages/browser/src/stagedCommandJournal/recoverStagedCommands.ts#L117) · [Original retention](https://github.com/morgs32/zerospin/blob/41b548a019ff1e08f65f60c9459e0908a80c64f5/packages/core/src/AggregateNode/acceptAggregateOriginalTx.ts#L47)
- **Keep read-table rebuilds and dev clean independent.** The former restores confirmed rows from a compatible baseline and history, then projects pending originals. The latter needs authenticated evidence of replacement before selecting a different file. Both rely on the existing session ownership boundary. Verifying command compatibility still requires data written by the actual released packages. The existing Core and browser suites exercise these writers. [Read-table recovery](https://github.com/morgs32/zerospin/blob/41b548a019ff1e08f65f60c9459e0908a80c64f5/packages/core/src/Node/rebuildConnectedReadTables.ts) · [Development storage selection](https://github.com/morgs32/zerospin/blob/41b548a019ff1e08f65f60c9459e0908a80c64f5/packages/browser/src/Node/selectDevelopmentStorage.ts#L34)
