# System Worker storage evolution

Primary-source research and current-source inspection on 2026-10-11. Revised to examine migrating permanent roots while creating fixed, replayed version children. This supersedes the earlier broad inference that each Repo should migrate. It does not approve implementation or change the pre-release policy requiring empty storage for changed fixed schemas. No tests were run.

**Architectural inference:** migrate durable facts that cannot be reconstructed; give rebuildable representations new physical identities. This can reduce migration scope substantially. It does not establish that only AggregateChain and ServiceChain need migrations: current children retain original async authority, and SystemRepo retains independent permanent facts. Those responsibilities can be redesigned, rather than accepted as inevitable constraints.

1. **The proposed split has established prior art.** Fowler's _Event Sourcing_ describes rebuilding application state from retained events, suppressing external updates during replay, and retaining historical external-query responses. _Memory Image_ emphasizes decoupling the log format from the model structure so a new model can still consume old history. **Inference:** changing a derived schema need not mutate its source of truth. The governing boundary is whether every necessary fact survives outside the representation being replaced. Sources: [Event Sourcing](https://martinfowler.com/eaaDev/EventSourcing.html), [Memory Image](https://martinfowler.com/bliki/MemoryImage.html).

2. **ZeroSpin has two different reconstruction paths.** Root histories retain command inputs and finalizations; a new VersionRepo replays finalized inputs using its new authored release. Selected actor/agent Chains instead apply recorded execution results and model operations without executing contracts again. Rebuilding a new canonical model and rebuilding a particular selected view therefore require different source histories. Sources: [root replay](../../packages/system-worker/src/AggregateChain/readReplayPage.ts#L12), [canonical replay](../../packages/system-worker/src/AggregateVersionRepo/replayCommands/replayCommand.ts#L31), [aggregate projection](../../packages/system-worker/src/aggregateProjection/applyEvaluatedCommands/applyEvaluatedCommandsTx.ts#L46), [service projection](../../packages/system-worker/src/serviceProjection/applyServiceResultsTx.ts#L43).

3. **A current VersionRepo is more than a disposable projection.** It retains original execution results and async producer identity, scheduling, recorded-but-unadmitted responses, and command outboxes. Replay deliberately creates no producer authority. A completed external response becomes available in root history once its child command is admitted and finalized; pending requests and responses not yet admitted remain VersionRepo-only. **Inference:** if the child commits but the root acknowledgement is lost, its recorded original result is still authoritative evidence of execution; replacing it with an empty child loses that evidence. A new release can rebuild business state without reconstructing unfinished original work. That work must remain recoverable in its old owner, migrate explicitly, or move to a stable authority owner in a redesigned architecture. Current resources, retained execution result, and async intent commit within one synchronous transaction. Moving authority across DOs changes that atomic boundary; it cannot be implemented as merely forwarding an RPC to the root. Sources: [execution transaction](../../packages/system-worker/src/AggregateVersionRepo/materializeCommandTx.ts#L14), [async storage](../../packages/system-worker/src/externalOperations/externalOperationsDbConfig.ts#L24), [replay preparation](../../packages/system-worker/src/externalOperations/prepareExternalOperation.ts#L12).

4. **The version must identify the representation being opened.** Fixed child identities include owner release version and actor/agent versions. Their schemas combine authored models with framework tables, while accepted owner definitions omit a framework storage revision. Existing bootstrapped storage skips provisioning. **Inference:** a release bump can select fresh children, but upgrading the package under the same release identity cannot silently mean a different physical layout. Incorporating framework layout into aggregate/service releases is viable if each release identifies the complete execution/layout combination and old combinations remain interpretable. A separate internal layout identity is another design choice; these sources do not mandate one. Sources: [fixed identities](../../packages/system-worker/src/makeFixedDORepo/FixedRepoIdentity.ts#L24), [accepted owner projection](../../packages/core/src/system/project/projectOwnerSpec.ts#L29), [bootstrap guard](../../packages/system-worker/src/makeFixedDORepo/makeFixedDORepo.ts#L138).

5. **Replay requires retained history, not merely current rows.** Root acknowledgement keeps input commands. Selected views also require compatible complete execution history, including browser delta/cursor and completion prefixes; current resource rows alone are insufficient. **Inference:** permanent replay must retain every reconstruction input and required interpretation. If history is truncated, a retained snapshot must be a sufficient starting point for the new representation, or have an explicit transformation. Giving a view a new name does not recover deleted information. Sources: [root acknowledgement](../../packages/system-worker/src/AggregateChain/acknowledgeOriginalDispatch.ts), [projection commit](../../packages/system-worker/src/aggregateProjection/commitProjectionTx/commitProjectionTx.ts#L63), [Parallel Model](https://martinfowler.com/eaaDev/ParallelModel.html).

6. **SystemRepo remains an independent storage concern.** It permanently locks accepted definitions and catalogs registered identities, including aggregates that may never receive a command. Root command logs cannot recreate those facts. Session tickets have a different lifecycle and can have an invalidation/reissue policy. **Inference:** a narrowed migration design still needs a SystemRepo evolution policy; it need not preserve every transient row. Source: [SystemRepo responsibilities](https://github.com/morgs32/zerospin/blob/79c1824b1a0353f770211851c0bfe1cc54d0ba46/packages/system-worker/src/SystemRepo/README.md#L1).

7. **A new child identity does not pin old framework code.** Cloudflare assigns a code version per DO, with different DOs potentially on different versions during deployment. Keeping old fixed children requires code that can still interpret their stored layouts; a business release bump alone supplies no such isolation. Local constructor migration gating is supported, with a 30-second limit, but neither local migration nor fresh projection identity solves incompatible cross-Repo RPCs. Sources: [DO deployments](https://developers.cloudflare.com/workers/versions-and-deployments/gradual-deployments/with-durable-objects/), [initialization gating](https://developers.cloudflare.com/durable-objects/api/state/#blockconcurrencywhile).

**Working conclusion:** favor a small permanent authority layer plus separately identified rebuildable views. Decide placement from retained facts and transaction ownership. Rebuildable views can evolve through fresh children; permanent history, accepted identities, original external work, and historical observations still require retention and evolution rules. This avoids assuming either a full parallel successor graph or migrations for every child.
