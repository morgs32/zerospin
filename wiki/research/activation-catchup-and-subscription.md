## Agreed behavior

The requested destination is explicit: **refactor `catchupMaterialization()` and await that procedure from `onDOActivation()`, inside the existing constructor `blockConcurrencyWhile`.** It must complete local materialization from already-deliverable upstream history before activation finishes. Keeping the named procedure outside activation is not the proposed outcome. The factory already awaits `onDOActivation()` inside its gate, so no additional concurrency gate or public readiness interface is required: [constructor lifecycle](../../packages/system-worker/src/makeMigratableDORepo/makeMigratableDORepo.ts#L281).

For a resource-owning consumer, catch-up resumes from its saved checkpoint through a fixed upstream position, then ensures future delivery resumes from the committed checkpoint. Ordinary session opening uses a consistent committed projection snapshot and receives subsequent results through delivery; it does not force pending admitted commands to finish. These are the decisions reached in the accompanying conversation. Projection activation already provides the dynamic-subscriber construction: [projection activation](../../packages/system-worker/src/AggregateActorVersionRepo/AggregateActorVersionRepo.ts#L57), [catch-up before enrollment](../../packages/system-worker/src/makeFanoutSubscriber/subscribe.ts#L35).

The upstream stream depends on the consumer. A VersionRepo replays the Chain's contiguous finalized admitted-command prefix. A projection Repo applies the VersionChain's published execution packets. Neither startup pull needs to request original execution. Reading replay history already excludes admitted commands whose original `commandOutcome` is pending, and projection subscribers read their bound VersionChain: [finalized replay page](../../packages/system-worker/src/AggregateChain/readReplayPage.ts#L7), [projection source](../../packages/system-worker/src/aggregateProjection/evaluatedCommandsFanoutSubscriber/evaluatedCommandsFanoutSubscriber.ts#L40).

Remove the unused Aggregate and Service `flush(N)` methods rather than preserving a hypothetical caller requirement. A repository search during this research found their implementations, class wrappers, capability type exposure, errors and documentation, but no production or verification caller. Other `flush` calls concern telemetry, SQLite or test cleanup. Representative remaining declarations: [Aggregate wrapper](../../packages/system-worker/src/AggregateVersionRepo/AggregateVersionRepo.ts), [Service wrapper](../../packages/system-worker/src/ServiceVersionRepo/ServiceVersionRepo.ts), [Aggregate capability](../../packages/system-worker/src/repoServices/AggregateVersionRepos.ts#L19), [Service capability](../../packages/system-worker/src/repoServices/ServiceVersionRepos.ts#L23).

## What the activation gate currently does

Cloudflare documents that `blockConcurrencyWhile` delays other incoming events until its callback completes. An exception resets the object, and a callback exceeding 30 seconds also resets it. Cloudflare recommends keeping the callback's work small: [Durable Object State](https://developers.cloudflare.com/durable-objects/api/state/#blockconcurrencywhile).

Zerospin's constructor gate registers the Repo, initializes its schema, runs optional one-time bootstrap and confirms those writes, then awaits `onDOActivation()`. The activation hook therefore runs on each cold activation; the bootstrap marker skips only the optional bootstrap callback: [constructor lifecycle](../../packages/system-worker/src/makeMigratableDORepo/makeMigratableDORepo.ts#L281).

Thus the agreed activation model is already implemented for projections. Applying pure history catch-up to VersionRepo activation is an implementation change; do not describe it as current behavior or add a second independent membership mechanism.

## Paginated catch-up followed by subscription

The existing subscriber procedure does the following:

1. Reads the consumer's durable checkpoint.
2. Requests a page after that position. Without an explicit bound, fixes the finishing position from the first response's deliverable tip.
3. Applies the page through the same receiver used for pushed delivery, then rereads the durable checkpoint.
4. Repeats until that fixed position is reached. Concurrent new history does not extend the pass.
5. Reads the committed checkpoint and enrolls/resumes the subscription at that position.

Sources: [page loop and fixed finishing position](../../packages/system-worker/src/makeFanoutSubscriber/runFanoutCatchup.ts#L33), [durable progress checks](../../packages/system-worker/src/makeFanoutSubscriber/runFanoutCatchup.ts#L65), [enrollment after catch-up](../../packages/system-worker/src/makeFanoutSubscriber/subscribe.ts#L35).

Enrollment deliberately runs outside the fanout delivery semaphore. It holds a producer lease to arm recovery, checks the source tip, and atomically inserts or monotonically advances the subscriber cursor. History arriving after the pull remains eligible for delivery from that cursor. Enrollment must not await a delivery drain that may already be waiting for the activating receiver: [separate enrollment path](../../packages/system-worker/src/makeFanoutQueue/makeFanoutQueue.ts#L444), [producer recovery lease](../../packages/system-worker/src/makeFanoutQueue/makeFanoutQueue.ts#L306), [monotonic enrollment](../../packages/system-worker/src/makeFanoutQueue/makeFanoutQueueStorage.ts#L139), [lagging subscriber selection](../../packages/system-worker/src/makeFanoutQueue/makeFanoutQueueStorage.ts#L108).

## Why the current `catchupMaterialization()` must change

The current Aggregate method first calls `AggregateChain.executeCommandsThrough()`, then replays finalized history into its own resources, then publishes execution history through its captured local position. It is an execution-driving workflow, rather than just the paginated subscriber operation: [complete method](../../packages/system-worker/src/AggregateVersionRepo/catchupMaterialization/catchupMaterialization.ts).

Moving that method unchanged into activation introduces a concrete circular wait. A Chain dispatch can hold its outbox delivery permit while acquiring the receiving VersionRepo's subscriber. If the cold receiver's activation calls back to `executeCommandsThrough()`, that call tries to drain the same queue whose delivery is waiting for receiver startup. This is an inference from the call and lock ownership, not a runtime reproduction performed by this research: [dispatch to the receiving Repo](../../packages/system-worker/src/AggregateChain/AggregateChain.ts#L194), [permit held across page delivery](../../packages/core/src/outbox/makeOutboxDelivery.ts#L324), [delivery waits for receiver](../../packages/core/src/outbox/makeOutboxDelivery.ts#L286), [original-progress call](../../packages/system-worker/src/AggregateVersionRepo/catchupMaterialization/catchupMaterialization.ts).

Pure replay does not make that original-progress request. It consumes only the finalized prefix and runs this version's replay transaction; external-operation production is skipped in replay mode: [read-only source page](../../packages/system-worker/src/AggregateChain/readReplayPage.ts#L7), [replay materialization](../../packages/system-worker/src/AggregateVersionRepo/replayCommands/replayCommand.ts#L36), [external output discarded on replay](../../packages/system-worker/src/AggregateVersionRepo/utils/prepareAggregateOutput.ts#L25).

## Concrete construction for moving the procedure

The proposed VersionRepo lifecycle is:

```text
constructor blockConcurrencyWhile
  register Repo; initialize schema; run optional one-time bootstrap
  onDOActivation
    reestablish durable recovery for pending deliveries and external work
    await catchupMaterialization
      pull finalized admitted-command pages after the local checkpoint
      commit replay resources, checkpoint and complete pending output
      stop at the fixed deliverable position
  finish the gate; accept incoming requests and deliveries
```

Invoke the local Effect procedure directly from `onDOActivation()`. The existing Aggregate helper already returns an Effect and the factory already awaits the hook; a public RPC wrapper is unnecessary once request-time callers are converted. The Service equivalent must stop delegating to `progressServiceVersion`, because that helper also calls `executeCommandsThrough()`: [Aggregate Effect procedure](../../packages/system-worker/src/AggregateVersionRepo/catchupMaterialization/catchupMaterialization.ts#L10), [Aggregate activation hook](../../packages/system-worker/src/AggregateVersionRepo/AggregateVersionRepo.ts), Service progress helper (`../../packages/system-worker/src/ServiceVersionRepo/progressServiceVersion.ts`; removed by Plan 192).

**Change the procedure's responsibility to local replay catch-up.** Remove the unconditional request for original execution. Use the existing `replayCommandsFanoutSubscriber(...).catchup()` page loop, then read the local execution checkpoint. Keep replay's synchronous resource/checkpoint/outbox transaction and keep page RPCs outside SQL and the execution permit. No replacement public force-progress operation is needed: [current orchestration](../../packages/system-worker/src/AggregateVersionRepo/catchupMaterialization/catchupMaterialization.ts), [existing paginated catch-up](../../packages/system-worker/src/makeFanoutSubscriber/runFanoutCatchup.ts#L33), [replay transaction and result recovery](../../packages/system-worker/src/AggregateVersionRepo/replayCommands/replayCommand.ts#L36), [atomic checkpoint and packet retention](../../packages/system-worker/src/AggregateVersionRepo/utils/retainEvaluatedCommandTx.ts#L34).

### Preserve the two existing subscription constructions

VersionRepo membership is already owned by AggregateChain/ServiceChain: source activation inserts every authored release into `replaySubscribers` and arms recovery. VersionRepo activation can therefore pull history through the existing `.catchup()` operation and rely on that retained source subscription. Dynamic actor/agent projections still need `.subscribe()`, which pulls and then enrolls their individual identities. This achieves activation materialization without adding duplicate membership ownership: [Aggregate source membership](../../packages/system-worker/src/AggregateChain/onDOActivation/onDOActivation.ts#L18), [Service source membership](../../packages/system-worker/src/ServiceChain/onDOActivation/onDOActivation.ts#L19), [pure catch-up operation](../../packages/system-worker/src/makeFanoutSubscriber/catchup.ts#L32), [dynamic subscription operation](../../packages/system-worker/src/makeFanoutSubscriber/subscribe.ts#L35).

There is a concrete recovery reason not to copy projection `.subscribe()` blindly into VersionRepo startup. An original command can commit local execution checkpoint 10 and its outgoing rows before its original outcome reaches the Chain. The Chain's replayable prefix is then 9, while this Repo is legitimately at 10. The pure page loop accepts that there is no replay work to do, but generic fanout enrollment rejects a consumer cursor above the deliverable source tip. Keep the local checkpoint intact and preserve source-owned membership; do not rewind local resources or wait for pending originals just to satisfy the projection enrollment rule. This scenario is inferred from the independent commit/delivery paths: [local checkpoint plus pending original outcome](../../packages/system-worker/src/AggregateVersionRepo/utils/retainEvaluatedCommandTx.ts), [finalized source prefix](../../packages/system-worker/src/AggregateChain/readReplayPage.ts#L14), [already-ahead catch-up completion](../../packages/system-worker/src/makeFanoutSubscriber/runFanoutCatchup.ts#L65), [enrollment cursor restriction](../../packages/system-worker/src/makeFanoutQueue/makeFanoutQueue.ts#L473).

### Let delivery recovery proceed independently of activation completion

Catch-up must arm output recovery before local replay commits, but should not await downstream fanout or original-outcome delivery before opening its own gate. The existing output wrapper arms recovery and starts background drains when the producer completes. External recovery similarly reestablishes its alarm and launches work/delivery without waiting for remote completion: [output wrapper](../../packages/system-worker/src/AggregateVersionRepo/AggregateVersionRepo.ts#L281), [outbox producer lifecycle](../../packages/system-worker/src/makeOutboxQueue/makeOutboxQueue.ts#L267), [external recovery lifecycle](../../packages/system-worker/src/externalOperations/makeExternalOperationQueue.ts).

In particular, an awaited original-outcome drain in activation is unsafe: fresh outcome acceptance calls back to this same Repo's `getPendingFinalizedOutcome` RPC to prove the retained message. The incoming proof request needs the receiver gate to open. Arm that delivery and let its existing recovery run independently: historical `receiveFinalizedOutcomes.ts` original-outcome source proof, [gate blocks incoming events](https://developers.cloudflare.com/durable-objects/api/state/#blockconcurrencywhile).

The earlier suggestion that startup catch-up must publish execution history before returning was tied to the current snapshot path asking VersionRepo to drive progress and return N. The agreed session behavior removes that dependency. Activation now promises committed local resources/checkpoint/complete pending output; it does not promise that downstream owners have already received that output. Projection snapshots still publish their own captured pending output through their captured N before returning a matching snapshot/history pair: [current snapshot-to-VersionRepo dependency to remove](../../packages/system-worker/src/aggregateProjection/getSnapshot/getSnapshot.ts#L88), [local pending output retention](../../packages/system-worker/src/AggregateVersionRepo/utils/retainEvaluatedCommandTx.ts#L34), [snapshot's own exact publication requirement](../../packages/system-worker/src/aggregateProjection/getSnapshot/getSnapshot.ts#L105).

## Consequences for the agreed implementation

- Refactor `catchupMaterialization()` into local replay catch-up and await it from VersionRepo `onDOActivation()`. Retain source-owned authored subscriptions for VersionRepos and pull-then-enroll for dynamic projection Repos. Sources: [local procedure](../../packages/system-worker/src/AggregateVersionRepo/catchupMaterialization/catchupMaterialization.ts#L10), [subscriber construction](../../packages/system-worker/src/makeFanoutSubscriber/subscribe.ts#L35), [source membership](../../packages/system-worker/src/AggregateChain/onDOActivation/onDOActivation.ts#L18).
- Ordinary session opening must stop forcing original admission backlog progress. Changing the projection snapshot alone is insufficient: current authorization also calls `catchupMaterialization()` before running authored authorization. Preserve authorization itself. Sources: [snapshot progress request](../../packages/system-worker/src/aggregateProjection/getSnapshot/getSnapshot.ts#L88), [authorization progress request](../../packages/system-worker/src/AggregateVersionRepo/authorizeAggregateSession/authorizeAggregateSession.ts).
- Remove the old request-time orchestration dependencies from snapshot, query and authorization wrappers when materialization becomes activation-owned. These operations then read their owner's current committed state; they no longer implicitly execute all pending admitted commands first. Preserve claims/lock validation and the authored authorizer, including any command it explicitly executes and awaits. This is a deliberate freshness change, not a claim that no caller behavior changes. Sources: [query caller](../../packages/system-worker/src/AggregateVersionRepo/executeAggregateQuery/executeAggregateQuery.ts#L45), [authorization caller](../../packages/system-worker/src/AggregateVersionRepo/authorizeAggregateSession/authorizeAggregateSession.ts), [claims and lock validation](../../packages/system-worker/src/AggregateVersionRepo/authorizeAggregateSession/authorizeAggregateSession.ts#L75), [authorizer's explicit command execution](../../packages/system-worker/src/AggregateVersionRepo/authorizeAggregateSession/authorizeAggregateSession.ts#L120).
- Preserve command-specific result waiting and predecessor ordering. Direct execution waits for its requested command's result; original command N first replays through N-1. These are existing execution requirements and do not require the unused `flush(N)` method. Sources: [direct result wait](../../packages/system-worker/src/AggregateChain/executeAggregateCommand/executeAggregateCommand.ts#L59), [predecessor replay](../../packages/system-worker/src/AggregateVersionRepo/finalizeCommand/finalizeCommand.ts#L44).
- Preserve the exact snapshot/publication relationship: capture resources and checkpoint N together, publish their pending projected history through N, verify that exact checkpoint and recover private completion only through N. Removing admission-backlog waiting does not remove this consistency requirement. Source: [captured snapshot publication](../../packages/system-worker/src/aggregateProjection/getSnapshot/getSnapshot.ts#L105).

Apply this lifecycle change to Aggregate and Service together; it changes the Aggregate behavior that Plan 191 originally proposed copying. The named activation procedure can be an internal implementation detail once its external callers are removed. Remove the unused public `flush(N)` surface and obsolete progress helpers/type exposure during that change. Existing capability exposure to reconcile: [Aggregate capabilities](../../packages/system-worker/src/repoServices/AggregateVersionRepos.ts#L12), [Service capabilities](../../packages/system-worker/src/repoServices/ServiceVersionRepos.ts#L12).

## Verification needed during implementation

Use existing verification files to prove: cold original dispatch can awaken a receiving VersionRepo without a circular wait; startup pulls a fixed finalized prefix without calling `executeCommandsThrough`; local checkpoint 10 with source finalized prefix 9 activates successfully; partial replay preserves committed checkpoints and complete pending publication across restart; ordinary snapshot/query/authorization no longer force admission backlog execution; authored authorization and command-specific result waiting still run. The existing activation suite (`packages/system-worker/test/migratable-do-repo/system-repo-activation.workerd.spec.ts`, removed 2026-10-17) is an available extension point, not evidence that the proposed changes already pass.

## Runtime limit and evidence limits

A fixed history position bounds how much history the loop follows; it does not bound execution duration. The existing page loop has no total activation time budget. Consequently a large or slow catch-up can exceed Cloudflare's documented 30-second gate timeout. This research records that constraint without introducing an unrequested readiness state machine or claiming arbitrarily large backlogs fit in one activation: [page loop](../../packages/system-worker/src/makeFanoutSubscriber/runFanoutCatchup.ts#L45), [Cloudflare gate timeout](https://developers.cloudflare.com/durable-objects/api/state/#blockconcurrencywhile).

Evidence consists of source inspection, repository caller searches and official Cloudflare documentation. No runtime probe, test, reset or deployment was performed. Only this research note was added; implementation, plans, ADRs and existing work were left unchanged.
