These are distinct durable steps. - **Handling an external Failure successfully can commit durable model changes.** `AggregateVersionRepo.evaluateAggregateCommand` evaluates the prepared external invocation normally. `executeAggregateOccurrence` then applies its operation batch inside a savepoint, and `materializeCommandTx` commits resource changes, the pending execution packet and checkpoint together. `finalizeAggregateOccurrence` chooses `commandOutcome` from the continuation's execution, independently of `externalOutcome`. The service implementation has the same savepoint structure. - **A decline and an unusable response carry different knowledge.** Stripe exposes issuer-decline information through a response/API result, while a timeout does not establish whether Stripe executed the request; even a `500` can accompany remote side effects. Therefore a definite decline belongs in the authored response value, while `ExternalRequestFailure` means no usable response and can justify reconciliation. This interpretation matches the current failure schema; it does not assert that a payment failed remotely. [Stripe declines](https://docs.stripe.com/declines#issuer-declines), [Stripe network and server errors](https://docs.stripe.com/error-low-level#network-errors), [failure schema, lines 3–8](../../packages/core/src/contracts/ExternalOutcomeSchema.ts#L3-L8).

## Findings

1. **A terminal external failure needs an application transition.** Shopping reserves tracking refresh before scheduling work. If production stops without a continuation, later refresh commands see the retained pending reservation and schedule nothing. Delivering the failed observation lets the authored program release its matching reservation or record a need for reconciliation. Payment and label creation retain uncertainty rather than asserting that a missing response proves the provider did nothing. [Refresh reservation](../../examples/shopping/src/zerospin/aggregates/user/contracts/updateTrackingInfoV1.ts), [refresh continuation](../../examples/shopping/src/zerospin/aggregates/user/contracts/refreshExternalTrackingInfoV1.ts), [payment continuation](../../examples/shopping/src/zerospin/aggregates/user/contracts/processExternalPaymentV1.ts).
2. **Retry ownership and terminal failure handling are separate.** Temporal returns exhausted or non-retryable Activity errors to workflow code. Step Functions evaluates retry policies before routing unresolved errors through Catch handlers. These systems support the separation; they do not prescribe Zerospin's storage representation. Zerospin keeps author-owned retries inside `external.request`. [Temporal Activity lifecycle](https://docs.temporal.io/activity-execution), [Step Functions error handling](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-error-handling.html), [retry decision](../adrs/011-author-owned-external-request-retries.md).
3. **Request failure does not establish remote business failure.** Stripe documents that a timeout can leave execution unknown and a server error can accompany side effects. Stable idempotency keys and reconciliation preserve the remote operation's identity. A provider's definite decline already belongs in the authored response codec; no usable response is a distinct request observation. [Stripe advanced error handling](https://docs.stripe.com/error-low-level), [Shopping provider evidence](../../examples/shopping/src/zerospin/ShoppingProviders.ts).
4. **External observation and continuation result are independent.** The authored continuation can receive an external Failure and successfully commit its failure-handling model changes. Automatically refusing that command would skip the required transition. Original execution and replay evaluate the frozen observation, with no new provider invocation. [Outcome preparation](../../packages/core/src/contracts/decodeExternalCommandInput.ts), [external recording](../../packages/system-worker/src/externalOperations/makeExternalOperationQueue.ts), [original/replay ownership](../adrs/005-ordered-original-execution-and-finalized-replay.md).
5. **Preserve the first observation.** Both outcome branches and their continuation enqueue commit together. Delivery retries preserve the complete outcome and first recording time. Later reconciliation is a new observation and command, not a replacement for the earlier timeout. Internal persistence failure remains a recovery problem and must not be presented as a definitive provider result. [External runtime](../../packages/system-worker/src/externalOperations/makeExternalOperationQueue.ts), [complete source proof](../../packages/system-worker/src/externalOperations/verifyExternalCommandDeliveries.ts).

## Selected representation

Use `commandOutcome` and `externalOutcome`, with distinct command and external request failure types. Each recorded value is either `{ _tag: 'Success', success, recordedAt }` or `{ _tag: 'Failure', failure, recordedAt }`.

Success contains the encoded command result or exact contract-encoded external response. Null stays outside the union: pending command outcome, or no external observation. A successful JSON-null response remains `{ _tag: 'Success', success: null, recordedAt }`. Recording times belong to their separate events, are sampled by the executing owner, and are preserved through retry and transport. [Command outcome schema](../../packages/core/src/contracts/CommandOutcomeSchema.ts), [external outcome schema](../../packages/core/src/contracts/ExternalOutcomeSchema.ts).

ADR 012 replaced the prior no-child terminal-failure policy, and the current source implements that decision. It does not introduce framework-owned request retries, automatic compensation, or a claim of exactly-once remote effects. Plan 152 records its completed implementation work; the source inspection above does not repeat its runtime verification.
