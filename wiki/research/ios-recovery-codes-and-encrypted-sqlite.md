# iOS recovery codes and encrypted SQLite

Research reviewed 2026-11-10. The options below apply to an iOS app with its own data store. The earlier Zerospin note implementation used one encrypted note file and a Files export and restore flow; it has since been removed from the app. Its historical design and verification are recorded in [Plan 295](../archive/plans/295-plan-ios-note-files-recovery.md). Existing note files and exported backups were not deleted by that code removal.

## Why accounts issue a sheet of codes

GitHub gives users 16 recovery codes for 2FA. Google gives users 10 eight-digit codes that can stand in for the usual second step. The user enters one unused code. Successful use spends that code, and generating a replacement batch invalidates the previous batch. The number is a product choice. A batch lets the user get through several future sign-ins with the same saved sheet. [GitHub 2FA recovery](https://docs.github.com/en/authentication/securing-your-account-with-two-factor-authentication-2fa/configuring-two-factor-authentication-recovery-methods#generating-a-new-set-of-recovery-codes), [Google backup codes](https://support.google.com/accounts/answer/1187538?hl=en).

NIST SP 800-63B-4 distinguishes **saved recovery codes** from **issued recovery codes**. For saved account recovery codes, NIST specifies at least 64 random bits, hashed verifier storage, throttled verification, and invalidation and replacement after use. An issued code goes to a previously established recovery address, can be as short as six decimal digits, and has a limited lifetime. These rules describe account recovery at a credential service provider. They do not establish an offline encryption key length. [NIST SP 800-63B-4 §4.2.1](https://pages.nist.gov/800-63-4/sp800-63b/events/#account-recovery-methods).

An encrypted backup has no online verifier to mark a secret spent. Anyone with a copy of the encrypted file can guess offline, and anyone who already has both the file and key can decrypt it again. App-side limits or local “used” flags cannot affect those copies. Use one **recovery key** generated from at least 128 bits of randomness for this job. Format it for copy and manual entry. A checksum can catch transcription mistakes and contributes no secret entropy. NIST's verifier rules and Signal's design illustrate the difference. [NIST saved recovery codes](https://pages.nist.gov/800-63-4/sp800-63b/events/#saved-recovery-codes), [Signal Secure Backups design](https://signal.org/blog/introducing-secure-backups/), [Apple secure random bytes](<https://developer.apple.com/documentation/security/secrandomcopybytes(_:_:_:)>).

## What the recovery key opens

For local-first Zerospin data, the recovery key can open an **encrypted backup** containing a consistent snapshot of the data that the app promises to recover. A new iPhone needs access to both the backup and the key. Restoring a manually exported file recovers the snapshot in that file. A copy that only exists on the lost phone offers no device-loss recovery. Signal's hosted backups illustrate automatic refresh and its on-device export illustrates a user-selected storage destination. [Signal Secure Backups design](https://signal.org/blog/introducing-secure-backups/), [Signal iOS release 8.30](https://github.com/signalapp/Signal-iOS/releases/tag/8.30.0.1882).

On a fresh install, offer **Create** and **Restore from backup**. A proposed manual restore has the user choose the file from Files and enter their recovery key. If typing the key alone should discover the backup, Zerospin needs a separate way to retrieve ciphertext, such as the user's iCloud private database or a backup service with its own lookup and access model. A custom service can store ciphertext without receiving the recovery key. Decide what happens when the storage account, last backup, or key is unavailable. For a device that still opens the data, a replacement key can protect a new backup. Any prior copies remain decryptable with their original key. [Apple's Files document picker](https://developer.apple.com/documentation/uikit/providing-access-to-directories), [Apple CloudKit user-data encryption](https://developer.apple.com/documentation/cloudkit/encrypting-user-data), [Signal's key and storage model](https://signal.org/blog/introducing-secure-backups/).

## Native backup flow

- **Save your recovery key.** Show the key in large, selectable groups and recommend a password manager accessible on a replacement device or a written copy in a safe place. Ask the user to confirm they can retrieve it. Signal's shipped flow offers password manager or manual saving followed by confirmation. [Signal setup instructions](https://support.signal.org/hc/en-us/articles/9708267671322-Signal-Secure-Backups), [Signal iOS save and confirm views](https://github.com/signalapp/Signal-iOS/tree/main/Signal/Backups/RecoveryKey).
- **Save an encrypted backup.** Use a SwiftUI file exporter for Save to Files, with `ShareLink` as an optional way to send the encrypted file. Give the key its own save action. The general share sheet can hand its contents to Messages, Mail, or another app, so the item passed to it should be the encrypted backup. Treat completion of a Files export as a local save, with cloud upload status separate where available. [Apple file exporter](<https://developer.apple.com/documentation/swiftui/view/fileexporter(ispresented:document:contenttype:defaultfilename:oncompletion:)>), [Apple ShareLink](https://developer.apple.com/documentation/swiftui/sharelink?language=objc).
- **Keep screenshots secondary.** A screenshot puts the key in Photos, which can sync across devices with iCloud Photos. It can still leave the user with a single copy on the original phone. The screenshot notification arrives after capture, so it cannot prevent the saved image or establish that it is recoverable. Use the large text for “Save your recovery key somewhere you can reach without this iPhone.” [Apple screenshot behavior](https://support.apple.com/guide/iphone/take-a-screenshot-iphc872c0115/ios), [Apple iCloud Photos](https://support.apple.com/guide/icloud/set-up-icloud-photos-mm7e90c1ba48/icloud), [UIKit screenshot notification](https://developer.apple.com/documentation/uikit/uiapplication/userdidtakescreenshotnotification).

## SQLCipher recipe for a single authoritative database

Zetetic's supported encrypted-to-encrypted export allows separate keys for daily use and for the portable backup. This is a candidate when one database contains the complete recovery payload. For a collection of databases or files, use an application-level archive at a defined consistent cut, with an authenticated manifest and an explicit restore procedure. SQLite's WAL documentation explains why independent database commits cannot supply that consistency. [Zetetic encrypted export](https://www.zetetic.net/sqlcipher/sqlcipher-api/#sqlcipher_export), [SQLite WAL](https://sqlite.org/wal.html).

1. **Create the working database.** Generate a random 32-byte SQLCipher key for this installation, store it in a device-only Keychain item, and key every connection before the first database access. Use a Keychain accessibility class suited to whether the app opens the database while the phone is locked. Verify `PRAGMA cipher_version` and query the schema. A wrong key can surface on the first read. [Zetetic's Swift integration tutorial](https://www.zetetic.net/sqlcipher/sqlcipher-apple-community/), [Apple Keychain accessibility](https://developer.apple.com/documentation/security/restricting-keychain-item-accessibility), [Signal iOS working-database source](https://github.com/signalapp/Signal-iOS/blob/main/SignalServiceKit/Storage/Database/GRDBDatabaseStorageAdapter.swift).
2. **Create the portable backup.** Derive a 32-byte backup key from the independently generated recovery secret with CryptoKit HKDF and backup-format-specific context. A subsequent export can use that backup key from Keychain if exports need to proceed without asking for the recovery key each time. On a dedicated SQLCipher connection, attach a fresh staging database under the backup key and use `sqlcipher_export` to copy schema and rows. Give the export a consistent source read, with the app's database writer serialized during the export for a simple first implementation. Copy any header metadata the app needs explicitly. Zetetic documents the omission of `user_version` and `auto_vacuum`. Source inspection also shows no copy of `application_id`. Version the backup format explicitly, reopen and check the encrypted staging file, then publish the complete file. SQLite can retain committed changes in the WAL, so copying the main live file can lose committed data. [Apple HKDF](https://developer.apple.com/documentation/cryptokit/hkdf), [Zetetic export and implementation notes](https://www.zetetic.net/sqlcipher/sqlcipher-api/#sqlcipher_export), [SQLCipher export source](https://raw.githubusercontent.com/sqlcipher/sqlcipher/master/src/sqlcipher.c#L3742-L3885), [SQLite header pragmas](https://sqlite.org/pragma.html#pragma_application_id), [SQLite WAL](https://sqlite.org/wal.html).
3. **Restore on the new phone.** Import a staged copy through Files. Derive the same backup key, open the encrypted file, verify its format and integrity, and export into a new encrypted working database under a fresh device-local key. Persist that key and activate the staged database through a recoverable commit so an interruption leaves the existing workspace usable and retryable. A wrong key or invalid backup should leave the current workspace intact. Zetetic supports `sqlcipher_export` across encryption settings and limits the SQLite backup API to compatible settings. [Zetetic key verification and integrity checks](https://www.zetetic.net/sqlcipher/sqlcipher-api/#pragma-cipher_integrity_check), [Zetetic's SQLite backup API limitation](https://discuss.zetetic.net/t/database-created-by-low-version-sqlcipher-sqlite3-backup-on-a-higher-version-sqlcipher-results-in-error-11/6933/2), [Apple file importer](<https://developer.apple.com/documentation/swiftui/view/fileimporter(ispresented:allowedcontenttypes:oncompletion:)>).

## Tutorials and production examples

- **Zetetic SQLCipher** has a Swift tutorial with key setup, raw 256-bit key handling, and runtime verification. Its maintained Swift package is the straightforward place to start for a small native storage experiment. [Community Edition Apple tutorial](https://www.zetetic.net/sqlcipher/sqlcipher-apple-community/), [SQLCipher.swift](https://github.com/sqlcipher/SQLCipher.swift).
- **GRDB** documents connection configuration, passphrase changes, and exports. Its ordinary Swift Package Manager setup uses system SQLite. A Swift Package Manager build against SQLCipher requires a GRDB fork and a manifest edit in the maintainer's documented setup. [GRDB encryption](https://github.com/groue/GRDB.swift/blob/master/README.md#encryption), [GRDB package manifest](https://github.com/groue/GRDB.swift/blob/master/Package.swift).
- **Signal iOS** is a shipping Swift example for both sides. `GRDBKeyFetcher` generates and stores a SQLCipher key specification in Keychain for the working database. Signal separately derives backup key material from a 64-character account entropy pool and serializes encrypted message backups. The hosted backup docs and encrypted file export release show two ways to get ciphertext to another device. Its archive format and account integration are specific to Signal. [Working database source](https://github.com/signalapp/Signal-iOS/blob/main/SignalServiceKit/Storage/Database/GRDBDatabaseStorageAdapter.swift), [Signal backup key source](https://github.com/signalapp/Signal-iOS/blob/main/SignalServiceKit/Backups/MessageRootBackupKey.swift), [libsignal backup format and APIs](https://github.com/signalapp/libsignal/blob/main/doc/src/backups/README.md), [Signal iOS export release](https://github.com/signalapp/Signal-iOS/releases/tag/8.30.0.1882).
- **KeePassium** is a second production iOS example of opening an encrypted portable file on a new phone using the original unlock credential. It uses the KeePass KDBX format. Its migration instructions are a useful Files and manual-restore UX reference. [KeePassium source](https://github.com/keepassium/KeePassium), [KeePassium new-device guide](https://support.keepassium.com/kb/new-device/).

## If the app adopts Zerospin’s native runtime

`SQLiteHost` opens system SQLite files in WAL mode without app-level keys. Adopting SQLCipher for those files would change the native host. [Swift package linkage](../../packages/swift/Package.swift), [SQLiteHost.open](../../packages/swift/Sources/Zerospin/SQLiteHost.swift#L118-L139).

`makeNativeStandaloneSession` opens both the AggregateNode and the persistent Aggregate session replica. Startup reconciles pending commands before installing the AggregateNode snapshot in the replica. A lossless backup of this pair needs a consistent cut across both stores, including any retained commands and identities required to reopen them. In connected mode, an authenticated backend baseline can rebuild a replica. Local-only commands in the two stores need their own preservation decision. Import and recovery must preserve the Zerospin parallel-model command execution and replay boundary. [Standalone startup](../../packages/native/src/makeNativeStandaloneSession.ts#L108-L166), [Connected startup](../../packages/native/src/openAggregateNativeNodeOwner.ts#L148-L164), [Zerospin parallel-model rules](../../packages/sdk/skills/zerospin-parallel-models/SKILL.md).
