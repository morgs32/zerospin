## Historical pre-change snapshot

The recommendations and numbered findings below preserve the original inspected source, before the approved changes recorded above. They are not a current backlog; historical source links may have shifted or been removed.

### Original recommendation

1. **Give Aggregate and Service one explicit logical-time rule for authored evaluation.** Freeze the Effect wall clock at `outcome.finalizedAt` for payload adaptation, guards, and contract programs. This is the clearest bounded correctness change.
2. **Decide and implement the failure boundary deliberately.** Recommend aborting materialization without progress for missing/broken payload adapters in both owners; retain declared business refusals from guards/programs and supported release-local unsupported-contract refusals. Preserve defects, interruptions, and composite Causes. Do not mechanically copy either existing code list.
3. **Defer capability parity and schema cleanup.** Historical session versions and authorization commands need a demonstrated caller before changing Service capabilities. Private recovery behavior needs an explicit API contract decision. Actor fanout identity and producer indexes are smaller follow-up cleanup, with fixed-schema cutover constraints.

These recommendations come from the mechanisms below; no application failure was reproduced.

## 1. Logical time: confirmed difference, plus a narrower Service gap

`ServiceVersionRepo.executeServiceOccurrence` wraps `evaluateServiceCommand` with `withServiceEvaluationClock`, using the occurrence's `finalizedAt`. The helper freezes Effect milliseconds and nanoseconds, while keeping monotonic time and sleep delegated to the live Clock. Aggregate calls `evaluateAggregateCommand` directly without an equivalent Clock service. Both evaluation procedures run owner guards and then `executionContract.evaluate`. Sources: [Service evaluation](../../packages/system-worker/src/ServiceVersionRepo/utils/executeServiceOccurrence.ts#L41-L54), [Clock implementation](../../packages/system-worker/src/ServiceVersionRepo/utils/withServiceEvaluationClock.ts#L3-L19), [Aggregate evaluation](../../packages/system-worker/src/AggregateVersionRepo/utils/executeAggregateCommandTx.ts#L42-L52), [Aggregate guard/program order](../../packages/system-worker/src/AggregateVersionRepo/utils/evaluateAggregateCommand.ts#L24-L63), [Service guard/program order](../../packages/system-worker/src/ServiceVersionRepo/utils/evaluateServiceCommand.ts#L24-L63).

Both owners distinguish fresh parallel evaluation from restoration. When this release already has retained evaluated output, `materializeCommandTx` invokes `restoreEvaluatedCommandTx` instead of evaluating. `replayCommand` rejects missing own-original-release output rather than inventing a new evaluation. The time discrepancy therefore affects **first evaluation by a new parallel release**, not restoration of retained output. Sources: [Aggregate branch](../../packages/system-worker/src/AggregateVersionRepo/materializeCommandTx.ts#L38-L54), [Service branch](../../packages/system-worker/src/ServiceVersionRepo/materializeCommandTx.ts#L33-L49), [Aggregate recovery rule](../../packages/system-worker/src/AggregateVersionRepo/replayCommands/replayCommand.ts#L40-L50), [Service recovery rule](../../packages/system-worker/src/ServiceVersionRepo/replayCommands/replayCommand.ts#L38-L48).

For replay, both read the source command's `outcome.finalizedAt`. For original execution, Service samples Effect Clock, while Aggregate calls `new Date()` directly. Aggregate retains the historical timestamp in its output even though guards/programs see the current Effect Clock. Sources: [Aggregate sampling](../../packages/system-worker/src/AggregateVersionRepo/utils/readAggregateCommandTx.ts#L73-L80), [Service sampling](../../packages/system-worker/src/ServiceVersionRepo/utils/readServiceOccurrenceTx.ts#L56-L68), [Aggregate outcome construction](../../packages/system-worker/src/AggregateVersionRepo/utils/makeEvaluatedAggregateCommand.ts#L21-L28).

**Failure mode, inferred from these sources:** a guard/program comparing Effect Clock with an expiry can take a different branch when a fresh Aggregate release evaluates the same admitted command later, solely because time passed. A Service contract already demonstrates this exact programming shape: `createTimedReservation` compares `Clock.currentTimeMillis` with `expiresAt`. That is an existing Service example of time-sensitive behavior, not evidence that a current Aggregate application already failed. Source: [timed contract declaration](../../packages/system-worker/tests/support/servicePublicationConfig.ts#L83-L114).

**The Service wrapper is too narrow for a complete logical-time rule.** `resolveServiceExecution` runs before the Clock override and calls `decodeAndAdaptPayload`; Aggregate also resolves before evaluation. Payload adaptation invokes the authored adapter through `Effect.suspend`. A valid adapter reading Effect Clock therefore still observes replay time in both owners. Sources: [Service resolution ordering](../../packages/system-worker/src/ServiceVersionRepo/utils/executeServiceOccurrence.ts#L41-L54), [Service adaptation](../../packages/system-worker/src/ServiceVersionRepo/utils/resolveServiceExecution.ts#L62-L83), [Aggregate adaptation](../../packages/system-worker/src/AggregateVersionRepo/utils/resolveAggregateExecution.ts#L88-L100), [authored adapter invocation](../../packages/core/src/contracts/decodeAndAdaptPayload/adaptPayload/adaptPayload.ts#L93-L104).

**Bounded next work:** use one domain-neutral logical Clock helper for both owners, sample original `finalizedAt` from Effect Clock, and encompass authored payload adaptation, guard evaluation, and program evaluation inside that context. Keep the existing synchronous savepoint and enclosing transaction boundaries. Retained-output restoration remains restoration. This supplies a specific Effect Clock guarantee, not general determinism: it cannot intercept authored `Date.now()` or `new Date()`, and does not freeze random values or external observations. The existing helper's live monotonic/sleep delegation is a useful boundary to preserve. Source for that existing boundary: [Clock helper](../../packages/system-worker/src/ServiceVersionRepo/utils/withServiceEvaluationClock.ts#L8-L19).

For later authorized verification, the smallest meaningful evidence is a time-sensitive fresh parallel Aggregate evaluation after an expiry, a retained-output restore that does not reevaluate, and an Effect Clock-reading adapter. This research does not authorize creating those tests.

## 2. Failure policy: durable progress, not error presentation

The pasted claim is current: Service retains `contract-payload-adapter-missing`, `contract-payload-adapter-failed`, and `contract-payload-adapter-output-invalid` as public `Failure`; Aggregate propagates them. Service additionally lists `contract-payload-version-unsupported` and `service-contract-lineage-unsupported`, while Aggregate retains its own actor-contract unsupported cases. Both have specific replay-only unsupported-contract handling. Sources: [Service classification](../../packages/system-worker/src/ServiceVersionRepo/utils/executeServiceOccurrence.ts#L87-L130), [Aggregate classification](../../packages/system-worker/src/AggregateVersionRepo/utils/executeAggregateCommandTx.ts#L85-L137).

The decoder makes the adapter distinctions concrete: missing means the required adapter/destination definition is absent; `adapter-failed` means the authored callback produced a single typed failure; output-invalid means the adapter returned a value rejected by the destination payload schema. A thrown defect is **not** necessarily `adapter-failed`: `runAuthoredCallback` preserves Causes with no typed Fail reason and composite Causes. Both executors propagate those Causes, except their deliberate conversion of an asynchronous synchronous-program violation. Sources: [adapter failure sources](../../packages/core/src/contracts/decodeAndAdaptPayload/adaptPayload/adaptPayload.ts#L75-L104), [callback Cause handling](../../packages/core/src/execution/runAuthoredCallback.ts#L62-L91), [Aggregate Cause handling](../../packages/system-worker/src/AggregateVersionRepo/utils/executeAggregateCommandTx.ts#L70-L84), [Service Cause handling](../../packages/system-worker/src/ServiceVersionRepo/utils/executeServiceOccurrence.ts#L72-L86).

Both owners run execution in `withSavepoint`; failure rolls back the savepoint before classification. A retained `Failure` becomes `{ outcome: { result: { _tag: 'Failure', failure }, finalizedAt }, operations: [] }`, and then the outer transaction inserts the complete pending evaluated command and advances `materializationHead`. An outer failure reaches neither retention step. Sources: [rollback](../../packages/core/src/drizzle/withSavepoint.ts#L41-L60), [Aggregate materialization](../../packages/system-worker/src/AggregateVersionRepo/materializeCommandTx.ts#L47-L54), [Service materialization](../../packages/system-worker/src/ServiceVersionRepo/materializeCommandTx.ts#L42-L49), [Aggregate Failure output](../../packages/system-worker/src/AggregateVersionRepo/utils/makeEvaluatedAggregateCommand.ts#L21-L42), [Service Failure output](../../packages/system-worker/src/ServiceVersionRepo/utils/makeEvaluatedServiceCommand.ts#L19-L40), [Aggregate atomic pending output/checkpoint](../../packages/system-worker/src/AggregateVersionRepo/utils/retainEvaluatedCommandTx.ts#L16-L40), [Service atomic pending output/checkpoint](../../packages/system-worker/src/ServiceVersionRepo/utils/retainEvaluatedCommandTx.ts#L16-L38).

That difference has two consequences. For original execution, the Chain selects its oldest command with null `outcome`, so an infrastructure failure leaves that command pending and blocks later original execution. For first evaluation by a new parallel release, a propagated failure prevents that release's materialization checkpoint from advancing; a retained Failure permits it to progress past the command. Sources: [Aggregate oldest pending selection](../../packages/system-worker/src/AggregateChain/readPendingAggregateCommand.ts#L6-L22), [Service oldest pending selection](../../packages/system-worker/src/ServiceChain/readPendingServiceCommand.ts#L6-L22), [Aggregate original delivery/acknowledgement](../../packages/system-worker/src/AggregateChain/AggregateChain.ts#L171-L198), [Service original delivery/acknowledgement](../../packages/system-worker/src/ServiceChain/ServiceChain.ts#L129-L152), materialization/retention sources above.

Do not describe this as automatic immediate retry of all failures. The outbox transport schedule retries only a marked retryable transport Error; `readRpcEnvelope` and durable acknowledgement happen after transport success. Queue recovery remains held when a drain fails or pending work remains. Sources: [transport retry discrimination](../../packages/core/src/outbox/makeOutboxDelivery.ts#L223-L285), [receipt before acknowledgement](../../packages/core/src/outbox/makeOutboxDelivery.ts#L288-L295), [durable queue recovery](../../packages/system-worker/src/makeOutboxQueue/makeOutboxQueue.ts#L307-L343).

### Recommended policy, requiring a deliberate decision

| Condition                                                                                                        | Recommended behavior in both owners                 | Reason                                                                                                                      |
| ---------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Declared business refusal from a guard/program                                                                   | Retain public Failure and advance                   | It is a valid evaluated result of this release's command logic.                                                             |
| Required payload adapter missing, single typed adapter failure, or invalid adapter output                        | Abort with no outcome/checkpoint progress           | The release cannot reliably interpret admitted history; do not turn a broken translation into permanent domain disposition. |
| New parallel release deliberately lacks a contract supported by valid retained source authority                  | Retain a release-local unsupported-contract Failure | It is a deliberate lack of release support, distinct from pretending a supported transformation succeeded.                  |
| Missing source authority, invalid retained command, SQL/transport failure, defect, interruption, composite Cause | Abort, preserving Cause                             | These do not establish one trustworthy evaluated refusal.                                                                   |

This recommendation changes Service's present adapter behavior. It is a policy proposal, not a conclusion forced by SDK types, and it does not justify silently reclassifying every existing program validation error. Both owners already retain certain program/result/operation validation errors; review those separately against the same boundary instead of enlarging the change mechanically. The immediately unsettled decision is whether a broken adapter should permanently skip a command or stop the release until its declaration is corrected. Current source supports both mechanics but implements different choices. Sources for present lists: [Aggregate](../../packages/system-worker/src/AggregateVersionRepo/utils/executeAggregateCommandTx.ts#L104-L120), [Service](../../packages/system-worker/src/ServiceVersionRepo/utils/executeServiceOccurrence.ts#L94-L113).

The SDK cannot settle that policy: it exports `resolveFailure` from core, and core recognizes declared business codecs while preserving the wire failure. Recognition decides whether a client has a typed handler; it does not decide retention, progress, or retry. Sources: [SDK export](../../packages/sdk/src/index.ts#L24-L28), [core recognition](../../packages/core/src/contracts/failureCodec.ts#L108-L129), [unknown-code fallback](../../packages/error/src/matchZerospinErrorCode.ts#L81-L88).

A retained Service adapter Failure already belongs to immutable release output; correcting the adapter does not reevaluate that retained command during restoration. A policy cutover must respect current development-line rules and cannot assume existing storage may be reset. Sources: [Service restoration branch](../../packages/system-worker/src/ServiceVersionRepo/materializeCommandTx.ts#L35-L40), [parallel-model rules](../../packages/sdk/skills/zerospin-parallel-models/SKILL.md#L23-L30), [repository cutover policy](../../AGENTS.md#L3-L14).

## Scope of the next change

Start with logical Effect Clock evaluation only. Do not create a universal Aggregate/Service execution abstraction: the source already exposes the exact shared invariant without requiring ownership, authorization, or session-version capabilities to converge. Follow with a short settled policy for adapter failures, then implement that policy in both executors. Leave actor identities, schema constraints, and recovery-contract decisions for independent work when their benefit justifies a cutover.
