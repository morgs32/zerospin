# Hosting Aggregate agent behavior

**Date:** 2026-10-21. **Status:** Source research and provisional design; no implementation or runtime verification.

**Superseded hosting recommendation:** The subsequent discussion selected a separate `AggregateAgentBackendNode` consuming the same retained Agent Chain stream as the client, with its own per-row behavior state and alarm registry. See the [updated source research](aggregate-agent-backend-node.md) and [design draft](../archive/plans/249-plan-aggregate-agent-backend-node.md). The colocated-host recommendation below is historical context, not the selected design.

**Requested behavior:** React automatically to selected rows, with retries and delays. The user clarified this during research; explicit invocation alone does not meet the request.

## Finding

The reusable declaration already exists. `makeAggregateAgentRelease` captures exact Aggregate and agent versions, the query database, selections, ordinary contracts and row-to-payload bindings. It declares what an agent can see and submit, but contains no autonomous behavior. The missing capability is a durable behavior host. A second materialization Repo is not yet justified. [Core declaration](../../packages/core/src/agent/makeAggregateAgentRelease.ts#L37-L47), [captured result](../../packages/core/src/agent/makeAggregateAgentRelease.ts#L140-L145).

## Current ownership

- `AggregateAgentVersionRepo` already materializes the agent view, subscribes during activation, publishes selected deltas and exposes snapshot/bootstrap methods. Its exact identity is `{ systemId, aggregateId, aggregateName, aggregateVersion, agentName, agentVersion }`. Although the public graph is selected, its physical database currently retains all Aggregate-release model tables because RAW selections do not declare their complete dependencies. [Repo](../../packages/system-worker/src/AggregateAgentVersionRepo/AggregateAgentVersionRepo.ts#L35-L139), [identity](../../packages/system-worker/src/AggregateAgentVersionRepo/aggregateAgentVersionRepoName.ts#L6-L11), [physical graph](../../packages/system-worker/src/AggregateAgentVersionRepo/aggregateAgentVersionRepoMigratableDORepoConfig.ts#L19-L31).
- `AggregateAgentVersionChain` delegates retained projected-history and socket behavior to `AggregateSessionChain`. History insertion and private command-resolution insertion share one synchronous transaction. Keep this history responsibility separate from materialized resource ownership. [Chain](../../packages/system-worker/src/AggregateAgentVersionChain/AggregateAgentVersionChain.ts#L14-L32), [retention](../../packages/system-worker/src/aggregateSessionChain/appendExposedCommands.ts#L26-L29), [agent history writes](../../packages/system-worker/src/aggregateSessionChain/appendExposedCommands.ts#L107-L127), [repository rule](../../AGENTS.md).
- The browser constructor calls the core declaration constructor, then adds `sessionType` and its application `layer`. Sharing the core declaration does not require mounting a browser session or copying its optimistic Node and socket lifetime into a Durable Object. [Browser extension](../../packages/browser/src/sessionDefinition/makeAggregateAgentRelease.ts#L86-L114).
- Shopping's `purchases` declaration selects paid purchases and binds `createTrackingLabel` and `updateTrackingInfo`. It specifies no automatic paid-purchase trigger. That is a useful concrete first behavior, rather than evidence of an existing automation. [Purchases declaration](https://github.com/morgs32/zerospin/blob/0e3ad6f97f825faf23e26bf073949485579e9942/examples/shopping/src/zerospin/agents/purchasesAgentRelease.ts#L16-L42).

## Proposed seam

Reuse the exact shared agent release for visibility and command permissions. Author server behavior separately against a small interface: read its selected committed graph and submit one of its declared commands. Server-only dependencies belong to the behavior implementation. Do not make every browser release carry a server behavior or server dependency layer.

For one behavior per exact Aggregate-agent identity, first consider hosting that behavior inside `AggregateAgentVersionRepo`, with a cohesive internal behavior module. It already owns the relevant committed graph and activation seam. Current behavior progress and complete pending command deliveries can live with materialization; retained execution or audit history cannot. A separate `AggregateAgentRepo` becomes meaningful if there are independently identified behavior instances, independent behavior versions or a distinct lifecycle. Those requirements have not been established. This is a placement proposal, not implemented behavior. [Existing materialization owner](../../packages/system-worker/src/AggregateAgentVersionRepo/AggregateAgentVersionRepo.ts#L48-L95), [ownership rule](../../AGENTS.md).

For reactive behavior, the durable sequence should be:

1. Observe committed selected state. Record the decision's stable identity, complete command envelope and behavior progress in a synchronous transaction. If decisions must observe every materialized transition, make this part of the receiving transaction; a later snapshot only establishes current-state behavior.
2. Submit the pending envelope to `AggregateChain.admitAggregateCommands`, using the exact agent origin and declared session. Admission already validates agent version, Aggregate release, session and ordinary contract version. It retains admitted commands transactionally and recovers equal retries by command `id`.
3. After durable admission acknowledgement, delete dedicated pending admission delivery. If the behavior waits for execution, retain explicit current waiting state until the command's `outcome` is observed; admission alone does not prove execution or success.

This sequence extends existing transaction and admission seams; it is not a new direct model-write path. Existing projection replay applies command operations and commits graph changes, `materializationHead` and complete pending publication transactionally. Agent behavior must continue to change authored model rows only through command execution. [Projection transaction](../../packages/system-worker/src/aggregateProjection/applyEvaluatedCommands/applyEvaluatedCommandsTx.ts#L26-L29), [operation application](../../packages/system-worker/src/aggregateProjection/applyEvaluatedCommands/applyEvaluatedCommandsTx.ts#L100-L108), [projection commit](../../packages/system-worker/src/aggregateProjection/commitProjectionTx/commitProjectionTx.ts#L97-L130), [agent admission checks](../../packages/system-worker/src/AggregateChain/admitAggregateCommands/validateAgentCommand.ts#L18-L37), [retained admission](../../packages/system-worker/src/AggregateChain/admitAggregateCommands/admitAggregateCommandsTx.ts#L18-L54), [equal retry checks](../../packages/system-worker/src/AggregateChain/admitAggregateCommands/readRetainedCommand.ts#L17-L40), [parallel-model rule](../../AGENTS.md).

## Two decisions that matter

**What identifies one reaction?** Current selected-row reconciliation and processing every committed transition are different requirements. For `paid purchase -> createTrackingLabel`, decide whether each paid purchase needs one action, whether changing relevant purchase fields permits another, and what a rejected command means for later reconciliation. A newly generated command `id` on each activation defeats admission deduplication: stable command-ID retries solve delivery duplication, not recurring-trigger identity. Existing agent admission also requires `sessionName`; a proposal cannot silently substitute an all-null producer tuple. Non-null `nodeId` requires durable contiguous `pushIndex` and unchanged origin/session/release. [Retry equality](../../packages/system-worker/src/AggregateChain/admitAggregateCommands/readRetainedCommand.ts#L19-L28), [session validation](../../packages/system-worker/src/AggregateChain/admitAggregateCommands/validateAgentCommand.ts#L23-L31), [producer continuity](../../packages/system-worker/src/AggregateChain/admitAggregateCommands/validateAggregateNodeContinuation.ts#L18-L55).

**Who starts and resumes it?** Existing projection activation subscribes when that Repo is activated; it does not by itself establish automatic creation of behavior hosts for every Aggregate. A reactive implementation must establish enrollment/startup, process already matching rows, and recover pending command submissions after restart. Reuse `makeMigratableDORepo` activation and the existing `recoveryRegistry`: register lazy recovery, arm recovery before committing pending work, and recover from durable rows. The current registry provides a shared one-second recovery wake-up, not a general authored deadline scheduler. Independent behavior versions also need an explicit handover policy so two versions do not both perform one intended business action. [Projection activation](../../packages/system-worker/src/AggregateAgentVersionRepo/AggregateAgentVersionRepo.ts#L59-L68), [factory activation/alarm](../../packages/system-worker/src/makeMigratableDORepo/makeMigratableDORepo.ts#L281-L343), [recovery implementation](../../packages/system-worker/src/makeRecoveryRegistry/makeRecoveryRegistry.ts#L22-L68).

## Required retry and delay semantics

The requested delay needs a persisted due time such as `wakeAt` in current behavior state. Activation must restore it and an alarm must discover due work after restart; an in-memory sleep cannot establish that guarantee. A delayed invocation should also specify whether the selected row must still match when due. The existing recovery registry can recover durable pending work, but its fixed one-second reconciliation is not an existing arbitrary-deadline facility; exact alarm integration remains a design choice. [Current registry scheduling](../../packages/system-worker/src/makeRecoveryRegistry/makeRecoveryRegistry.ts#L27-L39), [cold recovery](../../packages/system-worker/src/makeRecoveryRegistry/makeRecoveryRegistry.ts#L52-L68).

Retry of an uncertain admission must resend the same frozen command envelope and `id`. Retry after a retained `outcome.result._tag === 'Failure'` is a new behavior decision and must follow an authored failure policy; retrying delivery of the original command cannot turn its retained outcome into success. Keep retry due time, current attempt state and waiting command identity as current behavior state, with retained execution history in a Chain if needed. Do not automatically retry every domain rejection. [Admission recovery](../../packages/system-worker/src/AggregateChain/admitAggregateCommands/admitAggregateCommandsTx.ts#L37-L45), [exact-envelope equality](../../packages/system-worker/src/AggregateChain/admitAggregateCommands/readRetainedCommand.ts#L19-L40), [outcome schema](../../packages/core/src/contracts/CommandSchema.ts#L173-L181).

The next design work should settle reaction identity, whether current-state reconciliation is sufficient, retryable failure classification, and durable deadline integration. Reactive behavior with retry and delay is established scope; a new physical `AggregateAgentRepo` remains provisional.
