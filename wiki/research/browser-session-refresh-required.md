# Refresh required for a retired Aggregate browser session

Reviewed Zerospin main at `90a41dc245` and QRK's current App wiring. This is a proposal based on source inspection.

## The decision belongs to browser session admission

Promoting a canonical Aggregate release does not retire a browser session. The session selects one exact Aggregate/Actor release and declaration lock. AggregateChain retains the original input and routes original execution to its retained `aggregateVersion`. The canonical release supplies the adopted replay history prefix. A compatible old browser can continue writing after promotion. A candidate session can also write a command that its own release supports while the old canonical release records a release-local unsupported refusal during replay. Sources [versioning and deployment](../../docs/content/handbook/versioning-and-deployment.md#add-functionality-through-a-new-release), [AggregateChain admission and original delivery](../../packages/system-worker/src/AggregateChain/AggregateChain.ts#L472-L505), [canonical history](../../packages/system-worker/src/AggregateChain/AggregateChain.ts#L116-L134), [unsupported replay](../../packages/system-worker/src/AggregateVersionRepo/utils/executeAggregateCommandTx.ts#L89-L132).

For a breaking cutover that keeps historical releases registered, make accepting new browser sessions/pushes a separate explicit decision about the retired exact binding. Its identity can use the existing aggregate/actor/session lock facts. Comparing the version to `canonical` would also reject deliberate candidate and compatible historical sessions. Generic missing-release, malformed lock, authored refusal and network errors also lack proof that a reload will help. The existing code validates the admitted Actor and claims in AggregateAccessApi, then checks the exact release lock in AggregateVersionRepo. Sources [AggregateAccessApi.authorize](../../packages/system-worker/src/AggregateAccessApi/authorize/authorize.ts#L45-L95), [validateAggregateSessionLock](../../packages/system-worker/src/AggregateVersionRepo/authorizeAggregateSession/validateAggregateSessionLock.ts#L27-L78).

Use one stable framework error such as `aggregate-session-refresh-required`, with user-facing text “Refresh this page to use the latest version.” Check the same policy in authenticated session acquisition and fresh live socket push admission. The latter already has the authenticated live connection, validates the command identity and granted contract, and calls AggregateChain. Its existing failure envelope carries structured failures. A reconnect must encounter the policy through authorization or ticket/resume even with no pending push. A hibernated or still-open connection must encounter the policy before its next fresh push. A proactively interrupted idle connection would require a separate signal; the user described incompatible pending pushes, so reject on an existing protocol interaction first. Keep authenticators, authorizers and scope checks in force and preserve durable evidence for earlier accepted commands. Sources [admitAggregateSessionCommand](../../packages/system-worker/src/aggregateSessionChain/onMessage/admitAggregateSessionCommand.ts#L23-L64), [admitSocketCommand](../../packages/system-worker/src/aggregateSessionChain/onMessage/admitAggregateSocketCommand.ts#L58-L86), [AggregateNode network](../../packages/browser/src/AggregateNode/aggregateNodeNetwork.ts).

## Reuse terminal reporting and the existing error page

AggregateNodeSynchronization currently routes a socket admission failure to `AggregateNode.admissionRejected`. That blocks the Node, and the tab failure observer normally treats the rejection as a nonterminal notice for the command originating in that particular tab. A command from an older document or another attached tab may have no matching origin in this document. Special-case the proven refresh-required signal as a session-wide blocked failure and preserve its code through both startup and warm paths. Publish it to every attached tab, bypass per-command origin filtering and classify it as terminal `origin: 'session'`. The existing reporter withdraws readiness and pins the first terminal error. Neither a client retry nor automatic Node repair can make the stale executable compatible. Sources [socket failure handling](../../packages/browser/src/AggregateNode/AggregateNodeSynchronization.ts#L580-L629), [AggregateNode.admissionRejected](../../packages/core/src/AggregateNode/AggregateNode.ts#L1355-L1363), [makeSessionFailureObserver](../../packages/browser/src/Node/makeSessionFailureObserver.ts#L24-L44), [blocked-state observer](../../packages/browser/src/Node/makeSessionFailureObserver.ts#L73-L107), [terminal store reporter](../../packages/core/src/sessionFailure/makeSessionFailureReporter.ts#L36-L59).

`SessionReady` already calls the author's `renderError(error, retry)` for terminal session failures. The managed `retry` replaces the session generation inside the current executable, so it cannot implement document refresh. Keep the existing rendering seam. Let Zerospin select a recovery action with a label and callable action from the failure, with “Refresh page” for this code and the existing session retry for ordinary recoverable errors. The host keeps placement, branding and general layout; a full-page `SessionReady` owner can render a full-page error. A plain web host can use `window.location.reload()`; an app with a service worker can supply its app-update action. If the renderer takes only the error, the framework can render the action next to that content, but the author should still be able to place and style it within the same page. Sources [SessionReady](../../packages/react/src/SessionReady.tsx#L69-L90), [managed retry](../../packages/react/src/managedSession/makeManagedSession.ts#L85-L110).

QRK already uses the signed-in user layout for this gate and renders its `AppError` there. `AppError` already shows a reload button without a retry callback, but that path is a direct browser reload. QRK's AppUpdatePrompt owns the approval, waiting-worker activation and controller-change reload. The forced-refresh page should use that same action so a waiting service worker can serve the new shell. Today this action is inline inside the toast, so QRK would have to expose or share the existing behavior. Keep reload user-initiated. In-memory form drafts belong to QRK and have their own lifecycle; replacing the signed-in subtree removes its form-level beforeunload handlers. Sources [QRK SessionReady renderer](../../../qrk.sh/apps/app/app/%5Busername%5D/layout.tsx#L79-L109), [QRK AppError button](../../../qrk.sh/apps/app/app/error.tsx#L180-L187), [QRK waiting-worker reload](../../../qrk.sh/apps/app/app/AppUpdatePrompt.tsx#L43-L72), [QRK activation handling](../../../qrk.sh/apps/app/app/AppUpdatePrompt.tsx#L74-L100), [form unload hook](../../../qrk.sh/apps/app/lib/useWarnBeforeUnload.ts).

## Refresh replaces code, pending work has its own fate

An original that was already durably admitted must remain eligible to complete under the retained Aggregate/Actor bindings and producer coordinates. An incompatible local-only original cannot be moved to the new binding by refreshing; preserve its old local state, do not mark it successful or replay it under a changed contract, and explain that outstanding local changes may not carry over. The Node session identity selects its storage namespace and includes exact authored bindings. The 43.x pre-baseline transition is also separate: existing runtime-hash databases are left in place and are not scanned or adopted into the new namespace. This is an explicit alternative to operator drainage for a breaking browser cutover if the maintainer accepts stranded local-only edits. It does not change the server's separate incompatible fixed-schema storage requirement. Sources [identity/session key](../../packages/core/src/Node/sessionKey.ts), [browser Node namespace](../../packages/browser/src/Node/nodeStorageNamespaces.ts), [browser storage upgrade rules](../adrs/027-connected-browser-node-storage-upgrades.md), [storage cutover and first adoption](../../docs/content/handbook/versioning-and-deployment.md#separate-framework-schema-cutovers-from-domain-upgrades).

The first rollout needs special sequencing: a browser bundle already installed without the new handler cannot retroactively render it when the backend emits the new code. Ship the handler in a build that still speaks the current backend protocol before enforcing retirement, and have a replacement frontend build available when enforcement starts. Validate a warm old tab, an old tab reconnecting with persisted work, an in-flight original already admitted at cutover, and a reload with a waiting QRK service worker. Source for current generic admission handling [makeSessionFailureObserver](../../packages/browser/src/Node/makeSessionFailureObserver.ts#L73-L107).
