# Worker-owned connected-session discovery

**Date:** 2026-11-01. **Original status:** source research and proposed design at the baseline below; no runtime changes, storage changes, tests, or timing captures were part of this research. This note did not authorize storage resets.

**Implementation update:** the approved design is implemented in the connected host factories and tracked by [Plan 284](../archive/plans/284-plan-worker-owned-connected-session-discovery.md), which owns implementation and verification status. Connected routing now selects a declaration/backend host independently of its authenticated Node databases, and the host reuses each attachment's verified snapshot. Build-specific storage remains intentional. The findings below retain their original baseline meaning; they are not a latency benchmark.

The checkout contains unrelated Studio/system-diagram work; the inspected browser startup and core identity files have no working-tree changes. Findings below cite this checkout's owning source, not generated consumer bundles.

## Answer

**Yes: remove page-owned authenticated discovery and let the SharedWorker select the authenticated Node.** To remove a request, the SharedWorker must retain and reuse the snapshot that established the authenticated identity. Merely moving `resolveAggregateNode` into a SharedWorker, followed by the current unconditional attachment authentication, would still fetch two snapshots.

The recommended separation is:

- The SharedWorker connection is selected by known request/declaration scope, before authentication.
- The AggregateNode or ServiceNode and its persistent database are selected only after server verification, using the existing complete identity hash.
- An attachment receives only the Node whose verified identity matches its own credentials and expected claims.

This changes browser routing and ownership, not backend admission authority. Normal online startup should perform **zero page snapshot requests, one SharedWorker snapshot request, then the existing WebSocket-ticket request**. Recovery and reconnection can legitimately require additional verification. This is a design inference grounded in the current duplicated requests and already-reusable verified admission value. [Page discovery][resolve], [worker verification][verify], [verified admission][verified], [socket startup][socket].

## What the code establishes

1. **The page fetches data it does not carry forward.** `resolveAggregateNode` obtains credentials, fetches `snapshot(null)`, checks the aggregate ID and expected claims, and returns a definition plus attachment metadata. It carries claims, aggregate ID, revision, and online state; it discards snapshot resources and checkpoint. `makeConnectedAggregateConnection` then hashes the verified definition to choose a SharedWorker name. [Resolver][resolve], [connection startup][connection].

2. **SharedWorker selection and persistent identity are currently coupled.** `sessionKey` hashes the complete identity, including server-verified claims. `makeSharedWorker` parses this key from the SharedWorker name. `makeAggregateSharedWorker` uses that same name for the database namespace and exclusive namespace lease. This coupling explains the preflight; it does not prove that preflight is inherently necessary. [Identity hash][key], [name construction][names], [entry selection][entry], [persistent owner construction][aggregate-host].

3. **AggregateNode attachment authenticates again.** `makeAggregateWorkerRuntime` reconstructs the supplied definition and checks it against its fixed storage key. It later uses `makeNodeAuthentication` to obtain credentials and call `snapshot(localNodeId)`, returning verified identity, environment, and baseline. The same mechanism already protects concurrent credential providers, timeouts, detachment, and identity matching. [Attachment identity check][prepare], [second snapshot][verify], [authentication result matching and lifecycle][authentication].

4. **The two snapshot calls have a real difference that must be preserved where relevant.** `snapshot(null)` has `resolvedThrough: 0`; a snapshot addressed by Node ID can carry that producer's private completion prefix. A new Node installs its first baseline once. An existing initialized Node does not overwrite that baseline on ordinary attachment; its WebSocket resumes from its retained Node ID, outcome index, aggregate index, and disposition chain hash. Therefore the proposed one-snapshot normal path can use the initial full snapshot to authenticate and bootstrap an empty Node, while a retained Node continues from its own checkpoint. Recovery paths that need the Node-specific completion prefix must retain their Node-specific snapshot request. This normal-path reuse remains an implementation hypothesis to verify against retained pending-command scenarios. [Server prefix selection][server-snapshot], [one-time baseline][baseline], [baseline use in attachment][baseline-use], [resume and replay validation][resume].

5. **Credentials can stay on the page while discovery moves.** `AggregateSharedWorkerApi.attach` already accepts an RPC credential/admission callback. The application need not move Clerk into a SharedWorker or put tokens in its name. WebSocket startup separately invokes the verified provider and requests a ticket. Removing page discovery eliminates one normal aggregate credential callback; it does not by itself eliminate the ticket callback. Clerk's valid-token caching is a separate consumer optimization. [Attach interface][attach], [socket credentials and ticket][socket].

6. **Service sessions have the same snapshot duplication, with different credential reuse.** `resolveServiceNode` also fetches a snapshot before naming its SharedWorker. Its connection retains the initial admission value and returns it once to the SharedWorker callback, so do not assume an identical three-token-call saving for Services. Aggregate and Service implementations should remain explicit rather than gain an `ownerKind` switch. [Service resolver][service-resolve], [Service connection and one-shot reuse][service-connection], [repository rules](../../AGENTS.md).

## Recommended startup sequence

The following is proposed behavior, not current behavior.

1. **Connect before discovering identity.** `makeConnectedAggregateConnection` computes a routing hash from the known complete request and requested aggregate ID; the Service equivalent hashes its complete request. Include endpoint, publishable key, system, selected owner/Actor/session versions, and the exact session lock. Do not use a token or asserted claims as authentication. This hash selects only a SharedWorker host, never a database. Keep one session definition per entry module. [Existing request fields][request], [Service fields][service-request], [entry contract][entry].

2. **Validate the host before data access.** Preserve document liveness locks, executable URL checks, and protocol checks. `ready()` now means the entry and protocol are ready; it cannot wait for an identity-specific database lease that has not yet been selected. The SharedWorker independently checks the request against its registered declaration and routing scope before starting a domain execution runtime. [Port lifetime][port], [artifact check][artifact], [declaration validation][execution].

3. **Discover inside the SharedWorker.** The attachment supplies request, requested aggregate ID where applicable, optional expected claims, retry/diagnostic options, and its credential callback. The SharedWorker owns discovery revision reads, bounded credential acquisition, the authenticated snapshot request, expected-claims checks, and offline lookup. Remove client assertions that `claims` and `online` have already been verified. Expected claims remain an exact assertion, not proof; online callers without expected claims remain supported. [Current resolver contracts][resolve], [exact claims comparison][assert-claims], [attachment schema to replace][attach].

4. **Select a per-identity durable owner.** From the authenticated result, compute the existing exact `sessionKey`. Within this one-definition SharedWorker host, acquire or join that identity's AggregateNode runtime, namespace lease, and SQLite database. Distinct claims or accounts must not share data, pending commands, failure state, or sign-out state. Simultaneous joins of the same identity need one acquisition record; an arriving join must wait for that identity's closing owner to drain. This replaces the current single-owner assumption inside `makeWorkerConnections` and connected host factories; it does not introduce another bootstrap worker or backend coordinator. [Current single-owner host][connections], [namespace lease][lease], [connected host][aggregate-host].

5. **Consume the verified result once.** Carry the SharedWorker's verified snapshot, identity, environment, producing attachment, and cancellation generation into initial attachment internally. Do not accept a page-supplied "verified" flag or snapshot. Avoid immediately calling `makeNodeAuthentication.authenticate()` again for that same initial proof. For an empty Node, install the baseline once; for a retained Node, retain its Node ID, pending command identities, checkpoint, and replay path. Preserve authentication for future reconnects and the existing WebSocket ticket. Readiness is still published only after synchronization succeeds. [Verified value][verified], [current authentication/baseline/synchronization sequence][baseline-use], [resume validation][resume], [publish after synchronization][publish].

6. **Bind the page from the delivered Node view.** Keep the existing replica receiver's schema, declaration, aggregate ID, full identity, and expected-claims checks. Preserve the facade's fixed authenticated identity on later attachment attempts; a new identity requires a new facade. No new application-visible bootstrap API is justified by this change. [Replica binding][replica], [facade's fixed claims](https://github.com/morgs32/zerospin/blob/c2adda3cf3c874d7832166f2b6d048322b117297/packages/browser/src/makeConnectedAggregateSession.ts#L207).

## Ownership and interruption requirements

These are requirements of the proposed sharing arrangement, derived from the current identity and cleanup behavior:

- **Unauthenticated port:** owns its credential request and cancellation only. It cannot read an already-running account's Node simply because it reached the same SharedWorker host. A detached or timed-out request cannot later create/join a runtime or publish readiness. Preserve distinct credential, local-preparation, backend, and offline-discovery failures. [Authentication][authentication], [current resolver failure classification][resolve].
- **Verified identity runtime:** owns its namespace lease, execution, storage, authentication generation, synchronization, and attachment set. Serialize acquisition/retirement per verified identity, not across unrelated identities. A failed database must not poison every account connected to the host. [Current host's single failure/closing scope][connections], [cleanup order][cleanup].
- **Sign-out:** revoke all attachments and pending authentication work for the matching identity, invalidate its offline eligibility/revision, and preserve unrelated identities in the host. A late snapshot from before sign-out must fail the revision/generation recheck before opening storage or publishing. [Existing revocation][signout], [discovery revision checks][discovery], [authentication cancellation][authentication].
- **Offline reopening:** move the existing discovery registry rather than manufacture identity from expected claims. Only eligible exact matches may reopen retained storage after the currently recognized backend-unavailable outcomes. Missing credentials, rejection, ambiguous identity, and mismatching claims must not become offline authorization. [Resolver classification][resolve], [eligible exact discovery][discovery].

## Scope, cutover, and verification

**Implementation surface:** connected Aggregate/Service connection modules, resolver modules, both SharedWorker APIs and connected host factories, `makeWorkerConnections`, identity-specific runtime acquisition, and shared name parsing. Keep Aggregate/Service methods explicit. Standalone startup does not need authenticated discovery and should retain its current storage rules. Keep backend snapshot and WebSocket-ticket APIs unless implementation identifies a concrete missing capability. [Standalone namespace](https://github.com/morgs32/zerospin/blob/c2adda3cf3c874d7832166f2b6d048322b117297/packages/browser/src/StandaloneNode/makeStandaloneSharedWorker.ts#L12), [existing backend snapshot API](https://github.com/morgs32/zerospin/blob/c2adda3cf3c874d7832166f2b6d048322b117297/packages/system-worker/src/AggregateSessionApi/getSnapshot/getSnapshot.ts#L10).

**Architecture documentation:** update or supersede the process/name/storage assumptions in ADR 019 and the browser session workflow docs; retain its useful one-definition-per-entry decision. An ADR is context, not a reason to preserve duplicate requests. [ADR 019](../adrs/019-one-session-per-shared-worker.md), [repository rules](../../AGENTS.md).

**Storage/protocol:** separate the new routing hash from the exact authenticated storage key. Do not rename a routing key to `sessionKey` and use it to open a shared account database. Connected database names currently contain the runtime/WASM content version as well as the verified key. A changed browser runtime can consequently select a different namespace already; preserving full claims in the key does not promise cross-release persistence. Determine the concrete new naming/version contract in implementation planning, following the repository's hard-cutover policy. No compatibility readers, migrations, storage deletion, or resets are authorized by this research. [Name format][names], [runtime version](https://github.com/morgs32/zerospin/blob/c2adda3cf3c874d7832166f2b6d048322b117297/packages/browser/src/sharedWorkerVersion.ts#L1), [database namespace][aggregate-host], [repository cutover policy](../../AGENTS.md).

**Smallest useful verification:** extend the existing browser scenarios and existing authentication/disposal specs rather than add new test files or fixtures. Verify request counts (zero page snapshot requests and one normal SharedWorker snapshot), first startup, retained pending commands and Node ID on reload, same-identity joins, distinct-identity isolation, expected-claims mismatch, offline reopening and revoked eligibility, sign-out during an unresolved snapshot, and acquisition while the prior same-identity owner drains. Recovery is allowed an additional snapshot and must be tested separately from the normal request-count assertion. Existing entry points include [aggregate public bootstrap/recovery](https://github.com/morgs32/zerospin/blob/c2adda3cf3c874d7832166f2b6d048322b117297/packages/browser/tests/aggregate-public.browser.ts#L106), [aggregate host scenarios](https://github.com/morgs32/zerospin/blob/c2adda3cf3c874d7832166f2b6d048322b117297/packages/browser/tests/aggregate-host.browser.ts#L219), [Service public scenarios](https://github.com/morgs32/zerospin/blob/c2adda3cf3c874d7832166f2b6d048322b117297/packages/browser/tests/service-public.browser.ts#L209), [authentication deadlines](https://github.com/morgs32/zerospin/blob/c2adda3cf3c874d7832166f2b6d048322b117297/packages/browser/tests/node-authentication.spec.ts#L20), and [subscriber disposal](https://github.com/morgs32/zerospin/blob/c2adda3cf3c874d7832166f2b6d048322b117297/packages/browser/tests/node-subscriber-disposal.spec.ts#L1). No such verification was run for this research.

**Expected benefit:** one fewer aggregate credential acquisition, one fewer authenticated snapshot round trip, and removal of page-owned discovery. This research does not establish a timing improvement or approve the proposed implementation; Red Rope's previous token waits are motivation, not a benchmark for this refactor.
