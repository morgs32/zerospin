# Producer sequences and Archive range routing

Researched 2026-10-26 against primary external sources and current local source at HEAD `bf029423dd`, including the dirty Plan-270 work in progress. Research only: no implementation, tests, fixtures, or storage changes. This extends [Chain storage capacity and segmentation](chain-storage-capacity-and-segmentation.md).

## Answer

The proposed `(producerId, nonce)` identity is a sound basis for **compressing Archive location metadata when a producer's commands enter a particular Chain in sequence order**. Actor Nodes already supply the useful coordinates as `(nodeId, pushIndex)`, scoped to the owning Chain; `nodeId` alone grants no authority. Interleaving many Nodes in the Chain does not invalidate producer ranges. The producer sequence and `aggregateIndex`/`serviceIndex` remain different coordinate systems.

This does not by itself bound all metadata, preserve independent command-ID uniqueness, or supply sequences for every command kind. Out-of-order external completions do not make range representation impossible; they remove the guarantee of one compact, disjoint producer span per Archive. Those are separate conclusions.

The first AggregateVersionChain/ServiceVersionChain archival milestone should continue using its known domain positions without changing command-ID encoding. Producer-span routing is a later admitted Actor history decision.

## Primary prior art: what it establishes

**Kafka:** KIP-98 introduces a producer ID and monotonically increasing sequence per topic partition. A stable transactional identity and producer epoch distinguish producer incarnations and fence previous instances. The original idempotent-producer design has session-scoped guarantees; transactional producer recovery adds a stable application identity. This is direct precedent for producer-scoped sequencing and incarnation control, not proof of a permanent message-location directory. Source: [KIP-98](https://cwiki.apache.org/confluence/spaces/KAFKA/pages/66854913/KIP-98+-+Exactly+Once+Delivery+and+Transactional+Messaging).

Kafka's versioned 4.1 protocol includes producer IDs and epochs; `InitProducerId` checks the epoch and uses producer identity to disambiguate reuse after transactional-ID expiration. Source: [Kafka 4.1 protocol](https://kafka.apache.org/41/design/protocol/). The 4.1 broker reference documents `producer.id.expiration.ms` with a one-day default and possible earlier expiration when retention removes the producer's last write; `transactional.id.expiration.ms` defaults to seven days. These are bounded producer-state lifetimes, not an indefinite retry lookup guarantee. Source: [Kafka 4.1 broker configuration](https://kafka.apache.org/41/configuration/broker-configs/#producer.id.expiration.ms). These versioned references establish the cited behavior; KIP-98 is historical design context rather than a claim that all original configuration details remain current.

**NATS JetStream:** `Nats-Msg-Id` deduplicates within the stream's configured duplicate window, documented as two minutes by default. A repeat inside that window returns the same stream sequence. Source: [JetStream publishing](https://docs.nats.io/learn/jetstream/publishing#avoiding-duplicate-writes). Direct historical reads use stream sequence or subject criteria. Source: [JetStream direct reads](https://docs.nats.io/learn/jetstream/get-direct). This cleanly separates short-lived duplicate detection from later message retrieval; it does not establish an everlasting message-ID locator.

A producer high-water mark can identify an old ordered sequence number, but cannot alone recover its original admitted command, compare changed input, or return its retained `outcome`. Fencing a replaced producer prevents sequence reuse by an obsolete incarnation; it does not locate historical commands. These are deductions from the mechanisms above, not claims that Kafka or NATS implements Zerospin's proposed Archive index.

## Why ranges survive interleaving

Assume one producer incarnation's admitted nonce values are strictly increasing within one owner Chain. Divide that Chain into non-overlapping contiguous Archive ranges by `aggregateIndex` or `serviceIndex`. Project each Archive's commands onto that producer. Every nonce in an earlier nonempty Archive is smaller than every nonce from that producer in a later Archive. Therefore that producer's per-Archive nonce envelopes are ordered and disjoint. Other producers can interleave arbitrarily without changing this proof.

For example, an Archive may contain Node A pushes 1 and 2 mixed with many Node B commands, while the next Archive contains A pushes 3 and 4. A retry of A push 2 selects the earlier Archive using A's span; an exact local lookup there finds the command. The span does **not** mean the Chain positions for A are contiguous, so nonce-to-Chain-position arithmetic is invalid.

If the producer sequence is dense for that destination, its span is exact membership. If producer numbers also cover other destinations, skipped numbers create holes: a min/max span identifies a candidate Archive, not proof the requested command exists. Exact `(producerId, nonce)` lookup inside the Archive must return absence for a hole. Range lookup is a location index, not admission evidence.

The general size bound is the sum of distinct producer incarnations represented in each Archive. One long-lived Node contributing many commands per Archive compresses well. One new producer per command produces one span per command: **worst-case O(commands)**. Even one producer spanning indefinitely many Archives accumulates indefinitely many location spans. Keeping the entire directory in AggregateChain or ServiceChain would move the same finite-storage problem into metadata; its physical placement and bounded partitioning remain design work.

## Current Actor Nodes already provide the ordered case

Every Actor command carries `nodeId`, `sessionName`, and positive `pushIndex`. Node acceptance allocates `pushIndex` transactionally only for a new original command. Backend continuation freezes the Node's owner/release, session, actor, and claims and requires the exact next push index. These facts support the ordered-producer proof for the Node's owner Chain. Sources: [CommandSchema](../../packages/core/src/contracts/CommandSchema.ts), [aggregate Node acceptance](../../packages/core/src/AggregateNode/acceptAggregateOriginalTx.ts), [service Node acceptance](../../packages/core/src/ServiceNode/acceptServiceOriginalTx.ts), [aggregate continuation validation](../../packages/system-worker/src/AggregateChain/admitAggregateCommands/validateAggregateNodeContinuation.ts), [service continuation validation](../../packages/system-worker/src/ServiceChain/admitServiceCommands/validateServiceNodeContinuation.ts).

Ordinary reconnection reuses the Node and its acknowledgement prefix; it does not renumber original commands. Authorized baseline replacement rotates `nodeId`, providing a distinct producer identity for the new sequence. Locally rejected staging does not allocate a Node push position, and exact Node retries return the retained original before allocating another position. Sources: [AggregateNode](../../packages/core/src/AggregateNode/AggregateNode.ts), [ServiceNode](../../packages/core/src/ServiceNode/ServiceNode.ts), [aggregate acceptance](../../packages/core/src/AggregateNode/acceptAggregateOriginalTx.ts), [service acceptance](../../packages/core/src/ServiceNode/acceptServiceOriginalTx.ts).

The relevant retry APIs already receive complete commands. Session outcome APIs forward the Actor envelope; Chain outcome methods currently find by opaque `id` and compare retained input, despite having the Node coordinates available. No scoped public historical ID-only getter was found. Consequently, **an honest full-command retry does not require its command ID to encode the Node coordinates to route an Archive lookup**. Sources: [aggregate outcome API](../../packages/system-worker/src/AggregateSessionApi/awaitCommandOutcome/awaitCommandOutcome.ts), [service outcome API](../../packages/system-worker/src/ServiceSessionApi/awaitCommandOutcome/awaitCommandOutcome.ts), [aggregate outcome lookup](../../packages/system-worker/src/AggregateChain/awaitActorCommandOutcome.ts), [service outcome lookup](../../packages/system-worker/src/ServiceChain/awaitActorCommandOutcome.ts).

## The independent command-ID invariant

Current Chain storage enforces both unique `id` and unique `(nodeId, pushIndex)`. Admission first finds retained input by `id` and compares the complete command. Sources: [AggregateChain schema](../../packages/system-worker/src/AggregateChain/aggregateChainDbConfig.ts), [ServiceChain schema](../../packages/system-worker/src/ServiceChain/serviceChainDbConfig.ts), [aggregate retained lookup](../../packages/system-worker/src/AggregateChain/admitAggregateCommands/readRetainedCommand.ts), [service retained lookup](../../packages/system-worker/src/ServiceChain/admitServiceCommands/readRetainedServiceCommand.ts).

Tuple routing plus complete equality detects a changed payload under the same tuple and a different ID submitted at an occupied tuple. It does not detect this case: `cmd_A` was archived at `node_X/1`, then arrives as `cmd_A` at `node_Y/1`. Looking only for `node_Y/1` misses the original. Current ID-based lookup rejects that conflicting identity.

Preserving that behavior requires an explicit choice: retain a partitioned historical ID lookup, enforce command IDs derived unambiguously from the producer coordinate, or deliberately change the identity contract to use the pair. A structured ID is not required just for full-command routing; it becomes relevant if it replaces the independent ID uniqueness index.

Existing construction allocates the opaque ID before Node acceptance assigns `pushIndex`, and optimistic execution already uses that ID. Deriving it from the Node position therefore changes allocation, staging, wire identity, and recorded child-command provenance. It is not a cosmetic string substitution. Sources: [aggregate session command construction](../../packages/core/src/aggregateSession/stageCommand/makeSessionCommand/makeSessionCommand.ts), [service optimistic evaluation](../../packages/core/src/serviceSession/evaluateServiceSessionCommandTx.ts), [aggregate Node acceptance](../../packages/core/src/AggregateNode/acceptAggregateOriginalTx.ts), [service Node acceptance](../../packages/core/src/ServiceNode/acceptServiceOriginalTx.ts).

## Other command kinds need separate reasoning

**System commands:** recorded delivery already has a source position and `operationIndex`, but the frozen destination command does not retain a universal producer sequence. Source positions can skip for a particular destination. That natural pair may be a useful future coordinate, but adding it requires a separate contract decision. Sources: [command delivery queue](../../packages/system-worker/src/commandOperations/makeCommandDeliveryQueue.ts), [recorded command preparation](../../packages/core/src/contracts/prepareCommandOperation.ts), [CommandSchema](../../packages/core/src/contracts/CommandSchema.ts).

**Agent commands:** Agent name/version identifies the Agent but is not an emission counter. Multiple commands can arise from one observed state; pending delivery drains concurrently. Do not substitute the observed materialization index for a command sequence. Sources: [Agent behavior reconciliation](../../packages/core/src/agentBehavior/reconcileAgentBehaviorsTx.ts), [Agent Node runtime](../../packages/system-worker/src/agentNodeRepo/makeAgentNodeRuntime.ts), [CommandSchema](../../packages/core/src/contracts/CommandSchema.ts).

**External completions:** invocation IDs are allocated before provider work, and completions can arrive out of issuance order. However, current callback handling looks up pending invocation state, atomically admits the observation and deletes pending work; a repeated callback after deletion returns without a historical ID lookup. Do not justify an indefinite completion-ID archive directory with a lookup this path does not require. Sources: [external operation preparation](../../packages/system-worker/src/externalOperations/prepareExternalOperation.ts), [aggregate completion admission](../../packages/system-worker/src/AggregateChain/recordExternalOutcomeAndAdmitCommandTx.ts), [service completion admission](../../packages/system-worker/src/ServiceChain/recordExternalOutcomeAndAdmitCommandTx.ts).

Out-of-order completion does not prohibit ranges. Suppose invocation 11 enters Archive 1 and invocation 10 later enters Archive 2: issuance order no longer matches Archive order. Extend this to Archive 1 containing 11 and 13 while Archive 2 contains 10 and 12. Their min/max envelopes overlap. A query for 11 must search every matching candidate and compare exact identity; one Archive's absence does not establish global absence. Exact disjoint nonce runs avoid false candidates but may fragment to one entry per command. Both representations are correct with their respective search rules; neither guarantees compact single-Archive routing. This is an analytical counterexample, not observed production traffic.

**Evaluated history:** AggregateVersionChain and ServiceVersionChain already receive the known domain position for indexed reads and replay. Continue routing those Archives by `aggregateIndex`/`serviceIndex`; no new producer-ID scheme is needed for that milestone. Their lifetime ID uniqueness remains a separate append invariant, as described in the [earlier investigation](chain-storage-capacity-and-segmentation.md#evaluated-history-archival-design-investigation). Sources: [AggregateVersionChain](../../packages/system-worker/src/AggregateVersionChain/AggregateVersionChain.ts), [ServiceVersionChain](../../packages/system-worker/src/ServiceVersionChain/ServiceVersionChain.ts).

## Recommendation and unresolved choices

Investigate Node producer spans as a concrete optimization for admitted Actor history. Preserve both complete-command equality and existing lifetime command-ID behavior until an identity change is explicitly agreed. Publish complete span metadata before removing local history, retain archive lineage across reconstruction, and distinguish a valid absence from an unavailable or corrupt Archive.

Do not invent a universal producer abstraction for System, Agent, and External commands to make all paths look alike. First settle whether command IDs remain independent identities and where an indefinitely growing producer-span directory lives. Those decisions determine whether Node range routing is a useful compressed secondary index or a broader command identity redesign. They do not block the independent evaluated-history milestone from using its existing domain positions.
