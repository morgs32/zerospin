# QRK production Owner Chain reuse

Reviewed Zerospin 39.0.0 source at `14d1219910` and 43.1.1 at `495a1cd41c`, QRK's retained deployment evidence, and the live administrative inventory from this investigation. No Worker deployment, storage operation, or registry change was performed.

## Authored release and framework upgrade are separate

**An authored V9 → V10 canonical promotion reuses the AggregateChain.** Its Durable Object name is keyed by System ID, Aggregate ID and Aggregate name. V9 and V10 have distinct AggregateVersionRepos and AggregateVersionChains. Actor-facing chains add the Actor release and path. The unversioned Chain retains admitted commands, progress and delivery responsibilities. Original execution still uses the admitted command's exact release. [AggregateChain name](../../packages/system-worker/src/AggregateChain/aggregateChainName.ts#L7-L18), [AggregateVersionRepo name](../../packages/system-worker/src/AggregateVersionRepo/aggregateVersionRepoName.ts), [AggregateVersionChain name](../../packages/system-worker/src/AggregateVersionChain/aggregateVersionChainName.ts#L7-L20), [Actor chain name](../../packages/system-worker/src/AggregateActorVersionChain/aggregateActorVersionChainName.ts#L8-L26), [original delivery](../../packages/system-worker/src/AggregateChain/AggregateChain.ts#L472-L505).

If the AggregateChain has pruned an adopted prefix, it reads that prefix from the persisted old AggregateVersionChain, which can delegate to its Archives. It reads the remaining finalized suffix from its own command table. The replacement release replays this logical history, and the AggregateChain switches to the new history source only after its publication covers the old fixed boundary. The receiving release retains its own outcomes and operations. A canonical change neither redirects existing browser sessions nor retires a release. QRK currently registers V9 and V10, selects canonical V9, and the App selects exact V10. [Logical read](../../packages/system-worker/src/AggregateChain/readReplayPage.ts#L19-L89), [VersionChain archive read](../../packages/system-worker/src/AggregateVersionChain/AggregateVersionChain.ts#L346-L394), [handoff transaction](../../packages/system-worker/src/AggregateChain/adoptCanonicalAggregateHistory.ts#L16-L37), [verified handoff design](../archive/plans/277-plan-canonical-chain-history-handoff.md#logical-history-and-canonical-changes), [QRK registry](../../../qrk.sh/apps/zerospin/src/system.ts#L6-L13), [QRK App session](../../../qrk.sh/apps/app/zerospin/userSessionDefinition.ts#L35-L42).

**Cloudflare can keep the same Worker, domain and namespace IDs when the existing live SQLite class exports remain intact.** Unchanged namespace and object IDs locate the same data. They supply no conversion of Zerospin's SQL tables or encoded rows. A delete tombstone permanently removes the class namespace and its stored data. [Cloudflare Durable Object class exports](https://developers.cloudflare.com/durable-objects/reference/durable-objects-migrations/#define-a-durable-object-class).

## QRK live evidence and framework blockers

Authenticated inspection during this investigation returned Worker version `495cfbd0-1a34-4e14-832d-88ad2630a765`. That matches QRK's recorded 39.0.0 deployment, with implementation provenance pinned to the 39 source revision. The live inventory returned **zero registered child Repos across all 20 child kinds**, **zero SystemRepo `aggregates` rows**, and **one retained `acceptedSystemSpecs` row**. The parsed stored spec was rejected by installed 43.1.1's `SystemSpecSchema`. [Deployment evidence](../../../qrk.sh/wiki/research/evidence/qrk-startup-39/README.md#provenance-and-limits), [live deployment version record](../../../qrk.sh/wiki/research/evidence/qrk-startup-39/deployment.txt), [39 post-upload acceptance](../../../qrk.sh/wiki/research/zerospin-declaration-startup-cost.md#regular-worker-cloudflare-acceptance-confirmed).

The 39 runtime registers each typed child Repo with the executing accepted SystemSpec before provisioning its own SQL and allowing events. AggregateChain activation also records Aggregate membership before admitting commands. The 39 SystemRepo persists child type/name registrations with upserts, and its inspection returns those rows. Its own SystemRepo listing is synthesized from the addressed singleton. Zero registrations and memberships are strong evidence that there is no normally activated QRK Aggregate history under the current catalogue. They do not prove that every Cloudflare namespace is physically empty, because earlier catalogues or orphaned instances could leave storage. An independent authenticated Cloudflare namespace-object listing covered all 21 live namespace IDs. Each of the 20 non-SystemRepo namespaces returned zero objects, with no continuation cursor. SystemRepo alone returned one object, with `hasStoredData: true`. This establishes that no stored child objects were listed at inspection time. Two independent blockers in a 39 → 43.1.1 in-place upgrade:

- **AggregateChain physical SQL, if an old AggregateChain exists.** 39 retains separate `admissionPosition.lastIndex` and `finalizedPosition.lastIndex` singleton tables. 42 replaces them with `commandProgress.admittedThroughIndex` and `finalizedThroughIndex`. 43.1.1 declares no AggregateChain migration and validates the exact table graph on activation. The name and key are unchanged, so a 43.1.1 Worker would open the same incompatible physical database if it exists. The audited source diff has no equivalent physical table change for AggregateVersionChain, AggregateActorVersionChain or Archives. [39 SQL](https://github.com/morgs32/zerospin/blob/14d1219910/packages/system-worker/src/AggregateChain/aggregateChainDbConfig.ts#L7-L26), [current SQL](../../packages/system-worker/src/AggregateChain/aggregateChainDbConfig.ts#L7-L26), [migration configuration](../../packages/system-worker/src/AggregateChain/aggregateChainMigratableDORepoConfig.ts#L11-L15), [exact physical schema validation](../../packages/core/src/drizzle/provisionDb/validateDbSchema.ts#L21-L46), [42 release policy](../../CHANGELOG.md#4200-2026-11-03).
- **SystemRepo accepted catalogue JSON, confirmed live.** 39 embeds model, contract, Actor and Agent definitions inside each release. 40 replaces embedded definitions with exact version references into normalized owner registries. The SQL table name and columns can stay the same while the stored JSON and content hash become incompatible. 43.1.1 decodes retained rows and verifies their hashes before it compares immutable declaration facts and accepts a new spec. Success from its healthcheck alone would not prove this worked. ## Preservation options

**The observed production state supports a catalogue-only path.** With the inspected 20 child namespaces returning no objects, 43.1.1 can provision compatible child instances on demand in the same existing namespaces. Recheck the live inventory immediately before any later cutover. The remaining conversion concerns one legacy accepted SystemSpec row. A preservation path must capture and verify the original bytes/hash, project the original accepted definitions to the normalized format, recompute the normalized content hash, verify that the same immutable versioned facts survive and compare them against the candidate SystemSpec. If the user chooses a new catalogue instead, treat it as a separately scoped metadata replacement with explicit loss of the existing on-platform acceptance record and preserve its provenance elsewhere if required. Replacing only SystemRepo via a class tombstone affects every object under that class and changes its namespace ID. A same-object metadata conversion can keep that ID but has no shipped conversion path today. Simply deleting the accepted row would discard the immutability check. [Acceptance transaction](../../packages/system-worker/src/SystemRepo/acceptSystemSpec/acceptSystemSpecTx.ts#L54-L103), [SystemSpec hashing](../../packages/core/src/system/hashSystemSpec.ts), [Cloudflare deletion](https://developers.cloudflare.com/durable-objects/reference/durable-objects-migrations/#delete-a-durable-object-class).

**If legacy child data exists, preserve the entire connected history graph during conversion.** An approved in-place migration could atomically copy the two verified positions to one `commandProgress` singleton, preserve the adopted-history pointer and local command suffix, and retain producer checkpoints, pending delivery, external work, versioned evaluated history and Archives. A migration must reconcile contiguous indices and declared provenance before reopening admission. Starting AggregateChain again at zero while keeping old version chains would lose the pointer and collide with old checkpoints; old Archives by themselves cannot reconstruct pending originals or establish admission progress. Original/Actor releases still needed by the retained graph must remain executable. Compare catalogue and replay with real legacy state in an isolated rehearsal first. No compatible in-place migration or supported history import is shipped in 43.1.1. [Original progress and canonical handoff](../archive/plans/277-plan-canonical-chain-history-handoff.md#logical-history-and-canonical-changes), [AggregateChain fresh activation](../../packages/system-worker/src/AggregateChain/onDOActivation/onDOActivation.ts#L20-L42), [current empty migration list](../../packages/system-worker/src/AggregateChain/aggregateChainMigratableDORepoConfig.ts#L11-L15), [Cloudflare SQLite transactions and PITR](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/).

The live evidence establishes a concrete catalogue incompatibility, no currently registered QRK command graph and no listed child objects. The same Worker, domain and all 21 namespace IDs can be retained if the SystemRepo catalogue is converted in place. The 43.x browser storage baseline is a separate local-client compatibility boundary and cannot repair server catalogue or Chain storage. [Browser storage policy](../adrs/027-connected-browser-node-storage-upgrades.md).
