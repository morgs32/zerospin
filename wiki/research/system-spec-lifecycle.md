# SystemSpec compilation, system deployments, and accepted versioned specs

**Researched:** 2026-10-25 against Zerospin source HEAD `4c7f0e9d4b` and current sibling Zerospin Cloud source. **Status:** findings and recommendation only. No implementation, dependency installation, tests, storage changes, or plan edits were performed.

## Concise recommendation

Compile one portable `SystemSpec` from the authored System and its factory-owned declaration specs. Use that same schema/compiler for inspection, the system-deployment artifact, candidate attestation, and explicit spec acceptance. Keep the executable System as execution authority; the JSON spec describes it and does not reconstruct programs. Name the persisted immutability facts **accepted versioned specs**. No extra domain term such as “catalogue” is required. The current `acceptedDefinitions` table implements that responsibility; it is not another authored registration map. [Assembler](../../packages/core/src/system/make/makeSystemSpec.ts), [Worker serialization](../../packages/system-worker/src/getSystemSpec/getSystemSpec.ts), [current storage](../../packages/system-worker/src/SystemRepo/systemRepoDbConfig.ts#L8).

A complete SystemSpec snapshot answers **what a particular system-deployment artifact contains**. Accepted versioned specs answer **what an already accepted named version means, permanently**. Those are distinct lifetimes: accepted locks can survive a failed candidate rollout and definitions omitted from a later SystemSpec. Store full spec values if field-level mismatch diagnostics are useful; a hash could detect changes but would not itself explain them. This is a recommendation based on the required behaviors, not an endorsement of the current helper/envelope machinery. [Acceptance transaction](../../packages/system-worker/src/SystemRepo/acceptedDefinitions/acceptDefinitionEntriesTx.ts#L24), [deployment failure retains locks](../../packages/cli/src/deploy/deployWranglerFn.ts#L40), [JSON differences](../../packages/system-worker/src/SystemRepo/assertAcceptedSpec/assertAcceptedSpec.ts#L18).

## Precise terms

1. An **authored Aggregate/Service release version** is a positive integer inside the System registry. It selects an executable composition, not a system-deployment attempt or Cloudflare Worker code version. [SystemSpec registry schema](../../packages/core/src/system/SystemSpecSchema.ts#L8), [release snapshot](../../packages/core/src/declaration/makeReleaseSpecs.ts#L57).
2. A **Cloudflare Worker version** identifies uploaded executable Worker code. The direct CLI records Wrangler's reported `version_id`, may stage it at zero percent, promotes it separately, then asks the actual SystemRepo which Worker version it executes. HTTP routing promotion alone is not SystemRepo attestation. [Stage](../../packages/cli/src/deploy/utils/stageSystemWorkerUpdate.ts#L66), [promote](../../packages/cli/src/deploy/utils/promoteSystemWorkerUpdate.ts#L34), [Repo attestation](../../packages/cli/src/deploy/utils/awaitSystemRepoVersion.ts#L7).
3. A **Cloud system deployment** is a `dpl_` control-plane resource for an attempt to deploy an immutable artifact to one instance. Its artifact contains the script, private configuration/credential references, and whole SystemSpec; its resulting Worker version is a separate fact. The direct Wrangler path uses Cloudflare deployment/version records rather than this Cloud `dpl_` resource. [Cloud attempt/artifact creation](../../../zerospin-cloud/apis/src/CliApi/deploySystemWorker.ts#L81), [artifact schema](../../../zerospin-cloud/apis/src/CloudRepo/DeploymentArtifact.ts#L5), [Cloud provider attestation/completion](../../../zerospin-cloud/apis/src/CliApi/deployArtifact.ts#L110).
4. **Spec acceptance** is an explicit durable comparison/insertion operation. It happens before later promotion/readiness steps in the direct CLI and is not itself the completion of a system deployment. [CLI ordering](../../packages/cli/src/deploy/deployWranglerFn.ts#L40), [SystemApi acceptance](../../packages/system-worker/src/SystemApi/acceptSystemSpec/acceptSystemSpec.ts#L19).

## Current compilation and consumers

1. A contract factory seals its own selected-version JSON facts. Aggregate, Service, and Agent release factories construct and seal their portable release metadata. Current owner metadata still uses the historical contract projector; Plan 266 proposes replacing its payload/failure history maps with own version specs and independent acceptance. [Contract factory](../../packages/core/src/contracts/make/constructContractVersion.ts#L272), [release factories](../../packages/core/src/declaration/makeReleaseSpecs.ts#L56), [Plan 266](../archive/plans/266-plan-independent-contract-version-specs.md).
2. `makeSystemSpec` assembles the factory-owned release snapshots under owner names/versions and adds current Aggregate/Service Agent Node selections. It does not re-create programs from specs. Node selections are mutable current bindings, not another immutable authored release version. Whole-system snapshots therefore need not remain byte-identical when current configuration legitimately changes, while reused versioned declaration facts must remain identical. [Assembler](../../packages/core/src/system/make/makeSystemSpec.ts#L15), [schema and binding validation](../../packages/core/src/system/SystemSpecSchema.ts#L20).
3. Local `zerospin studio` loads authored configuration and calls that assembler. It serializes the resulting snapshot into a server-only virtual module; the RSC passes the data to the shared Declaration Board. No system deployment is involved in local inspection. [Local launcher](../../packages/cli/src/commands/useStudioServer.ts#L45), [serialized server module](../../packages/studio/src/server/makeStudioViteConfig.ts#L23), [RSC](../../packages/studio/src/entry.rsc.tsx#L10).
4. `SystemApi.makeSystemSpec()` and `SystemApi.acceptSystemSpec()` both invoke `getSystemSpec`, which assembles and validates metadata from declarations in the **executing Worker**. Acceptance obtains this snapshot internally, then forwards it to the singleton SystemRepo. Current code reassembles through the same compiler; it does not literally reuse a single previously allocated SystemSpec object across processes. [Worker compiler](../../packages/system-worker/src/getSystemSpec/getSystemSpec.ts#L23), [inspection API](../../packages/system-worker/src/SystemApi/makeSystemSpec/makeSystemSpec.ts#L16), [acceptance API](../../packages/system-worker/src/SystemApi/acceptSystemSpec/acceptSystemSpec.ts#L19).
5. Cloud receives a SystemSpec with the uploaded artifact input and stores the entire immutable artifact in `DEPLOYMENT_ARTIFACTS`. The inspected current standalone CLI is the direct Wrangler path; this research does not establish which external client originally produced the Cloud upload's submitted spec. [Cloud input](../../../zerospin-cloud/apis/src/CliApi/deploySystemWorker.ts#L25), [staging](../../../zerospin-cloud/apis/src/CliApi/deploySystemWorker.ts#L81), [immutable storage](../../../zerospin-cloud/apis/src/CloudRepo/CloudRepo.ts#L154).
6. During Cloud deployment, `deployArtifact` reads the candidate Worker's actual SystemSpec and compares it with the submitted artifact snapshot before acceptance. It then accepts, waits for SystemRepo Worker-version readiness, initializes, and completes the control-plane deployment. Candidate matching and immutable-version acceptance are separate checks. [Cloud ordering](../../../zerospin-cloud/apis/src/CliApi/deployArtifact.ts#L122).
7. Cloud's instance Studio resolves the active instance artifact and passes its SystemSpec to the shared Declaration Board. Historical deployment pages retrieve the chosen deployment's artifact snapshot. Neither is a historical snapshot of current Repo/table data. [Active spec API](../../../zerospin-cloud/apis/src/CloudApi/CloudApi.ts#L109), [historical spec API](../../../zerospin-cloud/apis/src/CloudApi/CloudApi.ts#L136), [Cloud Studio](../../../zerospin-cloud/cloud/app/(authed)/(console)/[organizationId]/system/[systemId]/instances/[instanceId]/studio/page.tsx#L24).

## Where acceptedDefinitions fits

`SystemRepo.acceptSystemSpec` strictly decodes the whole submitted SystemSpec, derives versioned declaration entries, and accepts every entry in one transaction. The table stores only `key` and complete JSON `spec`; it is an index of accepted declaration facts, not a whole-system-deployment record, model state, command history, or executable definition registry. Rows omitted from a later acceptance batch are not deleted. [SystemRepo acceptance](../../packages/system-worker/src/SystemRepo/acceptSystemSpec/acceptSystemSpec.ts#L13), [entry derivation](../../packages/system-worker/src/SystemRepo/acceptedDefinitions/projectAcceptedDefinitionEntries.ts#L6), [storage](../../packages/system-worker/src/SystemRepo/systemRepoDbConfig.ts#L8), [transaction](../../packages/system-worker/src/SystemRepo/acceptedDefinitions/acceptDefinitionEntriesTx.ts#L24).

The table name and a separate `{ identity, spec }` envelope are implementation choices. The required comparison address can be derived from owner family/name plus declaration name/version; the owner release version is excluded for a contract identity shared across owner releases. Do not add full owner identity to a factory-owned, reusable contract spec. [Identity investigation](contract-spec-identity.md), [Plan 266 decisions](../archive/plans/266-plan-independent-contract-version-specs.md#problem-and-agreed-behavior).

The accepted store must be owned by SystemRepo even in direct Wrangler/self-hosted operation, rather than depending on Cloud's deployment-artifact service. Removing accepted rows in favor of “latest SystemSpec” would lose omitted version facts. Replacing them with all past deployment snapshots could preserve the facts only if every accepted candidate snapshot, including a later failed rollout, were permanently retained and versioned facts were independently checked across that history. It would still need lookup/comparison behavior; it does not remove the requirement. This is a clean-slate design inference from the direct CLI and immutable acceptance lifetimes, not a claim that current rows are the only possible implementation. [Direct CLI](../../packages/cli/src/deploy/deployWranglerFn.ts#L40), [permanent acceptance](../../packages/system-worker/src/SystemRepo/acceptedDefinitions/acceptDefinitionEntriesTx.ts#L24).

## Recommended diagram labels

Use `Authored System → compile SystemSpec → {local Declaration Board, system-deployment artifact, SystemRepo acceptance}`. Inside SystemRepo, label durable data `Accepted versioned specs (currently acceptedDefinitions)`, not an unexplained “catalogue.” From this accepted history show scoped Repo checks and historical replay checks. From the authored owner release show exact new-command support. The new independent contract entries proposed by Plan 266 belong to accepted versioned spec history; they are not another top-level registration mechanism or a new system-deployment type.
