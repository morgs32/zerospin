# addToCart product snapshot: backend impact

**Date:** 2026-10-17  
**Status:** Original source research of a proposal; the implementation follow-up below records the subsequent application change.

**Source boundary:** Inspected working-tree source. Observed HEAD was `0f4b726a8268d71481b7311dc3b940a1fc13c447`; concurrent changes mean this is not a clean-commit audit. No runtime checks were run for this research.

## Conclusion

Changing `addToCartV1.payload.product` from a full Product resource envelope to `{ id, name, price }` would change the command's validation and serialized payload. **It need not change the cart writes, authoritative quotation, or payment behavior**, provided the three fields retain their current validation and `addToCartV1.program` remains the same. That program reads only those three Product fields: it finds a cart line by `product.id`, copies `product.name` and `product.price` when creating a line, and updates only quantity when the line already exists. [Current payload and program](../../examples/shopping/src/zerospin/aggregates/user/contracts/addToCartV1.ts#L14-L88).

This is an application command-payload change. It does not require changing SQL query results or making `IInferModelRow` pretend to contain `modelName` and `version`. Model table construction explicitly omits those two columns. [Model table construction](../../packages/core/src/models/make/makeModelVersion.ts#L372-L378).

## What would change

- **The accepted command data becomes smaller.** The current JSON field uses `productV1.resourceSchema`, which describes the complete resource and checks its exact model name and schema version. The proposed field would validate only the Product ID, display name, and display price. Description, timestamps, model name, and model version would no longer be required or validated by this command. Preserve the existing three field codecs; narrowing the payload is not a reason to accept an arbitrary ID or loosen price typing. [Payload declaration](../../examples/shopping/src/zerospin/aggregates/user/contracts/addToCartV1.ts#L14-L18), [Product attributes](../../examples/shopping/src/zerospin/services/marketplace/models/product/ProductV1.ts#L5-L13), [resource schema and identity check](../../packages/core/src/models/make/makeModelVersion.ts#L449-L457), [key and JSON codecs](../../packages/shapes/src/compileDescriptor.ts#L180-L186).
- **Both local staging and backend admission must use the new declaration.** The browser session and backend user actor register the same `addToCartV1`. AggregateChain validates the submitted payload, and contract evaluation validates the decoded payload again. This cannot be implemented as only a React prop-type adjustment. [Browser registration](../../examples/shopping/src/zerospin/shopperSessionRelease.ts#L27-L31), [backend registration](../../examples/shopping/src/zerospin/aggregates/user/actors/userActorV1.ts#L60-L65), [admission validation](../../packages/system-worker/src/AggregateChain/admitAggregateCommands/validateSubmittedPayload.ts#L6-L18), [evaluation validation](../../packages/core/src/contracts/make/constructContractVersion.ts#L651-L666).
- **Retained command payloads become smaller; CartItem columns do not change.** AggregateChain retains the admitted command's payload, and exact retry recovery compares that payload with the retained one. Historical admitted commands would no longer retain the submitted Product description, timestamps, model name, or model version; identical cart behavior does not mean identical retained context. CartItem already stores only its cart/product IDs, copied name/price, and quantity in addition to common row fields. Do not rewrite a retained command into a different payload under the same command ID. [Command retention](../../packages/system-worker/src/AggregateChain/admitAggregateCommands/appendAggregateCommand.ts#L21-L35), [exact retry comparison](../../packages/system-worker/src/AggregateChain/admitAggregateCommands/readRetainedCommand.ts#L17-L32), [CartItem declaration](../../examples/shopping/src/zerospin/aggregates/user/models/cartItem/CartItemV1.ts#L9-L29).

## Backend behavior that can remain identical

1. **The user actor still authorizes the user's Aggregate.** `userActorV1` verifies the Clerk subject and checks its Aggregate identity. Narrowing Product data does not require changing authentication, actor authority, or model ownership. `addToCartV1.models` contains Cart, CartItem, and Purchase; it does not read Marketplace's Product table or perform an external request. [Actor authentication and authorization](../../examples/shopping/src/zerospin/aggregates/user/actors/userActorV1.ts#L35-L61), [addToCart declaration](../../examples/shopping/src/zerospin/aggregates/user/contracts/addToCartV1.ts#L20-L38).
2. **Cart creation, merging, and refusal behavior stay the same.** `addToCartV1.program` refuses changes while the linked Purchase is preparing, pending, or needs reconciliation. It checks positive safe quantities and safe addition. A new line stores the supplied name/price; adding the same Product again changes quantity without refreshing those copied values. The emitted model operations and transaction machinery need no change for this proposal. [Cart decisions and operations](../../examples/shopping/src/zerospin/aggregates/user/contracts/addToCartV1.ts#L39-L88).
3. **Checkout still freezes identity and quantity, not the submitted price.** `checkoutV1` builds `PurchaseSnapshot` from CartItem IDs, Product IDs, and quantities. It creates preparing Purchase/PurchaseItem rows with no authoritative price yet. `checkoutServerV1` records those writes and emits `getExternalPurchaseQuote`. Neither the Product resource envelope nor the cart's copied name/price enters that quotation snapshot. [Snapshot and initial writes](../../examples/shopping/src/zerospin/aggregates/user/contracts/checkoutV1.ts#L81-L120), [snapshot schema](../../examples/shopping/src/zerospin/purchaseQuote.ts#L3-L13), [checkout adapter](../../examples/shopping/src/zerospin/aggregates/user/contracts/checkoutServerV1.ts#L12-L44).
4. **Marketplace still supplies authoritative names and prices.** `getExternalPurchaseQuoteV1.external.request` calls Marketplace's `quotePurchase`. That query reads each current Product by ID, refuses missing Products or unsupported prices/quantities, and computes the total from catalog prices. The continuation correlates the response with the frozen lines, writes authoritative PurchaseItem names/prices and Purchase total, and only then emits `processExternalPayment`. [Quotation request](../../examples/shopping/src/zerospin/aggregates/user/contracts/getExternalPurchaseQuoteV1.ts#L30-L74), [Marketplace pricing](../../examples/shopping/src/zerospin/services/marketplace/marketplaceServiceReleaseV1.ts#L45-L82), [quotation validation and payment emission](../../examples/shopping/src/zerospin/aggregates/user/contracts/getExternalPurchaseQuoteV1.ts#L95-L164).
5. **Payment still uses the quoted Purchase total.** The external request passes its retained payment payload to `ShoppingProviders.pay`. The continuation requires the matching pending Purchase, amount, payment key, and frozen Cart/PurchaseItem correspondence. An uncertain request records `needs_reconciliation`; CartItems are deleted only for a paid response. Narrowing `addToCart` does not change these inputs or branches. [Payment request and continuation](../../examples/shopping/src/zerospin/aggregates/user/contracts/processExternalPaymentV1.ts#L15-L105).

## Trust and observable consequences

The current full resource envelope is **not catalog evidence**. Its `modelName` and `version` must identify the expected Model declaration, but `addToCartV1.program` does not look up the supplied Product ID, verify its name/price against Marketplace, or compare Product timestamps. A caller can already fabricate a schema-valid full envelope. Removing the unused envelope fields removes structural requirements; it does not remove a catalog-authenticity or stale-price check that currently exists. [Resource identity filter](../../packages/core/src/models/make/makeModelVersion.ts#L449-L457), [complete addToCart program](../../examples/shopping/src/zerospin/aggregates/user/contracts/addToCartV1.ts#L33-L88).

For example, if a caller supplies display price `1` for a Product whose current Marketplace price is `10`, CartItem and the cart subtotal can show `1`. With either payload shape, checkout obtains `10` from Marketplace and emits payment using that authoritative quote. A fabricated but correctly formatted Product ID can enter the cart today; Marketplace refuses its quotation if the Product does not exist. These are deductions from the current source, not newly executed scenarios. [Copied cart price](../../examples/shopping/src/zerospin/aggregates/user/contracts/addToCartV1.ts#L77-L85), [display subtotal](../../examples/shopping/src/components/ShoppingCartSidebar.tsx#L62-L73), [catalog lookup and quotation](../../examples/shopping/src/zerospin/services/marketplace/marketplaceServiceReleaseV1.ts#L45-L82), [payment emission](../../examples/shopping/src/zerospin/aggregates/user/contracts/getExternalPurchaseQuoteV1.ts#L148-L164).

The proposal therefore preserves advisory cart-display pricing. If the requirement is to verify Product existence or price when adding to the cart, that is additional backend behavior requiring an authoritative Marketplace read; a three-field payload alone provides no such guarantee. The existing shared ordinary declaration currently provides immediate local cart operations and is also registered on the backend user actor. [Current declaration and program](../../examples/shopping/src/zerospin/aggregates/user/contracts/addToCartV1.ts#L10-L88), [shared registrations](../../examples/shopping/src/zerospin/aggregates/user/actors/userActorV1.ts#L60-L65).

## Implementation and cutover implications

The change should use an explicit three-field payload schema. **Correction to the original research:** ProductCard does not need to manually trim its queried Product row. Both command validation and staging prepare the invocation through `validateCurrentPayload`, which first encodes each JSON field using its declared schema. That encoding selects the declared Product fields before strict payload validation; later strict encoding and backend decoding receive the normalized snapshot. ProductCard can pass its queried row directly while keeping description and other fields for display. This corrects the earlier claim that strict excess-property handling required callers to trim the object themselves. [JSON normalization before strict validation](../../packages/core/src/contracts/validatePayload.ts#L95-L138), [invocation preparation](../../packages/core/src/contracts/prepare/prepareAggregateInvocation.ts#L51-L52), [ProductCard invocations](../../examples/shopping/src/components/ProductCard.tsx#L26-L94), [strict encoding](../../packages/core/src/contracts/encodePayload.ts#L57-L64), [strict decoding](../../packages/core/src/contracts/decodeAndAdaptPayload/decodeAndAdaptPayload.ts#L105-L116).

This is not a transparent deployment under an already accepted definition. Contract specs include `payloadShape`; SystemRepo compares retained and incoming definitions and rejects differences. Any implementation must coordinate the application declarations and affected retained/pending command and accepted-definition state under the repository's pre-release hard-cut policy. CartItem's physical model schema need not change. This research performs no reset, migration, compatibility adaptation, or deployment. [Contract spec](../../packages/core/src/contracts/make/constructContractVersion.ts#L335-L345), [accepted-definition comparison](../../packages/system-worker/src/SystemRepo/acceptedDefinitions/acceptDefinitionEntriesTx.ts#L33-L40), [mismatch rejection](../../packages/system-worker/src/SystemRepo/assertAcceptedSpec/assertAcceptedSpec.ts#L33-L39), [repository cutover policy](../../AGENTS.md#L3-L7), [CartItem schema](../../examples/shopping/src/zerospin/aggregates/user/models/cartItem/CartItemV1.ts#L9-L29).

## Research limits

The original research's business-behavior equivalence was conditional on preserving the existing `id`, `name`, and `price` field validation and all current programs. At that stage no proposed schema was installed, no application/framework files were edited, and no tests, browser journeys, storage changes, or runtime checks were performed. This note was the only artifact authored during that research; its original conclusion was a source-grounded proposal rather than a claim of verified implementation.

## Implementation follow-up

The approved application change is implemented: `addToCartV1.payload.product` uses a three-field `Schema.Struct` with the existing Product `id`, `name`, and `price` codecs, and ProductCard destructures its queried row without reconstructing `modelName` or `version`. Source comparison confirms `addToCartV1.program` is unchanged; Marketplace quotation and payment programs were not modified. The narrower retained admitted command payload changes the accepted definition and requires fresh affected command, client, and accepted-definition state under the pre-release hard cutover; no migration, reset, or deployment was performed.

Scoped verification completed on 2026-10-17: Shopping's existing Nx typecheck and lint passed, with three pre-existing lint warnings; touched-file formatting and whitespace checks passed. Direct payload probes confirmed reuse of all three original field codecs, normalization and encoding/backend-decoding round trip of a queried Product row with exactly `id`, `name`, and `price`, and rejection of a malformed Product ID. No test files, fixtures, runners, configuration, or browser checks were added.
