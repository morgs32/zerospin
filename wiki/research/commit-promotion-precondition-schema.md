# Commit promotion precondition and Effect Schema

**Date:** 2026-10-21

**Scope:** Whether the skip precondition in `commitExternalPromotionV1.program` and `commitExternalPromotionV1_1.program` should be an Effect schema check. It runs after `sdk.findFirst` has loaded `purchase` and `cart`. A mismatch returns `null` from a successful program. The later boolean that refuses the purchase is in scope only where it shows what a narrower type would change. No runtime source change is made by this research.

**2026-10-21 refactor note:** This research records the earlier response-progress
schema. [ADR 018](../adrs/018-shopping-promotion-ownership-and-observation.md) now
uses `Purchase.promotionCommitRequested` in the commitment guard and command
operations for reserve, release and redeem. The historical analysis below is
preserved; Shopping source citations are pinned to that earlier schema revision.
The clean-state integer V1 reset now retains only
[`commitExternalPromotionV1`](../../examples/shopping/src/zerospin/aggregates/user/contracts/commitExternalPromotionV1.ts); no second release or continuation remains registered.

## Recommendation

Keep the boolean in the inspected `commitExternalPromotionV1.program` and `commitExternalPromotionV1_1.program` versions. Their original source citations are preserved below.

Replacing it with `Schema.decodeUnknownEffect` changes the command outcome. A schema mismatch fails that effect with `SchemaError`. [`evaluateContract`](../../packages/core/src/contracts/evaluateContract.ts#L68) runs the program through [`runAuthoredCallback`](../../packages/core/src/execution/runAuthoredCallback.ts#L85), which maps a non-business failure to the Zerospin error `contract-program-failed`. The current mismatch returns `null` while the result schema is `Schema.Null`, and the purchase stays as loaded. The refuse update, `paymentState: 'refused'` plus a pending release, runs only after this precondition has passed.

`Schema.is` can stay inside the same `return null` branch, and it still answers a different question. It reports whether one value matches one schema's decoded type. This precondition is one conjunction: bound `aggregateId` against `payload.aggregateId`, purchase presence, `cartId` and `reservationId` equality, and the literals `paymentState === 'preparing'`, `promotionRequest.action === 'commit'`, and `promotionRequest.requestState === 'pending'`. A schema that covers only the literals would let a purchase for another cart or reservation reach the refuse update.

Moving the column predicates that `findFirst` can express into `where` splits that conjunction. `aggregateId` is the program argument. `promotionRequest.action` and `promotionRequest.requestState` sit inside a JSON column, and the contract read filter type has no path operator for them. A `where` that drops either check loads a purchase the current precondition skips, and that purchase can enter the refuse update.

## API findings from primary sources

| Operation                            | Established behavior                                                                                                           | What it decides here                                                                    |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| `Schema.is(schema)`                  | Type guard for the schema's decoded type. Schema mismatches become `false`. A cause that is not entirely schema issues throws. | A boolean shape test of one already decoded value.                                      |
| `Schema.decodeUnknownEffect(schema)` | Effectful decode from `unknown` through the codec, including its encoding, failing with `SchemaError`.                         | A failing effect inside the program becomes `contract-program-failed`.                  |
| `Schema.Literal` / `Schema.Literals` | One literal, or a union of literals. Decode and the type are that literal.                                                     | The right tool when the value under test is a literal field.                            |
| `Schema.check`                       | Adds a runtime filter and leaves the TypeScript type unchanged.                                                                | A constraint on a schema, with the same type the caller already has.                    |
| `Schema.refine`                      | Narrows `Type` through a type-guard filter.                                                                                    | A schema-level narrowing helper. The installed package has no exported `Schema.filter`. |

`Schema.is` is documented as checking the decoded side, returning `false` for schema issues, and throwing when the cause contains defects, interruptions, or asynchronous work. The implementation builds that guard from `SchemaAST.toType`. The public signature is `<I>(input: I) => input is I & S["Type"]`. Sources: installed [SchemaParser.is](../../packages/core/node_modules/effect/src/SchemaParser.ts#L143), [\_is](../../packages/core/node_modules/effect/src/SchemaParser.ts#L185), [Schema.is](../../packages/core/node_modules/effect/src/Schema.ts#L1437), and [getSchemaIssueOrThrow](../../packages/core/node_modules/effect/src/internal/schema/cause.ts#L17). The official v4 introduction agrees that `is` checks the output type `Type`, in the diagram under [Understanding Decoding and Encoding](https://effect.website/docs/v4/schema/introduction#understanding-decoding-and-encoding).

`Schema.decodeUnknownEffect` parses `unknown` with the schema AST, so encoding transformations run, and the effect fails with `SchemaError`. `SchemaParser.decodeUnknownEffect` is the adapter that fails with `SchemaIssue.Issue` directly. Sources: [Schema.decodeUnknownEffect](../../packages/core/node_modules/effect/src/Schema.ts#L1511) and [SchemaParser.decodeUnknownEffect](../../packages/core/node_modules/effect/src/SchemaParser.ts#L270). `Schema.toType` sets `Encoded` equal to the decoded `Type` and drops the encoding path. [Schema.toType](../../packages/core/node_modules/effect/src/Schema.ts#L2566) calls [SchemaAST.toType](../../packages/core/node_modules/effect/src/SchemaAST.ts#L4704). The installed `NumberFromString` example on that AST function shows the type AST tag `"Number"`.

An in-memory probe of this install agreed. `Schema.is(Schema.FiniteFromString)(42)` was `true` and `Schema.is(Schema.FiniteFromString)("42")` was `false`. `Schema.is(Schema.Literal("preparing"))("preparing")` was `true` and the same guard rejected `"pending"`. `Schema.is` on the promotion-request struct accepted the decoded object, including an extra enumerable field, and rejected the JSON string `{"action":"commit","requestState":"pending"}`. Extra fields stay accepted because the default `onExcessProperty` is `"ignore"`. [ParseOptions](../../packages/core/node_modules/effect/src/SchemaAST.ts#L490) and [defaultParseOptions](../../packages/core/node_modules/effect/src/SchemaAST.ts#L602).

`Schema.Literal` stores one literal and types it as that literal. `Schema.Literals` builds a union of those literals. [Literal](../../packages/core/node_modules/effect/src/Schema.ts#L2700), [Literals](../../packages/core/node_modules/effect/src/Schema.ts#L5001). `Schema.check` attaches filters without changing the TypeScript type. [check](../../packages/core/node_modules/effect/src/Schema.ts#L5145). `Schema.refine` narrows `Type` with a type guard. [refine](../../packages/core/node_modules/effect/src/Schema.ts#L5197). The `Filter` annotation text still says the node is created via `Schema.filter`. [Filter](../../packages/core/node_modules/effect/src/Schema.ts#L17251). This install's `Schema.ts` does not export a `filter` function; `src/index.ts` does not re-export one either.

[`validate-at-boundary.ts`](../patterns/apis/validate-at-boundary.ts#L4) is repository guidance: validate unknown inputs at trust boundaries. It is an Effect usage rule for this repo, separate from Effect's API.

The earlier note [command-origin-schema-guards.md](command-origin-schema-guards.md) describes `Schema.is` the same way: decoded-side validation, `false` on schema mismatch, throw when the cause is not entirely schema issues. That description matches the installed parser and the `FiniteFromString` probe above. Its recommendation is about exhaustive origin-kind dispatch. This precondition is a skip conjunction on a loaded purchase, so that dispatch recommendation stays with the origin note.

## What this guard is doing

Both programs load the purchase by `payload.purchaseId` and the cart by `payload.cartId`, then return `null` when any arm of the conjunction is true. [v1 load and precondition](https://github.com/morgs32/zerospin/blob/2063b745eb3b9d7f90f82546dc44704e589d8d25/examples/shopping/src/zerospin/aggregates/user/contracts/commitExternalPromotionV1.ts#L43), [v1.1 precondition](https://github.com/morgs32/zerospin/blob/2063b745eb3b9d7f90f82546dc44704e589d8d25/examples/shopping/src/zerospin/aggregates/user/contracts/commitExternalPromotionV1.ts#L43). The arms are separate jobs.

**Scope equality.** `aggregateId !== payload.aggregateId` compares the bound aggregate argument with the payload field. [`prepareAggregateExternalInvocation`](../../packages/core/src/contracts/prepare/prepareAggregateExternalInvocation.ts#L36) requires a nonempty string `command.aggregateId`, then [`decodeExternalCommandInput`](../../packages/core/src/contracts/decodeExternalCommandInput.ts#L23) decodes the frozen payload before the invocation is returned. The program payload type is [`IInferCommandPayload`](../../packages/core/src/models/types.ts#L107). `payload.aggregateId` is `sdk.primitives.text()`, so both sides are `string`. `Schema.Literal(payload.aggregateId)` types as `string` as well, and `Schema.is` intersects the input with that same `string`. The comparison remains an equality of two decoded strings.

**Row absence.** [`findFirst`](../../packages/core/src/contracts/findFirst.ts#L26) returns `IContractReadResult | undefined`. [`IContractReadResult`](../../packages/core/src/contracts/make/makeContractReadDb.ts#L134) is Drizzle's `BuildQueryResult` for the contract's models. The relational config defaults the decoded column view to on. [`IDrizzleRelationsFromModels`](../../packages/core/src/drizzle/types.ts#L123). `!purchase` narrows the continuation to that row. `Schema.is` of a schema whose `Type` excludes `undefined` also removes `undefined` on the success path, through `I & S["Type"]`, and the same `false` covers every other schema mismatch. Presence is the question `!purchase` answers.

The row `findFirst` returns is the decoded query row. [`makeDbConfig`](../../packages/core/src/drizzle/make/makeDbConfig/makeDbConfig.ts#L14) renders `querySchema` with decoded JSON. For a JSON column that schema assigns `mapFromDriverValue` to `Schema.decodeUnknownSync` and `mapToDriverValue` to `Schema.encodeSync`. [primitiveMaps.ts](../../packages/shapes/src/primitiveMaps.ts#L280). [`makeContractReadDb`](../../packages/core/src/contracts/make/makeContractReadDb.ts#L279) calls `query.findFirst(...).sync()` on that query API. [`AggregateVersionRepo.evaluateAggregateCommand`](../../packages/system-worker/src/AggregateVersionRepo/utils/evaluateAggregateCommand.ts#L37) passes that database into the contract read adapter. `purchase.promotionRequest` is therefore the decoded struct or `null`, which is the `Type` of the authored codec. [JSON scalar type](../../packages/shapes/src/types.ts#L119), [nullability](../../packages/shapes/src/types.ts#L98).

[`readContractRow`](../../packages/core/src/contracts/readContractRow.ts#L15) is a different read. It decodes one subject row with `Schema.decodeUnknownEffect(Schema.toType(...))` and fails as `contract-row-invalid`. These two programs call `sdk.findFirst` for `purchase` and `cart`.

**Instance equality.** `purchase.cartId` and `purchase.reservationId` are model ids. On the purchase, `reservationId` is nullable; on the commit payload it is required. [PurchaseV1](https://github.com/morgs32/zerospin/blob/2063b745eb3b9d7f90f82546dc44704e589d8d25/examples/shopping/src/zerospin/aggregates/user/models/purchase/PurchaseV1.ts#L11), [commit payload](https://github.com/morgs32/zerospin/blob/2063b745eb3b9d7f90f82546dc44704e589d8d25/examples/shopping/src/zerospin/aggregates/user/contracts/commitExternalPromotionV1.ts#L18). A TypeScript 6.0.3 probe used those unions and the same `!==` chain. On the success path, `purchase.reservationId !== payload.reservationId` narrowed `` `rsv_${string}` | null `` to `` `rsv_${string}` ``. `cartId` was already the same template-string type on both sides. `Schema.Literal(payload.cartId)` carries that same wide id type, so `Schema.is` intersects the field with the type it already has. The probe was a stand-in program, and this research did not typecheck `examples/shopping`.

**Literal state.** `paymentState` is the enum `preparing | pending | paid | declined | refused | needs_reconciliation`. `promotionRequest` is a nullable struct whose `action` is `commit | release | redeem` and whose `requestState` is `pending | succeeded | failed`. [PurchaseV1 attributes](https://github.com/morgs32/zerospin/blob/2063b745eb3b9d7f90f82546dc44704e589d8d25/examples/shopping/src/zerospin/aggregates/user/models/purchase/PurchaseV1.ts#L15). The enum compiler builds `Schema.Literals`, and the JSON column compiler builds `Schema.fromJsonString` of the authored struct. [compileDescriptor](../../packages/shapes/src/compileDescriptor.ts#L167).

In the same TypeScript 6.0.3 probe, `paymentState !== 'preparing'` narrowed the success path to `'preparing'`. `Schema.is(Schema.Literal('preparing'))` does that for the field, as the runtime probe showed. `purchase.promotionRequest?.action !== 'commit'` left `promotionRequest` nullable: the probe reported `Object is possibly 'null'` for `.action` and `.requestState` after the full boolean. `Schema.is` of a struct typed as `{ action: 'commit'; requestState: 'pending' }` narrows those two literals and excludes `null`.

After the precondition, both programs read `purchase.id`, `purchase.subtotal`, and `purchase.reservationId`. They assign a new `promotionRequest` in the refuse update and again in the success update. [v1 refuse and success](https://github.com/morgs32/zerospin/blob/2063b745eb3b9d7f90f82546dc44704e589d8d25/examples/shopping/src/zerospin/aggregates/user/contracts/commitExternalPromotionV1.ts#L72). They do not read `promotionRequest` again, so the struct narrowing has nothing further to unlock. The later boolean still depends on `purchase` being defined, which `!purchase` already provides.

**`where` on `findFirst`.** Column filters are Drizzle's `RelationsFieldFilter`: `eq`, `ne`, range operators, `in` / `notIn`, `like`, `isNull` / `isNotNull`, and their boolean combinations. [RelationFieldsFilterInternals](../../packages/core/node_modules/drizzle-orm/relations.d.ts#L271). For an object column, the shorthand form of the filter is `never` (`T extends object ? never`), so a nested `{ action: { eq: 'commit' } }` is outside that type. [RelationsFieldFilter](../../packages/core/node_modules/drizzle-orm/relations.d.ts#L293). The compiler sends any other key to `operators[key]`. [relationsFieldFilterToSQL](../../packages/core/node_modules/drizzle-orm/relations.js#L550). The operator map contains `eq` and `isNull`. It has no `action` key. [operators](../../packages/core/node_modules/drizzle-orm/relations.js#L177). The contract read scope check accepts any value on a known column and leaves that operator question to Drizzle. [makeContractReadDb](../../packages/core/src/contracts/make/makeContractReadDb.ts#L239).

So `where` can express `cartId`, `reservationId`, and `paymentState` with `eq`, and it can express `promotionRequest` with `eq` of the whole decoded object or with `isNull`. It cannot express `promotionRequest.action` or `promotionRequest.requestState` as their own predicates. Whole-object `eq` binds the parameter through `mapToDriverValue`. [sql.js parameter mapping](../../packages/core/node_modules/drizzle-orm/sql/sql.js#L159). That function is `Schema.encodeSync` of `Schema.fromJsonString`, whose encoding step is `JSON.stringify` of the encoded value. [fromJsonString](../../packages/core/node_modules/effect/src/Schema.ts#L9762). The probe encoded the pending commit request as `{"action":"commit","requestState":"pending"}`. The boolean compares decoded fields after the row mapper has decoded the stored text. This research did not execute that `where` against SQLite.

Shopping contract programs that branch on purchase state use boolean comparisons. [`releaseExternalPromotionV1`](https://github.com/morgs32/zerospin/blob/2063b745eb3b9d7f90f82546dc44704e589d8d25/examples/shopping/src/zerospin/aggregates/user/contracts/releaseExternalPromotionV1.ts#L54) checks payment state and the release request. [`redeemExternalPromotionV1`](https://github.com/morgs32/zerospin/blob/2063b745eb3b9d7f90f82546dc44704e589d8d25/examples/shopping/src/zerospin/aggregates/user/contracts/redeemExternalPromotionV1.ts#L41) uses the same shape as commit, with `'paid'` and `'redeem'`. [`getExternalPurchaseQuoteV1`](https://github.com/morgs32/zerospin/blob/2063b745eb3b9d7f90f82546dc44704e589d8d25/examples/shopping/src/zerospin/aggregates/user/contracts/getExternalPurchaseQuoteV1.ts#L97) combines `paymentState !== 'preparing'` with cart and line equality. [`applyPromotionV1`](https://github.com/morgs32/zerospin/blob/2063b745eb3b9d7f90f82546dc44704e589d8d25/examples/shopping/src/zerospin/aggregates/user/contracts/applyPromotionV1.ts#L57) does put `reservationId: { eq }` in `findMany` `where`, then uses `purchase.promotionRequest !== null` on the loaded rows. The `Schema.is` calls under `examples/shopping` distinguish operation schemas in adapter programs, [`checkoutServerV1`](https://github.com/morgs32/zerospin/blob/2063b745eb3b9d7f90f82546dc44704e589d8d25/examples/shopping/src/zerospin/aggregates/user/contracts/checkoutServerV1.ts#L24) and [`removePromotionServerV1`](https://github.com/morgs32/zerospin/blob/2063b745eb3b9d7f90f82546dc44704e589d8d25/examples/shopping/src/zerospin/aggregates/user/contracts/removePromotionServerV1.ts#L21). A search of `examples/shopping` found no `Schema.is` of a loaded model row used as a state precondition.
