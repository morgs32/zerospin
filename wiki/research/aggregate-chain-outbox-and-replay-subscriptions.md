# AggregateChain command outbox and release replay

**Date:** 2026-10-15  
**Status:** Historical exploratory research; the selected original-finalization protocol is now implemented and verified in Plan 193.

**Evidence:** Pre-Plan-193 working-tree snapshot, including uncommitted Plans 189/190 work. This note does not update Plan 151 or its recorded finding.

**Implemented follow-up:** [Plan 193 — synchronous original finalization](../archive/plans/193-plan-synchronous-original-finalization.md) and [ADR 014](../adrs/014-synchronous-original-finalization.md) replace the separate dispatch flag/outcome outbox with the returned exact original outcome. Duplicate recovery uses pending publication or permanent AVC history without reevaluation. Scoped type/lint, Workerd typecheck/runtime and all ten verify-plan140 groups passed. The exploratory alternatives and source references below describe the preceding snapshot; they do not govern the implemented protocol.

## What already exists

`AggregateChain.commands` already supplies `finalizeCommandOutbox`. That queue sends one admitted command at a time to the `AggregateVersionRepo` selected by the command's retained `aggregateVersion`. `finalizeCommandSubscriber` is the named RPC capability receiving that delivery. `makeOutboxSubscriber` supplies `receive(rows)` and RPC outcome encoding; acquiring that capability does not enroll an aggregate release in a durable subscription. [Original outbox and routing](../../packages/system-worker/src/AggregateChain/AggregateChain.ts#L131-L206), [outbox capability implementation](../../packages/system-worker/src/makeOutboxSubscriber/makeOutboxSubscriber.ts#L43-L90).

There are three distinct delivery responsibilities:

| Direction                                        | Durable source and purpose                                                                                                     | When progress is recorded                                                                                                      |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| AggregateChain → designated AggregateVersionRepo | `finalizeCommandOutbox`, reading retained `commands`; execute the command originally on its selected release.                  | The returned command ID/position receipt sets `commands.originalDispatchAcknowledged`.                                         |
| Designated AggregateVersionRepo → AggregateChain | `finalizedOutcomeOutbox`; deliver the original `commandOutcome` after execution commits.                                       | AggregateChain authenticates and retains the complete outcome before AggregateVersionRepo deletes its pending outcome message. |
| AggregateChain → aggregate releases              | `replayCommandsFanout`, reading the contiguous finalized input history; materialize each release using that release's program. | `replaySubscribers.acknowledgedAggregateIndex` advances independently for each release.                                        |

[Original execution receipt](../../packages/system-worker/src/AggregateVersionRepo/finalizeCommand/finalizeCommandRows.ts#L15-L26), historical `acknowledgeOriginalDispatch.ts` transaction, [outcome outbox delivery](../../packages/system-worker/src/AggregateVersionRepo/AggregateVersionRepo.ts#L246-L279), historical `receiveFinalizedOutcomes.ts` source proof and retained retry, [replay fanout and per-release cursors](../../packages/system-worker/src/AggregateChain/AggregateChain.ts#L75-L121), [release-local replay](../../packages/system-worker/src/AggregateVersionRepo/replayCommands/replayCommand.ts#L24-L43).

The durable replay relationship is the other way around from “AggregateChain subscribes to AVRs”: AggregateVersionRepo catches up from AggregateChain and enrolls its committed position in AggregateChain's replay fanout. AggregateChain activation also seeds the authored release cursors. [Catch-up then enrollment](../../packages/system-worker/src/makeFanoutSubscriber/subscribe.ts#L34-L57), [bound replay source](../../packages/system-worker/src/AggregateVersionRepo/replayCommandsFanoutSubscriber/replayCommandsFanoutSubscriber.ts#L50-L67), [activation enrollment](../../packages/system-worker/src/AggregateChain/onDOActivation/onDOActivation.ts#L18-L31).

## Would a pending-only commands table be simpler?

It would simplify one deletion rule: delete the command after its designated AggregateVersionRepo commits execution. It would also remove authoritative input needed by other releases, future releases and exact admission retries. The current replay reader reads retained `commands`, and admission checks retained command IDs before allocating another position. Original execution of command N first catches up the selected release through N−1. A replacement must preserve those responsibilities somewhere. [Finalized history reads](../../packages/system-worker/src/AggregateChain/readReplayPage.ts), [retained admission retries](../../packages/system-worker/src/AggregateChain/admitAggregateCommands/admitAggregateCommandsTx.ts#L30-L52), [original predecessor catch-up](../../packages/system-worker/src/AggregateVersionRepo/finalizeCommand/finalizeCommand.ts#L39-L46).

That is the distinction between pending delivery and retained history. AWS's transactional-outbox example deletes pending rows after successful publication and requires duplicate-safe processing. Microsoft's event-sourcing guidance retains an append-only record for reconstruction. These sources explain the different responsibilities; they do not establish that Zerospin's admitted-command replay is identical to event replay. [AWS transactional outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html), [Microsoft retained reconstruction history](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing).

**Design inference:** adding a separate deletable command outbox while keeping admitted input history could make lifetimes more explicit, but it adds another table and atomic transfer without yet removing the original-outcome return path or per-release replay progress. Replacing release cursors with one deletable broadcast row still needs acknowledgement from every covered release and retained history for later enrollment. Changing the table's label does not remove those requirements. [Current retained history and independent delivery ownership](../adrs/013-aggregate-delivery-history-and-projection-ownership.md), [current table and cursor shapes](../../packages/system-worker/src/AggregateChain/aggregateChainDbConfig.ts#L9-L45).

## Two actual simplification directions

**Original command delivery could remain pending until AggregateChain stores its original `commandOutcome`.** Under that proposed protocol, a separate persisted dispatch receipt might be unnecessary: an interrupted delivery would retry the same command, and committed execution would recover its existing result. Current code already has an already-executed checkpoint branch and result recovery from pending publication or AggregateVersionChain history. However, those paths alone do not prove the redesign complete: lost replies, duplicate recovery and queue recovery must work without the flag, and the queue must stop once the Chain retains the outcome. Preserve AggregateVersionRepo's complete pending outcome message until AggregateChain acknowledges it; do not replace durable outcome delivery with an unprotected RPC return. [Duplicate execution branch](../../packages/system-worker/src/AggregateVersionRepo/utils/readAggregateCommandTx.ts#L40-L45), [committed result recovery](../../packages/system-worker/src/AggregateVersionRepo/finalizeCommand/finalizeCommand.ts#L66-L75), [pending/publication history reads](../../packages/system-worker/src/AggregateVersionRepo/readEvaluatedCommand/readEvaluatedCommand.ts#L30-L57), historical `retainAggregateResultTx.ts` original-outcome insertion.

This is a larger protocol alternative to Plan 151's proposed normalization, which keeps both fields and sets the dispatch flag when a proven outcome arrives. Plan 190 explicitly chose separate retained dispatch/outcome facts; exploratory discussion may reconsider that choice, but it has not been changed or approved here. [Current superseding finding](../reviews/storage-tables/aggregate-chain-commands.md#current-finding--2026-10-15), [Plan 190 dispatch contract](../archive/plans/190-plan-aggregate-delivery-history-and-projection-ownership.md#aggregatechain-dispatch-versus-outcome-completion).

**Live replay into every aggregate release could be replaced by catch-up when an AggregateVersionRepo is used.** That could remove proactive replay subscriptions if the product accepts inactive releases remaining behind. Every operation requiring current release resources would need a defined catch-up checkpoint; active projections and client updates would also need a delivery mechanism. Original execution already demonstrates bounded catch-up before local execution, but that is not proof that all read/projection freshness requirements are covered. The existing activation research instead records catch-up followed by continued delivery, so a fully demand-driven design changes that agreed behavior. [Bounded original catch-up](../../packages/system-worker/src/AggregateVersionRepo/finalizeCommand/finalizeCommand.ts#L39-L46), [current replay fanout](../../packages/system-worker/src/AggregateChain/AggregateChain.ts#L75-L121), [existing activation direction](activation-catchup-and-subscription.md#agreed-behavior).

The focused follow-up is which responsibility the proposed outbox should replace: the original dispatch/outcome handshake, or live replay into other aggregate releases. They have different deletion and freshness requirements.
