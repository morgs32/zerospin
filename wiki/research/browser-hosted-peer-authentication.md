# Browser-hosted data and peer authentication

Date: 2026-11-14. Research only: this explores the browser and protocol capabilities, not a settled Zerospin design or an implementation.

## Finding

A browser tab can hold data locally, decide which other browser can access it, and execute requests for that browser. The hosted data stays on the owner's device unless the owner tab sends some of it elsewhere. The owner tab and visiting browser both need a way to find each other and communicate; a relay can provide that service without being the authority that decides access. A tab is an intermittently available host, however, not an always-running server. [Browser storage](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria), [WebSocket standard](https://websockets.spec.whatwg.org/), [page lifecycle](https://developer.chrome.com/docs/web-platform/page-lifecycle-api)

There are three separate questions: **how do the browsers find each other; how do they know which browser is on the other end; and what can the visiting browser do?** Encryption is essential but does not answer those questions by itself. A share link can introduce the browsers and convey an invitation; the owner tab can keep the resulting access grants and decide each request locally.

## A concrete picture

1. The owner opens a host tab. Its data and access rules are in that browser's storage. The tab connects outward to a relay and advertises a temporary address or room.
2. The owner creates an invitation and shares a link or QR code with a visitor. A separate trusted channel, such as an in-person scan, can help establish who received it.
3. The visitor opens the link. Both browsers connect outward to the relay. They establish an authenticated encrypted session and the owner tab decides whether to grant access. The link or the subsequent approval can identify a particular invited device, or the link itself can be a bearer capability.
4. The visiting browser sends requests inside that session. The owner tab checks its current access rules, reads or changes its own data, and returns the permitted result. The visitor renders a UI from the returned data.
5. If the owner tab closes, sleeps, loses network access, or the relay is unavailable, the visitor may no longer be able to use the data. A visitor cannot assume a request failed simply because the connection dropped before its response arrived; reconnection needs a deliberate retry and duplicate-handling design. [HTTP retry semantics as an analogous treatment of uncertain completion](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2), [page lifecycle](https://developer.chrome.com/docs/web-platform/page-lifecycle-api)

This is an illustrative flow, not a protocol specification. What the invitation conveys, when the owner must approve it, how access is revoked, and whether a visitor can work offline are still open.

## Two transport choices

**WebSocket relay.** A browser's WebSocket API connects to a WebSocket server; ordinary browser JavaScript does not open a WebSocket listening port for another browser to dial. Both tabs can connect to a relay, and the relay forwards messages between them. `wss:` protects each connection to the relay using TLS, but the relay terminates those connections: to hide application messages from it, the browsers need a separate authenticated end-to-end encryption protocol before sending application data. The relay can still observe traffic metadata, block or delay messages, and affect availability. [WebSocket standard](https://websockets.spec.whatwg.org/), [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455.html#section-10.6)

**WebRTC data channel.** The browsers can exchange arbitrary data through an `RTCDataChannel`, whose transport is encrypted with DTLS. They still need a signaling channel to exchange connection information; it can itself use a WebSocket relay. ICE tries available network routes, and a TURN relay may be needed when direct connectivity fails. A TURN relay can carry the encrypted data even though the application has a peer-to-peer data channel. [RFC 8827](https://www.rfc-editor.org/rfc/rfc8827.html#section-6.5), [WebRTC signaling](https://developer.mozilla.org/en-US/docs/Web/API/WebRTC_API/Signaling_and_video_calling), [ICE](https://developer.mozilla.org/en-US/docs/Glossary/ICE)

WebRTC encryption alone does not establish that the other endpoint is the intended owner or visitor. RFC 8827 explains that even a TLS-protected signaling service can substitute connection fingerprints unless the peers verify their keys independently. A trusted introduction or authenticated exchange must bind the established session to the intended invitation or peer. A malicious signaling service may still deny service. [RFC 8827, communications security](https://www.rfc-editor.org/rfc/rfc8827.html#section-9.1)

A WebSocket relay is a straightforward topology to explore first if an existing relay is acceptable. WebRTC may reduce application data passing through the signaling service, but introduces connection negotiation and possibly TURN. Either choice requires an explicit trust and authorization design; neither proves that no infrastructure is needed.

## What a link can mean

A **bearer invitation** contains a high-entropy secret: anyone who gets it can claim whatever access it grants. It can be scoped, expire, be revoked or consumed by the owner, and optionally require interactive owner approval. Those controls reduce exposure but do not identify a human: forwarding or stealing the link gives another person the same initial opportunity to claim it. [Bearer-token definition](https://www.rfc-editor.org/rfc/rfc8959.html#section-1)

A **device pairing** can instead use the invitation to introduce a visitor's public key, with the owner recording that key in an access grant. Later, the visiting device proves possession of the corresponding private key during an authenticated session; the owner checks its grant and permissions. A proof tied to a fresh challenge and the session is needed to resist replay. This identifies a key-holding device, not automatically the human using it. The cryptographic handshake and binding should use an established, reviewed protocol and implementation, not a new ad hoc construction. Web Crypto exposes key generation, signatures and key agreement, but those primitives alone are not a complete protocol. [Web Crypto operations](https://www.w3.org/TR/WebCryptoAPI/), [Noise protocol framework](https://noiseprotocol.org/noise_rev34.html), [proof-of-possession and replay example](https://www.rfc-editor.org/rfc/rfc9449.html)

A URL fragment is not sent as part of an HTTP request, so it can keep an invitation secret out of the initial request to the hosting service. It remains visible to the receiving page's scripts, browser extensions and the person holding the URL, and redirects can disclose fragments. A fragment is therefore not a guarantee of secrecy. The relay needs routing information, but should not need the secret used to authenticate peers or encrypt data. [RFC 9110 §17.11](https://www.rfc-editor.org/rfc/rfc9110.html#section-17.11)

Authentication answers which key or capability the visitor controls. Authorization answers which operations and data the host allows that key or capability to use. For example, an owner might permit one visitor to read a particular collection while permitting another to edit it; the owner checks those permissions at the request boundary. Revocation prevents future access enforced by the owner, but cannot retract data a visitor has already received or copied.

## Trust and availability boundaries

- **Delivered application code is part of the trust boundary.** A malicious or compromised script running in the owner origin can access data made available to that application and can misuse cryptographic operations. Encrypting traffic does not protect plaintext from the code that legitimately handles it. A trusted code-delivery and update path matters. [Web Crypto security considerations](https://www.w3.org/TR/webcrypto-1/#security-considerations), [RFC 8827 on content JavaScript](https://www.rfc-editor.org/rfc/rfc8827.html#section-9.1)
- **Local data needs a recovery story.** Browser data is normally best-effort, subject to quota and possible eviction. Persistent storage can be requested but may not be granted; user deletion and device loss remain possible. Private-browsing data is usually deleted when that session ends. Encryption is not a backup. [Storage quotas and eviction](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)
- **A tab is not a daemon.** Browsers can freeze or discard background pages, and an operating system can suspend a device. Network access, browser policies, a closed tab, or a sleeping device affect whether the host can answer. A service worker is also lifecycle-managed; it is not a promise of a continuously running host. [Chrome page lifecycle](https://developer.chrome.com/docs/web-platform/page-lifecycle-api), [service worker lifetime](https://www.w3.org/TR/service-workers/#service-worker-lifetime)
- **An encrypted relay is not anonymous.** A relay can observe connections and traffic patterns, and a direct WebRTC route has its own IP-address privacy implications. Neither transport itself proves a person's real-world identity. [RFC 8826, IP address privacy](https://www.rfc-editor.org/rfc/rfc8826.html#section-4.3)

## Questions for the design discussion

1. Is the first use case two people on different devices, or the same person using a second device? Does the owner need to approve each visitor live?
2. Should a link itself grant access to whoever holds it, or should it enroll a particular device for later use? What rights should that device have, and can the owner revoke them?
3. Must the visiting UI work while the owner tab is closed, or is showing the host as offline acceptable? If offline work matters, where can an encrypted replica or pending work live?
4. Is a relay permitted to know connection metadata and route encrypted traffic? Is the application hosting service trusted to deliver its code correctly?
5. What data can the visitor retain locally, and what backup and recovery guarantees does the owner need?

The answers determine the protocol and operational needs; this research does not assert that an existing Zerospin session, relay, authorization mechanism, or storage upgrade already implements them.

## Email invitations without revealing the invitation secret to the email provider

An ordinary email can deliver a **non-secret link** that starts a connection or a request for access. It must not contain a bearer invitation secret if the email provider is outside the trust boundary. Encryption in transit protects network hops but does not stop an email provider that handles the plaintext message from reading it. Email routing metadata remains visible to the services handling delivery. [RFC 3207, SMTP transport security](https://www.rfc-editor.org/rfc/rfc3207.html), [RFC 9787, email security guidance](https://www.rfc-editor.org/rfc/rfc9787.html)

There are several possible introductions:

- **Encrypt the invitation before sending it.** OpenPGP or S/MIME can encrypt the message body for a recipient's public key, allowing the recipient's client to decrypt it. The sender needs the correct recipient public key in advance; an unverified key provided by an untrusted directory could belong to an impostor. Email providers may still see sender, recipient, timing and other metadata, and many encrypted-email clients leave the subject unprotected. Do not put the invitation secret in the subject. This requires a compatible recipient client and a trustworthy key-introduction process. [OpenPGP](https://www.rfc-editor.org/rfc/rfc9580.html), [S/MIME recipient key requirement](https://www.rfc-editor.org/rfc/rfc8551.html#section-2.4.3), [email header protection](https://www.rfc-editor.org/rfc/rfc9788.html)
- **Send a non-secret link by email and the invitation secret separately.** For example, share a high-entropy secret through an already trusted encrypted messaging channel or an in-person QR scan. The host accepts the invitation only when its protocol verifies possession of the secret. Anyone who obtains both parts can attempt to redeem a bearer invitation; sending both through the same email provider does not protect it from that provider.
- **Use the email as a connection request and verify the pairing separately.** The visitor opens the non-secret link, and the owner and visitor compare a short authentication string or use a QR code through an independent trusted channel. The comparison must be bound to the actual cryptographic handshake and visitor key using an established, reviewed protocol. Clicking approve on an unidentified request alone does not establish who sent it. [WebRTC peer identity and fingerprint verification](https://www.rfc-editor.org/rfc/rfc8827.html#section-9.1)

For the owner's own devices, an in-person QR pairing avoids depending on email for the initial secret. For invited people who cannot meet in person, a pre-existing trusted communication channel, an already-verified public key, or another explicit identity-verification method is needed to establish who is being paired. Encrypting the email body also does not protect against compromised application code that can read the invitation before encryption or after decryption. [Web Crypto security considerations](https://www.w3.org/TR/webcrypto-1/#security-considerations)

## A visitor-generated key and an encrypted invitation

One possible flow is for a visitor's browser to generate a public/private key pair, retain the private key, and give the host its public key and an email address. The host encrypts an invitation for that public key before sending it through email. The visitor opens the email in the same browser, which uses its private key to decrypt the invitation. A subsequent authenticated connection must bind the device key and invitation to the host and session; encryption to a public key by itself does not prove the sender's identity. This is an exploration, not a specified handshake or a claim that Zerospin already supports it. [Web Crypto API](https://www.w3.org/TR/webcrypto-2/), [OpenPGP encryption](https://www.rfc-editor.org/rfc/rfc9580.html#section-2.1), [WebRTC identity threat](https://www.rfc-editor.org/rfc/rfc8827.html#section-9.1)

The host must know that the public key actually belongs to the intended visitor. An untrusted key directory or intermediary could substitute its own key; the host would then encrypt the invitation for the wrong device. An email address beside a public key does not establish that binding. Verification could use an independently compared fingerprint or an already trusted contact channel. For the owner's devices, showing a QR code from one device to the other could establish the binding. Whether such verification is necessary depends on which components the owner chooses to trust. [OpenPGP key association](https://www.rfc-editor.org/rfc/rfc7929.html#section-6), [WebRTC signaling threat](https://www.rfc-editor.org/rfc/rfc8827.html#section-9.1)

The private key should not be put in a cookie: cookies are sent with matching HTTP requests. Web Crypto `CryptoKey` objects can be persisted through browser storage such as IndexedDB, and a non-extractable private key can be used without exposing raw key bytes through `exportKey`. This is not protection from malicious application code: script running in the origin may use the key or transfer a `CryptoKey` object, and the standard does not promise encrypted key material on disk. Browser storage can also be cleared. [Cookies](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies), [Web Crypto storage and security](https://www.w3.org/TR/webcrypto-2/#security-considerations)

A recovery code or saved encrypted backup can make a lost browser key recoverable, but that changes the key-management design: a non-extractable key cannot later simply be exported as a backup. Recovery material must be generated and protected as part of a deliberate design; anyone who obtains usable recovery material may be able to recover that identity. Alternatively, the owner can revoke the lost device and pair a new key. A short human-chosen password is not equivalent to a randomly generated high-entropy recovery secret and needs appropriate password-hardening and an explicit threat model. [Web Crypto key export](https://www.w3.org/TR/webcrypto-2/#SubtleCrypto-method-exportKey), [NIST password storage](https://pages.nist.gov/800-63-4/sp800-63b.html)
