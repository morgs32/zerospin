# Browser peer key management landscape

Date: 2026-11-14. Research for the proposed browser-hosted application and [encrypted-email introduction](./browser-hosted-peer-authentication.md). This is not a settled design, an implementation, an audit, or a claim that Zerospin already supports these mechanisms.

## Finding

There are mature browser-accessible building blocks and established encrypted-message formats; no blockchain is necessary. A reasonable first direction to investigate is a separate key for each visitor browser, an encrypted invitation addressed to that browser's public encryption key, and an owner-controlled way to replace a lost device. Keep normal use automatic and consider a deliberately designed recovery export only if recovery without the owner is a requirement. Authentication, encrypted invitation delivery, transport encryption, and recovery each need an explicit protocol and a trust decision; a library cannot settle those product questions. This is a design inference from the sources below, not a recommendation to ship a particular package without further review.

## The keys have different jobs

The visitor needs a public **encryption** key and corresponding private key if the host is to encrypt an invitation that only that visitor can read. To authenticate later browser connections, the host needs a way to verify that the connecting browser controls an authorized private key; that can be a distinct **signing** key or a different established authentication protocol. Algorithm and key types cannot be mixed casually: a signing credential is not automatically an encryption credential. The host must authenticate its own identity to the visitor as well. A session must be cryptographically bound to the invitation and authorized peer; encrypting the invitation alone does not authenticate either side of the subsequent WebSocket conversation. [OpenPGP encryption and signatures](https://www.rfc-editor.org/rfc/rfc9580.html#section-2), [WebRTC identity risks](https://www.rfc-editor.org/rfc/rfc8827.html#section-9.1), [Web Crypto key usages](https://www.w3.org/TR/webcrypto-2/#dfn-CryptoKey)

The email protocol can provide a practical mailbox-access check with a specific threat model: the browser proposes a public key and email address, and the host sends the corresponding ciphertext solely to that mailbox. If an outsider cannot access that mailbox or obtain the ciphertext through another path, they cannot use their own proposed key to complete the flow. An honest-but-curious provider sees the ciphertext but cannot decrypt the visitor's copy. A provider that can actively impersonate the user can submit its own key and read the mailbox; a substituted key or compromised app code has the same kind of consequence. Treat public-key lookup and mailbox possession as separate facts. Delivery can be delayed, the host may be offline, and expiry or reissuance needs explicit behavior. [OpenPGP key association considerations](https://www.rfc-editor.org/rfc/rfc7929.html#section-7), [Web Crypto security considerations](https://www.w3.org/TR/webcrypto-2/#security-considerations)

## Browser key storage and recovery

**Web Crypto and IndexedDB.** Browser Web Crypto can generate or import `CryptoKey` objects and use them for supported algorithms. IndexedDB can persist those objects between sessions. A non-extractable key cannot be exported or wrapped through the normal Web Crypto export APIs, so the raw private key need not be exposed to application JavaScript during normal use. This property is not hardware protection or a guarantee of encryption at rest: the standard does not require a particular underlying storage mechanism, and malicious same-origin code may invoke operations with the key or transfer access to it. Supported algorithms, browsers, secure-context requirements and the chosen library's key interface need verification for the actual product. [Web Crypto storage and security](https://www.w3.org/TR/webcrypto-2/#security-considerations), [Web Crypto key storage](https://www.w3.org/TR/webcrypto-2/#key-storage)

**Cookies.** Do not put the private key in a cookie. Cookies are designed to be attached to matching HTTP requests and do not offer the right semantics for a browser-only cryptographic key. Cookies can have unrelated uses, such as maintaining a conventional HTTP session, but that does not make them appropriate private-key storage. [HTTP cookies](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies)

**Persistence is not a backup.** IndexedDB and other site data can be cleared, and storage is generally best-effort unless a persistent storage request is granted. Private-browsing storage usually disappears when that session ends. WebKit documents a seven-day limit for script-writable storage in specified non-interaction conditions, including IndexedDB, with documented exceptions. Persistence also cannot recover a lost or broken device. [Browser quotas and eviction](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria), [WebKit tracking prevention](https://webkit.org/tracking-prevention/)

**The simplest recovery when a host can re-invite a visitor:** generate a fresh browser key, repeat the host's admission process, revoke the lost device if it was already authorized, and grant the replacement. This need not recover the original private key. It does require the host to be available and a trusted route to establish the replacement's authority. Old ciphertext addressed only to the lost encryption key remains unreadable unless there was a backup or another recipient. Copies already disclosed cannot be revoked. This is a product design inference, not a property of IndexedDB.

**Recovery file or phrase:** a user can keep a random recovery secret or encrypted backup outside browser storage, but the recovery material must be designed when the key is created. A non-extractable `CryptoKey` cannot simply be exported later. A saved secret that restores a key and a one-time code that authorizes a host to enroll a new key are different mechanisms; the latter does not magically decrypt old data. A stolen usable secret or backup can give its holder access, and a user-chosen short password permits guessing against any stolen encrypted backup. Use a reviewed backup format, sufficiently random recovery material, and an appropriate password KDF where a password is used; do not invent a deterministic seed-to-key or wrapping construction. [Web Crypto `exportKey`](https://www.w3.org/TR/webcrypto-2/#SubtleCrypto-method-exportKey), [NIST saved recovery codes](https://pages.nist.gov/800-63-4/sp800-63b.html#saved-recovery-codes), [OpenPGP password-derived encryption](https://www.rfc-editor.org/rfc/rfc9580.html#section-3.7)

**Multiple devices:** per-device keys let the owner revoke one device and avoid copying its private key; each device needs its own authorized grant and an invitation encrypted to its own recipient key. A recoverable shared identity simplifies moving between devices but copying the same private key makes the devices harder to distinguish and revoke individually. If a backup is lost or copied, it remains a credential until the affected grants are revoked. These are consequences of the selected ownership model, not capabilities already provided by Zerospin.

## Candidate JavaScript and TypeScript building blocks

- **Web Crypto API:** built into browsers; generates and uses keys, signatures, and encryption primitives, including non-extractable `CryptoKey` objects. It is not an invitation format, end-to-end messaging protocol, key directory, or recovery system. Its standard explicitly discourages designing new cryptographic protocols. [Web Crypto](https://www.w3.org/TR/webcrypto-2/)
- **`age-encryption` (Typage):** a TypeScript implementation of the age format with browser support, documented recipient/identity generation, ASCII-armored ciphertext and passphrase encryption. This is a focused candidate for encrypting an invitation or backup. The standard `generateIdentity()` example returns a serializable private-key string; the documented alternative accepts a non-extractable X25519 Web Crypto `CryptoKey`, which could be stored in IndexedDB where supported. Those modes have different recovery properties, and X25519 support on the chosen browsers must be verified. An age ciphertext does not authenticate its sender; use a separately specified authenticated introduction. Age does not by itself define this application's live WebSocket protocol or authorization rules. [Typage documentation](https://github.com/FiloSottile/typage#web-crypto-identities), [age sender authentication discussion](https://github.com/FiloSottile/age/discussions/229)
- **OpenPGP.js:** browser-capable JavaScript OpenPGP implementation with TypeScript declarations and support for encryption and signatures. It is a natural candidate if interoperating with existing OpenPGP email or key tooling matters. It provides a format and operations, not a trustworthy mapping from email addresses to public keys. [OpenPGP.js](https://github.com/openpgpjs/openpgpjs), [OpenPGP specification](https://www.rfc-editor.org/rfc/rfc9580.html)
- **libsodium.js / HPKE / noble:** libsodium.js offers browser JavaScript/WebAssembly cryptographic APIs; its sealed boxes encrypt to a recipient but do not authenticate the sender. `hpke-js` implements the HPKE standard, whose modes have distinct authentication properties. Noble supplies audited cryptographic primitives. These are useful lower-level components, not complete authorization, recovery, or interactive secure-channel solutions. [libsodium.js](https://github.com/jedisct1/libsodium.js), [sealed boxes](https://libsodium.gitbook.io/doc/public-key_cryptography/sealed_boxes), [hpke-js](https://github.com/dajiaji/hpke-js), [HPKE RFC 9180](https://www.rfc-editor.org/rfc/rfc9180.html), [noble curves](https://github.com/paulmillr/noble-curves)

These are candidates, not an evaluation of present maintenance, browser compatibility, vulnerabilities, or audit coverage for a chosen release. Check those for the exact dependency versions and platform before selecting one. A library's primitive or format review does not verify the surrounding app protocol, authorization, code delivery, or recovery flow.

## Passkeys and wallet conventions

**Passkeys** use WebAuthn credentials to authenticate by signing challenges; the credential's private key is controlled by the authenticator, and passkeys can be synced by some credential providers. That is appealing for account/device authentication, but the normal WebAuthn signing credential is not a general public key to which another browser can encrypt an invitation. [WebAuthn](https://www.w3.org/TR/webauthn/), [Google passkeys](https://developers.google.com/identity/passkeys)

The optional WebAuthn PRF extension can produce client-side key material for symmetric encryption or wrapping. The browser/authenticator must support the extension and the encrypted app-key backup still needs to be stored and made available on recovery. Typage documents this mode, with authenticator confirmation on each use, and explicitly identifies it as symmetric: the host cannot encrypt to the visitor's passkey public key using this mode without access to that visitor's authenticator. A passkey's ability to sync does not automatically back up separate IndexedDB encryption keys. Treat PRF support, provider recovery and its user experience as a separate exploration. [WebAuthn PRF](https://www.w3.org/TR/webauthn/#prf-extension), [Typage passkey support](https://github.com/FiloSottile/typage#encrypt-and-decrypt-a-file-with-a-passkey)

**Blockchain wallets** popularized generated recovery phrases. BIP-39 is a convention for encoding generated 128–256-bit entropy as memorable words and deriving a wallet seed; it explicitly is not a recipe for turning a user-invented sentence into a secure secret. It also documents limitations including short checksums and no format versioning. The convention does not require a blockchain to encode random material, but adopting it would be a product choice and would not itself define key lifecycle, browser storage, encryption or session authentication. Never ask users to enter an existing cryptocurrency wallet recovery phrase into this app. [BIP-39](https://github.com/bitcoin/bips/blob/master/bip-0039.mediawiki), [BIP-85 key separation rationale](https://github.com/bitcoin/bips/blob/master/bip-0085.mediawiki)

Wallet signing support is not equivalent to an invitation-decryption API: for example, MetaMask deprecated its `eth_decrypt` and `eth_getEncryptionPublicKey` APIs. Key reuse across purposes introduces additional design concerns. [MetaMask encryption API deprecation](https://metamask.io/en-GB/news/metamask-api-method-deprecation)

## Decisions still needed

1. Is email verification sufficient under an honest-but-curious email provider assumption, or must the design resist an actively impersonating email provider and key-directory service?
2. Can an invited person request another invitation if a browser or device is lost, or must they recover the same key and decrypt older invitations without the host?
3. Is each browser a separate revocable device, or should one identity and its keys follow a person across devices? What data must remain readable after a key is lost?
4. Which browser/OS combinations, app origin, trust in delivered code, and availability of the host and relay are in scope?
5. Is interoperability with existing OpenPGP email clients necessary, or will the app itself decode an encrypted invitation? Which reviewed end-to-end channel protocol and sender-authentication approach will bind that invitation to the live session?
