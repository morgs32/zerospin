# Chain storage capacity and segmentation

Researched 2026-10-26 against current Cloudflare documentation and local source at `8724ae821d`. This is research and a preliminary recommendation, not an approved implementation plan. No production usage or storage telemetry was inspected.

## Recommendation

Prepare for bounded physical history storage while retaining one logical command history. Do not rely on Cloudflare removing the limit, and do not replace the infrastructure solely because a single database has a finite size. Prefer immutable history segments, potentially archived in R2, with release-specific snapshots as an optional replay optimization. Do not use one release's model snapshot as the universal replacement for earlier commands.

That distinction follows directly from Zerospin's parallel release behavior: a fresh release evaluates shared history using its own programs, whereas reconstruction of an already evaluated release reuses its retained immutable output. Copying an older release's model state into an arbitrary new release would skip the new release's historical evaluation. Sources: [replayCommand](../../packages/system-worker/src/AggregateVersionRepo/replayCommands/replayCommand.ts), [parallel-model policy](../../packages/sdk/skills/zerospin-parallel-models/SKILL.md).

## Verified platform facts

- The documented SQLite-backed Durable Object limit is **10 GB per object on Workers Paid**, not 15 GB. Paid account and class storage are unlimited across objects. Cloudflare measures GB as 1,000,000,000 bytes. A general limit-increase form exists, but its wording does not promise that this particular limit can be increased. Source: [Durable Objects limits](https://developers.cloudflare.com/durable-objects/platform/limits/).
- When full, inserts and updates fail with `SQLITE_FULL`; reads and deletes remain available. Operational rollover must therefore happen before the database reaches capacity. Source: [Durable Objects FAQ](https://developers.cloudflare.com/durable-objects/reference/faq/#what-happens-when-a-durable-object-exceeds-its-storage-limit).
- `ctx.storage.sql.databaseSize` exposes current database bytes. The PITR API restores the object's own database to a point in the last 30 days; that is disaster recovery, not an indefinite history archive or a cross-release snapshot bootstrap protocol. Source: [SQLite storage API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/).
- The limit has increased before: Cloudflare announced 10 GB at SQLite Durable Objects GA on April 7, 2025. That historical change is not a commitment to another increase or its date. Source: [GA announcement](https://developers.cloudflare.com/changelog/post/2025-04-07-sqlite-in-durable-objects-ga/).
- An individual Durable Object is single-threaded with a documented soft limit around 1,000 requests/second, varying with the work. This is a distinct throughput constraint, not a command throughput guarantee. Source: [Durable Objects FAQ](https://developers.cloudflare.com/durable-objects/reference/faq/#how-much-work-can-a-single-durable-object-do).

## What can fill first in Zerospin

`AggregateChain` is partitioned by `systemId`, `aggregateName`, and `aggregateId`. `ServiceChain` is partitioned by `systemId` and `serviceName`. Consequently, many independent aggregate identities distribute storage, while a busy shared service can accumulate commands from all of them in one ServiceChain. The service's traffic concentration can make it the first capacity concern. Sources: [aggregateChainName](../../packages/system-worker/src/AggregateChain/aggregateChainName.ts), [serviceChainName](../../packages/system-worker/src/ServiceChain/serviceChainName.ts).

An admitted command is larger than its payload. AggregateChain and ServiceChain retain payload, identity/provenance, claims, external outcome, and command `outcome`, plus SQL indexes. Their delivery and external-operation outboxes also occupy space while pending. The effective bytes per retained command must include all of this, database overhead, and normal pending work. Sources: [AggregateChain schema](../../packages/system-worker/src/AggregateChain/aggregateChainDbConfig.ts), [ServiceChain schema](../../packages/system-worker/src/ServiceChain/serviceChainDbConfig.ts).

`AggregateVersionChain` separately retains complete evaluated commands. `AggregateVersionRepo` retains model state, its materialization checkpoint, and pending evaluated-command publication. Its historical reads consult AggregateVersionChain, and reconstruction fails when required original evaluated output is missing. Archiving only AggregateChain would therefore leave another growing history database and break reconstruction if its evaluated history were discarded. Service and actor Chain families require the same responsibility-by-responsibility review; no claim is made that all have identical bytes per command. Sources: [AggregateVersionChain schema](../../packages/system-worker/src/AggregateVersionChain/aggregateVersionChainDbConfig.ts), [AggregateVersionRepo schema](../../packages/system-worker/src/AggregateVersionRepo/aggregateVersionRepoDbConfig.ts), [findEvaluatedCommand](../../packages/system-worker/src/AggregateVersionRepo/readEvaluatedCommand/findEvaluatedCommand.ts), [replayCommand](../../packages/system-worker/src/AggregateVersionRepo/replayCommands/replayCommand.ts).

## How soon: sensitivity estimates, not a forecast

For one physical database:

`days remaining = (operating budget bytes - current database bytes) / (commands per day × effective retained bytes per command)`

When direct storage growth is measured, use `(operating budget bytes - current database bytes) / growth bytes per day`; this also captures pending rows and other growth outside retained commands.

The following hypothetical examples use the entire 10,000,000,000-byte limit, zero initial storage, and constant effective bytes per command. Real rollover must reserve headroom, so its deadline comes earlier:

- At **2 KiB per command**, capacity is approximately **4.88 million commands**: 100/day lasts 134 years; 10,000/day lasts 1.34 years; 100,000/day lasts 48.8 days; one/second lasts 56.5 days.
- At **10 KiB per command**, capacity is approximately **977,000 commands**: 10,000/day lasts 97.7 days; 100,000/day lasts 9.77 days.
- An illustrative 8 GB operating budget gives 80% of those durations. This is an example reserve, not a validated safe threshold.

These calculations establish why neither “soon” nor “years away” is defensible without measurements from the busiest physical Chain. Measure database growth over a representative finalized-command interval, separately for admitted and evaluated histories. Also measure replay time: rebuilding millions of commands can become operationally unacceptable before storage fills. This last point is an architectural inference, not an observed Zerospin performance result.

## Separate history segmentation from snapshots

**History segmentation addresses capacity.** Keep one logical sequence and split the bytes into bounded physical segments. Preserve canonical command IDs, `aggregateIndex`/`serviceIndex`, `outcome`, retained evaluated output, and boundary hashes. Never restart logical indexes when rotating physical storage. Existing replay reads consume an ordered finalized prefix; segmentation should change where that prefix is read, not its meaning. Sources: [readReplayPage](../../packages/system-worker/src/AggregateChain/readReplayPage.ts), [replayCommand](../../packages/system-worker/src/AggregateVersionRepo/replayCommands/replayCommand.ts).

**Snapshots address replay cost.** A command-derived snapshot can restore the same release at a precise checkpoint, then replay its suffix. It must identify the exact release/model semantics and checkpoint, including `dispositionChainHash`; pending delivery state needs explicit treatment. A new release may use an applicable snapshot only if its semantics are explicitly established. There is no generic rule that every AggregateVersionRepo can copy the latest snapshot from another release. Source: [parallel-model policy](../../packages/sdk/skills/zerospin-parallel-models/SKILL.md); snapshot format and applicability are proposed design obligations, not existing capabilities.

**Snapshot plus deletion changes the product's guarantees.** Deleting all pre-snapshot command history prevents an arbitrary future release from evaluating that history unless there is a separate sufficient representation or an explicit new genesis policy. For example, a release retaining only current balance cannot supply a later release's lifetime spending totals by category from that balance alone. Preserve archived commands when future historical reinterpretation remains a requirement. Preserve exact evaluated output as well for reconstructing originating releases; admitted input alone does not replace its recorded operations, identities, and outcomes. This follows from the current [replay path](../../packages/system-worker/src/AggregateVersionRepo/replayCommands/replayCommand.ts).

Pruning also affects deduplication: AggregateChain currently finds an existing command by its canonical `id` in local `commands`. Any archive design must preserve historical duplicate detection and outcome lookup rather than accidentally readmitting old commands. Subscriber cursors must continue to reach older ranges, and pending deliveries must not disappear merely because a range was archived. Source: [readRetainedCommand](../../packages/system-worker/src/AggregateChain/admitAggregateCommands/readRetainedCommand.ts), [AggregateChain schema](../../packages/system-worker/src/AggregateChain/aggregateChainDbConfig.ts).

## Why R2 is a plausible archive

R2 has unlimited bucket storage and object counts, with individual objects up to 5 TiB; ordinary single-part uploads are limited to 5 GiB. Bounded archive segments can be much smaller. Source: [R2 limits](https://developers.cloudflare.com/r2/platform/limits/).

R2 object writes, reads, deletes, and listing are strongly consistent. This makes a verified uploaded segment immediately readable, but does not create a transaction spanning R2 and a Chain's SQLite database. Source: [R2 consistency](https://developers.cloudflare.com/r2/reference/consistency/).

Standard R2 storage is $0.015/GB-month, plus $4.50/million Class A and $0.36/million Class B operations; egress is free. Ten GB of archive therefore costs about $0.15/month in storage before included allowances and operation charges. Source: [R2 pricing](https://developers.cloudflare.com/r2/pricing/).

A preliminary archival protocol would freeze a finalized range, upload an immutable segment, verify its identity/content, durably publish its location and boundaries, and only then remove eligible local history bytes. Each interrupted phase must be retryable, with orphan cleanup and no interval in which history is unavailable. Durable pending delivery and historical lookup remain responsibilities. R2 I/O permits request interleaving, so local synchronous transactions cannot simply encompass upload. Sources: [Cloudflare's non-storage-I/O guidance](https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/#avoid-race-conditions-with-non-storage-io), [SQLite transaction API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/). This protocol is a proposed shape, not implemented Zerospin behavior.

Keeping sealed ranges in additional Durable Objects is another capacity option: each immutable closed database remains below its cap while a new database collects the suffix. R2 instead keeps cold history outside SQL, with a bounded local hot suffix and a manifest/index whose own growth must be bounded. Neither chronological segmentation nor R2 archival increases the throughput of the active logical Chain. Snapshots also cannot bound a materialized resource dataset that itself grows beyond one object's capacity. If measured command execution or materialized live state exceeds a single Durable Object's practical limits, revisit owner boundaries or infrastructure for that demonstrated requirement. Cloudflare itself recommends partitioning independent workloads across objects. Source: [Rules of Durable Objects](https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/#message-throughput-limits).

## Next decision

Obtain per-Chain database size/growth and replay duration first. Agree whether indefinite new-release historical replay is required; the current design implies that it is. Then design one bounded history/archive mechanism covering admitted and evaluated history, with optional exact-release snapshots. Implement it before the busiest Chain's projected headroom becomes shorter than the delivery and validation lead time. Do not initiate a storage reset or build a cross-release snapshot-copy path from this research alone.

## Evaluated-history archival design investigation

Investigated 2026-10-26 following authorization to examine a first archival milestone. Everything below is a recommendation for design review; none of it has been implemented or runtime verified. Scope this milestone to AggregateVersionChain and ServiceVersionChain evaluated history. Keep snapshots, admitted-history archival, and actor/agent history archival separate.

### Address history by fixed position windows

Recommend a fixed immutable window width `W` in the archive format. Position `n` belongs to window `floor((n - 1) / W)`. Close only complete windows; retain the incomplete suffix locally. Select complete windows using an explicit recent-history retention policy, with measured storage headroom as an additional constraint. Do not make archiving an emergency action initiated only when SQLite fills. An exact lookup computes the window key, reads that window's descriptor, then reads the containing page. An ordered range lookup walks successive pages/windows and merges the recent SQL suffix. No global manifest, predecessor search, R2 listing, or variable-chunk directory is needed for these readers.

These access patterns match the current APIs: `getEvaluatedCommand` reads by `aggregateIndex` or `serviceIndex`; fanout reads ascending positions after its subscriber cursor; ServiceVersionChain also exposes `getInputCheckpoint` by `serviceIndex`. Sources: [AggregateVersionChain](../../packages/system-worker/src/AggregateVersionChain/AggregateVersionChain.ts), [ServiceVersionChain](../../packages/system-worker/src/ServiceVersionChain/ServiceVersionChain.ts).

Inside a window, encode complete evaluated commands into deterministic JSON page objects bounded by encoded bytes. Publish one bounded descriptor listing page position intervals, keys, byte lengths, and content hashes. Page and descriptor hashes protect exact bytes; `dispositionChainHash` remains the command disposition lineage and is not a substitute for a content checksum. Preserve every command field, operation, identity, and `outcome`; archival must not re-evaluate programs or regenerate IDs.

`W`, page byte limits, and descriptor limits must derive from the largest supported encoded evaluated command, including JSON expansion and encoding buffers. Average command size is insufficient. A single command must fit the chosen page format, or the format must explicitly support a larger individually bounded page. Count-bounded windows alone do not bound memory. Archive complete windows early enough to maintain a bounded hot reserve; keeping fewer than `W` recent positions is useful only if the worst supported suffix also fits that reserve. Numeric sizing remains a measured design choice.

Keys must identify the archive format and the **evaluating Chain's exact identity**, including its release: AggregateVersionChain uses `systemId`, `aggregateId`, `aggregateName`, `aggregateVersion`; ServiceVersionChain uses `systemId`, `serviceName`, `serviceVersion`. Do not derive that namespace from the admitted command's originating release, which can differ during parallel replay. Sources: [aggregateVersionChainName](../../packages/system-worker/src/AggregateVersionChain/aggregateVersionChainName.ts), [serviceVersionChainName](../../packages/system-worker/src/ServiceVersionChain/serviceVersionChainName.ts).

**Lineage remains a design choice to settle.** Current storage registration validates `systemId` against configured `env.ZEROSPIN_SYSTEM_ID`; that does not prove that an authorized storage reset always changes the ID. Reusing the same system/Chain key for a new genesis while old immutable R2 objects remain would collide. The archive namespace must identify the physical history lineage, either through an existing guaranteed-unique instance identity or an explicitly established lineage identifier. The minimal integration policy is an isolated archive prefix for each fresh genesis, preserved during reconstruction of that history. Do not create a new prefix per activation or assume a deployment ID represents that lineage. Settle how this prefix is established before implementation. Sources: [makeMigratableDORepo](../../packages/system-worker/src/makeMigratableDORepo/makeMigratableDORepo.ts), [validateRepoSystemId](../../packages/system-worker/src/SystemRepo/registerRepo/validateRepoSystemId.ts).

### Preserve canonical command identity without another permanent ID directory

The evaluated schemas currently enforce unique command `id` in SQL. Deleting archived rows would remove that cross-position uniqueness guard. Index-addressed archive reads alone therefore do not preserve append behavior. Sources: [aggregate evaluated shape](../../packages/system-worker/src/AggregateVersionChain/evaluatedAggregateCommand.ts), [service evaluated shape](../../packages/system-worker/src/ServiceVersionChain/evaluatedServiceCommand.ts).

Recommend a strengthened invariant for **new evaluated appends**: before the local SQL transaction, read the canonical admitted command at that position through `AggregateChain.getAggregateCommand` or `ServiceChain.getServiceCommand`. Compare the complete immutable admitted input, including canonical `id`, original release, payload, claims, and provenance. The canonical Chain's unique `id` establishes that the same admitted command cannot occupy another position. Exclude `outcome`, evaluated operations, and `dispositionChainHash` from this comparison: the source `outcome` can still be null when original evaluated output is published, and parallel releases can produce different evaluated outcomes. Sources: [AggregateChain getter](../../packages/system-worker/src/AggregateChain/AggregateChain.ts), [ServiceChain getter](../../packages/system-worker/src/ServiceChain/ServiceChain.ts), [AggregateChain schema](../../packages/system-worker/src/AggregateChain/aggregateChainDbConfig.ts), [ServiceChain schema](../../packages/system-worker/src/ServiceChain/serviceChainDbConfig.ts).

Those getters read retained input; they must remain free of admission, execution, materialization catch-up, and finalization waits. Make the RPC for a new append before opening the evaluated Chain's synchronous transaction. After any asynchronous reads, re-read the evaluated Chain's logical head, archive frontier, and local rows before appending. Old repeats first compare the complete retained evaluated command, including archived output, and reject any mismatch; an exact retained repeat needs no fresh source lookup or current declaration registration validation. Preserve this retained-first recovery even if current definitions are absent. Reconstructing the same release uses its recorded output and frozen model IDs, rather than rerunning programs to generate identities. Current append code does not validate canonical input this way: this recommendation strengthens the existing invariant and requires behavioral proof. Sources: [aggregate append](../../packages/system-worker/src/AggregateVersionChain/appendEvaluatedCommandsTx.ts), [service append](../../packages/system-worker/src/ServiceVersionChain/appendEvaluatedCommandsTx.ts), [replayCommand](../../packages/system-worker/src/AggregateVersionRepo/replayCommands/replayCommand.ts).

This avoids per-command R2 ID locator objects in the evaluated layer. It does not solve admitted-history archival: AggregateChain and ServiceChain still own historical command-ID and node/push duplicate detection, which a later milestone must preserve.

### Publish before pruning, with bounded recovery state

Retain a durable logical head/index/hash, `archivedThrough`, existing subscriber cursors, and at most one bounded archive job containing its fixed range, format/configuration, and progress. A local SQL maximum is no longer the logical head after pruning; update append gap checks, fanout's `lastIndex`, and default checkpoint reads accordingly. Sources: [aggregate append](../../packages/system-worker/src/AggregateVersionChain/appendEvaluatedCommandsTx.ts), [service append](../../packages/system-worker/src/ServiceVersionChain/appendEvaluatedCommandsTx.ts), [AggregateVersionChain](../../packages/system-worker/src/AggregateVersionChain/AggregateVersionChain.ts), [ServiceVersionChain](../../packages/system-worker/src/ServiceVersionChain/ServiceVersionChain.ts).

1. In a synchronous local transaction, capture the closed window, logical head/frontier, and deterministic archive job. Read source rows in bounded pages before each R2 await; keep them locally until publication succeeds.
2. Upload immutable data pages with create-only writes. On a retry whose conditional PUT returns null, verify the existing object's identity, exact expected checksum, and length. An existing key alone is insufficient.
3. After verifying every referenced page, publish the immutable descriptor last. Then synchronously revalidate the job and frontier and advance `archivedThrough`. Readers may use only fully published windows. A missing/corrupt archived dependency is an error, never a normal missing-command null.
4. Delete eligible local rows in bounded synchronous transactions. Retain the job through cleanup and start the next job only after cleanup finishes, bounding duplicate retained storage. A crash during cleanup resumes cleanup; it does not republish a different history.

Before descriptor publication, local rows remain authoritative. After descriptor publication but before the local frontier advances, retry verifies the same archive while local rows remain available. After frontier publication, complete archive dependencies already exist; remaining SQL rows are duplicates awaiting bounded cleanup. Read the local frontier and local rows together before asynchronous archive access. A concurrent archive transition or append requires revalidation of any assumptions used by the final local write. Never hold a SQL transaction or `blockConcurrencyWhile` across R2 I/O. Source: [non-storage I/O guidance](https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/#avoid-race-conditions-with-non-storage-io).

### Platform constraints affecting this shape

R2 binding `get` supports streams and byte ranges; `put` accepts SHA-256 checksums and conditions, returning null on failed conditions. Use full bounded pages when verifying their whole-object checksum. Source: [R2 Workers API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/).

Current workerd source maps `etagDoesNotMatch: '*'` to the wildcard precondition. Use create-only PUT for protocol immutability and verify existing content on retry; this is not protection against an unrelated writer intentionally overwriting or deleting archive objects. Source: [workerd R2 implementation](https://github.com/cloudflare/workerd/blob/main/src/workerd/api/r2-bucket.c++).

R2 limits include one write/second to the same key, 1,024-byte object keys, and 8,192-byte metadata. Put the descriptor in the object body. Deterministic unique page keys avoid a frequently rewritten global manifest. Source: [R2 limits](https://developers.cloudflare.com/r2/platform/limits/). Workers have a 128 MB per-isolate memory limit; bounded pages and streaming avoid buffering an entire window, but actual encode/decode memory must still be measured. Source: [Workers limits](https://developers.cloudflare.com/workers/platform/limits/#memory).

### Integration boundary and future behavioral proof

The milestone must cover both evaluated Chain classes and schemas, both `appendEvaluatedCommandsTx.ts` procedures, exact indexed getters, ServiceVersionChain's checkpoint getter, and fanout page/head reads. Existing source getters provide canonical identity; their behavior must remain read-only. Generic physical SQL inspection still reports physical local rows; only logical history APIs merge R2 history. Pending publication and subscriber acknowledgement retain their existing responsibilities.

The smallest future proof should establish exact archived repeat equality/mismatch, canonical input and cross-position ID rejection, indexed/range/checkpoint reads across the archive frontier, a stale preflight racing archival/append, and restart recovery around descriptor publication, frontier publication, and bounded deletion. This note creates no tests or fixtures.

If R2 is unavailable, do not advance the frontier or delete required rows. Recent local work can continue while storage headroom permits; archive-dependent recovery, new-release reconstruction, and historical reads can fail or wait explicitly. Existing materialized resources need not be erased or declared unavailable solely because archived history cannot currently be fetched. Without explicit backpressure at command admission/publication, the unarchived backlog can grow without bound during an outage; define that policy before headroom is exhausted. This is the proposed failure policy, not verified current behavior.
