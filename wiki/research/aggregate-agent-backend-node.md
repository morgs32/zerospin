# AggregateAgentBackendNode research

**Date:** 2026-10-21. **Status:** Current-source research supporting the proposed design; no implementation or runtime verification.

**Integer V1 cutover:** Shopping now registers only revision `1`; see the
[current Node definition](../../examples/shopping/src/zerospin/agents/reservationsAgentNodeDefinition.ts) and
[current registry](../../examples/shopping/agents.ts). The earlier declaration
citations below are pinned to the inspected source snapshot and preserve the
research's historical design context.

## Settled direction

`AggregateAgentBackendNode` is a separate durable consumer of the retained stream already consumed by the client `AggregateAgentNode`. Both hosts can execute the same behavior from one shared pure `AggregateAgentNodeDefinition` referencing the canonical agent release. Exactly one host is chosen for the containing logical Node instance: the definition bound to `systemId`, `aggregateName`, `aggregateId`, `aggregateVersion`, `agentName` and `agentVersion`, with its canonical `sessionName`. This supersedes the earlier colocated-host recommendation in [Aggregate agent Repo research](aggregate-agent-repo.md). The existing `AggregateAgentVersionRepo` remains the selected-view publisher. The [naming research](aggregate-agent-definition-naming.md) grounds `NodeDefinition` in the existing Node ownership and Agent Session facade split.

The user settled one behavior instance per selected row, keyed by `modelName` and `resourceId` inside that logical Node instance. In a Backend Node, those instances are durable and share its selected resource view, stream checkpoint, command producer and alarm registry; they are not separate Durable Objects. In a browser Node, behavior state and timers are transient within that Node's lifetime. The selected Node host owns its own producer and runtime state; browser and backend hosts do not share them. This first design does not route individual rows between hosts.

## Stream and completion findings

`AggregateAgentVersionChain` currently exposes browser socket handling, publication and checkpoint methods; a durable Backend Node subscription is an addition, rather than an existing RPC to reuse verbatim. Add history-backed delivery to this same Chain rather than another retained command stream. The source retains history; backend subscriber acknowledgement records progress and must not delete that history. [Chain interface](../../packages/system-worker/src/AggregateAgentVersionChain/AggregateAgentVersionChain.ts#L14-L93), [history ownership](https://github.com/morgs32/zerospin/blob/79c1824b1a0353f770211851c0bfe1cc54d0ba46/packages/system-worker/src/AggregateAgentVersionChain/README.md).

Public agent history carries selected deltas and Aggregate checkpoint identity. Private command resolution adds producer identity and nullable `failure`; it does not carry canonical `outcome.result` or `outcome.finalizedAt`. A Backend Node can observe its own command completion/refusal using the exact owned producer context. Its behavior interface must not promise canonical return values or a full `outcome` merely because it consumes this stream. [History/private reconstruction](../../packages/system-worker/src/aggregateSessionChain/readExposedCommands.ts#L26-L110), [Chain schema and disclosure](https://github.com/morgs32/zerospin/blob/79c1824b1a0353f770211851c0bfe1cc54d0ba46/packages/system-worker/src/AggregateAgentVersionChain/README.md).

The current Chain already exposes `getBrowserCommands` and `getResolvedThrough` for bounded public replay and independent owned completion recovery. `getBrowserCommands` limits pages, validates contiguous Aggregate positions, redacts other producers' failures and reports the source tip separately from returned progress. Public `failure: null` on another producer's command does not establish that command succeeded. [Chain methods](../../packages/system-worker/src/AggregateAgentVersionChain/AggregateAgentVersionChain.ts#L34-L92), [bounded replay and disclosure](../../packages/system-worker/src/aggregateSessionChain/getBrowserCommands/getBrowserCommands.ts#L94-L224).

Existing fanout provides catch-up followed by durable-cursor reread and enrollment; retained source history covers that gap. Its history reader is source-bound, not recipient-bound. The smallest proposed extension is public backend fanout plus exact owned completion reads, rather than widening generic fanout to publish private failures. [Enrollment](../../packages/system-worker/src/makeFanoutSubscriber/subscribe.ts#L30-L57), [queue interface](../../packages/system-worker/src/makeFanoutQueue/makeFanoutQueue.ts#L39-L84), [fanout guidance](../patterns/system-worker/i-fanout-repo.ts).

Initial bootstrap can capture selected resources/checkpoint N from `AggregateAgentVersionRepo`, publish through N, verify the retained Chain checkpoint and bound private completion to N. Proposed behavior starts by reconciling current matching rows at N, then consumes positions after N. Restart resumes the durable Backend Node checkpoint instead of replacing it with a later snapshot that would skip unprocessed positions. Replaying all historical positions with behavior enabled is a different policy that can issue actions for historical states. [Snapshot handshake](../../packages/system-worker/src/aggregateProjection/getSnapshot/getSnapshot.ts#L76-L128), [private bootstrap](../../packages/system-worker/src/aggregateProjection/getSnapshot/getAgentBootstrap.ts#L35-L66).

Backend delivery should commit selected resource changes, checked `aggregateIndex`/`dispositionChainHash`, current behavior transitions and complete pending actions in one synchronous receiving transaction before acknowledgement. The Backend Node needs a stable durable `nodeId` and contiguous `pushIndex` for its own private completions; a fresh producer identity on each activation loses that ownership. [Producer continuity](../../packages/system-worker/src/AggregateChain/admitAggregateCommands/validateAggregateNodeContinuation.ts#L18-L55), [existing transactional baseline mechanics](../../packages/core/src/AggregateAgentNode/AggregateAgentNode.ts#L693-L824).

## Primary prototype: release an expired promotion reservation

The user chose releasing an uncommitted promotion reservation after ten minutes as the primary prototype. `reservePromotion` records `expiresAt = now + promotionDuration` when it creates a reserved row; `promotionDuration` is already `10 * 60 * 1000`. The shared behavior therefore schedules the absolute `row.expiresAt`, rather than adding another ten minutes when a Node starts, restarts or first sees the row. An already expired matching row is due during initial reconciliation. This is the proposed automation over existing recorded domain facts. [Recorded deadline](../../examples/shopping/src/zerospin/services/promotion/ReservePromotionV1.ts#L66-L81), [ten-minute policy](../../examples/shopping/src/zerospin/services/promotion/promotionPolicy.ts#L1-L2).

For each selected reservation, the proposed shared row behavior initializes current state from its recorded deadline. At wake-up the chosen host first catches its selected graph up through a captured published Service Agent Chain checkpoint, then rechecks row membership and `expiresAt <= now`. If still due, it submits `releaseUncommittedReservation` with only `{ id: row.id }`. Browser hosting uses lifetime-fenced timers; backend hosting persists that same absolute deadline and uses its alarm registry. Neither host may reset the deadline on reconstruction. Published-view catch-up is not a claim that no newer canonical execution exists; command execution still validates the reservation's current status and purchase binding.

`releaseUncommittedReservationV1` currently refuses with `notReleasable` when the reservation is absent, no longer reserved or has a Purchase. It does **not** inspect `expiresAt`; manual release can occur early. The ten-minute condition belongs to this automation's decision rule, and this prototype must not claim the existing contract enforces expiry. An owned `notReleasable` refusal stops/reconciles that behavior attempt; it is not a reason to issue automatic new business attempts. Uncertain admission still retries its exact original command envelope. [Existing release guard and update](../../examples/shopping/src/zerospin/services/promotion/ReleaseUncommittedReservationV1.ts#L17-L47).

The prototype requires the Service counterparts of the general design: proposed `makeServiceAgentNodeDefinition` shared by `ServiceAgentNode` and `ServiceAgentBackendNode`, consuming `ServiceAgentVersionChain` with `serviceIndex`/`dispositionChainHash` and submitting through `ServiceChain.admitServiceCommands`. `ServiceAgentVersionRepo` remains the materialized Service Agent publisher and `ServiceVersionRepo` remains canonical execution owner. Do not manufacture an Aggregate identity or route the reservation command through `AggregateChain` to fit this document's Aggregate design. Service ownership is an explicit prototype requirement; the Aggregate behavior/host design above remains applicable to Aggregate Agents. [Service Agent history and ownership](https://github.com/morgs32/zerospin/blob/79c1824b1a0353f770211851c0bfe1cc54d0ba46/packages/system-worker/src/ServiceAgentVersionChain/README.md#L3-L29), [existing Service stream interface](../../packages/system-worker/src/ServiceAgentVersionChain/ServiceAgentVersionChain.ts#L30-L105), [Service admission](../../packages/system-worker/src/ServiceChain/ServiceChain.ts#L331).

## Design consequences

**Shared authoring.** Proposed `makeAggregateAgentNodeDefinition` returns `IAggregateAgentNodeDefinition`, references the canonical agent release once and declares per-row state, initialization, decisions, retry policy and delay policy. This pure definition is executable by both `AggregateAgentNode` and `AggregateAgentBackendNode`; it contains no browser timers, Durable Object storage, alarm calls or host service layer. The behavior receives the selected row, the shared committed selected graph, current behavior state and explicit decision inputs such as time/completion observations. It returns state transitions, permitted command intentions and scheduling decisions for its host to enact. The constructor, type and behavior shape are proposals; current `makeAggregateAgentRelease` has no behavior fields. Release owns visibility/contracts, definition owns behavior, instance creation/configuration chooses the host, and the host owns storage/scheduling. [Naming recommendation and evidence](aggregate-agent-definition-naming.md).

**Host choice.** Configuration or instantiation selects exactly one host for the containing logical Node instance, covering all of its per-row behavior instances. An Agent Session instantiates the shared Node definition in `AggregateAgentNode`; a backend registration instantiates that same definition in `AggregateAgentBackendNode`. Do not enable both for the same logical Node instance. A browser-hosted Node explicitly designates one executing browser lifetime; two tabs are not automatically fenced by this proposal. This is an explicit placement choice, not a global exclusion guarantee, automatic lease, cross-host exclusion protocol or handover system. Each host uses its own producer identity, command submission state and execution dependencies. The exact agent version comes from the shared Node definition's canonical release; no additional globally active-version selector is required by this design.

**Equal behavior semantics, different persistence.** Both hosts apply the same initialization, row-change, owned-completion, retry and due-time decision rules. The browser host keeps current behavior state and scheduled timers for its transient Node lifetime. The Backend Node persists current behavior state and deadlines, restores them after reconstruction and schedules its own alarm. A browser disposal ends its timers and behavior runtime; a later browser instance does not inherit Backend Node state or durable producer progress. Direct external side effects remain outside the pure behavior and are expressed through the permitted commands and their existing execution adapters.

Browser behavior reads the authoritative selected baseline, rather than its derived optimistic view. Commit behavior state changes and originating command-input staging together in one local transaction, so rerunning a decision cannot create a second invocation after only half its local state was recorded. Browser timers are fenced to their owning Node lifetime and behavior revision; a disposed or superseded callback cannot stage another command. These are proposed behavior-host requirements, not an assertion that current `AggregateAgentNode` already runs autonomous behavior.

**Current state, not retained execution history.** The Backend Node may persist its selected resource replica, materialization checkpoint, current behavior state, current waiting-command identity and complete pending command-admission deliveries. It must not become another retained command/execution/audit-history owner. Delete dedicated delivery rows after durable admission acknowledgement; any state still waiting for execution has a distinct current responsibility. Terminal behavior state may establish the current workflow state, but an append-only record of all prior attempts would be history and needs a separate owner. [Ownership rule](../../AGENTS.md), [local lifecycle guidance](../patterns/system-worker/repo-lifecycle.md).

**Delay.** The shared definition expresses due times and row/revision revalidation. The browser host implements them using its transient state and timers; the Backend Node persists the due time in current behavior state and uses its alarm. Selection loss or a newer behavior revision must make stale delayed work harmless on either host. The Backend Node cannot rely on `Effect.sleep`, closures or an in-memory retry schedule to survive reconstruction. Durable deadline scheduling remains a proposed requirement, not functionality supplied by the current registry.

Before deciding due work, catch up through a captured published Agent Chain tip if that is the selected freshness policy. That only establishes published-view progress, not the canonical Aggregate execution tip; the command must still enforce authoritative guards during canonical execution. Define this explicitly rather than promising a globally current selected graph at a deadline.

**One scheduler within the Backend Node.** Give the Backend Node one alarm registry coordinating all of its named deadlines, including delivery recovery and authored behavior delays. Schedule their earliest durable deadline. Extend or inject scheduling through the existing physical-owner factory; do not run an independent `setAlarm` owner beside the existing `recoveryRegistry`, whose final `release()` can delete its alarm. Preserve a recovery wake before committing a newly scheduled action, then reconcile from durable state; a crash between state commit and scheduling must not strand the action. [Current deletion behavior](../../packages/system-worker/src/makeRecoveryRegistry/makeRecoveryRegistry.ts#L27-L50), [factory ownership](../../packages/system-worker/src/makeMigratableDORepo/makeMigratableDORepo.ts#L258-L268).

Cloudflare provides one alarm per Durable Object and at-least-once alarm execution. Its automatic retry is finite, with up to six retries; it cannot replace an application retry policy. Constructor code runs before alarm dispatch and must not overwrite an existing scheduled alarm. Keep due work durable, make alarm processing idempotent and reconcile/rearm remaining work before returning. [Cloudflare alarm API](https://developers.cloudflare.com/durable-objects/api/alarms/), [Durable Object lifecycle](https://developers.cloudflare.com/durable-objects/api/base/).

**Retry categories.** On either host, an uncertain admission retries the same frozen command. A privately observed command refusal can produce a new command only under the shared authored retry policy; redelivering its retained original cannot convert it into a successful execution. Transport/recovery errors must not silently become domain failures. The browser host retains current policy state and deadlines within its lifetime; the Backend Node persists the state required to resume the same policy after reconstruction. Success and refusal observed through agent history remain separate from a canonical full `outcome`.

**Enrollment.** A backend host registration references the shared Node definition and establishes which Aggregate instances durably enroll Backend Nodes; a browser host starts through Agent Session instantiation. Merely deploying a class or declaring an agent does not activate every corresponding Durable Object. Reconstructing an enrolled Backend Node must restore its stream position, per-row behavior state and earliest deadline before running due work. Registrations and browser instantiation must honor the explicit single-host choice. [Current agent registry normalization](../../packages/core/src/system/make/makeSystem/decodeSystemProps/decodeSystemProps.ts#L9-L49), [current factory activation](../../packages/system-worker/src/makeMigratableDORepo/makeMigratableDORepo.ts#L281-L329).

The proposed startup path adds lazy `initializeAggregateAgentBackends` recovery to `AggregateChain`. Its activation arms that operation's recovery hold and returns; it must not await Backend Node initialization under its constructor activation gate, because Backend Node bootstrap may call back into that Aggregate's source graph. The recovery operation starts the configured Backend Nodes independently of stream length, then releases its hold after their initialized acknowledgement. Thus an Aggregate at position zero can start automation without waiting for a first command or a Studio connection. This extends the existing activation-owned registration/recovery seams; the named operation is new. [Aggregate activation](../../packages/system-worker/src/AggregateChain/onDOActivation/onDOActivation.ts#L9-L40), [activation gate](../../packages/system-worker/src/makeMigratableDORepo/makeMigratableDORepo.ts#L281-L329).

For a newly enabled backend on already registered but idle Aggregate instances, extend `SystemRepo.initialize`'s existing recovery path to scan the registered Aggregate catalog and initialize the configured Backend Nodes. Source activation alone cannot cover owners that remain idle after configuration changes. Catalog scanning uses explicitly backend-hosted Node definitions and their exact canonical agent releases; it does not enable every registered agent version or browser-hosted behavior. [Existing System initialization](../../packages/system-worker/src/SystemRepo/initialize/initialize.ts).

**Lifecycle switching.** Each shared Node definition pins its exact canonical agent release. Switching a running logical Node instance between browser and backend hosts, transferring producer progress, or handing durable state across agent versions is outside this proposal. No implicit state transfer or automatic handover follows from the versioned registry. A future switching request must establish its concrete lifecycle semantics before adding coordination. [Current versioned registry](../../packages/core/src/system/types.ts#L229-L237), [current registry validation](../../packages/core/src/system/make/makeSystem/validateAgentReleases.ts#L20-L37).

## Remaining design choices

1. Does initial bootstrap reconcile current selected state, or must behavior observe every historical transition? The chosen starting checkpoint must state that difference for either host.
2. Which privately observed refusals permit a new business attempt, and what shared retry/backoff policy should authors express?

The settled architecture is one shared pure Node definition, one explicit browser or backend host for each containing logical Node instance, and per-row behavior instances inside that host. The Backend Node is a separate durable stream consumer; these details do not reopen placement in `AggregateAgentVersionRepo`, introduce per-row host routing or imply a cross-host handover protocol.
