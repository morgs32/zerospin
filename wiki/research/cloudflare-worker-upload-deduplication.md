# Skipping unchanged Cloudflare Worker uploads

**Date** 2026-11-21

Zerospin could build each mutable Worker once, hash its modules and effective version configuration, and compare that digest with a fingerprint recorded on the version currently serving. This has precedent in Cloudflare infrastructure tooling. The sources reviewed establish the technique and related workflows but provide no prevalence data for whole-Worker fingerprints. [Cloudflare Terraform guidance](https://developers.cloudflare.com/workers/platform/infrastructure-as-code/#module-content) · [Wrangler version commands](https://developers.cloudflare.com/workers/wrangler/commands/workers/#versions)

## What Cloudflare does

- A version captures bundled code, assets, bindings, and compatibility settings. Cloudflare documents that each code upload creates a version. `wrangler versions upload` creates it separately from the deployment that assigns traffic. In Wrangler's implementation, the normal upload path sends the multipart payload to the versions API. Its command surface exposes dry-run and bundling controls without an upload-if-different option. [Versions and deployments](https://developers.cloudflare.com/workers/versions-and-deployments/#versions) · [Wrangler upload options](https://developers.cloudflare.com/workers/wrangler/commands/workers/#versions-upload) · [Wrangler upload implementation](https://github.com/cloudflare/workers-sdk/blob/main/packages/deploy-helpers/src/deploy/versions-upload.ts#L299-L356)
- Read the serving deployment first, then query its `version_id` with `wrangler versions view <id> --json`. Wrangler writes `--tag` and `--message` as version annotations and returns them on that exact version. The version API's `resources.script.etag` describes hashed script content. The documented schema also exposes bindings and runtime settings separately and offers no digest covering the effective version inputs. The beta API can return version modules and source maps for inspection. [Deployment API](https://developers.cloudflare.com/api/resources/workers/subresources/scripts/subresources/deployments/methods/get/) · [Upload annotations](https://github.com/cloudflare/workers-sdk/blob/main/packages/deploy-helpers/src/deploy/versions-upload.ts#L268-L272) · [Wrangler version readback](https://github.com/cloudflare/workers-sdk/blob/main/packages/wrangler/src/versions/view.ts#L62-L74) · [Version API](https://developers.cloudflare.com/api/resources/workers/subresources/scripts/subresources/versions/methods/get/) · [Beta version API](https://developers.cloudflare.com/api/typescript/resources/workers/subresources/beta/subresources/workers/subresources/versions/methods/get/)
- Wrangler supports `versions upload --dry-run --outdir <dir>` to materialize the bundle and `--no-bundle` to use prebuilt modules with a suitable config. Verify that the resulting upload preserves the exact module names and bytes with Zerospin's generated config. Wrangler's `--outfile` writes serialized multipart form data, whose framing and upload-time metadata make it a poor fingerprint input. Its dry-run path also skips some remote work such as asset synchronization. The newer `cf` CLI has an explicit artifact handoff with `cf build` and `cf workers versions create --prebuilt`. That command still creates a version when invoked. [Wrangler flags](https://developers.cloudflare.com/workers/wrangler/commands/workers/#versions-upload) · [Dry-run asset behavior](https://github.com/cloudflare/workers-sdk/blob/main/packages/deploy-helpers/src/deploy/versions-upload.ts#L213-L218) · [Multipart output](https://github.com/cloudflare/workers-sdk/blob/main/packages/deploy-helpers/src/deploy/versions-upload.ts#L464-L474) · [Cloudflare CLI prebuilt upload](https://developers.cloudflare.com/cf/projects/#upload-a-version)

A local probe with Wrangler 4.152.0 ran `versions upload --dry-run` twice against the same small Worker with `--outfile`, `--outdir` and a dummy `--secrets-file`. The raw output hashes differed. Replacing the generated multipart boundary yielded equal hashes for this probe, and both output files contained the dummy secret. The probe made no Cloudflare writes. [Wrangler multipart serialization](https://github.com/cloudflare/workers-sdk/blob/main/packages/deploy-helpers/src/deploy/versions-upload.ts#L464-L474)

## Precedents and adoption

- Cloudflare's Terraform provider tracks each module attached to `cloudflare_worker_version` using `content_sha256`. Cloudflare documents that switching the input representation with identical content updates Terraform state without an API update. This is the closest first-party precedent for digest-based change detection. [Terraform Worker version module content](https://developers.cloudflare.com/workers/platform/infrastructure-as-code/#module-content)
- Cloudflare's standard GitHub Actions example invokes Wrangler on pushes to `main`. Workers Builds exposes per-Worker watch paths as its monorepo filter. The g1t project publishes a more selective variant that reads each live Worker's commit from its version annotation and deploys units affected by the Git diff. These compare repository inputs. [Cloudflare GitHub Actions](https://developers.cloudflare.com/workers/ci-cd/external-cicd/github-actions/) · [Workers Builds watch paths](https://developers.cloudflare.com/workers/ci-cd/builds/build-watch-paths/) · [g1t deployment guide](https://docs.g1t.sh/guides/deploy-to-cloudflare/)
- Cloudflare's static asset protocol deduplicates file transfers by hash. After Cloudflare reports that all files are already present, the client can proceed directly to uploading the Worker script or version. [Static asset upload protocol](https://developers.cloudflare.com/workers/static-assets/direct-upload/#upload-manifest)

## How it could fit Zerospin

`prepareSystemWorkerCandidate` writes the SystemSpec and pinned owner releases into the `SystemWorker` build and supplies owner release service bindings to the Agent Worker. A new owner release can therefore affect both mutable Workers with identical library code. Accepted owner release pins continue to identify their exact executable. [Candidate preparation](../../packages/cli/src/deploy/utils/prepareSystemWorkerCandidate.ts#L77-L104) · [Owner pin validation](../../packages/system-worker/src/SystemRepo/acceptSystemSpec/acceptSystemSpecTx.ts#L56-L91)

1. After serving preflight, build each desired Worker once. Hash the entrypoint and additional modules by name, type and bytes, along with effective version configuration such as compatibility settings, bindings, variables, asset manifests and generated SystemSpec with owner release pins. Normalize only incidental inputs such as temporary local paths, multipart framing and the per-run tag. Treat secrets from `--secrets-file` as version inputs using a private keyed digest or an authoritative secret revision. If the effective secrets or inherited settings cannot be established, run the ordinary upload flow. Deployment-level settings such as routes and cron require their own checks. [Current serving preflight](../../packages/cli/src/deploy/utils/verifyServingSystem.ts#L60-L113) · [Cloudflare version inputs](https://developers.cloudflare.com/workers/versions-and-deployments/#versions) · [Wrangler secret and variable behavior](https://developers.cloudflare.com/workers/wrangler/commands/workers/#versions-upload) · [Separate trigger updates](https://developers.cloudflare.com/cf/projects/#deploy-triggers)
2. Read the fingerprint on the verified serving Cloudflare version. Store a format-versioned fingerprint as a Worker version message on upload and keep Zerospin's unique run tag for recovery. Reuse the serving version when the fingerprint equals the desired fingerprint and the deployment and required bindings still verify. A missing fingerprint or one whose provenance cannot be established takes the regular upload path. Version messages are uploader-supplied metadata, so verify how out-of-band version creation such as secret rotation handles them before treating a match as proof. Check the serving deployment again before relying on reuse. [Worker version annotations](https://developers.cloudflare.com/workers/versions-and-deployments/#versions) · [Existing annotation reader](../../packages/cli/src/deploy/utils/readWorkerVersionBindings.ts#L23-L53) · [Run tag recovery](../../packages/cli/src/deploy/utils/prepareOwnerReleaseBindings.ts#L105-L131) · [Serving deployment recheck](../../packages/cli/src/deploy/utils/verifyServingSystem.ts#L97-L116)
3. Make reuse explicit in the deploy orchestration. `deployWranglerFn` currently stages and promotes a new `SystemWorker`, waits for `SystemRepo` to attest that version, then activates the Agent Worker and initializes the System. Its traffic recovery record expects different incumbent and candidate version IDs. An Agent-only change would need to proceed with the verified serving `SystemWorker`; a SystemWorker-only change would keep the serving Agent Worker after verifying its bindings. Preserve bootstrap, pending deployment recovery, and readiness checks. [Current orchestration](../../packages/cli/src/deploy/deployWranglerFn.ts#L163-L218) · [Traffic recovery record](../../packages/cli/src/deploy/utils/systemTrafficRecord.ts#L28-L50) · [Existing concurrency research](first-deploy-concurrency.md)

Build reproducibility and prebuilt upload equivalence for Zerospin's generated Wrangler projects remain unverified. Relevant cases include an identical repeat run, changes confined to each Worker, a secret rotation, and a staged upload that never received traffic.
