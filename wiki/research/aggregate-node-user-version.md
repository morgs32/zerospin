# AggregateNode `user_version` stamp

**Date:** 2026-10-26  
**Scope:** Current Zerospin source, plus SQLite's own description of `PRAGMA user_version`. This note records what the AggregateNode header integer does and what deleting its read-check and its write would change. It does not propose a replacement.

## Findings from primary sources

1. **The stamp is SQLite's application header integer, not a table column.** `PRAGMA user_version` gets or sets the user-version integer at offset 60 in the database header. SQLite does not use that integer. The file format defines it as the 4-byte big-endian field at that offset, distinct from `sqlite_schema` rows. The current pragma page does not state an initial number. AggregateNode treats a nonempty file as unacceptable unless the first cell of `PRAGMA user_version` is the number 21, so a missing cell fails the same comparison (`version?.[0] !== 21`). The only in-repo reader that substitutes 0 for a missing cell is the native session replica, and that reader is a different file.
   [SQLite pragma `user_version`](https://www.sqlite.org/pragma.html#pragma_user_version),
   [SQLite file format, header offset 60](https://www.sqlite.org/fileformat.html#the_database_header),
   [AggregateNode read](../../packages/core/src/AggregateNode/AggregateNode.ts#L180-L192),
   [native replica fallback](../../packages/native/src/openPersistentAggregateReplica.ts#L66-L73).

2. **`AggregateNode.initialize` reads the header before it reads any row, and a nonempty file whose header is not 21 never reaches metadata.** Inside the SQL gate's immediate transaction the order is: read `PRAGMA user_version`; list user tables from `sqlite_master` (`type = 'table'`, name not like `sqlite_%`); compute `retainedSessionKey` (`standalone.storageKey`, otherwise `sessionKey(definition.identity)`); if that list is nonempty, require the header cell to be 21 or throw `node-storage-reset-required`; then `readAggregateNodeMetadata`; then compare `aggregateId`; then, unless a replacement baseline was passed, compare `sessionKey` and maybe require a checkpoint; return false. Only a missing or replacement create continues: optional `DROP TABLE`, `CREATE TABLE` for `nodeMetadata`, `commands`, and compiled resource tables, insert of one metadata row (including `dispositionChainHash: null`), then `PRAGMA user_version = 21`, then the replacement baseline. A nonempty file whose header is not 21 throws on that inequality before metadata, before the `aggregateId` and `sessionKey` comparisons, and before any drop or create. The replacement argument does not skip the inequality: standalone replacement of a nonempty file with another header value also throws `node-storage-reset-required` and does not drop inside `initialize`. An empty user-table list skips the inequality entirely, including when the header is not 21, and the create path then writes 21. The gate rolls the transaction back on that throw. Because the error is a `ZerospinError`, the gate does not record it as `persistenceFailure`.
   [Initialize order](../../packages/core/src/AggregateNode/AggregateNode.ts#L168-L261),
   [transaction rollback](../../packages/core/src/Node/makeNodeSqlGate.ts#L34-L49),
   [typed errors skip persistenceFailure](../../packages/core/src/Node/makeNodeSqlGate.ts#L25-L30).
   Historical intent only: archive plan 143 describes this order (version before metadata, including an explicit replacement). The current method matches that description; the plan is not what the running check is.

3. **Deleting the inequality and the `user_version = 21` write leaves the rest of that order in place.** The header read would still run and then be unused. A nonempty file would continue into `readAggregateNodeMetadata` and the `aggregateId` / `sessionKey` / checkpoint checks whatever the header integer is. A matching reopen would still return false and would not execute `CREATE TABLE`. A standalone replacement whose metadata row is readable and whose `aggregateId` matches would still drop user tables, create the current tables, and insert metadata, without writing the header. An empty user-table list would still create and insert; the header would stay at whatever value the file already had, because nothing else in AggregateNode writes it. Connected `initialize` still refuses a replacement argument with `standalone-storage-reset-required` before the transaction.
   [Same initialize method](../../packages/core/src/AggregateNode/AggregateNode.ts#L172-L256).

4. **The header check does not inspect columns. Layout differences are accepted or rejected by later SQL, and only when the header is already 21 today.** Current `nodeMetadata` columns are `nodeId`, `aggregateId`, `sessionKey`, `admittedThroughPushIndex`, `aggregateIndex`, `dispositionChainHash`, and `pushPaused`. `commands` adds the command journal columns, including JSON-mode `claims`, `stagingOutcome`, `failure`, and `exposedDelta`. Resource tables are compiled from `lock.models`: `makeNodeResourceTables` omits `modelName` and `version`, and `compileSqliteTableDefinition` emits `CREATE TABLE` plus index statements with no `IF NOT EXISTS`. `initialize` runs that SQL only on the create path. `readAggregateNodeMetadata` is `select().from(nodeMetadata)` limited to two rows. The installed `drizzle-orm` SQLite dialect builds that select as a list of column identifiers, not `SELECT *`. This repository does not catch a failed select, so the failure is the driver's rejection of that statement. It is not `node-storage-reset-required`. `node-metadata-missing` and `node-metadata-ambiguous` are thrown only after a select returns zero rows or more than one. `node-execution-checkpoint-invalid` is thrown only after a row is in hand and the `aggregateIndex` / `dispositionChainHash` pair is incomplete or ill-formed. A driver rejection is not a `ZerospinError`, so the SQL gate records it as `persistenceFailure` and rethrows it. `initialize` does not read `commands` or resource tables. Those named selects happen later, for example `readAuthoritativeResources` during snapshot.
   [Metadata columns](../../packages/core/src/AggregateNode/aggregateNodeTables.ts#L17-L57),
   [resource compilation](../../packages/core/src/Node/makeNodeResourceTables.ts#L7-L42),
   [encoded-table columns](../../packages/shapes/src/primitiveMaps.ts#L294-L307),
   [CREATE TABLE text](../../packages/core/src/drizzle/definition/compileSqliteTableDefinition.ts#L70-L76),
   [metadata select](../../packages/core/src/AggregateNode/readAggregateNodeMetadata.ts#L7-L24),
   [later resource select](../../packages/core/src/AggregateNode/AggregateNode.ts#L357-L366).

   Three files:
   - **(a) Nonempty file whose `nodeMetadata` columns are the current names.** Today, header 21 continues into the metadata and identity checks and returns false when they pass. Any other header throws `node-storage-reset-required` and does not read the row. Without the chip, both headers take the metadata path. A readable row with the same `aggregateId` and `sessionKey` is a silent reopen. Extra physical columns that the select does not name are not read and are not rejected here.
   - **(b) Nonempty file whose physical layout is not those columns.** Today, a header other than 21 still throws `node-storage-reset-required` before the select, so the layout is never examined. Header 21 already falls through to the select. Without the chip, every such file falls through. A missing or renamed `nodeMetadata` column fails as the driver's rejection of the named select, recorded as `persistenceFailure`, not as `node-storage-reset-required`. A `nodeMetadata` row that still has the declared names, with a different `commands` or resource table, passes `initialize` when identity matches; the later select is the first statement that names the drifted columns. `initialize` never compares `sqlite_master` SQL with `compileSqliteTableDefinition`.
   - **(c) No user tables.** Today and without the chip, the inequality is skipped. Create and the metadata insert run. Today the create ends by writing header 21. Without that write, the header is left unchanged. No AggregateNode reader consults it afterward.

5. **AggregateNode throws `node-storage-reset-required` in one other place, and the browser recovery paths do not all depend on the header.** On a nonempty file that already passed the header check, a standalone `sessionKey` mismatch throws `node-storage-reset-required`. The same mismatch on a connected node throws `node-storage-identity-mismatch`. An `aggregateId` mismatch throws `standalone-storage-identity-mismatch` or `node-storage-identity-mismatch`. The shared default message for `node-storage-reset-required` says the schema is incompatible; the standalone `sessionKey` throw uses that same code for a declaration mismatch.
   [Standalone sessionKey throw](../../packages/core/src/AggregateNode/AggregateNode.ts#L201-L208),
   [default message](../../packages/error/src/defaultErrorMessages.ts#L616-L619).

   Connected aggregate recovery during `initialize` special-cases only `node-storage-reset-required`. For a connected `AggregateNode` (no `standalone` argument), that code comes only from the header check. The worker then requires an online admission, one attempt, and `shouldResetConnectedNode`: environment `dev`, not yet attempted, and either `node-checkpoint-conflict` or `node-storage-reset-required`. Only then does it call `resetNodeStorage`, `initialize(true)`, and `initializeBaseline`. Production, a failed DEV proof, or a second attempt rethrows and the outer catch closes the owner. `node-storage-identity-mismatch` never enters that reset. The later synchronization recovery also calls `shouldResetConnectedNode`, but the successful branch uses `resetConnectedBaseline` for a checkpoint conflict; it does not depend on the header integer.
   [Connected initialize catch](../../packages/browser/src/AggregateNode/makeAggregateWorkerRuntime.ts#L323-L367),
   [DEV predicate](../../packages/browser/src/Node/shouldResetConnectedNode.ts#L5-L18),
   [checkpoint recovery](../../packages/browser/src/AggregateNode/makeAggregateWorkerRuntime.ts#L476-L498),
   [owner close on other errors](../../packages/browser/src/AggregateNode/makeAggregateWorkerRuntime.ts#L550-L557).

   Standalone recovery catches the same code with no DEV predicate: `resetNodeStorage`, then `initialize` again with the same replacement. That catch covers both the header mismatch and a standalone `sessionKey` mismatch. `attach` only allowlists the code so a propagated error can cross the worker boundary; it does not decide the reset.
   [Standalone catch](../../packages/browser/src/StandaloneNode/makeStandaloneWorkerRuntime.ts#L229-L249),
   [attach allowlist](../../packages/browser/src/StandaloneNode/attach/attach.ts#L33-L45).

   Native owner startup calls the same `AggregateNode.initialize()` and does not catch `node-storage-reset-required`. A header mismatch on that Node file fails there with no browser reset.
   [Native node initialize](../../packages/native/src/openAggregateNativeNodeOwner.ts#L183-L183).

   Removing the chip removes the header producer only. Standalone `sessionKey` mismatch still throws `node-storage-reset-required`, and standalone recovery still resets for that throw. Connected aggregate `initialize` no longer produces the code, so its DEV `resetNodeStorage` path no longer runs for a header mismatch. A driver rejection from a drifted select is not that code, so neither connected nor standalone recovery resets it. Checkpoint recovery and `shouldResetConnectedNode`'s checkpoint arm stay. The connected attachment allowlist still names the code, but connected `initialize` would no longer throw it.
   [Attachment allowlist](../../packages/browser/src/AggregateNode/makeAggregateWorkerRuntime.ts#L46-L70).

6. **ServiceNode and the native session replica keep their own stamps. The integer 21 is not shared with the replica.** `ServiceNode.initialize` repeats the same shape with its own literal: nonempty user tables whose header cell is not 21 throw `node-storage-reset-required`; create writes `PRAGMA user_version = 21`. Its metadata identity check is `sessionKey` only, and a mismatch is `node-storage-identity-mismatch`, never the reset code. There is no shared constant with AggregateNode. The connected service worker has its own copy of the DEV reset catch. Deleting the AggregateNode chip does not change those statements. The native session replica reads the header of a different file, rejects a nonempty file whose version is not 10 with `native-session-storage-reset-required`, and writes `PRAGMA user_version = 10` only when that file has no user tables. It also rejects a nonempty file with no decodable metadata row using the same native code. That file is not the AggregateNode database.
   [ServiceNode stamp](../../packages/core/src/ServiceNode/ServiceNode.ts#L163-L214),
   [service recovery catch](../../packages/browser/src/ServiceNode/makeServiceWorkerRuntime.ts#L230-L258),
   [replica stamp](../../packages/native/src/openPersistentAggregateReplica.ts#L66-L103).

7. **`sessionKey` proves a hashed declaration identity. It does not prove the physical SQL layout or a JSON-column meaning that keeps the same columns.** `sessionKey` is `hashNodeValue`: SHA-256 of a canonical JSON encoding of the value it is given. Connected AggregateNode hashes `definition.identity`. That identity includes `definitionHash`, which is `hashNodeValue(lock)`. The lock includes model `propertiesShape` and indexes, and contract `payloadShape` / result / failure / operations schemas. A change to those hashed fields changes the connected `sessionKey`. Standalone storage does not hash that identity; it stores `hashNodeValue({ key, aggregateId, lock })`, so a lock change fails the standalone comparison directly. Either mismatch is a declaration mismatch. Neither hash reads `sqlite_master`, column names, or stored command JSON. A framework column change on `nodeMetadata` or `commands` that leaves the lock and identity alone keeps the same `sessionKey`. A JSON interpretation change that leaves both the column names and the hashed lock alone keeps it too. On a file already stamped 21, the header check also accepts both of those files. Connected `sessionKey` mismatch remains `node-storage-identity-mismatch` and is not a DEV reset. Standalone `sessionKey` mismatch remains `node-storage-reset-required` and still resets.
   [sessionKey](../../packages/core/src/Node/sessionKey.ts#L16-L28),
   [identity and definitionHash](../../packages/core/src/AggregateNode/types.ts#L14-L30),
   [lock contents](../../packages/core/src/aggregateSession/AggregateSessionLockSchema.ts#L8-L56),
   [connected definition](../../packages/browser/src/AggregateNode/makeAggregateNodeDefinition.ts#L21-L29),

8. **No test, profile, or profile spec asserts `user_version` or `node-storage-reset-required`.** A search of `*.spec.ts`, `*.profiles.ts`, `*.profiles.spec.ts`, `*.test.ts`, and `*.snap` found neither string. Docs that do assert the number or the reset code disagree with each other. Code writes 21. 9. **`resetNodeStorage` still writes `user_version = 0` in the same transaction that drops every user table.** The write sits after the drops and before `COMMIT`. AggregateNode and ServiceNode consult the header only when the user-table list is nonempty. After this transaction commits, that list is empty, so the next `initialize` takes the create path and does not use the 0 to decide. Today's AggregateNode create then overwrites the header with 21. ServiceNode's create does the same on a service file. If AggregateNode no longer reads or writes the header, the 0 left by recovery is unused by AggregateNode on the following create, and a fresh AggregateNode file never replaces it. The statement still runs for aggregate, service, and standalone recovery because they share this function. It still does not decide ServiceNode's next create either, as long as the drop committed; ServiceNode's own `PRAGMA user_version = 21` remains the write that stamps a service file. A reset that rolls back leaves both the tables and the previous header.
   [reset write](../../packages/browser/src/Node/resetNodeStorage.ts#L17-L27),
   [AggregateNode consults the header only when tables exist](../../packages/core/src/AggregateNode/AggregateNode.ts#L189-L192),
   [ServiceNode does the same](../../packages/core/src/ServiceNode/ServiceNode.ts#L172-L175).

## If the chip is removed

Observable outcomes, each tied to the finding that owns it:

- A nonempty AggregateNode file whose `nodeMetadata` select succeeds is reopened or replaced according to `aggregateId`, `sessionKey`, and checkpoint rules, for every header integer. Header 21 and any other integer behave the same. Finding 3 and case (a) in finding 4.
- A nonempty file whose `nodeMetadata` columns are missing or renamed fails in the driver during that select. The SQL gate records `persistenceFailure`. Connected and standalone recovery do not reset it, because the error is not `node-storage-reset-required`. Today that reset happens only when the header is not 21; a file already stamped 21 already fails this way. Findings 4 and 5.
- A file whose `nodeMetadata` names match, but whose `commands` or resource tables do not, can pass `initialize` and fail on a later named select such as snapshot's resource read. Finding 4.
- An empty file is still created and given one metadata row. Its header is not set to 21. Finding 3 and case (c) in finding 4.
- Connected browser DEV recovery no longer discards an AggregateNode file because of the header. Production already refused that reset. Checkpoint conflict recovery is unchanged. Findings 5.
- Standalone recovery still discards storage when the stored key does not match `hashNodeValue({ key, aggregateId, lock })`. It no longer discards storage merely because the header is not 21. Finding 5 and finding 7.
- Native AggregateNode files use the same `initialize`. They lose the header refusal and gain no browser reset. Finding 5.
- ServiceNode still requires header 21 and still writes 21. The native session replica still requires 10 and still writes 10. Those integers are separate literals; 21 is not the replica's number. Finding 6.
- `resetNodeStorage` still sets the header to 0 while dropping user tables. AggregateNode would no longer read that 0, and its create would no longer replace it with 21. ServiceNode's own write of 21 is unchanged. Finding 9.
- No current test or profile spec locks the number 21. Docs that say schema 21 and docs that say schema 20 would both be stale relative to an AggregateNode that no longer reads the header. Finding 8.
