# Invitation ownership and acceptance in Red Rope

Date: 2026-10-22. Research only; current working-tree source inspected, with no provider calls, runtime verification, production edits, or storage changes.

## Finding

**Red Rope currently implements an email allowlist that produces a permanent Member access grant. It does not implement invitation consumption.** `Invitation` has only a unique `emailAddress`; the active membership continuation writes `Member.invitationAcceptedAt` without changing an Invitation row. [Invitation](/Users/morgs32/GitHub/redropeparking/apps/zerospin/src/models/Invitation.ts:7), [membership continuation](/Users/morgs32/GitHub/redropeparking/apps/zerospin/src/contracts/asyncResolveMembership.ts:193)

Plan 255's private typed read preserves that existing observation-and-grant behavior. It is a mechanical replacement for `hasInvitation`, not evidence that an external yes/no lookup is the right domain boundary for invitations. Removing named service queries remains a separate, settled change. [Plan 255 migration](/Users/morgs32/GitHub/zerospin/wiki/archive/plans/255-plan-typed-system-service-reads.md:166)

## What the lookup does and does not prove

The affirmative result proves that one observed verified primary email matched an Invitation row at the lookup's execution. The continuation's revision check prevents an older resolution from overwriting a newer resolution; it does not make the Invitation read and Member grant one transaction. A new invitation created after a negative observation does not alter that observation, and the creation command records no membership-resolution work. Conversely, hypothetical later removal of the allowlist row would not retract an existing Member grant. Those follow directly from the two owners and the continuation's permanent-grant rule. [creation](/Users/morgs32/GitHub/redropeparking/apps/zerospin/src/contracts/createInvitation.ts:51), [read](/Users/morgs32/GitHub/redropeparking/apps/zerospin/src/contracts/hasInvitation.ts:33), [continuation](/Users/morgs32/GitHub/redropeparking/apps/zerospin/src/contracts/asyncResolveMembership.ts:193)

The waitlist notification and membership resolution take independent observations. If an Invitation is added between those observations, a Slack announcement and an accepted Member can coexist. This is an advisory notification race, not proof that the Member grant is invalid. It matters if product meaning requires “waitlisted” to describe a committed enrollment decision rather than “not invited when this notification request checked.” [separate recorded operations](/Users/morgs32/GitHub/redropeparking/apps/zerospin/src/contracts/resolveMembershipAdapter.ts:77), [independent notification lookup](/Users/morgs32/GitHub/redropeparking/apps/zerospin/src/contracts/announceWaitlistedMember.ts:95)

Clerk identity does not supply Red Rope's domain grant. Clerk separately offers application invitations for account onboarding, access modes restricting sign-up, and Organization invitations that establish Organization membership. Those are distinct product authorities; this Red Rope path checks a Clerk user's verified email and writes its own Member grant, without reading a Clerk Organization membership. Replacing it with Clerk invitations would change enrollment ownership and should follow a product decision, not a query API migration. [Clerk application invitations](https://clerk.com/docs/guides/users/inviting), [Clerk access modes](https://clerk.com/docs/guides/secure/restricting-access), [Clerk Organization invitations](https://clerk.com/docs/guides/organizations/add-members/invitations), [Red Rope evidence/grant](/Users/morgs32/GitHub/redropeparking/apps/zerospin/src/contracts/asyncResolveMembership.ts:68)

## Two ownership choices worth discussing

**1. Keep Member authority in its existing shared `acct_1` aggregate and consider Invitation there.** Current `admin` groups Invitation with Partner and PartnerIntakeSubmission, while `member` owns Member/Garage/Car/MembershipResolution. Both intake and user authentication resolve every user to `acct_1`; the current source does not demonstrate a requirement for independently partitioned invitation ownership. An admin aggregate actor could administer Invitation alongside Member. A command continuation could consume recorded Clerk email evidence, read current invitation eligibility, and grant Member access in the same owner transaction. This removes the cross-owner yes/no lookup without inventing consumable invitations. [current owners](/Users/morgs32/GitHub/redropeparking/apps/zerospin/src/admin/admin.ts:14), [member owner](/Users/morgs32/GitHub/redropeparking/apps/zerospin/src/member/member.ts:14), [shared aggregate](/Users/morgs32/GitHub/redropeparking/apps/zerospin/src/member/actors/intake/intakeActor.ts:35)

The supported interface can keep the public payload as an applicant's intent and omit Invitation from browser selections. The existing canonical aggregate adapter/continuation can check private owner rows, and canonical actor guards run against authoritative state inside the command savepoint. Keep Clerk verification as recorded external work and return verified-email evidence for that private check; a future trusted authentication claim could supply that evidence if deliberately designed. Never trust a client payload's assertion of a verified email. This is a proposed interface, not a claim that the current response retains email: today it retains `clerkUserId`, `invited` and `message`. [visibility and canonical guards](/Users/morgs32/GitHub/zerospin/packages/sdk/skills/zerospin-authorize-actors/SKILL.md:29), [adapter boundaries](/Users/morgs32/GitHub/zerospin/packages/sdk/skills/zerospin-external-work/SKILL.md:44), [current response and trusted derivation](/Users/morgs32/GitHub/redropeparking/apps/zerospin/src/contracts/asyncResolveMembership.ts:19)

Moving existing Invitation ownership requires a separate authorized storage/history adoption decision under the no-reset constraint; this report is not authorization for that move or a compatibility path. If the current owners must remain, Plan 255's typed private read remains a mechanical interim option preserving today's allowlist behavior. [cutover policy](/Users/morgs32/GitHub/zerospin/AGENTS.md:3), [current planned substitution](/Users/morgs32/GitHub/zerospin/wiki/archive/plans/255-plan-typed-system-service-reads.md:166)

Under this alternative, invitation eligibility and access grant serialize at the Member owner's command execution. Clerk email verification remains an external observation at an earlier time; co-location cannot make Clerk and Zerospin atomic. `AggregateVersionRepo.materializeCommandTx` evaluates/applies model operations and retains the complete output in one transaction. An interruption before commit leaves neither local mutation committed; after commit, recorded output governs recovery. [transaction](/Users/morgs32/GitHub/zerospin/packages/system-worker/src/AggregateVersionRepo/materializeCommandTx.ts:16), [execution/apply](/Users/morgs32/GitHub/zerospin/packages/system-worker/src/AggregateVersionRepo/utils/executeAggregateCommandTx.ts:38)

**2. Keep a genuinely independent enrollment owner.** If independent enrollment ownership is required, the authoritative operation belongs there: evaluate verified identity evidence against that owner's current rules, record the enrollment decision, and record an ordinary command delivering the Member access grant. Add a consumed/accepted state only if the invitation's agreed meaning requires one. `makeCommandOperation` fits this cross-owner mutation responsibility; it is not a request/response query and does not return destination execution success. [command descriptor constraints](/Users/morgs32/GitHub/zerospin/packages/core/src/contracts/makeCommandOperation.ts:48), [recorded delivery semantics](/Users/morgs32/GitHub/zerospin/packages/sdk/skills/zerospin-external-work/SKILL.md:59)

This alternative has two commits: enrollment decision plus pending command at the source, then Member grant at the destination. An interruption may leave enrollment decided while Member activation is pending; durable admission acknowledgement does not prove the Member command's successful `outcome`. Destination rejection cannot roll back the source decision. The UI should observe the relevant persisted decision/grant, and any guaranteed completion requirement must address this actual gap. A typed private read alone closes none of it. [delivery and refusal](/Users/morgs32/GitHub/zerospin/packages/sdk/skills/zerospin-external-work/SKILL.md:59)

In both choices, authentication and reads remain read-only; external requests supply retained evidence, and registered command execution or replay changes models. Provider requests can repeat after uncertain process loss, so their use does not establish exactly-once notification delivery. Typed System service reads remain useful for other existing facts; invitations need not justify that API. [parallel-model rule](/Users/morgs32/GitHub/zerospin/packages/sdk/skills/zerospin-parallel-models/SKILL.md:21), [request interruption](/Users/morgs32/GitHub/zerospin/packages/sdk/skills/zerospin-external-work/SKILL.md:77)

## Decision to settle before invitation implementation

Is the Invitation simply **email eligibility for a permanent Member grant**, with administration as another actor of that same domain owner; or does Red Rope need an **independently owned enrollment decision** that must be delivered to Member? Current code supports the first meaning and offers no demonstrated reason for the current admin/member data boundary. Prefer the co-located transaction unless an actual independent enrollment responsibility establishes the second.
