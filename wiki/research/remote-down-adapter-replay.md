## Proposed call for position 42

The stable `AggregateChain` for one `user` Aggregate instance has finalized position 42. The admitted command addressed `user@3` and has contract `checkout@2`. The `user@2` VersionRepo at head 41 binds `checkout@1`. If it already has a saved `user@2` evaluation at 42, it restores or reads that evaluation. If it has no saved evaluation, it needs the source input and the authored `checkout@2 → checkout@1` conversion before executing its own program.

```text
user@2 AggregateVersionRepo.replayCommand(delivered42)
  look up any evaluated user@2 command at 42
  if fresh parallel replay needs the unavailable down edge:
    await stable.prepareAggregateReplayInput(owner, 42, commandId, user@2)
      stable Worker reads exactly 42 from the Chain's finalized history
      stable selects user@3 from the retained admitted aggregateVersion
      await user@3 release Worker.prepareCheckoutReplayInput(finalizedInput, checkout@1)
        decode the frozen payload using the exact source declaration
        run checkout@2.down and validate checkout@1 input
      return verified input preparation bound to owner, 42, commandId and releases
  acquire user@2 execution permit and run materializeCommandTx
    read local head again and require next position or recover a committed duplicate
    validate and consume adapted input with the local checkout@1 declaration
    evaluate checkout@1 and commit model operations, outcome, outbox and head
```

## What Core runs synchronously today

Core processes replay rows in order inside an asynchronous delivery. `replayCommand` verifies identity via the Chain and searches for receiving-release output in the Repo publication outbox or VersionChain before entering its execution permit and `materializeCommandTx`. The transaction checks the owner, finalization and contiguous next position, restores saved receiving-release output when present, or executes the command. Missing saved output for the same originally addressed release fails. ## Retry and latency

Position 42 is already durable in the Chain's logical finalized history. If the adapter RPC times out, returns invalid data or loses its reply, the receiving Repo has no committed 42 and retries from its retained progress. If the Repo stops after the reply and before its commit, it can request the pure preparation again. If the Repo commits and its reply to fanout is lost, the durable head and saved evaluation recover 42 without evaluating it again. Local SQL arbitrates concurrent fresh attempts and rechecks the next position. Reuse that check after the remote wait and recover a duplicate from evaluated history. An adapter outbox would record work the history and cursor already describe. Existing original command delivery and publication outboxes continue to own their respective acknowledgements. Here “synchronous original finalization” means the Chain waits for the addressed VersionRepo’s committed result before acknowledging original delivery. The cross-Repo call already awaits an RPC. The Chain’s acknowledgement is a separate local transaction. Replay also already suppresses newly emitted external work and outgoing commands. ## When a conversion would need durable storage

If retirement or availability requirements say that an older release must
finish replay after the newer executable is gone, it needs either a surviving
source of the exact adapter or a retained result of conversion. In the second
case, key the result to the exact finalized input, receiving contract and
adapter identity. That record is input for future replay. The Chain's finalized
history and cursor still supply recovery for ordered replay. A separate outbox
has a purpose only if we choose an independently scheduled producer that must
deliver prepared conversions or perform another side effect. The on-demand

## Workerd prototype

The receiving `user@2` Repo calls `AggregateChain.prepareAggregateReplayAdapter` with the owner key, position, command ID, and receiving release before taking its execution permit or opening SQLite. The Chain uses the finalized replay page bounded to that position and checks its ID. It reads the target contract from the receiving release’s declaration and sends the frozen input and `finalizedAt` to the binding for the recorded source release. The source Worker runs the authored `checkout@2.down` without Repo bindings. On success, `user@2` validates the converted payload with `checkout@1`, rechecks its local head, and evaluates and commits synchronously. The adapter and local program see the original `finalizedAt`. The test delays the source Worker by five seconds to exceed the receiving Repo’s one-second deadline. The Chain bounds its own source call to three seconds. [Adapter Worker](https://github.com/morgs32/zerospin/blob/ade99772fafbd6be56d7a7208e9e68883f0b8413/packages/system-worker/tests/remote-down-adapter/sourceAdapter.ts) · [Timeout scenarios](https://github.com/morgs32/zerospin/blob/ade99772fafbd6be56d7a7208e9e68883f0b8413/packages/system-worker/tests/remote-down-adapter/remote-down-adapter.workerd.spec.ts)

- **Cold startup.** A timeout resets the starting Repo. The Chain's finalized entry survives, the replay acknowledgement stays at zero, and there is no receiving-release evaluation to publish. After the adapter recovers, a fresh Repo activation catches up and retains the original ID, position, contract version, payload, and finalization time.
- **Already admitted.** The older Repo needs to replay position 1 before finalizing its original at position 2. During the timeout, positions 2 and 3 stay pending, and the older Repo writes no model rows or materialization head. The existing Chain alarm resumes ordered delivery after recovery. Both commands finish at their original positions without resubmission or a new outbox.
- **Explicit refusal.** The source Worker encodes only the authored `DownAdapterRefused` sentinel as `Refused`. The receiving Repo takes its existing unsupported-outcome path, writes no model operations at that position, and materializes the next position. The original outcome remains intact. The Chain rejects pending positions and mismatched command IDs. After canonical `user@4` adopts the finalized prefix, the same command ID and position still resolve to the `user@3` adapter binding.
