# Removing an Agent Node

2026-11-17. Source investigation of the Plan 309 working tree and Cloudflare's published lifecycle guarantees. Historical investigation before the installation-generation cutover. The maintainer subsequently chose to abandon pending deliveries on both removal and replacement. [Current decision](../adrs/029-independent-agent-command-callbacks.md)

## Required behavior

Removing an Agent declaration should stop its exposed-command and wake callbacks for every existing instance, including an idle instance with a scheduled alarm. A callback that committed before the stop may already have recorded a command. Its Node Repo must deliver that exact command under its original Agent and owner release until the owner Chain acknowledges admission. A newly created Aggregate must also observe the removal. These requirements follow from the Agent's existing command and wake ownership. [ADR 029](../adrs/029-independent-agent-command-callbacks.md)

## What the current code does

- **Discovery.** Each Agent Node Repo has a stable physical name across releases. An Aggregate Agent Node key includes the Aggregate instance ID. A Service Agent Node key includes the Service name. Both include the System ID and Agent name. `SystemRepo.initializeAgentNodes` combines selected Agents with persisted Node Repo registrations and calls `initialize()` on the union. `AggregateChain.initializeAgentNodes` also starts selected Agents for an individual Aggregate. - **Once the new configuration reaches the Node.** Both Node constructors capture their active release. With no entry, `makeAgentNodeRuntime.ready()` is false. Exposed-command delivery cannot invoke the authored callback, synchronization skips authored wakes, and `advance()` still calls `storage.drain()`. The Agent VersionChains also disable Node fanout for a deselected binding. Once no delivery or retry remains, `WakeRegistry.reconcile()` clears the platform alarm. The old pending-wake rows and initialization state stay in storage. A prior initialization error can still reach `SystemApi.initialize()` as a failure. Restoring exactly the old installation binding can reuse its checkpoint and wakes. - **Fresh admission after removal.** Both owner Chains validate the command against the exact live Agent release and its contract grant. Removing the whole Agent entry, or only the release named by the pending command, removes that grant. An unadmitted command then stays in the Node's outbox. A lost reply after successful admission is recoverable because the Chain checks its durable producer position before rechecking the grant. Only the Chain's acknowledgement allows the Node to delete that delivery row. - **Catalog and deployment.** The catalog checks immutable facts present in the candidate against retained snapshots. Omission alone passes that comparison. The storage preflight for adopting Plan 309 checks the storage format separately. The CLI accepts the candidate spec, promotes the candidate, waits for the candidate version of `SystemRepo`, then calls `initialize()`. Child Repo registration checks membership in the retained accepted-spec catalog. Neither the catalog nor `initialize()` supplies a per-Node acknowledgement that the old installation stopped. A declaration change during `zerospin dev` currently requires restarting the dev command. - **Platform timing.** Cloudflare can defer an active Durable Object's code update for up to 300 seconds by default. Durable Objects have no shutdown hook. Alarm delivery is at least once, and cancelling from an alarm handler only suppresses retries on a best-effort basis. An active Node therefore needs to enforce its own stop in every callback transaction. The earlier design supported removing a Node selection while the owner kept the Agent release available. Its Service workerd test recorded an unadmitted command, removed the selection, lost the first admission reply, evicted the Node, retried through SystemRepo discovery, and checked both the restored command identity and the absence of an alarm. Plan 309 combines registration and activation in one authored entry with a mandatory active version. Keeping a release registered also keeps it resolvable for observer sessions, and the owner VersionRepo continues evaluating selections for registered releases. Stopping Node automation and withdrawing all access to a release have different consequences. ## Superseded proposal for one-edit removal

1. The author deletes the Agent entry. After the candidate passes read-only compatibility checks, `SystemRepo` records the removal for that deployment and owner-scoped Agent name. Node registration and initialization observe this decision so that a newly created Aggregate cannot start the retiring Agent after `SystemRepo` enumerates existing Nodes.
2. `SystemRepo` asks each registered Node to stop. The Node commits its stopped installation and clears authored wakes in one synchronous transaction. Every path that can commit authored work checks that installation inside its transaction, including wake processing that began a history catch-up before removal. The Node preserves its producer position and command-delivery rows. This commit defines the stop boundary for that Node.
3. Under the still-serving release, each Node drains its outbox through its existing owner Chain admission RPC. Recovery repeats the same stop and drain after an interruption or lost reply. The Node acknowledges removal when stopped with no pending deliveries. A failed drain leaves removal pending and diagnosable. The deployment must retain the old executable grants through this step.
4. Promote the candidate after all affected Nodes acknowledge. If the same name is added later, install from a fresh owner snapshot and rebuild the wake schedule before enabling callbacks. Keep the stable producer position. Rollout recovery must distinguish an older deployment retry from an explicit later reactivation.

This protocol adds no author-facing retirement toggle. The Agent Node runtime owns the stop transaction. The proposed sibling `makeRebuildableDORepo` can provide identity, registration and rebuildable storage for both Agent Node classes. Selecting a constructor cannot coordinate delivery acknowledgement, publication of deployment intent, or the time at which another Durable Object changes code.
