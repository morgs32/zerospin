# Effect v4 and Cloudflare native tracing

Primary-source research on 2026-10-12. Inspected installed Effect and OpenTelemetry sources plus current official Cloudflare documentation. This is research, not an approved implementation plan. No production code, configuration, tests, fixtures, or deployment changed.

**Recommendation:** keep Effect as the source of application spans. For a faithful hosted Effect hierarchy, use standard OTLP export to the configured collector/provider. Cloudflare native custom tracing can expose application names, but its public API does not establish a faithful generic Effect tracer bridge. Direct OTLP changes the [handoff's](../archive/handoffs/2026-10-12-handoff-optional-cloudflare-telemetry.md) proposed Cloudflare-managed delivery ownership; that choice was settled and implemented by [Plan 143](../plans/143-plan-optional-effect-telemetry.md); configured delivery/indexing verification remains open.

## Current evidence

1. The installed packages are `effect@4.0.2` and `@effect/opentelemetry@4.0.2`. This research uses their v4 source, not v3 examples. Sources: [Effect package](../../packages/logger/node_modules/effect/package.json#L4), [OpenTelemetry package](../../packages/system-worker/node_modules/@effect/opentelemetry/package.json#L4).
2. Zerospin already supplies readable names through `makeFn`, which wraps authored work with `Effect.withSpan(name, options)`. Its collector records parent identifiers, timing, failure Cause text, and causal links. Retaining this instrumentation preserves domain vocabulary independently of the hosted persistence provider. Sources: [makeFn](../../packages/logger/src/makeFn.ts#L38), [collector spans](../../packages/logger/src/makeTelemetryTracer.ts#L58), [collector links](../../packages/logger/src/makeTelemetryTracer.ts#L91).
3. Cloudflare's September 25 API includes `enterSpan`, `startActiveSpan`, `startSpan`, `getActiveSpan`, attributes, exception recording, and ending. `enterSpan` supports synchronous callbacks. Native parenting follows JavaScript async context; `startSpan` never activates its span. The API lacks explicit parents, exposed IDs, status setting, links, and reactivation of an existing span. Native custom spans are included in managed OTLP exports. Sources: [custom-span API and limitations](https://developers.cloudflare.com/workers/observability/traces/custom-spans/), [custom-span export announcement](https://developers.cloudflare.com/changelog/post/2026-06-16-custom-spans/).
4. Native platform instrumentation includes Worker/DO RPC and DO SQL operations. Native traces have their own Cloudflare ancestry; preserving Zerospin's explicit causal links is a separate requirement. CPU-only timing can appear as zero, and native trace IDs are not propagated to external services. Sources: [RPC and SQL spans](https://developers.cloudflare.com/workers/observability/traces/spans-and-attributes/), [known limitations](https://developers.cloudflare.com/workers/observability/traces/known-limitations/).

## Why `Tracer.context` matters

Effect v4's tracer has both a synchronous span allocator and an optional `context(primitive, fiber)` hook. The evaluator invokes that hook for successive primitives, including resumed work. The v4 OpenTelemetry adapter reads the current fiber span and calls `Otel.context.with` to activate that existing span during evaluation. Sources: [Tracer interface](../../packages/logger/node_modules/effect/src/Tracer.ts#L31), [evaluation loop](../../packages/logger/node_modules/effect/src/internal/effect.ts#L624), [OpenTelemetry context bridge](../../packages/system-worker/node_modules/@effect/opentelemetry/src/OtelTracer.ts#L100).

**Source-based inference:** copying an Effect span name to native `startSpan` can preserve its name and lifetime, but does not make nested Effect operations its children. Wrapping individual evaluator steps in native `startActiveSpan` creates new spans; the API cannot reactivate the same existing span after a yield. Wrapping one whole `runPromise` with native `enterSpan` can provide a readable boundary and native platform children, but does not automatically reproduce nested Effect spans. Neither native tracing nor Effect documents a ready-made native Cloudflare adapter. Sources: [native callback/context behavior](https://developers.cloudflare.com/workers/observability/traces/custom-spans/), [Effect evaluation loop](../../packages/logger/node_modules/effect/src/internal/effect.ts#L651).

The installed `@effect/opentelemetry/OtelTracer` cannot simply receive the native Cloudflare tracing object: it requires a full OpenTelemetry tracer/context API, including `spanContext`, explicit context parenting, status, events, and links. Its support for these capabilities is useful with an actual OTel provider; it is not evidence that the native object implements that contract. Sources: [span construction](../../packages/system-worker/node_modules/@effect/opentelemetry/src/OtelTracer.ts#L453), [status/events/links](../../packages/system-worker/node_modules/@effect/opentelemetry/src/OtelTracer.ts#L483), [context activation](../../packages/system-worker/node_modules/@effect/opentelemetry/src/OtelTracer.ts#L112).

## Both local and hosted capture

1. This is feasible, but needs deliberate composition: `makeTelemetryLayer` and `OtlpTracer.layer` both install the same `Tracer.Tracer` service. Installing both does not establish two span consumers. Keep one application span path, with local capture and optional hosted delivery sharing consistent identities. This is an implementation inference, not an existing composite API. Sources: [local layer](../../packages/logger/src/makeTelemetryLayer.ts#L14), [OTLP tracer layer](../../packages/logger/node_modules/effect/src/observability/OtlpTracer.ts#L123).
2. Current local identifiers have `trc_`/`spn_` prefixes, and the collector filters other parents. OTLP expects hex identifiers; upstream v4 generates raw hex IDs and inherits a parent's trace ID. A faithful integration must reconcile both spans and links, plus their wire references, rather than pass current strings through unchanged. Sources: [local IDs](../../packages/logger/src/makeTelemetryIds.ts#L19), [parent filter](../../packages/logger/src/isTelemetrySpan.ts#L5), [v4 IDs](../../packages/logger/node_modules/effect/src/observability/OtlpTracer.ts#L238), [OTLP encoding](https://opentelemetry.io/docs/specs/otlp/#json-protobuf-encoding).
3. Span allocation and completion are synchronous; exporter delivery is buffered HTTP outside the domain operation. Keep that separation so synchronous SQL transactions remain synchronous. Export scopes/flushes must be owned by Worker invocation lifetimes; `ctx.waitUntil` can retain a delivery promise after the response. Source capability does not prove deployed behavior. Sources: [collector allocation](../../packages/logger/src/makeTelemetryTracer.ts#L106), [OTLP completion](../../packages/logger/node_modules/effect/src/observability/OtlpTracer.ts#L254), [buffered delivery](../../packages/logger/node_modules/effect/src/observability/OtlpExporter.ts#L267), [Worker lifetime](https://developers.cloudflare.com/workers/runtime-apis/context/#waituntil).

## Decision and remaining runtime evidence

1. Prefer full Effect-origin application traces over request-only traces plus logged span records when readability and hierarchy are requirements. Choose one hosted application-telemetry delivery path; retain local profiles/Devtools capture without SQLite fallback or duplicate hosted writes. This direction was approved and the source cutover is implemented in [Plan 143](../plans/143-plan-optional-effect-telemetry.md); see its verification evidence and Remaining work for the current completion status.
2. Native Cloudflare platform spans and a directly exported Effect tree cannot currently be promised to form one tree: native IDs/parent injection are unavailable. Shared application correlation attributes can aid investigation, but are not the same as trace ancestry. The native pipeline remains useful for platform observability. Source: [native limitations](https://developers.cloudflare.com/workers/observability/traces/custom-spans/#limitations).
3. Before implementation completion, verify in the actual Worker/DO runtime: nested names across async yields and forks; RPC links; scoped concurrent local capture; synchronous transaction behavior; disabled delivery; delivery failure preserving domain outcomes; bounded flush and provider arrival. No runtime fixture or runner was created, and none of these deployment claims was verified here.
