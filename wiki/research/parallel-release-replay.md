# Parallel releases and replay refusals

Source inspection on 2026-10-13, based on `ff57e22fb0b2d06f431c5a7ca595ff5480a9110d` and the bounded aggregate/service replay-refusal repair published as `6.0.2`. This note explains the parallel-release behavior and repair; final verification is recorded below.

Source-link destinations follow current module names; this note retains its dated source claims and verification evidence.

## Answer

The user's parallel-release model agrees with the implementation. Registering a newer release does **not** retire an older release, prevent its original commands, or make its sessions stale. All registered releases participate in live replay. A compatible browser session selects its aggregate/service and actor versions explicitly; it does not implicitly select the newest release. Sources: [aggregate membership reconciliation](../../packages/system-worker/src/AggregateChain/onDOActivation/onDOActivation.ts), [service membership reconciliation](../../packages/system-worker/src/ServiceChain/onDOActivation/onDOActivation.ts), [browser request identity](../../packages/browser/src/fetchAggregateSessionSnapshot.ts#L45-L68), [requested-release admission](../../packages/system-worker/src/AggregateApi/admit/admitAggregate/admitAggregate.ts#L39-L53).

The membership problem is a failure-classification bug, not a reason to retire releases. The new `acceptInvitation` command succeeds originally on member `3.1.0`; member `3.0.0` lacks that command. Its local replay should retain its own refusal, leave its model state unchanged, and continue with the next command. Before the repair, that local absence escapes as an infrastructure error and marks the old replay subscriber failed. Sources: [Red Rope's parallel registry](/Users/morgs32/GitHub/redropeparking/apps/zerospin/src/system.ts#L8-L17), [3.1 contract map](/Users/morgs32/GitHub/redropeparking/apps/zerospin/src/member/memberV31.ts#L9-L22), [3.0 contract map](/Users/morgs32/GitHub/redropeparking/apps/zerospin/src/member/member.ts#L7-L14), [server command provenance](/Users/morgs32/GitHub/redropeparking/apps/zerospin/src/membership/resolveMembership.ts#L146-L167), [absence classification](../../packages/system-worker/src/AggregateVersionRepo/utils/resolveAggregateExecution.ts#L51-L66), [refusal versus infrastructure rule](../../packages/system-worker/src/AggregateVersionRepo/utils/executeAggregateCommandTx.ts#L68-L96).

## Which version a session reaches

An authored aggregate session release includes `aggregateName`, `aggregateVersion`, `actorName`, and `actorVersion`. The browser sends those exact identities when admitting and authorizing its session. Backend admission resolves that exact registered aggregate release and requires its actor version to match. Authorization checks the selected release's actor, selected models, selected historical public contracts, and complete session lock; it never substitutes a newer release. Sources: [session release](../../packages/core/src/sessionRelease/makeAggregateSessionRelease.ts#L40-L62), [browser request](../../packages/browser/src/fetchAggregateSessionSnapshot.ts#L52-L68), [admission](../../packages/system-worker/src/AggregateApi/admit/admitAggregate/admitAggregate.ts#L39-L53), [lock validation](../../packages/system-worker/src/AggregateVersionRepo/authorizeAggregateSession/validateAggregateSessionLock.ts#L27-L59), [selected declarations](../../packages/system-worker/src/AggregateVersionRepo/authorizeAggregateSession/selectAggregateLockMembers.ts#L33-L91).

The snapshot then comes from an actor projection keyed by the admitted aggregate version, actor version, actor path, and aggregate identity. “Reachable by a browser session” means the registered release plus a supported session lock, successful authentication, and authorization; registration alone does not grant access. Sources: [versioned projection lookup](../../packages/system-worker/src/AggregateSessionApi/getSnapshot/getSnapshot.ts#L29-L57), [authorization against the chosen release](../../packages/system-worker/src/AggregateVersionRepo/authorizeAggregateSession/authorizeAggregateSession.ts#L75-L126).

## Shared input history, independent execution histories

`AggregateChain` is the shared admitted-command order for one aggregate identity. Activation enrolls **every** registered aggregate release as an active materializer. `ServiceChain` does the same for its registered service releases. Existing cursors and failure state survive reconciliation; the conflict update only sets `active: true`. No “highest version wins” rule appears in these paths. Sources: [aggregate enrollment](../../packages/system-worker/src/AggregateChain/onDOActivation/onDOActivation.ts), [service enrollment](../../packages/system-worker/src/ServiceChain/onDOActivation/onDOActivation.ts).

Original execution follows each command's retained `aggregateVersion`, including idempotent retries. Before original command `n`, that release catches up through `n - 1`. Only the contiguous prefix with finalized originals becomes available for replay. Sources: [original outbox routing](../../packages/system-worker/src/AggregateChain/AggregateChain.ts#L111-L183), [retry routing](../../packages/system-worker/src/AggregateChain/executeAggregateCommand/executeAggregateCommand.ts#L18-L34), [predecessor catch-up](../../packages/system-worker/src/AggregateVersionRepo/finalizeCommand/finalizeCommand.ts#L38-L63), [finalized replay prefix](../../packages/system-worker/src/AggregateChain/readReplayPage.ts#L11-L45).

Every receiving version independently selects its own release and reruns its own guards/program against its own state. Its outcome need not equal the original outcome. The retained input keeps its source `aggregateVersion`; `executionVersion` records the materializer that produced this local result. A local refusal is therefore an occurrence in a healthy version's history, not a declaration that the whole chain is broken. Sources: [receiving release selection](../../packages/system-worker/src/AggregateVersionRepo/replayCommands/replayCommand.ts#L25-L43), [local guards and program](../../packages/system-worker/src/AggregateVersionRepo/utils/evaluateAggregateCommand.ts#L25-L60), [local finalization](../../packages/system-worker/src/AggregateVersionRepo/utils/makeEvaluatedAggregateCommand.ts#L21-L34), [retained execution identity](../../packages/system-worker/src/AggregateVersionRepo/utils/retainEvaluatedCommandTx.ts#L18-L33). The corresponding service path selects its own release as well: [service replay](../../packages/system-worker/src/ServiceVersionRepo/replayCommands/replayCommand.ts#L20-L46).

The business savepoint rolls back a refusal's operations. The enclosing materialization transaction retains its final refusal. The latest retained occurrence determines the version's cursor; successful receiver completion advances the producer's subscriber acknowledgement. An infrastructure error instead fails the receiver, persists subscriber failure, and removes it from subsequent eligible deliveries until explicitly resumed. Sources: [savepoint and retained refusal](../../packages/system-worker/src/AggregateVersionRepo/utils/executeAggregateCommandTx.ts#L31-L51), [materialization transaction](../../packages/system-worker/src/AggregateVersionRepo/materializeCommandTx.ts#L33-L43), [cursor from immutable history](../../packages/system-worker/src/AggregateVersionRepo/readAggregateMaterializationHead.ts), [receiver acknowledgement/failure](../../packages/system-worker/src/makeFanoutQueue/makeFanoutQueue.ts#L250-L288), [failed-subscriber exclusion](../../packages/system-worker/src/makeFanoutQueue/makeFanoutQueueStorage.ts#L85-L124).

## What the repair changes

Aggregate replay already retains `actor-contract-unsupported` and `actor-contract-lineage-unsupported` as local refusals. Service replay already retains `contract-payload-version-unsupported`. The repair adds the ordinary administrative equivalent only when all three facts hold: execution is replay; the source release declares the command; the receiving release does not. Original execution and absent source declarations continue to fail as infrastructure errors. Sources: [aggregate predicate and existing refusal list](../../packages/system-worker/src/AggregateVersionRepo/utils/executeAggregateCommandTx.ts#L68-L96), [service predicate and existing refusal list](../../packages/system-worker/src/ServiceVersionRepo/utils/executeServiceOccurrence.ts#L68-L92), [source-release and source-contract resolution](../../packages/system-worker/src/AggregateVersionRepo/utils/resolveAggregateExecution.ts#L20-L66).

Admission still validates the submitted source release, origin authority, contract version, and payload before retaining an ordinary command. Consequently the repair does not admit an invented administrative command or permit a browser to execute one. Sources: [ordinary command validation](../../packages/system-worker/src/AggregateChain/admitAggregateCommands/validateNewAggregateCommand.ts#L24-L66), [system-origin metadata rule](../../packages/system-worker/src/AggregateChain/admitAggregateCommands/validateSystemCommand.ts#L14-L24).

The inspected regression asserts old success → new-command refusal → later success in the older materializers. The command at index 3 is authored originally on retained `1.0.0`, then forward-replays successfully into execution version `1.1.0`; both subscriptions remain `active: 1`, `currentIndex: 3`, `failure: null`. It also asserts historical source-version commands replay into the newer execution version. These are test assertions, not a claim here that the test passed. Sources: original older-release write and newer replay (`packages/system-worker/test/migratable-do-repo/system-repo-activation.workerd.spec.ts`, removed 2026-10-17), healthy parallel subscriptions (`packages/system-worker/test/migratable-do-repo/system-repo-activation.workerd.spec.ts`, removed 2026-10-17).

## Payload adaptation and external continuations

When both releases declare a related ordinary contract, replay does not need to refuse it. Payload decoding finds the retained contract version in either `previous` or `next` lineage; adaptation executes authored `up` or `down` edges and validates every resulting payload. This is the existing mechanism for old sessions/new materializers and new commands/old materializers when the command has an authored backward meaning. An entirely new command such as `acceptInvitation` has no old contract to down-adapt into. Sources: [bidirectional version discovery](../../packages/core/src/contracts/decodeAndAdaptPayload/decodeAndAdaptPayload.ts#L64-L102), [up/down traversal](../../packages/core/src/contracts/decodeAndAdaptPayload/adaptPayload/adaptPayload.ts#L45-L105).

Old async work is not automatically reassigned to a new release. The producer retains its exact emitting owner and receiving address; reconstructing the child preserves the receiving version and frozen payload/response. Original execution alone gets runnable producer lifecycle. Replay retains immutable async emissions with null lifecycle fields, preventing duplicated external work. Sources: [producer ownership and lifecycle](../../packages/system-worker/src/externalOperations/prepareExternalOperation.ts#L35-L83), [concrete receiving contract](../../packages/system-worker/src/externalOperations/readPreparedExternalCommand.ts#L40-L84), [child reconstruction](../../packages/system-worker/src/externalOperations/readPreparedExternalCommand.ts), [original/replay emission mode](../../packages/system-worker/src/AggregateVersionRepo/utils/prepareAggregateOutput.ts#L24-L47).

There is a bounded gap: the aggregate repair does **not** turn an absent receiving external-continuation contract into a local refusal. `resolveAggregateExecution` reports that absence as `external-contract-kind-mismatch`, which still escapes the refusal list. Existing external continuations remain valid when their source authority and local external implementation remain available; that is different from proving every newly introduced external contract can traverse every old release. The service absence predicate does cover missing local service contracts, including this absence case. Sources: [aggregate continuation selection and missing implementation](../../packages/system-worker/src/AggregateVersionRepo/utils/resolveAggregateExecution.ts#L32-L76), [external response authority](../../packages/system-worker/src/AggregateVersionRepo/utils/resolveAggregateExecution.ts), [aggregate refusal list](../../packages/system-worker/src/AggregateVersionRepo/utils/executeAggregateCommandTx.ts#L68-L96), [service missing implementation](../../packages/system-worker/src/ServiceVersionRepo/utils/resolveServiceExecution.ts#L19-L30), [service repair predicate](../../packages/system-worker/src/ServiceVersionRepo/utils/executeServiceOccurrence.ts#L68-L92).

## Recommendation

Keep parallel registered releases active, reachable, and writable. Apply the bounded replay-refusal repair for the observed ordinary `acceptInvitation` failure, run the regression proving a subsequent original command on the older release, and preserve source-invalid/original failures. Do not introduce retirement, highest-version routing, or an upgrade-required rule: none is needed to repair the observed classification defect.

Do not describe this repair as universal external-contract replay support. If that broader guarantee is required, distinguish **validated source authority plus absent receiving implementation** from actual external-kind/provenance failures in the resolver, then retain only the former as a local replay refusal. Simply adding every `external-contract-kind-mismatch` to the refusal list would hide invalid source authority. This recommendation follows the distinct branches cited above; it is an architectural inference rather than existing behavior.
