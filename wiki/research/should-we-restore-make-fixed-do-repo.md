# Should Zerospin restore makeFixedDORepo?

2026-11-17. Source review of the current main working tree and the change that removed the fixed factory.

**Recommendation: defer restoration.** The decision for each physical Repo is what should happen when its framework schema changes under an existing name. A fixed Repo would provision on empty storage, validate on reopen and refuse incompatible storage. A migratable Repo can perform those same first two steps and, with an explicitly supported migration, upgrade retained rows in place. The current evidence identifies consumers of the migration and rebuild policies. It does not identify a consumer that needs a fixed schema for its entire physical lifetime. [Framework storage decision](../adrs/009-forward-only-framework-storage.md) · [Current storage policy](../../AGENTS.md#pre-release-hard-cutover)

## Why the old factory disappeared

The old implementation returned immediately when it found a bootstrap marker. Otherwise it called `provisionDb`. Restoring that code would skip exact validation on a marked database. PR #50 deliberately moved all nine production owners of the time onto one forward-only lifecycle, even though all nine started with only the baseline. The recorded reason was to preserve authoritative data, pending work and alarm ownership across framework updates under the same physical identity. Creating successor objects instead would require a cutover. ## What the baseline buys today

- Twenty production classes declare an empty migration list, including both Agent Node Repos after the November 18 cutover. `SystemRepo` has one authored migration preserving original accepted SystemSpecs. Even an empty list creates an `applied_migrations` table and stamps migration zero. Its checksum covers the baseline definition. Separate inspection checks the actual SQLite graph. On reopen with no pending migration, the extra work is preparing the baseline checksum and reading and checking the ledger. This review found no measurement establishing significant cost. [SystemRepo migration](../../packages/system-worker/src/SystemRepo/SystemRepo.ts) · [History preparation](../../packages/system-worker/src/makeMigratableDORepo/migrationHistory.ts) · [Activation](../../packages/system-worker/src/makeMigratableDORepo/initializeMigratableSchema.ts)
- The baseline lets an existing Repo gain its first approved migration while keeping its physical identity. Zerospin used that option for the QRK SystemRepo catalog upgrade. A versioned name alone does not make data disposable. For example, `AggregateVersionArchive` owns evaluated commands, and `AggregateVersionRepo` owns pending publication to its VersionChain. A declaration version and a framework storage revision can change independently. [QRK catalog upgrade](https://github.com/morgs32/zerospin/commit/0ab58f40d2a10aedbdf383519f1c98963d7a8c83) · [Archive schema](../../packages/system-worker/src/AggregateVersionArchive/aggregateVersionArchiveDbConfig.ts) · [VersionRepo schema](../../packages/system-worker/src/AggregateVersionRepo/aggregateVersionRepoDbConfig.ts) · [Plan 139](../archive/plans/139-plan-migratable-do-repo.md)
- The two Agent Node Repos rebuild selected tables inside the Agent runtime and use the common migration lifecycle for operational storage. A release replacement explicitly abandons the old installation and rebuilds its selected view from an owner snapshot. The Node and owner Chain coordinate a new producer generation. Exact schema validation alone could never supply those semantics. ## Cost of switching

A strict fixed opener would reject an existing migratable database because its extra ledger table is outside the fixed declaration. In the opposite direction, the migratable opener explicitly refuses populated storage without a ledger. Selecting either constructor therefore commits an existing physical name to a storage format. Moving an existing owner requires a separately approved transition or fresh affected storage, with read-only deployment preflight before any writes. A local cold-start check by itself comes too late to establish deployment compatibility. Neither this investigation nor the choice of constructor authorizes a reset. [Exact table validation](../../packages/core/src/drizzle/provisionDb/validateDbSchema.ts) · [Missing-ledger refusal](../../packages/system-worker/src/makeMigratableDORepo/initializeMigratableSchema.ts) · [Deployment preflight](../patterns/system-worker/repo-lifecycle.md#check-deployment-compatibility-before-writes)

Revisit this when a named owner can use a genuinely fixed policy: either the physical schema will stay supported for the object's lifetime, or a documented replacement can safely recover or abandon every owned fact. Start with that owner on a clean storage boundary. A thin `makeFixedDORepo` over `makeDORepo` could reuse the existing provisioning and exact schema validation procedures. Keep migration capability explicit for owners that must evolve in place.
