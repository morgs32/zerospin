## Physical owner, row fact and constraints

One ServiceVersionChain database belongs to exact `{ systemId, serviceName, serviceVersion }`. A row is one complete release-local evaluation output shared by the enrolled ServiceActorVersionRepo subscribers that have not all acknowledged its position. It is **complete pending projection delivery**, not another evaluation, admitted command, materialized resource, recipient-specific message or permanent history.

Both `commands` and `actorVersionRepoFanout` use the identical ten-column shape. New append encodes once and inserts the same row into both in one synchronous transaction. Enrollment backfill copies retained commands unchanged. All values are immutable while a pending row exists; deletion/backfill changes whether the redundant copy exists, not its meaning. Actor recipient identity and acknowledgement live separately in subscriber progress. The table name correctly names its immediate receiving Repo; retaining that logical queue name does not require a SQL table with the same name.

`serviceIndex` is the integer primary key; `commandId` is required text with a unique constraint. Only `nodeId`, `sessionName` and `pushIndex` are nullable. No defaults, additional declared indexes, foreign keys, generated declared IDs, timestamps or delivery-status columns are added. Positive positions, canonical IDs, hash format and operation-body rules come from protocol/writer validation rather than additional SQL constraints.

## Every structured value

1. `origin` is Actor `{ kind: 'actor', actorName, actorVersion, claims }` or System `{ kind: 'system' }`. Actor name/version are required nonempty strings; claims is the complete application-defined record. No Agent variant or placeholder System claims exists. Claims determine private ownership; they are not delivery diagnostics.
2. `outcome` is `{ result: Success | Failure, finalizedAt }`, with the timestamp outside both branches. Success retains JSON `success`; Failure retains public `{ _tag: 'ZerospinError', code, message, scope?, status, extra }`, where scope is contract/actor/aggregate, status is nullable numeric and extra is JSON. Authored JSON null is valid data, not a missing outcome. The one logical `outcome.finalizedAt` supplies source and projection resource application; retries preserve it.
3. Model members contain exactly `operationIndex`, `modelName`, `modelVersion`, `resourceId`, `operationName` and encoded JSON-string `body`. The kind selects create/full `attributes`, update/patch `attributes`, delete/empty body or move/`property`, `prevId`, `nextId`. Move endpoints are string, safe integer or null according to the authored property codec. Parent `commandId` supplies mutation attribution; parent `outcome.finalizedAt` supplies application time. No nested command ID, inverse, prior resource snapshot or application timestamp is stored.
4. External members contain exactly `operationName: 'external'`, `operationIndex`, `externalContractName`, `externalContractVersion`, JSON `payload` and stable canonical `externalCommandId`. Parent command ID/full Origin and bound evaluating service release supply omitted standalone request context. Payload may be JSON null. These retained descriptions contain no observation, response, status, attempt or lease. ServiceChain alone owns pending requests and external invocation; projection delivery does not run them.
5. `operationIndex` is a safe nonnegative authored position, strictly increasing across the mixed union. Replay removes external emissions before preparation/ID allocation and leaves sparse positions; array offsets cannot replace them. Failure requires an empty array; no-operation Success can also have an empty array. Exact model/contract versions remain in complete output.
6. `dispositionChainHash` extends the previous hash with `serviceIndex`, canonical command ID and only `outcome.result._tag`. It excludes result contents, time and operation bodies. ServiceVersionChain compares complete retained output for retries and separately validates the prefix; no equality requirement is weakened by changing the delivery reader.

## Current lifecycle and failure boundaries

1. `ServiceVersionChain.appendExecutionPackets` acquires the actor queue producer lease before synchronous append. Append validates full output, immutable retries, ordered operations, exact declarations, contiguous history and disposition prefix. It atomically inserts permanent commands and identical pending fanout. A later failure rolls back the page's new inserts. An exact repeated append returns without resurrecting a deleted pending copy.
2. The queue captures one permanent-history tip per drain. Delivery reads at most 64 pending rows in ascending `serviceIndex`, bounded by that captured tip. Subscriber eligibility comes from acknowledged progress below the tip, not from counting pending rows.
3. `ServiceActorVersionRepo.actorVersionRepoFanoutSubscriber` binds the exact source system/service/release. Its receive procedure arms selected-publication recovery, then resolves the exact configured release and applies model members synchronously. Resources, projection checkpoint and complete selected pending publication commit together. Private resolution requires the exact actor identity/claims and producer context; raw complete output is not a browser frame.
4. Only a successful receiving RPC envelope advances that subscriber's acknowledgement to the last actual delivered row. Advertised source `lastIndex` is not the acknowledgement. That durable receipt proves ServiceActorVersionRepo's local projection commit, not ServiceActorVersionChain publication or socket delivery.
5. Acknowledgement advancement and pruning share one transaction. Pruning removes rows through the minimum cursor across all enrolled actor subscribers; one slow or failed subscriber preserves its needed suffix. With no subscribers, pruning deletes all pending copies. Permanent commands survive every case.
6. Cold ServiceActorVersionRepo activation first catches up from permanent history through a captured boundary, reads actual local progress and enrolls it. Enrollment monotonically records progress and backfills history above the minimum subscriber cursor in the same transaction. The backfill currently reads the entire retained suffix solely to recreate pending copies. Queue enrollment takes its producer lease outside the drain semaphore, preserving activation/delivery sequencing without a reentrant drain wait.
7. A lost receiving reply leaves the source cursor behind; projection progress skips already committed rows on redelivery. Failure preserves the subscriber cursor and alarm recovery while other subscribers can progress. Producer leases arm recovery before append; producer revisions prevent a concurrent drain from releasing the alarm hold for newly produced work.

## Why direct commands delivery is the clearer model

Permanent complete commands in the same database already cover every delivery and catch-up position. A subscriber's durable acknowledgement below the history tip identifies exactly what remains to deliver. The second payload table stores no independent message, recipient, eligibility or progress fact.

`makeFanoutQueue` already uses `readDeliveryPage ?? readPage`, and ServiceVersionChain's `readPage` already decodes complete commands. Removing the delivery-reader override uses that existing path without reconstructing output, querying another owner or reading current resources. Bounded pages, exact release/actor authority, full outcomes/operations, sparse indexes and independent subscriber acknowledgement remain intact.

Late enrollment needs no payload backfill: commands committed between the catch-up boundary and enrollment remain directly readable above the enrolled cursor. A no-subscriber drain need only find no eligible subscriber; future enrollment still reads the retained suffix. Lost receipts still redeliver against projection checkpoints. Keep producer leases/revisions and alarm recovery so commits and enrollment cannot lose delivery wake-up across interruption or concurrent drains.

An approved implementation should remove this physical declaration/append insert, the `readDeliveryPage` override, `#backfillActor`, `#pruneActor` and their hooks. Simplify the Service history page reader to its single retained source. Keep the public `actorVersionRepoFanout` queue/getter, subscriber storage, source-bound receiving capability and complete ten-field wire representation. No pointer replacement is needed.

ServiceVersionChain is the sole current fanout consumer of `readDeliveryPage`, `onEnrollment`, `afterAcknowledge` and `afterDrain`. Once these bindings are removed, delete that unused optional API/plumbing from `makeFanoutQueue` and its storage helper. This concerns fanout-copy hooks only: `makeOutboxQueue`/`makeOutboxDelivery` original-completion hooks have separate AggregateChain/ServiceChain responsibilities and must remain.

The recommendation challenges ADR 015's independent-copy requirement for a history-owning Chain. Resource-owning Repos still need complete pending publication because they do not retain history. Prior Aggregate fanout removals are supporting precedent; the Service-specific same-row writes, existing direct reader, exact receiving boundary and enrollment/acknowledgement trace establish this conclusion independently. There is no measured performance claim or proposal to reduce Service output fields.

If approved, amend ADR 015's copy/deletion rule and ADR 016's statement retaining the shared Service pending-payload hooks, along with affected consumers/documentation and existing check callers. Preserve complete Service output throughout. The fixed-schema hard cut requires empty affected ServiceVersionChain storage and no compatibility rows, aliases, backfill migration or automatic reset. This review authorizes no implementation, reset or deployment.
