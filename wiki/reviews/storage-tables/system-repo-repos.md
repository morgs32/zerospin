# SystemRepo.repos

**Reviewed:** 2026-10-16 against current source, including uncommitted work, with independent column-design and registration-lifecycle reviewers. Exactly this physical table is reviewed; activation, Aggregate membership, inspection and ticket consumers are dependencies. All verification remains deferred.

**Verdict: retain all three columns, current names and `(repoType, repoName)` uniqueness.** The row records a known physical child Repo and its **last committed declared table-name list**. It is mutable registration/discovery metadata, not readiness, authoritative SQLite inventory, immutable schema history or permission to read arbitrary tables. No required schema simplification or ordinary-path correctness defect is established.

Only this finding and [Plan 151](../../plans/151-plan-storage-table-review.md) change. No implementation subplan or production edit is needed for this verdict. The table-name freshness distinction is recorded explicitly below; prior implementation plans remain independently unverified.

## Physical scope and durable fact

One SystemRepo belongs to exact deployment systemId. One row identifies a registered concrete Durable Object namespace/name pair and the complete table list supplied by its most recently committed registration. Repeated registration replaces that list; the row is not a sequence of past schema changes or a record that initialization finished.

SystemRepo itself has no self-registration row. Its physical identity and fixed schema already establish the singleton; getRepoRegistrations synthesizes that one inspection entry. SystemLogRepo and the other configured concrete Repo kinds register normally. Standalone Repos that omit System registration are outside this catalogue.

## Every column and constraint

The declaration has three required/non-null columns and no defaults. The named unique index covers repoType then repoName. There is no declared primary key, foreign key, generated domain ID, timestamp, revision, readiness flag, count or expiry. SQLite's implicit rowid has no application role. The framework migration ledger is a separate table occurrence, not an additional member of this row.

### Every tableNames member

The JSON value is one complete array; each member is a physical table-name string returned by getTableName from the resolved schema. The schema allows an empty array, empty strings and repeated values; there are no stronger per-member codec constraints. The normal producer supplies declared table names, rather than arbitrary SQL, row data, column definitions, executable callbacks, model specs or table lifecycle flags. Declaration iteration supplies order, but there is no delivery position or history meaning attached to an array index.

Identity is `{ systemId, repoType, repoName }`, with systemId supplied by the physical SystemRepo. The complete physical name may itself contain System/release/Actor identity; it remains one canonical physical address. Add no separate System field, release column, copied resource schema or caller-chosen SQL expression.

## Registration, failure, retry and exact retention

1. The common Repo factory parses physical identity, verifies configured System identity and resolves the concrete database schema before registration. The producer sends repoType, actual repoName and table names from that resolved schema to the configured SystemRepo. Versioned resource schemas can differ by exact release and selected Actor/Agent model composition; a single per-kind static table list cannot substitute for every registered instance.
2. SystemRepo.registerRepo strictly decodes the executing complete SystemSpec and requires matching accepted definitions before any metadata write. Registration does not accept new definitions. Native registration remains a typed internal interface: it does not independently runtime-decode the registration envelope or compare its physical address with its forwarded fields. The supported framework producer supplies those from validated physical context; no malformed direct registration or ordinary-path inconsistency was observed or reproduced.
3. One synchronous makeTx transaction upserts the metadata row and, for AggregateChain only, records its logical Aggregate pair. Identity stays fixed; tableNames is replaced on conflict. The transaction performs no remote RPC. Failure during either write rolls both back; a lost reply can retry without adding another identity row. Aggregate logical membership has its own separately recorded table finding.
4. Registration commits before the registering Repo's foreign-key/schema initialization, bootstrap and onRepoStartup. A later failure leaves registration metadata intact, including the newly declared table list even if local schema provisioning failed. A dormant instance may retain an earlier list until it registers again. Concurrent executing code versions can replace metadata in commit order; the row is not a statement about the newest deployment or successful code promotion.
5. There is no supported update of identity, unregister, deletion, expiry, acknowledgement pruning or automatic retirement on current-code omission in the reviewed flow. Keep known registrations available for discovery and later reactivation. Absence of running code or a failed activation does not establish that the physical owner was deleted. No last-seen timestamp, deployment revision or readiness state is needed for this responsibility.

## Reads, discovery freshness and authority

SystemRepo.getRepoRegistrations filters one exact kind, sorts by physical name, validates known Repo kinds and decodes each JSON string array. A malformed retained row fails the listing with repo-registration-table-names-invalid; it is not silently treated as absent. The intrinsic SystemRepo result is derived from its current fixed schema instead of a stored row. SystemApi exposes inspection through its initialized, capability-bound System identity.

Studio displays the retained table count and names and limits its selected table to that discovered list. An old list can show an obsolete table or omit a new one. Re-registering the concrete Repo updates the list; a catalogue read alone does not contact or refresh every owner. This is the current discovery snapshot's freshness limit, not proof that the declared table physically exists.

SystemApi.getRepoTableRows checks exact registered Repo membership, then resolves the concrete kind/name under the capability's System ID. It does **not** grant table access based on stored tableNames. The addressed Repo accepts a table only if getTableName matches a table in its own bound schema, and selects through that Drizzle table. An obsolete discovered name fails there; a valid current table need not appear in an older catalogue array to pass that live schema gate. The API does not accept arbitrary SQL.

AggregateSessionApi and ServiceSessionApi ticket issuance also require exact Actor Chain registration. They use membership, not the table-name array. Because registration precedes readiness, that existence check must not be explained as proof that session initialization succeeded; subsequent Chain activation/admission retains its own requirements.

## Derivation challenge and reviewer reconciliation

Both independent reviewers retain all three fields and composite uniqueness. repoType is derivable from current naming prefixes, but keeping the namespace discriminator expresses the query/lookup identity directly. tableNames is derivable from an executable exact owner schema, but replacing the snapshot changes discovery to per-owner resolution/activation or duplicates dynamic schema construction. It also loses detached table-list discovery for registrations whose executable release has disappeared. Keeping a last-declared snapshot is a deliberate metadata responsibility, not a claim that current configured code cannot derive a schema.

The last-registration semantics, whole-array replacement and actual table-read gate resolve the stale-metadata concern without a new synchronization, version or cleanup protocol. Current raw-text repoType storage and manual JSON writes/reads are not evidence of a supported ordinary-path corruption defect; normal producers supply known kinds and complete string arrays, and retained reads validate them. No separate schema/style refactor is proposed.
