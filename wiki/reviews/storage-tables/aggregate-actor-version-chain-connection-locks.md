# AggregateActorVersionChain.connectionLocks

**Reviewed:** 2026-10-16 against current uncommitted source, with independent column-design and connection-lifecycle reviewers.

**Disposition: simplify — implemented under [Plan 209](../../archive/plans/209-plan-actor-connection-capabilities-and-cleanup.md).** The original finding recommended compact durable capabilities and complete connection disposal. The user approved both. Actor storage now has three required columns; full declaration validation stays at admission. Plan 209 records completed implementation, required verification and archival; the original review itself ran documentation checks only.

## Physical scope and row responsibility

AggregateActorVersionChain is bound to system, aggregate ID/name/version and actor name/version/path. One `connectionLocks` row records selected readable models and permitted command versions for one admitted WebSocket connection. This is connection authorization resource state, not retained command history, a materialization checkpoint, pending delivery or subscriber progress. The trusted attachment retains full actual Origin/claims, session, producer and replay phase/Node binding. Replay cursors remain local variables.

Actor and Agent now have separate connection table declarations. Agent retains its original two-column full-lock schema and unique index; Service storage is unchanged. Neither occurrence is reviewed by this Actor finding. The Actor Chain has no materialized application resource tables; retained public commands and private resolutions keep their separate lifecycles.

## Every current column

All three columns are required, immutable for the socket and have no defaults. There are no framework-added ID/timestamp columns. Empty lists/maps grant no corresponding capability. The text primary key enforces one row per connection without a separate unique connection index.

It is not a producer Node ID or named session definition.                          | Retain. Multiple sockets may share a Node/session; removing their individual association loses exact capability recovery and connection-specific reclamation.                                               |
| `modelNames`       | Required JSON array of selected readable model names, projected from the validated lock's own model keys. Replay/live/HTTP filtering consumes it. ## Original full-lock field audit

Before Plan 209, the Actor row had required `connectionId` plus required JSON `lock`, with a unique connection index and no declared primary key. The following audit explains why the full declaration was removed from Actor connection storage. Full client locks and their boundary validation remain unchanged. Agent still uses that complete lock in its own physical table.

All full-lock top-level fields are required. Record keys are strings; empty records authorize no corresponding model/contract. Optional index predicates and primitive metadata mean omission, not SQL null or extra authority. `Schema.Unknown` documents may contain JSON null as data. The storage recommendations in this original audit are implemented for Actor rows.

## Admission and consumer boundaries

`AggregateVersionRepo.authorizeSession` still validates selected model exposure and exact versions, model-reference closure, selected non-external contracts and their requested versions, and full structural agreement with the authored declarations. SystemRepo validates claims/canonical actor identity, consumes the ticket once, replaces caller-supplied trusted headers and forwards the admission to the exact Actor Chain. `onConnect` retains all forwarded lock/Origin checks before projecting capabilities.

Actor connection reads explicitly compare attachment Origin kind/name/version with the bound Actor owner, replacing the check that previously depended on the copied lock. Agent reads decode their existing full lock and retain its session/Origin checks before projecting the same compact runtime shape. Commands still match exact aggregate/session/full Origin/Node identity; private replay/live delivery keeps exact recipient comparison. No canonical admitted-command, `outcome`, history or acknowledgement shape changes.

Shared history reads now receive selected model names instead of a full lock. AggregateSessionApi derives them from its authorized lock and returns the already-filtered Chain page without filtering it a second time. Agent bootstrap adapts its full declaration only in memory. No new registry, hash, cache or remote lookup is introduced.

## Installation, disposal and activation reconciliation

SQL insertion and WebSocket attachment installation cannot share a transaction. `installConnection` encodes and inserts the owner's row, then installs `awaiting-resume` attachment state without an intervening yield. Actor failure disposal covers capability encoding, SQL insertion and attachment installation, including defects and interruption. Closing occurs even when insertion failed before creating a row; deletion is idempotent. This matters because Partyserver accepts the original socket before calling `onConnect`.

Actor close callbacks, explicit error handling and message/broadcast closure reclaim the row. `disposeConnection` deletes in `finally`, so a throwing close cannot bypass SQL cleanup. A failed notice/send also cannot bypass the Actor error-disposal path. Agent retains its existing close lifecycle; its physical table is selected explicitly rather than accidentally using Actor's new declaration.

Actor `onRepoStartup` runs after durable schema/bootstrap and before events. `reconcileConnectionLocks` obtains the complete set of surviving Partyserver socket IDs before pruning unmatched Actor rows in one synchronous transaction. Enumeration failure deletes nothing; every surviving socket is preserved regardless of replay phase. The hook covers cold RPC/alarm activation as well as socket events and does not depend on Partyserver's separately lazy `onStart`.

Hibernation is not disposal. A new socket receives newly admitted capabilities; this row is not a cross-connection recovery record. No TTL, credential-revocation policy or history pruning is introduced. Disposal never deletes `exposedCommands` or `commandResolutions`; publication acknowledgement and browser delivery are unrelated to capability reclamation.

The original source finding identified SQL-before-attachment installation without compensation and close-only reclamation (the inherited Partyserver error handler merely logged). It did not demonstrate unauthorized delivery or a production leak. Plan 209 closes those bounded gaps and the earlier encoding/SQL failure path; fail-closed row-plus-attachment checks remain required.
