# ServiceAgentNodeRepo.selectedResources

**Reviewed:** 2026-10-21 against current uncommitted source, with independent lifecycle and column-design reviewers. This finding covers exactly SANR's physical occurrence; AANR remains separate.

**Verdict: retain the three-column fixed selected materialization.** SANR needs local resource contents so selected changes, its checkpoint and wake reconciliation commit synchronously. The SQL identity repeats two envelope fields, but replacing this mixed-model container with ordinary Model tables would introduce schema/pin and partial-selection problems. No supported-path lifecycle defect or justified schema change was found.

**Review queue:** [Plan 151](../../plans/151-plan-storage-table-review.md). This is a source review, not new runtime verification or authorization to reset storage.

## Physical owner and represented fact

ServiceAgentNodeRepo is an unversioned MigratableDO identified by `(systemId, serviceName, agentName)`. One `selectedResources` row is one resource currently selected under the applied Service release. It is mutable scheduling materialization, not retained command, event, execution or audit history. ServiceAgentVersionRepo supplies selected resources; ServiceAgentVersionChain retains public selected history. Those separate durable owners do not remove SANR's need for local scheduling inputs.

## Every stored field

There are exactly three declared, required TEXT columns, without defaults. `resource` uses the JSON codec. There is no declared primary key, foreign key or synthesized timestamp column; one unique index on `(modelName, resourceId)` defines resource identity within this mixed-model table. SQLite's implicit rowid is not read or used for scheduling. No additional index is justified by the current readers.

## Transaction, recovery and deletion boundaries

1. **Initial baseline:** SANR obtains a coherent selected snapshot with actual `serviceIndex` and `dispositionChainHash`. A synchronous transaction replaces selected rows, installs `materializationHead` and reconciles wakes without firing due commands. A present checkpoint, including index zero, establishes initialization; same-pin reconstruction retains the rows and catches up.
2. **Selected pages:** SANR fences the complete source identity and applied Service version, validates the page and enforces contiguous progress. The page transaction deletes exited `(modelName, resourceId)` pairs, upserts selected envelopes, reconciles wakes and advances the checkpoint. Duplicate prior positions do not repeat these writes; a gap or conflicting current hash refuses the page. Failed writes or behavior decoding roll back the transaction.
3. **Due processing:** The Agent pass synchronizes selected eligibility before a synchronous due transaction reads these rows, marks an attempt and freezes complete command-delivery input. Failed synchronization skips new freezing while existing frozen commands remain deliverable. There is no remote resource read inside the resource/wake transaction.
4. **Selection exit:** Authoritative exit removes current resource and wake responsibility together. It does not delete `commandDeliveryOutbox` rows. SANR retries those frozen invocations independently of selected contents and deletes delivery only after validating exact durable admission acknowledgement. Admission acknowledgement does not establish execution commit or a retained `outcome`.
5. **Owner-pin change:** Pending delivery obstructs replacement before the new snapshot is installed. After delivery drains, baseline replacement and wake reconciliation are atomic, matching attempted markers survive, and old-source pages are refused. One `materializationHead` binds the whole selected set; adding per-row `serviceVersion`, source cursors or generations would duplicate that fact.

Removing this table and querying ServiceAgentVersionRepo on every alarm would lose the local synchronous boundary between selection, checkpoint, attempted markers and frozen input. Reconstructibility from the source is not a reason to discard the current materialization. Deletion follows current selection or whole baseline replacement, without history retention or an independent TTL.

## Representation challenge and reconciled decision

The column reviewer correctly identified duplicate envelope identity and proposed ordinary per-Model rows using existing row/envelope codecs. The lifecycle reviewer retained the fixed container. **Retain the current representation after considering both arguments:**

- **It is a fixed internal scheduling table, not a canonical `model.table` or authored row-query interface.** [Plan 236](../../archive/plans/236-plan-model-rows-and-resource-envelopes.md#design) removes Model identity from Model-bound SQL rows and preserves complete selected resource envelopes at boundaries. That rule remains applicable to ordinary Model tables. SANR deliberately stores heterogeneous selected input behind one stable internal schema. The duplication here supplies indexed SQL identity beside complete callback input; it is not another independent business fact.
- **Per-Model tables would change SANR's lifecycle.** `makeMigratableDORepo` initializes SQL before `onRepoStartup` runs the pending-pin guard. Deriving SQL from the new Agent pin could reject or change a shape-changing old materialization before SANR can report pending delivery and preserve state. The current fixed schema permits drain followed by atomic replacement without that additional schema-transition mechanism.
- **Selection is partial.** Service Agent resource capture explicitly disables reference closure. Copying canonical Model foreign keys into this selected database could reject valid selections whose referenced rows are absent. Ordinary Model-table composition is therefore not a declaration-only replacement.
- **A different generic attributes bag is not an established simplification.** Stripping envelope identity would add custom reconstruction and exact applied-Model binding while leaving heterogeneous content storage. No current reader needs SQL access to individual authored attributes. Fewer repeated values do not justify another representation or new lifecycle machinery without an actual requirement.
- **Resource JSON is not a canonical-byte identity copy.** SANR does not canonicalize or compare its bytes for equality, hashing, admission or recovery. It reads the resource contents. The [canonical-bytes prohibition](../../patterns/system-worker/no-canonical-bytes-in-sql.md) still applies, including its explicit ban on enclosing command serialization; the outbox finding does not make every JSON-valued resource field forbidden.

The broad [row/envelope lifecycle guidance](../../patterns/system-worker/repo-lifecycle.md) must be read with this distinction: retaining a fixed scheduler-input table does not restore `modelName`/`version` columns on canonical Model tables. This finding does not introduce a configurable storage policy, extra registry or compatibility path. No column removal, rename, new key/index or ownership change is recommended for this occurrence.
