## Physical owner and represented fact

One ServiceVersionChain database fixes `{ systemId, serviceName, serviceVersion }`. One subscriber row means a particular ServiceActorVersionRepo projection is enrolled and ServiceVersionChain has acknowledged its receiving materialization through an inclusive `serviceIndex`.

This is **subscriber membership and source acknowledgement**. It is not a resource, command, pending payload, socket presence, browser session or catalogue of every possible actor projection. Authored actor declarations do not enumerate dynamic `actorPath` identities or tell ServiceVersionChain which projections have enrolled. A projection can enroll without originating a command; Failure, no-op and empty selected-delta positions still advance its materialization.

Source acknowledgement can lag the receiving Repo's actual materialization head after a lost reply or interrupted enrollment. Neither that remote head nor ServiceActorVersionChain publication replaces this local scheduling fact. Enrollment normally reports the actual receiving head after catch-up; pushed delivery advances only after its durable receiving receipt.

## Proposed three-column row and exact version boundary

| Proposed column            | Required meaning and consumers                                                                                                                                 | Removal consequence                                                                 |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `actorName`                | Non-null text. Stored from the validated incoming projection key; used in membership, conflicts, selection, exact acknowledgement and receiver reconstruction. | Without it, distinct actor declarations with overlapping paths alias each other.    |
| `actorPath`                | Non-null canonical authored identity path. Membership and acknowledgement distinguish every enrolled actor identity partition.                                 | Without it, different identities within one actor share progress and delivery.      |
| `acknowledgedServiceIndex` | Non-null integer, with zero allowed. Enrollment and successful receipts monotonically advance the inclusive source acknowledgement.                            | Without it, ServiceVersionChain loses its durable per-projection scheduling prefix. |

The actor pair is unique together. Do not add a surrogate ID, packed substitute name, progress hash, nullable state or unproven secondary progress index. An absent row means **unenrolled**; zero means **enrolled without an acknowledged command position**. A caught-up row remains enrolled for future commands.

Deriving actor version must preserve exact identity, not choose whatever code is newest:

1. Keep the complete queue RPC key, including `actorVersion`, and retain the current comparison of every bound source owner field.
2. At `subscriberIdentityFromKey`, resolve only this Chain's exact configured Service release and its named actor. Compare the supplied version to that actor's exact version **before** extracting `(actorName, actorPath)`. Reject a mismatch; otherwise a wrong-version enrollment could update an existing valid pair's acknowledgement.
3. At `subscriberKeyFromIdentity`, combine this Chain's owner, stored actor name/path and that same bound actor declaration's version. Do not scan other Service releases, choose a latest version or substitute a command's original release.
4. Missing release/actor code fails reconstruction/delivery, preserving the membership/cursor and alarm recovery. It does not authorize deleting/filtering the row, resetting progress or selecting replacement code. No availability/retirement policy follows from this derivation.
5. Preserve exact receiving source checks, canonical actor-path validation, full-claims private resolution and the existing projection transaction. Source-side canonical-path validation need not move solely to perform the necessary version comparison.

The shared queue already supports named identity columns, an explicitly bound acknowledgement column and Effect identity/key callbacks. This proposal needs a Service-specific schema/binding change, not another shared string-ID mode or the fanout-copy hooks removed by Plan 215. Keep RPC `currentIndex` as the existing transport cursor; rename only the SQL acknowledgement field and its binding.

### Why not retain actorVersion as a fourth column?

The column reviewer favors retaining an explicit frozen receiving version so full-key reconstruction continues without consulting authored actor code. That four-column model preserves the current locator assertion and is technically sound. The lifecycle reviewer initially favored it, then recommended three after checking the Service-specific release map.

This finding recommends three because the exact bound Service release already determines the named actor's version, and successful receiving activation already requires that authored definition. No supported lifecycle requires delivery to an independently selected second version under this owner or successful delivery while that actor code is absent. A local authored lookup adds no cross-object coordination; when code is absent, failure retains membership/progress and retries, as receiving activation failure does today. The explicit enrollment comparison above prevents aliasing. Retaining a fourth field would repeat the fixed declaration association without another required durable fact.

This is a deliberate trade-off, not an assertion that actor version is unimportant or that all version fields should disappear. The complete capability key remains exact. Earlier Aggregate subscriber decisions are not reopened or automatically applied to this Service table. The immutable-catalogue and exact-release rules remain governing; deriving the version never authorizes replacement/latest routing.

## Enrollment, acknowledgement, recovery and deletion

1. ServiceActorVersionRepo activation arms pending selected-publication recovery and calls its source-bound subscriber's `subscribe()`. Catch-up fixes one history prefix, commits it, rereads the actual receiving materialization head and then enrolls. Failed catch-up does not create ordinary membership.
2. ServiceVersionChain decodes the complete receiver key and a nonnegative safe integer `currentIndex`, rejects progress beyond the committed source tip, and validates every bound owner field. Enrollment inserts identity/progress or monotonically advances it in a synchronous local transaction. The source trusts this internal report; its cursor is not a cryptographic proof or a public-client assertion.
3. A scoped producer lease spans the tip check and enrollment upsert outside the drain semaphore. This permits cold activation to enroll while a source drain awaits that Repo. Producer revisions preserve the new enrollment's recovery wake against an older empty drain.
4. Permanent commands cover the catch-up/enrollment interval. Each drain captures one source tip, selects lagging subscribers with bounded SQL, excludes in-flight/failed identities before the limit and reads each complete ordered suffix independently. Source production does not extend that drain indefinitely.
5. ServiceActorVersionRepo validates exact source/release/actor context and atomically applies resources, its materialization head and complete pending selected publication. Its successful receipt proves that local transaction. It does not prove ServiceActorVersionChain retention, private completion delivery, browser bootstrap or socket delivery.
6. Only after the successful receiving envelope does ServiceVersionChain acknowledge the last actual delivered row, using SQL `max`. The envelope's advertised `lastIndex` is not the acknowledgement. A stale in-flight receipt or repeated enrollment cannot rewind progress. A lost reply leaves the source cursor behind the receiving head; redelivery skips committed positions.
7. A failed subscriber keeps membership/progress unchanged for that attempt while other subscribers proceed. Later durable alarms retry backlog. Source append/enrollment producer leases, fixed-tip scheduling and alarm holds remain required. Caught-up rows remain members, and acknowledgement never deletes permanent commands.

**Deletion condition:** none in the supported lifecycle. There is no unsubscribe, expiry, idle cleanup or garbage collection. Capability disposal, browser disconnection, no selected delta and inactivity do not end membership. Deleting a row stops future pushes until that exact projection activates and enrolls again; resource/head/history rows remain separate facts.

## Current validation limits and bounded scope

The current source queue checks owner fields, key shape and cursor bounds, but does not independently resolve the authored actor/version/canonical path or supply `availableSubscriberIdentities`/`subscribersWhere`. Ordinary receiving activation resolves the exact actor/version and canonical path first. A direct internal enrollment can name unavailable actor code; a later delivery failure retains that row and its cursor for retry. No ordinary-path data-loss or privacy defect was established.

The proposed source-side exact version comparison is necessary **because stored version is removed**. It is not a proposal for general availability filtering, authored-path revalidation, retirement, retry suppression or deletion. Add no `active`, failure, last-seen, session or expiry columns. Missing code remains a failing recoverable delivery, not permission to invent another receiver.

If approved, implement only this fixed subscriber representation and queue binding, update affected ADR wording/consumers/existing checks, and require empty affected ServiceVersionChain storage under the hard-cut policy. No compatibility name column, migration, fallback lookup or replacement packed identity is justified. Keep Actor/Agent and other Service physical storage unchanged. This turn authorizes no implementation, reset or deployment.
