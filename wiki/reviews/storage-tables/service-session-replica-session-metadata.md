## Physical scope and row fact

[openServiceReplica](../../../packages/browser/src/sessionReplica/openServiceReplica.ts#L17-L41) composes selected model tables with the Service session tables and opens a fresh **in-memory SQLite database per owning Effect Scope**. Scope disposal closes it. The browser creates the local session ID for that lifetime before bootstrap; it does not restore a Service replica file. Mock Service sessions also acquire a fresh replica and seed resources/metadata together. Persistent ServiceNode identity/history belongs to a separate database and owner.

One row records **the Node prefix observed by this local replica and the authoritative Service resource base beneath its current optimism**. Its practical singleton is established by owning initialization. It is checkpoint state, not retained command history, canonical outcome, authenticated claims, pending delivery or a delivery acknowledgement. Initial resources may start at a nonzero captured prefix without retaining all covered Node/Service commands locally.

## Why Service needs three fields rather than Aggregate's four

The lifecycle reviewer initially retained sessionId as a database ownership witness. The column reviewer challenged whether that witness carries an independent supported fact. Both reviewers agree after reconciliation that it does not for this Service owner.

The browser generates the local ID and acquires a fresh database within the same Scope. [makeServiceReplicaValidator](../../../packages/browser/src/sessionReplica/makeServiceReplicaValidator.ts#L25-L43) fences the current initialized capability, captured sessionId and exact DB object. Asynchronous staging rechecks that exact capability before commit. Initialized callbacks also fence local ID/DB and release generation. The receiver validates the complete snapshot identity against its bound declaration and retained lifetime identity before resource replacement; it retains private full encoded claims across reset. Those are the actual authority/lifetime checks.

Service command IDs are independent generated CUIDs, not derived from local sessionId. No supported persistent Service replica restoration uses SQL sessionId to recover that local ID. Removing this field deliberately removes the extra core SQL miswiring assertion; it does not pretend to preserve that comparison elsewhere. Checkpoint presence and singleton cardinality remain real requirements and must replace key-dependent lookup/upsert plumbing explicitly.

Aggregate's Native replica restoration is a different ownership/lifecycle context. Its earlier four-column finding is not a reason to preserve a redundant Service field or to revise Aggregate in this turn. Existing Shapes and SQLite definition binding already permit tables without a declared primary key, so this three-field recommendation needs no schema-framework change or artificial fourth field. Initialization must own singleton creation/replacement; ordinary mutations must never silently update multiple checkpoint rows or pick an arbitrary one.

## Allocation, transaction, retry and recovery requirements

1. **Initialization:** validate snapshot release/Actor/session/full claims and receipt reconciliation before replacing resources. Ordinary snapshots retain local command rows and positions, clear current inverses, install resources/captured checkpoint, retain requested original/final evidence, then replay surviving inputs. The proposed singleton row and resources must commit together. Do not rebuild an authoritative checkpoint from retained command maxima or a cached capability.
2. **Local staging:** stage currently reads metadata, bounds the stored allocator, evaluates once, retains the command/current inverse state/resources and advances the counter under one synchronous transaction and final capability fence. Replace the allocator read/write with an indexed retained maximum computed in that same transaction before new insertion. Empty history allocates one. Reject a nonpositive, unsafe or exhausted candidate under the existing integer ceiling. No cached/outside-transaction allocation, replacement counter or reservation row is needed.
3. **Import/retry:** allocate only for a genuinely new original or final phase. Reuse local.sessionIndex for original/final coordinate enrichment. Exact retries return without allocation; point recovery ahead of the public prefix defers before allocation. Each later new row in a batch must see earlier inserts in that transaction. Failure/rollback consumes no local position or partial resource/checkpoint/inverse change. Keep both phase rows and their existing indexes; this metadata review does not reopen the command model.
4. **Ordered Node coverage:** page validation checks positive/dense Node coordinates against afterNodeIndex and the declared throughNodeIndex. Apply retained records, selected resource changes and pending replay first, then advance coverage within the same transaction. Empty pages cannot claim unseen coverage. Direct point receipts use recovery mode without a through-cursor, so even an observed high coordinate cannot skip intervening Node records.
5. **Service resource continuity:** new final application must advance serviceIndex by exactly one; equal-position hash disagreement fails. Covered finals may settle an original without reapplying their old delta. Ahead point recovery stays deferred for ordered stream delivery. Failure or no-op output can advance the prefix without visible resource changes. Nullable private failure does not establish canonical outcome.result.\_tag.
6. **Reset and retention:** an announced DEV reset withdraws the capability and marks discardPending before the replacement snapshot. Snapshot replacement then clears commands and metadata/resources as part of its synchronous transaction and seeds the new captured prefix. With empty retained commands, derived allocation naturally restarts at one. Ordinary reconnect, final observation and Node acknowledgement do not delete command rows or the checkpoint. Scope disposal closes the entire in-memory database. A future pruning/persistent Service design would need to reconsider the local allocator/identity model; no such path is introduced here.

## Original finding and limits

Both independent reviewers support the final three-column recommendation after explicitly reconsidering sessionId. The current counter/reset implementation has no identified ordinary supported-path defect in this source review. The finding is redundant identity/allocator storage and unnecessary key plumbing; its cleanup requires the explicit singleton and lifetime boundaries above. Existing readers and old ADRs are evidence of current machinery, not reasons to preserve it.

## Approved implementation — written, unverified

[Plan 226](../../archive/plans/226-plan-service-replica-checkpoint-and-session-index.md) now declares exactly three required columns on serviceSessionMetadata: afterNodeIndex, serviceIndex and dispositionChainHash. There is no declared primary key, SQL local/release identity, stored allocator or replacement singleton field. Core stage/import/ordered-retention/snapshot signatures no longer forward a local ID just to compare it against SQL. Local sessionId remains on the initialized capability and in Devtools, with captured ID/DB/current-capability fences and private full authenticated identity unchanged in responsibility.

readServiceSessionMetadataTx reads at most two rows and rejects ambiguous checkpoint state. Ordinary staging/import/final paths require exactly one row and reject absence. Initialization permits absence, checks singleton state before any resource mutation and deletes/reinserts exactly one checkpoint inside the same synchronous snapshot transaction. Snapshot resources/current inverses, retained receipt input and replay remain atomic with that checkpoint. Mock seeding writes the same three fields with resources. Progress publication selects only serviceIndex and dispositionChainHash rather than spreading identity/allocator columns over the capability.

allocateServiceSessionIndexTx reads the greatest retained command sessionIndex through its index, adds one and retains the existing positive/safe-integer/exhaustion ceiling. Staging and genuinely new imported phases allocate in their insertion transaction. Exact retries, coordinate enrichment and ahead point-recovery deferral keep/consume no new position; later batch inserts see earlier inserts. Ordinary snapshots retain all command positions. Explicit reset clears command history, so empty retained history naturally allocates one. The stored counter and its increment/upsert plumbing are removed.

Service commands retain their thirteen-column Plan 225 model and phase indexes. Bound identity/claims checks still precede projection mutation. Ordered Node coverage, cursor-neutral point receipts, Service prefix/hash continuity, covered-final non-reapplication and reset fencing keep their ownership. ServiceNode guard 15, AggregateNode guard 15, Native replica guard 5, Aggregate storage and Agent producer state are outside this Service cutover; preservation comparisons remain unrun. Empty affected storage is required without migrations, compatibility aliases/fallback decoding or automatic reset.

Actual browser/core consumers, existing identity/reset assertions, module READMEs, ADRs 003/004, glossary, affected architecture/pattern prose and Plan 151 record the change. The existing mock capability also binds encodedClaims for its current validator/API, preserving complete immutable claims ownership. No test/fixture/runner/configuration file is created. No deployment or commit occurs.
