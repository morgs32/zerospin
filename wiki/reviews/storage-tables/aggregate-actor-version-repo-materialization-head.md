## Physical scope and represented fact

AggregateActorVersionRepo is bound to `systemId / aggregateId / aggregateName / aggregateVersion / actorName / actorVersion / actorPath`. The release identifies the evaluated Aggregate history being materialized; the actor triple identifies the exact authored selection and canonical claims partition. Those identity fields belong to the physical owner, not this row.

Slot `1` records that AggregateActorVersionRepo has materialized the contiguous AggregateVersionChain command prefix through `aggregateIndex`, with its corresponding `dispositionChainHash`. It is a **materialization checkpoint**, not admitted input, contract evaluation history, source acknowledgement or selected-history publication progress. Overwriting the current checkpoint retains no per-command journal in this resource-owning Repo.

### Singleton and genesis semantics

The table uses ordinary `makeTable`. Its primary key guarantees uniqueness per integer; there is **no SQL `CHECK(singletonId = 1)`** enforcing one allowed slot. Supported writers/readers enforce slot `1`. Arbitrary additional slots are permitted by the physical schema but have no production writer or reader in this protocol. This is a representation distinction, not an observed supported-path defect or a reason to introduce another abstraction.

No row is inserted merely to represent genesis. An absent slot means `aggregateIndex = 0` and `genesisDispositionChainHash()`: no Aggregate command prefix has been materialized. This is a reader fallback, not nullable columns or a database default. The first applied command creates the head. No ordinary path clears it after publication or when resources become empty.

### What the hash establishes

`dispositionChainHash` incorporates the previous hash, Aggregate command position, canonical command `id` and only `outcome.result._tag`. It identifies the ordered Success/Failure prefix. It does **not** hash resource contents, operation bodies, result payloads, actor claims or finalization timestamps. Retain the precise name; do not describe it as a resource-integrity digest or complete evaluated-command identity.

## Atomic lifecycle and recovery

1. AggregateActorVersionRepo activation catches up and enrolls its source-bound projection subscriber. Catch-up reads this Repo's committed head after each page; enrollment reports that actual index to AggregateVersionChain. These RPCs run outside local SQL.
2. `applyEvaluatedCommandsTx` reads slot `1`, binds/validates each complete evaluated command and applies the delivered page synchronously. New positions must equal the local cursor plus one. Already committed positions do not reapply operations or create another selected publication; immutable repeated-command identity belongs to AggregateVersionChain.
3. For each new position, projection application applies model mutations, computes and checks the next disposition hash, computes the selected delta, and calls `commitProjectionTx`. That procedure inserts the complete pending selected publication and upserts the index/hash pair. Resources, all page publications and the final head commit together. A failure later in the page rolls back the whole page, including earlier commands in that page.
4. Refusals and commands with empty selected deltas still advance the prefix and retain their selected command positions. Resource rows, resource versions and timestamps therefore cannot reconstruct the head.
5. AggregateVersionChain advances its actor subscriber acknowledgement only after AggregateActorVersionRepo returns a successful page receipt. A lost receipt can leave source acknowledgement behind this head. Redelivery skips the materialized prefix; successful receipt or reenrollment can then advance source acknowledgement without reapplying resources.
6. Complete pending publication has independent alarm recovery and deletion. AggregateActorVersionRepo can commit its head while publication to AggregateActorVersionChain remains pending. Publication acknowledgement deletes pending rows but never deletes or rewinds this head. The head is necessary even after the pending table drains completely.

## Snapshot boundary and independent durable facts

`captureProjectionSnapshotTx` reads selected resources and the head in the same synchronous transaction, fixing resources/index/hash at N. Outside SQL, `getSnapshot` publishes through N, requests AggregateActorVersionChain's checkpoint at exactly N, compares its hash and bounds the requesting producer's private completion prefix through N. A concurrently published newer command cannot relabel the captured resource graph with a later position.

- [Local resource/head capture](../../../packages/system-worker/src/aggregateProjection/getSnapshot/captureProjectionSnapshotTx.ts#L26-L47), [publish and verify exactly N](../../../packages/system-worker/src/aggregateProjection/getSnapshot/getSnapshot.ts#L80-L116), [exact historical checkpoint lookup](../../../packages/system-worker/src/aggregateSessionChain/getCheckpoint.ts#L19-L35).

The local head, AggregateVersionChain's source acknowledgement and AggregateActorVersionChain's published history can legitimately differ after interruption. None is a redundant replacement for the others: this head proves local materialization; source acknowledgement records AggregateVersionChain's receipt; selected history records AggregateActorVersionChain's retention. Reading a remote maximum or pending row would change the local checkpoint contract and cannot occur inside the synchronous resource transaction.

The resource owner retains this one current checkpoint for its lifetime. There is no production deletion, expiry or reset path for the head. Deleting or rewinding it while keeping resources would discard duplicate protection and allow already applied operations to run again. No copied command ID, execution-start timestamp, publication cursor or source acknowledgement belongs in this row.

## Reconciled finding and verification limits

Independent column-design and lifecycle reviewers agree to retain all three columns and their current names. The singleton key is infrastructure; the index/hash pair is the durable local prefix associated with the resource graph. Current transaction, retry, enrollment and snapshot paths are sound. No schema change or unsettled implementation decision is proposed.
