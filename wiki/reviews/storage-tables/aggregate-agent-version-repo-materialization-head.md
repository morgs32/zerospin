## Historical physical owner and represented fact

AggregateAgentVersionRepo is bound to `systemId / aggregateId / aggregateName / aggregateVersion / agentName / agentVersion`. There is no actorPath or per-Node partition. The authored agent version fixes its Aggregate release, model selection and session definition. The physical owner already supplies these identity fields; none belongs in this checkpoint row.

Slot `1` records the contiguous AggregateVersionChain evaluated-command prefix materialized locally through `aggregateIndex`, with its corresponding `dispositionChainHash`. That prefix covers every Aggregate command, including other producers, Failure and commands with empty selected deltas. Agent name/version restricts private completion ownership; it does not restrict which source positions advance the materialization head.

This is a **materialization checkpoint**, not retained execution history, source subscriber acknowledgement, private producer progress or Agent Chain publication progress. AggregateAgentVersionRepo owns a resource graph; its separate AggregateAgentVersionChain owns permanent selected history. Replacing the current checkpoint does not retain a per-command journal in the resource owner.

### Singleton, constraints and genesis

The integer primary key enforces one row per key, not one allowed row for the entire table. There is no SQL `CHECK(singletonId = 1)`, index-range CHECK or hash-format CHECK. Supported writers/readers enforce slot `1`; arbitrary extra slots require out-of-protocol SQL and are ignored by production readers. This is a precise constraint limit, not an observed supported-path defect or a reason to introduce another singleton abstraction.

No genesis row is seeded. Missing slot `1` means index `0` and `genesisDispositionChainHash()` in readers; this is absence semantics, not nullable fields or SQL defaults. The first materialized command creates the head. An empty resource selection at a later index still has a retained head and does not imply genesis.

### Exact hash meaning

`dispositionChainHash` chains the previous hash, Aggregate position, canonical admitted command `id` and only `outcome.result._tag` (Success or Failure). It does not hash resource contents, model/external operations, result/failure payloads, claims or `outcome.finalizedAt`. It identifies the command/disposition prefix; it is not a resource-integrity or complete evaluated-command digest. No new hash or timestamp field is needed here.

## Atomic lifecycle and independent acknowledgements

1. Agent activation catches up and enrolls `agentVersionChainFanoutSubscriber`. It validates the source Aggregate tuple, reads this Repo's actual committed index after each catch-up page and reports that index during enrollment. Catch-up fixes a source boundary; subscription and RPC stay outside local SQL.
2. `applyEvaluatedCommands` resolves the bound release and enters `applyEvaluatedCommandsTx` for the delivered page. The transaction reads slot `1`, binds complete evaluated commands and validates them before skipping repeated positions. New positions must equal the local cursor plus one. Repeated committed positions do not apply resource mutations, advance the head or create another pending publication; immutable repeated-command identity belongs to AggregateVersionChain.
3. For each new position, the transaction applies model mutations, computes/checks the next disposition hash, computes selected resources/delta and calls `commitProjectionTx`. Its Agent branch inserts a complete `exposedCommandOutbox` row, then upserts slot `1`. Resources, every new pending publication in the page and the final index/hash commit together. A later failure rolls back the whole page, including earlier rows from that page.
4. Failure and no-op/unselected commands still advance this all-command prefix. External descriptions never schedule requests in this projection; only model mutations are materialized. No execution program is rerun to derive the checkpoint.
5. AggregateVersionChain advances this agent subscriber's acknowledgement only after AggregateAgentVersionRepo returns a successful receiving RPC envelope. A lost reply can leave source acknowledgement behind the committed head. Redelivery skips the committed resource prefix; a successful retry or reenrollment can advance source acknowledgement without replaying those mutations.
6. Complete selected publication has independent alarm recovery. `exposedCommandOutbox.producerLease` arms recovery before projection work; the Repo explicitly runs `exposedCommandOutbox.wake()` afterward without awaiting Chain publication. AggregateAgentVersionRepo may therefore commit its head while publication is still pending. The publication queue deletes only acknowledged pending rows; it does not delete, rewind or otherwise own this head.

## Snapshot and Agent bootstrap boundary

`captureProjectionSnapshotTx` reads selected resources and this head in one synchronous transaction, fixing resources/index/hash at N. Outside SQL, `getSnapshot` publishes through N, asks AggregateAgentVersionChain for the checkpoint at exactly N, compares `dispositionChainHash` and reads the requested Node/session/Agent Origin's contiguous private prefix bounded by N. Newer publication cannot relabel the captured resource graph with a later index.

`getAgentBootstrap` first obtains that coherent snapshot. It then recovers only the immutable private outcomes covered by `snapshot.resolvedThrough`, with both Aggregate bounds fixed to `snapshot.aggregateIndex`. Agent bootstrap does not read the head independently or substitute a private push maximum for its all-command position.

The three durable facts may legitimately differ: this head proves AggregateAgentVersionRepo's local materialization; AggregateVersionChain's subscriber cursor records its successful page receipt; AggregateAgentVersionChain history proves selected publication retention. Neither remote maximum nor a pending row replaces the checkpoint committed with local resources. In particular, retained history may lag local resources, and acknowledged pending rows may disappear entirely.

## Retention and reconciled finding

Retain the current head for the lifetime of this physical Agent Repo. There is no supported deletion, expiry or reset path for it. Publication acknowledgement, socket close, browser delivery and a caught-up source subscription are not deletion conditions. Deleting or rewinding this row while retaining resource tables would remove duplicate protection and could reapply previously materialized mutations. No copied command ID, timestamp, private producer cursor or source acknowledgement belongs in the row.

Independent column-design and lifecycle reviewers agree: retain all three columns, their current names and the existing transaction boundaries. The Agent-specific owner, actual Agent receive branch, physical pending table, all-command progress, bootstrap and recovery paths were checked rather than inferred solely from Actor schema reuse. No unsettled implementation choice or ordinary-path correctness defect was identified.

The original review changed only this finding and Plan 151. Current source, document links/ranges, formatting and scoped whitespace were checked. No runtime/type/lint/test/build checks were rerun; no production code, test files, fixtures, runners, storage or Explorer verification changed. Plan 210's later pending-only implementation verification is recorded separately in its archived plan; it does not change this head or turn the original source review into a runtime check. No schema change or storage reset is proposed. Additional AggregateVersionChain publication `dispositionChainHash` validation remains deferred at the maintainer's direction.
