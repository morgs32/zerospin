### Why the allocator derives from commands

Every allocated producer position is retained on its canonical command row. Final exposure preserves that pushIndex even though pending payload/time/inverses clear. Snapshot recovery replaces resources/checkpoint and current inverses, but does not prune commands. Foreign final-only rows have null pushIndex and do not contribute to the local maximum.

The only supported individual command deletion is a proven unadmitted, unfinalized refusal. That transaction deletes the refused row, shifts later pending positions down, decrements the current allocator and replays optimism together. Thus it removes/compacts exactly the evidence from which the next position can be derived. With no later positions, deleting the greatest refused row lowers the maximum naturally. Refusing the only allocated command returns empty allocated history to maximum zero/next one. Admitted/finalized proof cannot be removed or compacted by this path.

The existing stored counter therefore maintains the same invariant as retained commands; it is not an independent reservation/high-water fact. A later pruning or producer-restoration feature would need to revisit this reasoning, but no such path exists in this supported transient lifecycle.

1. Reread the canonical pending row and producer singleton inside the existing synchronous allocation transaction.
2. For an assigned coordinate, retain its exact value after current identity/phase/allocated-prefix checks. Do not enter a new-allocation exhaustion branch.
3. For an unassigned coordinate, read the retained maximum within that transaction, derive the next value, preserve positive/safe-integer/safe-successor checks and assign it atomically. Keep the current ceiling rather than silently changing protocol exhaustion semantics.
4. For receipt validation, prefix promotion, mismatch recovery and publication, use actual allocated maximum/bounds without blindly computing an unsafe successor. Derive bounds at the relevant transaction boundary, not from a cached UI value.
5. Keep refusal deletion/compaction/replay atomic but remove the redundant allocator decrement. Failure must roll back command positions, resources and current inverse state together.

## Why admission remains independent

Consider the same retained pending command at pushIndex 1 with aggregateIndex null. Before a receipt, prefix zero means its transmission may be uncertain and must remain retryable. After AggregateChain admission is acknowledged, prefix one permits the next submission even though command 1 is still optimistic and lacks final exposure. The command row itself has not gained a final field or another admission marker. Those identical rows therefore cannot reconstruct the admission fact.

Using maximum allocated pushIndex as admission would skip necessary retransmission after an admission timeout. Using only finalized command rows would forget acknowledged-but-unexposed work and repeatedly submit position one instead of allowing position two. Exact idempotent retries do not replace the independently required submission eligibility/progress behavior.

Final exposure can establish an additional admission lower bound. The journal promotes the known prefix from actual own producer rows with final proof and settles an active admission when its final arrives. A later receipt remains valid against the retained canonical ID/push position and cannot reduce the acknowledged prefix. Canonical outcome.result.\_tag is not inferred from this acknowledgement or nullable exposed failure.

A validated node-admission-index-mismatch has a different transition: the earlier expectedPushIndex can lower admittedThroughPushIndex to expected minus one while preserving allocated coordinates for retry. That rewind must refuse contradiction with any retained finalized producer position at or beyond the requested boundary. Do not replace this protocol with a permanently monotone max or derive its state from current finals alone.

## Singleton, publication and retention requirements

1. **Explicit cardinality:** the current unfiltered first-row reader and key-one writer can disagree on malformed wrong-key/extra-row state. Only the one-row seed is produced by supported ordinary code, so this is not a reproduced ordinary-path failure. Remove the constant key and require exactly one row for all readers/writers instead of silently picking/updating unrelated rows. Missing state must fail rather than reset acknowledgement.
2. **Separate lifetime ownership:** delivery metadata is initialized once with producer identity. Core resource snapshot installation replaces sessionMetadata, while acknowledged producer progress must survive reconnect/recovery. Retain this separate row/table; merging it into the resource checkpoint would make projection replacement carry unrelated browser producer-admission state.
3. **Publication:** derive displayed pushIndex from retained allocated maximum, including settled producer rows and refusal compaction. Update every bound/read/publication consumer of nextPushIndex. Allocation now changes commands without a counter write; preserve command-change and explicit allocation/refusal publication rather than relying on allocator metadata notifications. Keep acknowledgement and resource-checkpoint notifications as their own triggers.
4. **Transactions/privacy:** preserve canonical row reread, exact current-pending/receipt checks, captured producer/attempt/lifetime fences, admitted/finalized refusal contradictions and atomic rewind/delete/compaction/replay. Resource finalization and later admission-prefix promotion remain distinct facts; retained final proof permits recovery if promotion lags. Foreign final rows must never create local producer admission/failure authority.
5. **Retention:** do not delete/reseed admission metadata after ordinary receipt, final exposure, pending drain, snapshot or socket reconnect. Keep acknowledged/finalized command evidence. Scope disposal closes the whole transient database; a new lifetime has a new producer ID and fresh zero prefix. Add no TTL, automatic reset, persisted Agent restoration or per-command admission table.

### Reviewer reconciliation and limits

Both reviewers support one required admittedThroughPushIndex column, transaction-local command-derived allocation and an explicit singleton invariant. They agree that admission receipts, final proof and allocation are distinct facts, that refusal leaves no independent allocator high-water state, and that producer admission should remain separate from replaceable resource snapshots. The valid-existing-coordinate retry path must stay usable at allocation exhaustion.

No ordinary supported-path runtime failure was reproduced. This is redundant allocator/key state and a missing explicit singleton guard, with coordinated consumer/notification cleanup required by a later approved implementation. Existing readers and old ADRs do not justify preserving redundant state.

## Implementation outcome — unverified

The SQL key/counter, key predicates and counter updates are removed.

readAgentPushIndexTx supplies the retained allocated maximum, defaulting to zero. Publication reads allocated progress directly and subscribes to command changes as well as nodeMetadata/sessionMetadata changes.
