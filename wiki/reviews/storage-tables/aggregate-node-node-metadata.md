## Original source audit — before Plan 230

The following sections record the twelve-column implementation at review time. Current implementation is summarized above and below; descriptions of removed SQL fields are historical evidence.

### Physical scope, row fact and retention

[aggregateNodeMetadata](../../../packages/core/src/AggregateNode/aggregateNodeTables.ts#L13-L26) declares the SQL table nodeMetadata. Its single intended row combines persistent producer generation and storage binding, independent AggregateChain admission progress, the materialized resource checkpoint and an explicit submission-pause preference. It is mutable identity/checkpoint/control state, not retained command history, delivery payload or an authentication grant.

1. **Connected browser:** a named Aggregate SharedWorker and namespace lease own IndexedDB-backed SQLite. The retained fingerprint covers the complete bound identity, including API/System, Aggregate/Actor/session declarations, Aggregate owner, claims and definition hash. Attachment checks the expected storage identity before opening/using retained state. Closing the host drains work and closes SQLite; it does not delete this row or history. [SharedWorker ownership](../../../packages/browser/src/AggregateNode/makeAggregateSharedWorker.ts#L9-L38), [persistent SQLite opening](https://github.com/morgs32/zerospin/blob/41b548a019ff1e08f65f60c9459e0908a80c64f5/packages/browser/src/Node/openNodeStorage.ts#L8-L54), [attachment/storage binding](../../../packages/browser/src/AggregateNode/makeAggregateWorkerRuntime.ts#L91-L116).
2. **Standalone browser:** the durable address follows authored Aggregate/Actor/session scope and resolved path, rather than per-tab claims or compiled build identity. The stored sessionKey separately hashes that address key, aggregateId and full lock. Ordinary reopen compares the fingerprint; explicit replacement may change the lock but still rejects a different stored Aggregate owner before dropping state. [Stable standalone address](../../../packages/browser/src/StandaloneNode/standaloneIdentity.ts#L39-L53), [namespace](../../../packages/browser/src/StandaloneNode/makeStandaloneSharedWorker.ts#L18-L35), [stored fingerprint and replacement call](../../../packages/browser/src/StandaloneNode/makeStandaloneWorkerRuntime.ts#L173-L213), [owner check before replacement bypass](../../../packages/core/src/AggregateNode/AggregateNode.ts#L180-L208).
3. **Native:** the Aggregate Node uses a persistent node file named from the complete identity key, with the directory/storage owner retaining the host lease. It constructs the same AggregateNode and preserves its row across ordinary reopening. Authentication needs the stored nodeId before the first baseline is installed. [Native file/Node ownership](../../../packages/native/src/openAggregateNativeNodeOwner.ts#L30-L65), [baseline startup](../../../packages/native/src/openAggregateNativeNodeOwner.ts#L128-L142).

Fresh provisioning writes one row with generated nodeId, bound identity, initialized false, allocator values one, admission/outcome prefixes zero, index zero/genesis hash and pushPaused false. Initial baseline installation is a later resource/checkpoint transaction. Ordinary reconnect resumes this generation; it does not replace the baseline or clear history. Full replacement rotates nodeId and resets producer progress atomically with clearing commands and replacing resources. The connected path clears pause; ordinary standalone baseline reset preserves it. [Provisioning](../../../packages/core/src/AggregateNode/AggregateNode.ts#L218-L261), [baseline installation](../../../packages/core/src/AggregateNode/AggregateNode.ts#L279-L328), [whole-generation replacement](../../../packages/core/src/AggregateNode/AggregateNode.ts#L751-L831).

### Every current column and constraint

There are twelve declared fields: id is an integer primary key; the eleven others are explicitly required. initialized and pushPaused use integer boolean mode. There are no declared defaults, foreign keys, secondary indexes, expiry, timestamps or structured JSON members on this table. sessionKey is opaque text, not a retained identity object; its preimage is domain context, not nested SQL columns. The primary key does not restrict id to one, and no declared check enforces singleton cardinality, boolean values, safe ranges or checkpoint validity. Initialization explicitly supplies all values.

### Derivation, readiness and transaction requirements

1. Read allocator maxima inside the existing original/final append transaction, not from a previously published snapshot. Preserve exact duplicate behavior before new-allocation exhaustion checks and the existing positive/safe-integer/safe-successor ceiling. Commands are retained for the entire generation; replacement deletes all commands while rotating nodeId, so empty history naturally restarts allocation. No independent allocator reservation survives command deletion.
2. Derive private outcomeIndex by ordered original push positions and canonical-ID matching final evidence, retaining the first-gap stop. Current [hasNodeCommandFinal](../../../packages/core/src/Node/hasNodeCommandFinal.ts#L4-L15) and [completion scan](../../../packages/core/src/AggregateNode/retainAggregateFinalTx.ts#L118-L144) already express the relevant proof. Do not confuse Node append order, producer allocation, AggregateChain admission, private finalization or public materialization.
3. Keep a durable prebaseline row with nodeId/owner/fingerprint/admission/pause state. Seed both checkpoint fields null; reject partial pairs. Baseline installation atomically writes validated resources and both checkpoint fields. A present index must remain a safe nonnegative integer with valid hash; zero/genesis is a valid installed baseline. Ordinary new-original admission and final application require a present pair, and initialize(create=false) must still reject incomplete storage. Prebaseline snapshots must expose unready state without publishing a fabricated valid checkpoint. [Connected prebaseline authentication](../../../packages/browser/src/AggregateNode/makeAggregateWorkerRuntime.ts#L217-L244) and [Native startup](../../../packages/native/src/openAggregateNativeNodeOwner.ts#L63-L65) require nodeId, not an already materialized baseline.
4. Replace id=1 access with explicit singleton presence/cardinality checks before ordinary reads/mutations, keeping the check and mutation in the same admitted SQL program/transaction. Absence during initial provisioning permits creating the row; it must not silently recreate missing producer state on ordinary access.
5. Preserve resources/checkpoint/local history/admission settlement within the current commit boundary. ### Reviewer reconciliation and limits

Both reviewers support removing the key and three derived caches, retaining durable producer identity, storage/owner binding, independent admission and explicit pause, and keeping the actual materialization checkpoint. The lifecycle review initially retained initialized because today's nonnullable zero/genesis pair cannot distinguish readiness. The column review proposed absence of the checkpoint itself. After reconciling prebaseline authentication, both agree that the nullable pair preserves the readiness fact with seven columns, provided the durable row/nodeId, pair consistency, baseline transaction, incomplete-storage rejection and coordinated consumers remain intact.

No ordinary supported-path correctness defect was established by source review. The stored allocators/completion prefix duplicate retained history, the readiness boolean duplicates checkpoint presence once absence is represented honestly, and the key does not enforce the intended singleton. Existing readers and ADRs are context, not reasons to preserve those representations.

The original review changed only this finding and Plan 151. The approved follow-up implementation and documentation are now written under active Plan 230.
