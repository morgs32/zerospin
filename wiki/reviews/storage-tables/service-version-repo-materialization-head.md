## Physical owner and represented fact

ServiceVersionRepo is bound to `systemId / serviceName / serviceVersion`. Its configuration resolves that exact authored release and composes its Service-owned model tables with fixed infrastructure tables. Owner identity and release do not vary within this database and need no columns in the head.

One row in slot `1` means this exact release has locally evaluated and materialized the contiguous admitted-command prefix through `serviceIndex`, with the corresponding local disposition chain hash. This is **checkpoint state committed with resources**. It retains neither admitted commands nor execution/audit history, individual outcomes, external requests or publication acknowledgements.

## Every column, constraint and consumer

All three columns are required/non-null, with no SQL defaults. `singletonId` is the integer primary key. There are no secondary indexes, SQL foreign keys, structured JSON fields, extra framework-added declared IDs or timestamps. Supported progress comes from contiguous execution, not a SQL `max` update.

### Singleton and absence semantics

The primary key guarantees uniqueness per slot, not a SQL restriction that only slot `1` can exist. There is no `CHECK(singletonId = 1)`, positive-index CHECK or hash-format CHECK on this table. Supported readers/writers enforce the slot and contiguous progress; the reader selects scalar columns directly rather than validating/recomputing retained history. These are precise constraint limits, not an observed supported-path defect or a requirement for another state table.

There is no seeded genesis row. Before the first committed command, absent slot `1` yields `{ serviceIndex: 0, dispositionChainHash: genesisDispositionChainHash() }`. The Service genesis is SHA-256 of `zerospin.service.disposition.v1`. This is application-level empty-materialization semantics, not nullable columns, SQL defaults or a compatibility repair for resources whose checkpoint was manually removed. A later empty resource graph does not imply genesis.

### Exact disposition hash meaning

`dispositionChainHash` extends SHA-256 over `[previousHash, serviceIndex, commandId, outcome.result._tag]`, where the command ID is the admitted command's canonical `id`. It includes only the local Success/Failure decision. It excludes result/failure contents, resource/model/external-operation bodies, Origin, `executionStartedAt` and `outcome.finalizedAt`. It is not a resource checksum, complete execution-output digest or proof that an external provider performed an effect.

The hash is release-local because ServiceVersionRepo evaluates with its bound release. Replay requires a finalized source command but deliberately clears the original outcome before local evaluation; a different receiving release can derive a different disposition. No copied source-original hash or globally combined original-release hash belongs in this row.

ServiceVersionChain already recomputes published hashes against its retained predecessor and validates contiguous publication. Do not carry AggregateVersionChain's separately deferred additional-validation question over as an alleged missing Service check. This review proposes no historical recomputation in the head reader.

## Atomic materialization and duplicate recovery

1. A fresh original validates Service owner/release and a positive safe `serviceIndex`. It checks this head before predecessor replay or fresh declaration lookup. An already materialized position recovers its complete result; it never authorizes reevaluation merely because pending publication has been deleted.
2. A fresh original first catches up through its predecessor outside the execution permit. Under the permit it rechecks the head before resolving the exact release. `materializeCommandTx` rechecks local progress inside the synchronous transaction: a duplicate skips evaluation, a new position must equal `head.serviceIndex + 1`, and replay requires a non-null source `outcome`.
3. `executeServiceOccurrence` evaluates and applies successful resources inside the business savepoint. A supported public refusal rolls that savepoint back before finalizing a Failure outcome. Failure and zero-operation Success both commit a new head and complete pending publication; neither can be reconstructed by inspecting resource changes alone.
4. `finalizeServiceOccurrence` derives the local `outcome: { result, finalizedAt }` and next hash. `retainServiceResultTx` encodes/inserts the complete publication and upserts the head within the same outer transaction as resources. Encoding, SQL or head-write failure rolls everything back. Unclassified infrastructure failures, defects and interruption propagate their Cause without establishing a new prefix.
5. Committed duplicates read complete pending publication, otherwise exact permanent ServiceVersionChain history. Recovery validates its association with authoritative admitted input outside SQL/execution permits. The head proves completed local progress; it does not itself retain the command ID or outcome. Missing, conflicting or unavailable history fails recovery and does not permit reevaluation.
6. A replay page commits each command independently. If a later command fails, earlier resource/head/publication commits survive while source acknowledgement can remain at its old position. Retrying earlier commands recovers their committed result without reapplying resources. Replay omits external emissions before preparing them.

## Head, source acknowledgement and publication are different facts

ServiceVersionRepo commits this head with resources before returning an original result. ServiceChain subsequently retains its exact original output in `originalExecutions`; a lost original reply can leave this local head ahead of ServiceChain's contiguous finalized replay prefix. ServiceChain's replay-subscriber acknowledgement separately follows successful receiving RPCs and can lag the committed local head. ServiceVersionChain publication has independent recovery and can also lag local materialization. None of those remote positions replaces the resource-owning Repo's local checkpoint.

Activation arms pending-publication recovery and awaits `.catchup()` through one captured finalized source boundary. The subscriber reads this head after receiving pages; a local head already beyond that boundary is preserved without rewind or forced original finalization. Ordinary named queries and authorization read current committed local resources under the execution permit rather than forcing source-tip progress. Explicit command-result waits remain a separate bounded execution/replay path.

Acknowledged publication deletes pending publication rows, not this head. Retain the head for the lifetime of this physical materialized resource view; no supported expiry/delete/reset path exists. Deleting or rewinding it while retaining resources removes the atomic progress proof and can permit incorrect reevaluation or break continuity. Add no timestamp, original command ID, source-acknowledgement copy or publication cursor to repair that responsibility.
