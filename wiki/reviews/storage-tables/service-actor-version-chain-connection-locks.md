## Physical owner and row responsibility

One ServiceActorVersionChain fixes `{ systemId, serviceName, serviceVersion, actorName, actorVersion, actorPath }`. Configuration resolves the exact Service release and actor view/canonical path before using this history-and-connections schema. ServiceActorVersionRepo separately owns application resources and materialization state.

One `connectionLocks` row records the capabilities admitted for one server-created WebSocket connection. This is temporary **connection authorization resource state**. It is neither application resource history, a materialization checkpoint, complete pending delivery, immutable command history nor subscriber progress. SQL holds the selected capabilities; the hibernating attachment holds admitted identity, actual full claims, session, producer binding and phase.

`connectionId` identifies this socket, not a Node or named session. Multiple sockets can share actor, session, claims and Node while having independently admitted selections and lifetimes. Reconnect admits a new socket; it does not reuse a historical connection row.

## Current three-column model — historical contract selection

1. `connectionId`: required text primary key for one server-created socket.
2. `contractVersions`: required JSON map from each admitted ordinary contract name to its selected public lineage version.
3. `modelNames`: required JSON array of admitted model names.

Empty selections grant nothing and remain a present admission. Full lock,
selected declaration/claims/model validation and relational model closure remain
at admission. The contract must be exposed by the bound actor and the requested
version must resolve within its public lineage; the Service release and actor
remain pinned exactly. No global registry search or latest-version choice is allowed.

Capability recovery resolves every stored version within that same actor lineage,
validates selected model requirements, and returns null for missing, invalid,
external or malformed capabilities. Pushed contractVersion must equal the stored
selected version. The old name-only association cannot recover this historical
choice, so contractVersions is required domain state rather than a copied definition.

## Original admission, privacy and broadcast finding — before Plan 218

At the original review, SystemRepo replaced caller-supplied trusted headers and forwarded the spent admission to the exact ServiceActorVersionChain. `onConnect` validated forwarded Service version/path/session, lock actor/version/session, full declarations, actual claims codec and every canonical actor partition identity field, plus the issued Node. These checks still precede capability projection/installation; SystemRepo's ticket boundary remains separately governed by Plan 221.

The trusted attachment retains Service name/version, actor name/version/path, session name, complete actual encoded claims, nullable `issuedNodeId`, phase, resumed `nodeId` and live `admissionCommandId`. Those are identity, privacy and in-flight admission facts, not model/command selections to derive from another connection. Preserve issued/resumed Node binding, exact command Origin/full claims/Node/session/Service identity, and private refusal matching. Never replace actual full claims with path-only claims or a schema document.

**The reviewed live broadcast had a source-observed identity gap.** `onMessage` checked lock/attachment actor/version/session equality and attachment Service/version/actor/path against the bound key. `broadcastServiceCommands` received no bound key; it validated the retained lock using the attachment's Service/version/session, while that validator resolved actor identity from the lock itself. It did not prove the same lock/attachment/bound-owner equality before filtering this Chain's output.

Ordinary trusted admission established those equalities. However, separately valid but inconsistent retained state and lock could pass the reviewed broadcast validation; using the attachment's owner identity did not prove that it belonged to this Chain. The recommendation was to share a bound-owner capability read across messages and live broadcasts, preserving exact session/producer/claims privacy checks. Private failure filtering independently required matching actor/version/Node/session/full claims. This was a missing invariant for inconsistent retained state, **not a reproduced public/private leak or ordinary-route exploit**.

Current implementations preserve the [connect checks](../../../packages/system-worker/src/ServiceActorVersionChain/onConnect/onConnect.ts#L25-L83) and use the same [bound capability proof](../../../packages/system-worker/src/ServiceActorVersionChain/readServiceConnectionCapabilities.ts#L31-L129) from [messages](../../../packages/system-worker/src/ServiceActorVersionChain/onMessage/onMessage.ts#L23-L44) and [broadcast](../../../packages/system-worker/src/serviceProjection/broadcastServiceCommands.ts#L27-L60). The [class now supplies its key](../../../packages/system-worker/src/ServiceActorVersionChain/ServiceActorVersionChain.ts#L47-L64); [model/full-recipient filtering](../../../packages/core/src/serviceSession/filterServiceBrowserCommand.ts#L26-L69) remains separate from that owner proof.

## Original installation and teardown finding — before Plan 218

The reviewed admission encoded and inserted one SQL row, then installed `awaiting-resume` attachment state without an intervening yield. SQL and WebSocket attachment were separate persistence mechanisms, rather than a joint SQL transaction. The class's `onConnect` failure handler compensated ordinary failures by deleting the row and then closing the original socket. That compensation was incomplete if deletion threw before close; it was not an independent teardown/finalizer across every failed or interrupted installation.

Only `onClose` and failed `onConnect` called the reviewed SQL deletion procedure. Invalid message/state/replay paths generally sent a notice then closed, relying on a later close callback for reclamation. A throwing send skipped the following close in those branches. Broadcast caught a failure and attempted close, but neither deleted its row nor cleared attachment authority itself. A throwing close left no explicit revocation there.

Before Plan 218, ServiceActorVersionChain had no `onError` override. The inspected PartyServer dispatched a hibernating WebSocket error to `onError`, and the inherited implementation only logged; that path did not invoke `onClose` or delete the row. The class also had no `onRepoStartup` override; the shared hook defaulted to no work. No activation procedure reconciled retained rows against surviving sockets.

**Recommend one idempotent disposal path** that makes attachment authority unusable, attempts original-socket closure and deletes the row even when notice/send/close fails. Independent cleanup actions need finally/finalizer structure so one failed action does not skip the others. Use it for installation failure, invalid state/message/replay, broadcast failure, explicit close and error callbacks. Cover encoding/SQL failures before a row exists as well as attachment failure after insertion; avoid a cleanup path that only runs after successful admission.

**Recommend safe activation reconciliation:** obtain the complete set of surviving socket IDs before deleting any row, then prune only IDs absent from that set in one synchronous transaction. Enumeration failure must delete nothing; preserve every surviving connection regardless of replay phase. Reuse the real owner activation boundary after schema/bootstrap rather than depending on a separately lazy socket-start callback. This is not a TTL or credential-revocation policy.

**Deletion condition:** the connection admission is disposed or its socket is definitively absent from a complete surviving-socket enumeration. Hibernation is not disposal. Keep capabilities for surviving hibernated sockets; delete them when that connection ends. Command admission receipts, publication acknowledgement, replay completion and subscriber progress do not govern their retention. Disposal/reconciliation never delete `exposedCommands` or `commandResolutions`.

These were source-supported lifecycle gaps and cleanup requirements; the original review established no orphan count, failed-close reproduction, unauthorized delivery or production incident.

Current replacements are [SQL/attachment installation and failure finalization](../../../packages/system-worker/src/ServiceActorVersionChain/installConnection.ts#L20-L45), [independent disposal](../../../packages/system-worker/src/ServiceActorVersionChain/disposeConnection.ts#L16-L34), [normal close/error callbacks](../../../packages/system-worker/src/ServiceActorVersionChain/ServiceActorVersionChain.ts#L103-L125), [connect-failure compensation](../../../packages/system-worker/src/ServiceActorVersionChain/ServiceActorVersionChain.ts#L127-L156) and [outer message failure disposal](../../../packages/system-worker/src/ServiceActorVersionChain/ServiceActorVersionChain.ts#L159-L196).

## Approved implementation — 2026-10-16

[Plan 218](../../archive/plans/218-plan-service-connection-capabilities-and-disposal.md) replaces the full-lock SQL row with exactly required primary-key `connectionId`, `contractNames` and `modelNames`. Compact codecs/projectors retain the admitted record keys, including empty selections; no definition/version copy or parallel full-lock row path remains. Full lock, exact declaration/version/closure, claims and canonical partition validation remain before installation.

`readServiceConnectionCapabilities` synchronously decodes the attachment and selected row, proves exact bound Service/actor/path, issued/resumed Node and full claims/partition identity, then resolves only selected model/public ordinary contract declarations from that exact release. Runtime `models` preserves existing payload filters; derived `contractVersions` preserves exact pushed-version checks. Missing/malformed/unsupported capabilities fail closed. Messages and live broadcast use this same proof; no fake submitted lock, latest-version lookup or Actor/Agent schema change is introduced.

`installConnection` writes compact capabilities and installs the attachment without an intervening yield after SQL insertion. Its failure finalizer disposes encoding/insertion/attachment failures and interruption; the class admission boundary also disposes validation failures before installation. `disposeConnection` fences the attachment, then independently attempts optional notice, original-socket close and SQL deletion through finally structure. Explicit invalid/replay/message/broadcast paths and close/error callbacks use it; per-socket broadcast disposal failures remain isolated after durable history append.

`onRepoStartup` runs Service-specific reconciliation after schema/bootstrap. It completes surviving socket enumeration before pruning only absent IDs within one synchronous transaction. Surviving sockets of every phase remain; enumeration failure deletes nothing. No TTL, history deletion, automatic reset or changed admission-acknowledgement meaning is added. Plan 217's scalar prefix reads, actual joined private/public payload reads and final synchronous tail/send/live transition remain in source.
