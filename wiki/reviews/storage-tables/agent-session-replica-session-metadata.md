## Physical scope and row fact

[openAgentReplica](../../../packages/browser/src/agentSession/openAgentReplica.ts#L23-L50) captures one exact Agent declaration and Aggregate owner, generates a local session ID and acquires fresh **in-memory SQLite per owning Scope**. Reconnect attempts reuse that database/producer identity. Scope release marks it closed and closes SQLite. There is no supported persistent Agent replica restoration or Agent Node append journal in this flow.

[agentSessionRepoDbConfig](../../../packages/core/src/agentSession/agentSessionRepoDbConfig.ts#L40-L41) reuses the four-field Aggregate sessionMetadata table; browser composition includes it alongside the dedicated Agent commands and separate producer metadata. Its practical singleton is an initialization/reader responsibility: the current sessionId primary key permits different IDs, so the key does not itself enforce one row.

One row records **the authoritative selected Aggregate resource base beneath Agent optimism**: a global Aggregate prefix position and its dispositionChainHash. It is materialization checkpoint state, not producer identity, Node coverage, command history, canonical outcome or delivery acknowledgement. The selected snapshot can establish a later global Aggregate prefix even when this producer has no local outcome at that position.

## Why the table stays, while its inherited identity/cursor do not

A valid snapshot can have aggregateIndex greater than zero and resolvedThrough equal to zero. Resources then represent the captured selected Aggregate state, while the recovery outcome list is empty and commands need not contain a row at the public head. The outcome list is this producer's private finalized prefix, not the global Aggregate command log. Dropping the table and using maximum local command position/hash would lose the actual resource baseline, gap protection, equal-position conflict checks and snapshot regression guard.

By contrast, the SQL sessionId is a repeated local lifetime witness. The Agent creates its ID beside the in-memory database, uses it as producer nodeId for bootstrap/resume/submission, and retains it in the immutable initialized capability. Staging captures that exact capability, runs against its DB and checks current object identity before evaluation/retention and at commit. Connection attempts separately fence generation/cancellation. These real boundaries remain necessary; the metadata copy is not authentication or independently recoverable identity.

The inherited afterNodeIndex has no Agent coverage responsibility. Agent resumes with captured producer nodeId, its contiguous committed producer outcomeIndex and public aggregateIndex/hash. No source Node pages or throughNodeIndex cursor are imported. Do not retain an unused zero merely because Aggregate/Service Node-backed replicas have genuine append coverage to track.

## Singleton, capability and lifecycle requirements

1. **Own the two-field declaration:** stop reusing Aggregate's physical metadata shape for Agent. Existing Shapes/SQLite declarations support no primary key. Do not replace sessionId with singletonId or use a mutable Aggregate position as an artificial key. No naming change is required.
2. **Keep explicit cardinality/presence:** ordinary stage/import/final/publication/capability reads must require exactly one checkpoint row and reject missing or ambiguous state. Initial snapshot installation may start with no row but must reject multiple rows before mutation and install exactly one checkpoint in its synchronous resource transaction. Never silently choose the first row or update several rows after removing key predicates.
3. **Decouple capability construction:** makeInitializedAggregateSession currently queries Aggregate sessionMetadata.sessionId before constructing either Actor or Agent capabilities. Removing Agent columns without replacing that Agent SQL dependency would fail at runtime. Preserve the immutable Agent context and checkpoint-presence boundary while removing only the redundant SQL ID assertion. Keep Aggregate/Native metadata and their restoration behavior unchanged; add no fake sessionId projection, old-shaped row adapter or fallback path.
4. **Preserve stage and final transactions:** local stage requires an installed checkpoint and current capability, but does not advance authoritative progress. New exposure must pass exact final/name/occupied-position/equal-hash/contiguous-index checks before rewind, then commit selected resources and checkpoint together. Covered recovery retains/merges final evidence without reapplying older resource changes or moving the head backward. Optimistic rewind/replay changes pending state/resources, not the authoritative prefix.
5. **Preserve snapshot guards:** validate exact owner/release/session/Agent Origin, resource codecs and complete private producer coverage before mutation. Reject a regressed snapshot checkpoint or equal-position hash conflict before replacing resources. Singleton checking, inverse clearing, resources/checkpoint replacement, covered-final merge and pending replay remain one synchronous transaction. Retained exact final rows must not conceal an older resource base.
6. **Keep progress domains distinct:** public publication/resume/replay completion uses aggregateIndex/hash. Producer admission acknowledgement and contiguous outcome recovery remain independently owned by existing producer metadata/retained commands. A socket failure or withheld capability leaves the checkpoint in the same database; reconnect does not create a new producer. Metadata-table change notification still republishes the committed public pair.
7. **Retention/disposal:** initialization owns row creation, later snapshots replace the captured base after validation, and new final exposure updates it. Admission acknowledgement, final delivery, pending drain and ordinary reconnect never delete it. Scope disposal closes the whole in-memory database. Add no acknowledgement pruning, TTL, independent reset or new persistent Agent recovery path.

## Approved implementation — written, unverified

There is no declared primary key, SQL sessionId, afterNodeIndex or replacement singleton field. Aggregate's four-field and Service's three-field metadata declarations remain independently owned.

readAgentSessionMetadataTx reads at most two rows, accepts the actual DB/transaction read context and requires exactly one checkpoint for ordinary stage/import/final/capability/publication. Missing and ambiguous state fail; initialization alone permits absence. Snapshot installation rejects ambiguity before resource mutation and deletes/reinserts exactly one checkpoint inside the existing resource/current-inverse/covered-final/replay transaction. Key-based queries/upsert and SQL-only local-ID arguments are removed. Snapshot identity/resource/private-prefix, regression/equal-position hash and contiguous final guards remain.

makeInitializedAggregateAgentSession checks the exact Agent Origin and declaration, requires the Agent checkpoint and freezes the execution capability from the captured DB, Aggregate owner, declaration and runtime sessionId. It does not query Aggregate metadata SQL. The Aggregate initializer retains its Actor/Native path and removes the superseded Agent branch. Browser initialization uses the new constructor; checkpoint publication uses the same exact-singleton reader. Runtime sessionId still supplies protocol producer nodeId for bootstrap/resume/submission, and captured capability/current-lifetime/attempt fences retain their responsibilities.

Agent's eleven command columns, canonical-ID settlement/pending clearing, real producer correlation and three-field agentDeliveryMetadata are unchanged by these edits. Aggregate/Service storage and Node/Native guards are outside this Agent metadata cutover; preservation comparisons remain unrun.
