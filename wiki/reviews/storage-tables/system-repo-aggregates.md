# SystemRepo.aggregates

**Reviewed:** 2026-10-16 against current source, including uncommitted work, with independent column-design and registration-lifecycle reviewers. Exactly this physical table is reviewed; Repo metadata, activation, accepted definitions and Agent opening are dependencies. All verification remains deferred.

**Verdict: retain both columns, their current names and composite uniqueness.** This is SystemRepo's structured index of registered logical Aggregate identities: `{ aggregateName, aggregateId }` within its physical System scope. Keep release versions, physical addresses, timestamps and readiness out. No schema cleanup or ordinary-path lifecycle defect is established.

Only this finding and [Plan 151](../../plans/151-plan-storage-table-review.md) change. No implementation subplan or production edit is needed for this verdict. Prior implementation plans remain independently unverified.

## Physical owner and row fact

One SystemRepo is addressed by exact deployment systemId. One row means the logical Aggregate name/ID pair was registered through AggregateChain startup in that System. It is **persistent registration membership state**, not application resource data, a checkpoint, command/event history, pending delivery or subscriber acknowledgement. The set grows through registration; there is no supported update or deletion lifecycle.

Registration precedes the registering AggregateChain's local schema initialization, bootstrap and onRepoStartup. The row therefore does not prove successful initialization, a committed admitted command, materialized resources, current executable release availability, a live session or successful deployment. Those are separately owned facts.

## Every column and constraint

Both columns are required/non-null text with no defaults. There are no structured subfields, nullable members, explicit primary key, foreign key, generated domain ID, timestamp, status or counter. The named unique index covers aggregateName then aggregateId. No application consumer uses SQLite's implicit rowid. The framework migration ledger is a separate table occurrence, not another member of this row.

| `aggregateName`                       | Named Aggregate identity namespace. AggregateChain is versionless, so an Aggregate release version would partition one logical instance incorrectly. Actor/Agent identities, resources, command positions and table metadata do not belong to this row. Current names describe the domain directly; no rename is proposed.

## Registration, transaction, retry and retention

1. The common Repo factory parses the physical AggregateChain name and validates its configured System identity before resolving its database. registerRepoWithSystem extracts the Aggregate name/ID from that parsed key and addresses the configured SystemRepo. Other Repo types do not create Aggregate membership rows. The explicit SystemRepo singleton does not register itself.
2. SystemRepo.registerRepo strictly decodes the executing declarations' complete SystemSpec and requires every projected definition to match its already accepted catalogue entry. Registration never accepts new definition versions. Immutable accepted entries permit these comparisons before the write transaction without a later catalogue mutation invalidating the result.
3. One synchronous makeTx transaction upserts physical Repo/table metadata and inserts the Aggregate pair only for repoType AggregateChain. Either both writes commit or the transaction rolls back. No remote RPC runs inside this SQL transaction. The pair has no separate delivery or acknowledgement state.
4. Repeated activation refreshes physical table metadata and leaves existing membership unchanged through onConflictDoNothing. Failure before the transaction inserts no pair. Failure during the transaction rolls both writes back. Lost registration replies can retry the same pair without duplication. Once registration commits, a later schema/bootstrap/activation failure does not undo it; retrying activation can reuse that recorded membership.
5. There is no supported delete, unregister, expiry, acknowledgement pruning, deployment-omission cleanup or readiness transition in the reviewed flow. Keep membership across declaration removal/reintroduction and initialization retries. Deleting it while the Aggregate identity remains known makes its ID disappear from discovery and makes the Agent membership guard refuse it. This is unrelated to whether command delivery, projection catch-up or a Studio session has finished.

Current authored availability remains separate from registered membership. AggregateChain uses static database configuration and can reopen its retained admission journal without resolving a currently bundled Aggregate release. Requiring a live release merely to preserve or refresh registration would conflate that recovery ownership with version execution availability.

## Consumers and the physical-metadata redundancy challenge

SystemRepo.getAggregateIds reads only the ID column for an exact Aggregate name and sorts by ID. SystemRepo.hasAggregate checks one exact name/ID without opening or creating its AggregateChain. SystemApi.getAgentAggregateIds separately requires the requested authored Aggregate release, then lists the version-independent registered IDs. resolveRegisteredAgentSelection separately resolves the exact Agent and its bound Aggregate release, then requires pair membership before creating/bootstrapping its selected AggregateAgentVersionRepo. Membership supplies neither Agent authority nor executable declarations.

The duplication with repos is real. AggregateChain's physical name already encodes systemId, aggregateId and aggregateName; repos retains that physical name, and both rows share the registration transaction and current retention. Do not justify the second relation by inventing an independent lifecycle or another historical fact.

Retain this table as a deliberately structured logical identity index. Removing it is technically possible: hasAggregate could encode the canonical AggregateChain address and query the physical registration; getAggregateIds would need to read every AggregateChain registration, parse addresses with the existing canonical helper, establish System/name agreement, extract IDs and sort them. That couples logical discovery to physical address syntax and replaces direct name-filtered SQL with address interpretation. The two-column relation expresses the domain query directly, deduplicates logical identity and shares its write boundary with the physical registration so it needs no cache recovery or separate synchronization protocol. This is a data-model/query-ownership judgment, not evidence of a measured performance problem. No extra mirror, hash, parser, packed key or repos redesign is proposed.
