# AggregateActorVersionChain.exposedCommands

**Reviewed:** 2026-10-16 against current uncommitted source after [Plan 207](../../archive/plans/207-plan-actor-model-exposure-and-aggregate-command-names.md). Exactly this owner/table occurrence was reviewed. Its pending producer, optional private relation and browser consumers were dependencies; their separate table reviews remain outstanding where not already recorded.

**Verdict: retain the existing five-column model and indexes.** Keep `aggregateIndex`, `dispositionChainHash`, canonical admitted command `id`, `commandName` and `delta`. AggregateActorVersionChain needs immutable exposed-command history after AggregateActorVersionRepo deletes acknowledged pending publication. No column removal, rename or schema change is recommended. Independent lifecycle and column-design reviews found no ordinary-path correctness defect.

## Physical scope and represented fact

The physical AggregateActorVersionChain is bound to `systemId / aggregateId / aggregateName / aggregateVersion / actorName / actorVersion / actorPath`. The Aggregate version identifies the evaluating release; actor name/version/path identify the exposed model inventory and selected identity partition. Those fixed owner fields are correctly absent from each row.

One row is the frozen exposed command for one source `aggregateIndex`: its admitted command identity, ordered disposition-prefix hash and selected resource transition. Every new contiguous command occupies a row, including Failure, no-op and commands whose selected `delta` is empty. This is **immutable history**, not a resource view, materialization head, pending delivery, subscriber cursor or retained canonical `outcome`.

AggregateActorVersionRepo owns resources, the current materialization head and complete pending `exposedCommandOutbox`. AggregateActorVersionChain owns retained exposed commands. Source fanout acknowledgement proves the Repo's projection commit; Actor Chain publication acknowledgement proves retention of the complete exposed publication. Neither acknowledgement is command admission or original `outcome` retention.

## Every column and index

All five columns are non-null, have no SQL default and are insert-only through the supported publication path. `appendExposedCommands` is their writer. `readExposedCommands` and `getBrowserCommands` read the complete public row; `getCheckpoint` reads its position/hash. An identical retry inserts nothing; any changed retained publication is rejected.

No additional synthetic key, timestamp, lifecycle flag, resource column or secondary index is synthesized by this plain table declaration. There is no cross-Durable-Object SQL foreign key to AggregateVersionChain. SQL provides non-null/key constraints; positive safe positions, hash format and structured publication meaning are checked by codecs/append logic rather than SQL CHECK clauses.

`delta.upserted` contains complete newly visible or changed **exposed** resource rows, not necessarily newly created resources. `delta.deleted` contains refs leaving the selected graph; an exit need not mean the canonical resource was deleted. The producer compares the selected graph before and after each command, including selection changes caused through related resources.

### Hash meaning and validation limit

`dispositionChainHash` chains the previous hash, Aggregate position, canonical admitted command ID and only `outcome.result._tag`. It hashes neither command name, successful result contents, failure details, model operations, selected delta, resource timestamps nor claims. Equal hashes do not establish equal exposed commands or equal resources; append's full publication comparison is independently required.

AggregateActorVersionRepo verifies the rolling hash while applying new evaluated commands. AggregateActorVersionChain validates the publication shape, new position continuity and exact repeated-publication equality; its append does not recompute a rolling hash from retained public rows. Those rows deliberately lack every source disposition. Additional AggregateVersionChain publication hash validation remains deferred at the maintainer's direction and is not reopened or made a blocker by this finding.

## Commit, acknowledgement, retry and retention

1. AggregateActorVersionRepo applies a contiguous evaluated-command page in one synchronous transaction. Resource mutations, each frozen selected delta, complete pending publication and the materialization head commit together. Refusals and empty transitions still advance their individual source positions. A later failure rolls back the whole page.
2. `makeExposedCommandOutbox` sends the complete retained pending publication to AggregateActorVersionChain selected by the immutable projection key. It decodes the retained message rather than recomputing a delta from newer resources.
3. `appendExposedCommands` checks exact source-key equality and validates each publication. New positions must be contiguous. It inserts the public row and optional private child in the same transaction. Public insertion seals the resolution **or its absence**; a later retry cannot attach, remove or change the resolution or change any public field.
4. A successful append permits the pending producer's acknowledgement. Only then does the queue transaction delete the exact delivered pending indices. A lost reply, unavailable Actor Chain, contradictory publication, interruption or acknowledgement deletion failure leaves the complete pending message available for retry. An identical retry compares equal and performs no new history insert.
5. AggregateSessionChain broadcasts after the append transaction commits. Per-connection send failures close that connection without rolling back retained history. Socket reconnect reads the same immutable public history; publication acknowledgement does not mean a browser consumed the command.
6. No supported path updates, deletes, prunes or expires `exposedCommands` rows. Retain them for the lifetime of the bound physical Actor Chain. Pending publication deletion, source subscriber acknowledgement, socket close and an actor leaving a selection are not history deletion conditions. No TTL, acknowledgement floor or release-retirement cleanup policy exists for this table.

## Historical reads and privacy boundaries

`getCheckpoint` reads the hash at the exact requested index, with a separate genesis response at zero. `getSnapshot` captures resources/head N together in AggregateActorVersionRepo, publishes through N, compares AggregateActorVersionChain's exact checkpoint at N, and bounds private progress by the same N. Newer publication cannot relabel captured resources. Keeping only a latest row would break this contract.

`readExposedCommands` locally joins the optional private relation. Public replay remains one Aggregate-ordered stream, with session-lock model filtering and private failure disclosed only for exact Node/session/full reconstructed Origin ownership. The public `IAggregateExposedCommand` retains nullable `failure`, while the five-column public history table contains no failure/claims/producer fields. A null public failure alone does not prove a source Success. The child relation's column-purpose review is the next table, not part of this verdict.

Replay drains bounded pages, then performs its final read, delivery, checkpoint comparison and transition to `live` in one synchronous turn. Retained history supplies reconnect recovery after a socket failure or cold activation; moving reconstruction to AggregateVersionChain would introduce a new remote read/replay dependency.

No schema change, new pending stream, lifecycle flag or additional hash validation is proposed. No unsettled choice requires maintainer approval for this table.
