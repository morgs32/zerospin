## Original source finding — before Plan 224

The initial source finding recommended the six-to-four cutover above. The following column/lifecycle analysis records the original six-column declaration and why its Origin/counter copies were unnecessary. Its present-tense references describe that earlier source snapshot.

## Physical owner and row fact

One browser Aggregate session lifetime owns one in-memory SQLite replica containing selected resources, local command observations and this metadata row. Scope disposal closes the entire memory database. Standalone browser sessions use the same replica procedures, while their authoritative AggregateNode has its own persistent scope. Native uses the same replica declaration in persistent `session_<owner.key>` storage; closing that client preserves the row and local history for the next launch.

One row is the replica's **local session identity and checkpoint state**. It identifies the local staging owner, the covered Node append prefix and the authoritative Aggregate resource base beneath current optimism. It is mutable state, not an admitted command, canonical outcome, retained execution/audit history, pending delivery or remote subscriber acknowledgement. Its fields do not establish that AggregateChain admitted a command or that AggregateVersionRepo finalized it. Resource replacement/application and covered delivery determine its progress.

The database is a practical singleton by acquisition and initialization. `sessionId` is the primary key; the schema does not declare a constant singleton slot or an independent cardinality constraint. Initialization reads the existing row and refuses a different session ID. Other readers mix exact-ID lookups and singleton reads. Keep this owning-scope invariant explicit; adding another durable `singletonId` would not simplify the required facts. No table rename is needed.

### Origin members

The current metadata codec is `AggregateCommandOriginSchema`, with three branches:

1. Actor: `kind: 'actor'`, nonempty `actorName`, nonempty `actorVersion`, and complete string-keyed `claims` values.
2. Agent: `kind: 'agent'`, nonempty `agentName` and nonempty `agentVersion`.
3. System: only `kind: 'system'`.

Every member of the Actor/Agent value is already available from the bound observing session. The System branch is overbroad for a staged session: initialized Aggregate sessions accept only Actor or Agent. Removing the redundant metadata field is clearer than merely narrowing that copied codec. The per-command Origin union and full submitting claims retain their separate authority/replay responsibility.

## Why the allocator is derivable

Aggregate staging and ordered import allocate only when inserting a new phase row. Exact staged/final retries and Node coordinate enrichment preserve the existing sessionIndex and allocate nothing. One synchronous transaction owns the insertion and metadata update, so a failed transaction consumes neither row nor counter.

Normal snapshots replace resources/current inverse state while retaining every existing command row and session position. Neither final settlement nor Node acknowledgement deletes command history. The only Aggregate command deletion is the explicit discardPending branch: it clears all commands and metadata and deliberately restarts allocation at one. Therefore the stored counter and `max(sessionIndex) + 1` remain equal throughout the supported Aggregate lifecycle. No independent retired-position watermark remains to preserve.

The handoff owner uses sessionIndex as an internal throughIndex bound, so monotonic local positions do have a real consumer. Deriving them from retained history preserves that order until the same explicit reset that already replaces the handoff epoch. This is not a proposal to reuse live positions, renumber rows, derive from aggregateIndex/nodeIndex, or move allocation outside the insertion transaction.

The earlier commands finding's claim that maximum-based allocation would discard an allocator contract was too strong. A stored allocator is one implementation; the requirement is stable positions and atomic ordered allocation. Existing machinery and ADR wording do not make a redundant durable counter necessary. There is no currently supported Aggregate history-pruning feature requiring a separate high-water mark. If a later design adds one, it must specify its actual ordering/identity contract then.

Agent reuse needs explicit consumer handling rather than a blanket retention assumption. Agent rejection can delete an individual staged row; its command ID/pushIndex transport and synchronous sessionIndex row addressing differ from the Aggregate handoff. The derivation reviewer found no supported reader requiring a deleted Agent tail position to remain retired forever, but that source observation does not complete the separate Agent table review. An approved shared-schema implementation must trace that consumer and preserve its real producer/order guarantees. It must not silently remove an independent Agent submission counter or claim that Agent history is never pruned.

## Why metadata Origin is derivable, while command Origin is not

Connected browser acquisition creates a fresh replica and fixes its exact session declaration. The connection hashes the resolved complete Node identity and rejects a different key on reconnect during that replica lifetime. That identity includes API/System context, Aggregate name/version/ID, Actor name/version, session name, full claims and declaration hash. The key establishes storage/binding identity; actual authentication and claims validation still belong to their existing admission procedures.

Native creates and initializes that exact Node owner before opening the replica. AggregateNode checks its persisted Aggregate owner and exact session key. Native then opens only `session_<owner.key>`, where owner.key hashes the same complete identity. Each launch obtains its resource baseline from that bound Node before subscribing. The replica metadata Origin check supplies a second copy of an already established identity, not the sole supported ownership proof. Its removal intentionally removes that duplicate self-comparison, not authentication or source command provenance. Keep schema/presence/session-ID checks and validated bound context; add no replacement SQL fingerprint or partial-claims identity.

Standalone's authoritative Node intentionally shares non-routing incidental claims across attachments. Its observing replica remains transient, and snapshot identity uses that attachment's claims. A different tab's retained original command still carries its submitting Origin, which replay decodes directly. Metadata Origin is not that historical input. Removing metadata Origin therefore does **not** justify the previously rejected idea of deriving every command's Origin from current local credentials.

Snapshot identity must be checked against the bound context before replacing resources. Today initializeAggregateNodeProjection checks the retained session ID, commits graph/checkpoint replacement, and its browser caller then invokes makeInitializedAggregateSession's metadata-Origin equality check. The owning Node/connection identity checks constrain supported calls, so this is not a reproduced wrong-owner execution claim. An approved cleanup should express identity validation at the owning binding/snapshot seam before mutation, rather than retain a duplicate SQL Origin whose comparison occurs afterward.

## Independent progress, transactions and recovery

1. Snapshot initialization validates the requested pending partition and existing local session ID, then synchronously replaces selected resources/current inverses, retains or resets local history as appropriate, sets the captured Aggregate position/hash and Node coverage, merges captured receipts/unresolved originals and replays surviving optimism. Normal conflict updates preserve origin/session identity and allocator; explicit reset recreates them. Failure rolls the complete transaction back.
2. Local staging commits resources, original stagingOutcome, current command-row inverses, local row position and allocator together. It does not advance the authoritative Aggregate checkpoint or Node-stream coverage. The metadata row can therefore remain at genesis/captured progress while optimistic resource values change.
3. A streamed Node page must be contiguous relative to afterNodeIndex, within safe positive positions and consistent with its throughNodeIndex. Import retains commands, applies newly observed authoritative selected changes, advances aggregateIndex/hash where appropriate, and replays pending inputs; only then does the same transaction advance afterNodeIndex. Acknowledgement follows commitment. Receipt/recovery import is cursor-neutral and cannot skip unseen stream records.
4. A new final beyond the authoritative resource base must be the next Aggregate position. Equal-position hash conflict fails. Covered finals settle local staging without applying their resource delta again; point recovery ahead of the base defers until ordered delivery. The retained base can lead maximum local final position after a snapshot, and a Node cursor can lead maximum locally retained Node position after the same capture. These are independent coverage facts, unlike the derivable local row allocator.
5. Native captures a Node snapshot and later subscribes from the metadata afterNodeIndex to cover the intervening append gap. Connected browser subscriptions obtain a fresh capture on reconnect. The runtime binds the admitted Node ID and filters stale delivery; no extra persisted nodeId field is justified by this review. A replacement snapshot sets coverage for its admitted epoch under the existing reset/reconnection policy.
6. Publication observes committed metadata and updates reactive Aggregate progress; it cannot change the SQL commitment or original local outcome. There is no remote subscriber acknowledgement, delivery deletion or audit requirement on this row. A lost publication can read committed state again; a transaction failure cannot publish a partial resource/checkpoint pair.

## Exact retention and reviewer reconciliation

There is no ordinary delete, TTL, per-command acknowledgement pruning or deployment-omission cleanup for sessionMetadata. Browser Scope disposal releases its whole in-memory database. Native close preserves the row and command history. The explicit acknowledged reset path deletes metadata and commands together before reseeding, inside one transaction; this review neither adds a reset policy nor performs a reset. A later approved fixed-schema change requires the existing empty-storage hard cutover without aliases, translation migrations or fallback decoding.

The lifecycle reviewer initially identified six current roles; the column and derivation reviews challenged whether the counter and copied binding were independent facts. All three converge on the four-column model. Source consumers justify afterNodeIndex and the authoritative position/hash even when snapshots omit historical rows. The retained command lifecycle makes the allocator derivable, and the bound replica identity makes metadata Origin redundant. No old ADR or naming convention is used as a reason to preserve either mechanism. Keep sessionId because empty/import-only history does not encode the independently generated local staging owner.
