Stock execution-context controls await the actual background recording/reconciliation pass before asserting injected DELETE failure. Reconstructing the actual object starts an identical frozen retry from pending storage. Missing exact release/contract and invalid payload leave rows unchanged, admit no command and retain recovery.

All 86 System Worker tests across 25 files pass, including these four cases and the 14 existing Aggregate adapter cases. The suite exposed an existing fixture release missing `dispatchWork`; an explicit release-2 replay adapter repairs the fixture while preserving release 1's outgoing behavior and the successful final alarm assertion. No production implementation changes. Independent implementation/test review found no actionable defect.

The internal Actor append is trusted input, not authenticated authorization. Queue rows are seeded; this is no new authored original-to-continuation journey or mixed-model replay proof. Provider code is authored fixture code, and alarms are manually dispatched. Provider integration, deployed timing and independent Plans 196/211/212 remain outside this proof. Complete pending deletion proves observation admission, not continuation execution or retained continuation `outcome`.

## Physical owner and represented fact

AggregateChain is bound to `systemId / aggregateId / aggregateName`. Its physical identity contains neither an Aggregate release nor an Origin. One row means AggregateChain must run a frozen external invocation and atomically admit its observation under an already allocated external command ID.

This is **complete pending request state**, not immutable execution history, a resource view, a checkpoint, subscriber progress or an outcome cache. Original evaluated-command history belongs to AggregateVersionChain. The pending row is inserted once and never updated; a committed observation/admission transaction deletes it. There is no persisted started/failed flag, retry count, lease, allocator, delivery diagnostic or per-row clock.

## Original eight-column audit and indexes

At the reviewed pre-cutover snapshot, all eight columns were required/non-null, with no SQL defaults. `recordOriginalCommandOutcomeTx` is the supported insert writer. The queue reads frozen rows; observation settlement rereads by external command ID and deletes the complete row. SQL does not declare a primary key or a relationship to the parent/child command table. Positive-safe authored operation positions and exact external definition identity also depend on preparation/receipt validation.

| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `initiatingCommandId`     | Required parent canonical admitted command ID, copied from `input.id`. Appears in pending lineage and its composite unique index; neither request execution nor observation settlement consumes it.                                   | Remove from pending storage. This loses direct parent inspection on a pending row, not supported request/recovery behavior. Full evaluated-command history retains the parent relationship.                                        |

It is not execution order, a continuation position or a FIFO cursor. | Remove only from this pending table. The parent command and Aggregate owner do not identify which external declaration was emitted.                                                                                                                             |

`externalCommandId` is unique. Its `primitives.foreignKey({ abbreviation: 'cmd' })` descriptor validates an opaque ID and renders typed text; it does not declare a SQL foreign key to a command that has not yet been admitted. The separate unique `initiating_command_operation(initiatingCommandId, operationIndex)` was subsequently removed in Plan 213. There are no framework-added declared IDs/timestamps or additional indexes.

The original composite pair checked a relationship already established by supported production: immutable parent identity plus one retained outcome prevents a second emission transaction; strict increasing indexes prevent duplicate positions within the first receipt. Neither scheduling nor settlement needs the pair afterward. Keeping it solely for pending-row inspection would be a separate diagnostic requirement, absent from current consumers.

## Every structured value

`payload` is generic encoded JSON. Objects, arrays, strings, finite numbers, booleans and null are valid according to its declared codec; no framework nested keys are prescribed. Each external contract owns its portable payload shape. Preparation freezes that encoded value; request execution decodes it with the exact resolved contract. Do not add provider address, recipient, retry policy or parent context as framework fields inside arbitrary payloads. An authored payload may legitimately contain its own domain identity or provider key.

`origin` retains the shared Aggregate command variants:

| Variant | Required fields and necessity                                                                                                                                                                                                         |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Actor   | `kind: 'actor'`, nonempty `actorName`, integer `actorVersion`, full `claims: Record<string, unknown>`. The claims are application-defined encoded authority; the schema prescribes no further fixed keys. Retain all original claims. |
| Agent   | `kind: 'agent'`, nonempty `agentName`. Plan 151 removed independent Agent versions. AggregateChain spans Agents and other Origins, so the Agent name is not a physical-owner constant. No claims placeholder is needed.               |
| System  | `kind: 'system'`. Explicit System authority is required; null or omitted authority does not replace it.                                                                                                                               |

No nullable Origin branch or producer tuple is embedded here. External observation admission supplies null `nodeId`, `sessionName` and `pushIndex`; it retains frozen Origin independently of ordinary session submission metadata. No recorded `externalOutcome` exists in the pending request row. Its first durable Success/Failure observation belongs to the newly admitted command.

## Commit, requests, recovery and deletion

1. Original evaluation alone prepares external descriptions and allocates stable external command IDs. Replay omits external emissions before preparation/ID allocation. Complete evaluated-command publication/history retains every original operation with its authored position; parent `id` supplies lineage.
2. `recordOriginalCommandOutcomeTx` validates the bound reply against immutable admitted input, predecessor and operation-index order. Its synchronous transaction sets `commands.outcome` and inserts all external requests together. Failure outcomes cannot carry operations. A repeated exact retained outcome returns before insertion, including after pending requests have been deleted; retries cannot recreate work.
3. Original delivery retains recovery through its acknowledgement completion hook, which wakes external processing and replay. An empty drain repeats that hook. Activation independently wakes the registered external queue. A crash between receipt commit and wake therefore leaves recoverable pending work.
4. `wake` first reconciles the durable alarm, scans pending rows and reserves each `externalCommandId` synchronously before launching independent background promises. The reservation lasts through request finalizers, observation recording and alarm cleanup. No source-operation ordering or FIFO request execution is guaranteed. Observation/admission transaction order determines new Aggregate command positions.
5. Exact release/contract resolution and frozen payload decoding happen before the captured request Exit. Failure there leaves pending work for alarm recovery. The authored request runs with `{ payload }` and its timeout; response validation/encoding is included. Request failure, timeout, interruption or response-codec failure becomes a terminal external Failure observation, not an automatic provider retry after observation commit.
6. Settlement rereads the current pending row by `externalCommandId`, reconstructs the external command from frozen contract/payload/Origin/release and the observed Success/Failure, assigns the next `aggregateIndex`, then appends that command and deletes the pending row in one synchronous transaction. A failed transaction preserves pending work. A missing row makes a late/duplicate callback a no-op, preserving the first committed observation.
7. Settlement acquires `finalizeCommandOutbox.producerLease` before admission and explicitly runs `finalizeCommandOutbox.wake()` on exit, preserving the transaction result or Cause. Pending deletion proves observation admission; it does not prove the external command executed or retained its own `outcome`. That command begins with null `outcome` and later uses normal original/replay processing. A terminal external Failure can be handled successfully by its authored continuation and does not change the parent's retained outcome.
8. No durable in-flight marker survives process loss. A provider effect followed by process loss or failed observation storage can leave the request pending for another attempt. Stable local command identity does not promise exactly-once provider effects: `external.request` receives no automatic external ID or database. Provider idempotency/reconciliation belongs to the authored payload/request protocol. There is no TTL or post-admission pending-row retention.

## Approved six-column model

```ts
{
  externalCommandId; // existing stable cmd ID, unique
  externalContractName;
  externalContractVersion;
  payload; // frozen encoded JSON, including JSON null
  origin; // complete frozen continuation authority
  aggregateVersion; // exact original emitting release
}
```

Remove only the pending lineage pair and its composite index. Keep external ID uniqueness, exact release/contract identity, complete authority, frozen input, one-time receipt gating, atomic observation/admission/deletion, independent requests and durable recovery. Do not add a status flag, sequence, timestamp, allocator or replacement pointer.

Origin and release are honestly derivable from same-owner retained parent commands if `initiatingCommandId` remains. That local join is technically possible and is not a remote-history dependency. The recommendation instead drops unused pending parent association and keeps the complete facts required to run/settle an invocation, without introducing parent lookup/missing-parent assembly paths. Diagnostic parent inspection alone does not justify the extra lineage responsibility.

Plan 213 updates the Aggregate table-owned pending codec and the shared queue's required invocation fields while preserving prepared/evaluated-operation lineage and sparse `operationIndex` in AggregateVersionChain. ADRs 016 and 013 distinguish complete pending invocations from retained history. This Aggregate cutover removed no Service pending column/index; later Plan 219 independently applies the six-field model to ServiceChain, and Plan 256 changes Service evaluated-command representation. The verification follow-up must distinguish semantic lineage preservation from whole-file equivalence.

## Additional source observations and verification limits

No ordinary-path lifecycle or privacy defect was found. A malformed pending-row decode aborts the remaining scan; already launched valid requests continue, and pending state retains alarm recovery. Background execution uses invocation capture and suppresses promise rejection after scheduling. No durable failure diagnostic is stored. This is a source-observed limitation for malformed rows, not a reproduced incident or a reason to add persisted retry/error fields.

The original review identified “Request completion order” wording in the AggregateChain README. Its current wording specifies observation/admission transaction order, after the recovery hold preceding settlement. This clarification establishes no runtime ordering defect.

Aggregate preparation also transiently builds full parent context, strips repeated fields for evaluated-command storage, then restores Origin/release during receipt. This is shape-conversion work, not a second durable queue. Any later cleanup must preserve authored operation positions and complete request authority; it is not automatically approved by this table review.
