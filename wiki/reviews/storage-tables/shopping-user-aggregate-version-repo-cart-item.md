# Shopping user AggregateVersionRepo.cartItem

**Reviewed:** 2026-10-17 against current source, with independent lifecycle and column-design reviewers. Exactly the source AggregateVersionRepo.cartItem ownership context is reviewed. Cart, PurchaseItem, Marketplace Product and projection/Node/replica storage are dependencies, not additional completed reviews. All verification remains deferred, including Plan 236 implementation verification.

**Verdict: retain the table and all eight stored values; recommend two focused cleanups.** Rename amount to **quantity**, and declare **UNIQUE(cartId, productId)** through existing Model index support. The first removes inconsistent terminology; the second declares the one-product-line-per-Cart invariant already used by additions and first-match readers. Neither changes the row's lifecycle. These are recommendations only: no implementation is approved or performed by this review, and no reachable duplicate-line corruption was established.

**Implementation follow-up (2026-10-17):** The maintainer approved both recommendations in [Plan 237](../../archive/plans/237-plan-cart-item-quantity-and-product-uniqueness.md). Implementation is written, unverified: CartItem now stores quantity, and CartItemV1 declares `cartItem_cartId_productId_unique` with columns `['cartId', 'productId']` and `unique: true`. Existing add/update payloads, operation attributes, checkout/payment readers, UI props/validation/staging/subtotal and the existing worker invocation fixture use quantity. Add remains incremental; update remains absolute. SQLite enforcement uses the existing table compiler, with no new application uniqueness layer. Shopping README and glossary describe the change. Changed resource/payload/retained-operation/spec formats require empty affected storage; no reset, migration, compatibility path or deployment was performed. All checks remain deferred and Plan 237 stays active. The review below preserves the original pre-change field names and recommendation evidence; it is not verified completion evidence.

**Plan 239 follow-up (2026-10-17):** Approved [Plan 239](../../archive/plans/239-plan-shopping-promotion-reservations.md) keeps the eight-field quantity-based CartItem model and unique Cart/Product pair from Plan 237, but establishes integer USD cents for price and every downstream money amount. The display copy remains advisory; Marketplace independently quotes subtotal. Only UI formatting divides by 100. This supersedes the old unchanged-whole-dollar-unit statements below; field count, quantity behavior and ownership remain. Implementation is written and all verification remains deferred.

The [declaration](../../../examples/shopping/src/zerospin/aggregates/user/models/cartItem/CartItemV1.ts#L9-L23) has no SQL defaults, authored indexes, extra uniqueness, TTL or CHECK constraints. cartId is the sole concrete SQL reference and uses ordinary NO ACTION update/delete behavior, not cascading deletion. productId is identifier validation only. Timestamps, integers and references use the existing [primitive SQL mapping](../../../packages/shapes/src/primitiveMaps.ts#L124-L255). There are no structured JSON column members; relations are derived rather than stored copies.

Positive supported quantities come from authored add/update/checkout validation, not SQL CHECK constraints. CartItem.price is a safe integer under its codec but does not itself require nonnegative values; addToCartV1 copies the schema-valid client Product value without a nonnegative-price guard. A stale or client-chosen preview can affect the displayed subtotal, but checkout does not use that price to determine payment. This review neither calls preview data catalogue attestation nor invents a payment exploit.

## Lifecycle and authority

1. **Create or merge by Product.** [addToCartV1](../../../examples/shopping/src/zerospin/aggregates/user/contracts/addToCartV1.ts#L14-L85) accepts a full Product envelope, loads Cart/items/checkoutPurchase, rejects unresolved checkout and validates a positive safe-integer addition and resulting count. An existing matching productId increments the existing line; otherwise it creates the line with cartId and copied name/price. Repeated same-product additions do not refresh display snapshots. The authoritative command reevaluates against serialized committed state; a second first-add does not preserve an earlier speculative choice to create a duplicate line.
2. **Edit/remove only while unlocked.** [updateCartItemQuantityV1](../../../examples/shopping/src/zerospin/aggregates/user/contracts/updateCartItemQuantityV1.ts#L32-L61) selects the exact line, loads Cart.checkoutPurchase and requires a positive safe desired count. [removeFromCartV1](../../../examples/shopping/src/zerospin/aggregates/user/contracts/removeFromCartV1.ts#L26-L47) follows the same parent relation and deletes the exact resource. Both refuse preparing/pending/needs_reconciliation. [CartItemQuantityControls](../../../examples/shopping/src/components/CartItemQuantityControls.tsx#L25-L63) implements decrementing the final unit as removal, not a zero-count row.
3. **Display is local; quotation is separate.** [ShoppingCartSidebar](../../../examples/shopping/src/components/ShoppingCartSidebar.tsx#L43-L73) renders stored names and the snapshot subtotal. [checkoutV1](../../../examples/shopping/src/zerospin/aggregates/user/contracts/checkoutV1.ts#L65-L118) freezes only line identity, productId and quantity, initially creating PurchaseItem with null quoted name/price. Marketplace's [quotePurchase](../../../examples/shopping/src/zerospin/services/marketplace/marketplaceServiceReleaseV1.ts#L43-L83) independently reads current Products, rejects missing/invalid ones and computes the validated quote. [getExternalPurchaseQuoteV1](../../../examples/shopping/src/zerospin/aggregates/user/contracts/getExternalPurchaseQuoteV1.ts#L118-L164) installs those quoted values on PurchaseItem and records payment using the quoted total. CartItem preview values never become payment authority.
4. **Delete after the exact paid checkout, not on submission.** [processExternalPaymentV1](../../../examples/shopping/src/zerospin/aggregates/user/contracts/processExternalPaymentV1.ts#L49-L105) requires the associated pending Purchase, matching payment identity/total and exact Cart-to-Purchase line identity/product/quantity. Paid deletes CartItems; decline, quote refusal and uncertain payment preserve them for editing or reconciliation according to parent state. Delayed obsolete observations fail linkage/state checks before deletion. Catalogue deletion does not cascade across databases; later quotation can refuse an unavailable product. No TTL, acknowledgement-based pruning or retained CartItem history is needed.
5. **Resources, progress and complete publication commit together.** [materializeCommandTx](../../../packages/system-worker/src/AggregateVersionRepo/materializeCommandTx.ts#L14-L43) owns the synchronous transaction; [executeAggregateCommandTx](../../../packages/system-worker/src/AggregateVersionRepo/utils/executeAggregateCommandTx.ts#L38-L66) supplies the rollback savepoint. [applyAggregateOperationsTx](../../../packages/system-worker/src/AggregateVersionRepo/utils/applyAggregateOperationsTx.ts#L21-L48) preserves operationIndex/order and applies finalizedAt to row timestamps. [retainEvaluatedCommandTx](../../../packages/system-worker/src/AggregateVersionRepo/utils/retainEvaluatedCommandTx.ts#L9-L40) commits complete pending publication and materializationHead with resource changes. Original retry recovers committed output; replay suppresses external re-emission. Outbox acknowledgement does not delete editable cart lines.
6. **Optimism does not add another CartItem history owner.** Existing staging captures generic mutation inverses; updates retain prior attributes/timestamp and deletes retain a complete resource. [installAggregateNodeView](../../../packages/core/src/aggregateSession/installAggregateNodeView.ts#L94-L121) replaces the old resource graph and clears obsolete inverse data, then [replays uncovered originals](../../../packages/core/src/aggregateSession/replayLocalAggregateCommandsTx.ts#L28-L47). Those are dependency boundaries, not additional completed storage reviews or implementation verification. The [Actor exposure/selection](../../../examples/shopping/src/zerospin/aggregates/user/actors/userActorV1.ts#L29-L34) and [shopper declaration](../../../examples/shopping/src/zerospin/shopperSessionRelease.ts#L21-L31) preserve the current model's public resource surface.

## Recommended declarative invariant and reviewer reconciliation

Declare **UNIQUE(cartId, productId)** with the existing Model indexes facility. [addToCartV1](../../../examples/shopping/src/zerospin/aggregates/user/contracts/addToCartV1.ts#L54-L85) treats a Product as one line and merges its quantity; [ProductCard](../../../examples/shopping/src/components/ProductCard.tsx#L31-L38) also chooses the first matching line. The current schema permits two distinct IDs with the same pair, which would make those first-match assumptions ambiguous. The proposed constraint states the actual model rule directly; it is not a performance index justified by an invented workload. Existing [unique-index construction](../../../packages/shapes/src/primitiveMaps.ts#L307-L323) supports it without new framework machinery. Do not make productId globally unique: different Carts may contain the same Product.

Both reviewers agree that the sole current creator preserves this invariant from valid state, so no ordinary-path duplicate corruption is established. The lifecycle reviewer confirms that uniqueness contradicts no valid flow: remove/paid deletion frees the pair, later readdition can use a new resource ID, and resource-graph replacement followed by reevaluation merges against the installed canonical line rather than retaining two prior optimistic created IDs. Keep canonical id alongside this natural uniqueness rule.

Both reviewers also support amount→quantity, retaining the other seven meanings and the existing preview/quote authority split. A later approved implementation should update the Model declaration, existing add/update payloads, operation bodies and direct UI/checkout/payment consumers together, with no alias or dual decoder. Changed model/payload/retained-operation formats require an explicit empty-affected-storage cutover; this review performs no reset, migration or implementation. No extra state, history, version field, cache refresh process or cross-owner query layer is recommended.
