# Shopping user AggregateVersionRepo.cart

**Reviewed:** 2026-10-17 against current source, with independent lifecycle and column-design reviewers. Exactly the source AggregateVersionRepo.cart ownership context is reviewed. CartItem, Purchase and projection/Node/replica storage are dependencies, not additional completed reviews. All verification remains deferred, including Plan 236 implementation verification.

**Verdict: retain the table and all four stored columns.** Cart is a stable authored business resource: it owns the relationship to its items and selects the Purchase associated with its latest checkout attempt. No schema, naming or lifecycle cleanup is recommended. In particular, checkoutPurchaseId is not a pending-only lock and must not be cleared merely because checkout settles.

**Plan 239 follow-up (2026-10-17):** Approved [Plan 239](../../archive/plans/239-plan-shopping-promotion-reservations.md) extends Cart to **five SQL fields**, adding nullable promotion beside the retained four fields. The one current promotion context is `{ reservationId, action: 'apply' | 'remove', requestState: 'pending' | 'succeeded' | 'failed' }`. Apply selects; Remove clears selection while retaining cancellation identity/progress. Service allocation/status/deadline remain independent facts, observed through an authenticated zero-command Service session. Exact checkout selection and stale-continuation checks preserve Cart/Purchase association. No application-history table, Service Model in the Aggregate map or custom codec is introduced. Implementation is written and explicitly unverified; the original four-column review below remains historical and does not validate Plan 239.

## Ownership and representation

[userAggregateReleaseV1](../../../examples/shopping/src/zerospin/aggregates/user/userAggregateReleaseV1.ts#L18-L27) binds cart@1.0.0 under user@1.0.0. [CartV1](../../../examples/shopping/src/zerospin/aggregates/user/models/cart/CartV1.ts#L5-L18) declares the crt-prefixed resource and its single authored attribute, checkoutPurchaseId. The physical AggregateVersionRepo key is `(systemId, aggregateName='user', aggregateId, aggregateVersion=1)`. [Release resolution](../../../packages/system-worker/src/AggregateVersionRepo/AggregateVersionRepo.ts#L60-L85) and [generic model composition](../../../packages/core/src/drizzle/make/makeDbConfig/makeDbConfig.ts#L29-L44) place its model table beside the Repo's materialization checkpoint and complete pending evaluated-command publication.

Current [Model construction](../../../packages/core/src/models/make/makeModelVersion.ts#L331-L397) uses Plan 236's common row format: id, createdAt, updatedAt and authored attributes. Cart has **four SQL fields** and **six full resource-envelope fields**; bound modelName='cart' and version=1 remain in complete resources rather than SQL rows. [Plan 236](../../archive/plans/236-plan-model-rows-and-resource-envelopes.md) is written/unverified. This review reads the current representation without verifying that implementation or reopening its agreed design.

One row is current resource state. It is neither command history nor a checkpoint, delivery message or durable lock record. Removing Cart would require replacing its resource identity, item-parent relationship and selected checkout association elsewhere; it would not eliminate those domain facts.

[CartV1](../../../examples/shopping/src/zerospin/aggregates/user/models/cart/CartV1.ts#L8-L17) declares no defaults, secondary indexes, TTL or SQL CHECK constraints. checkoutPurchaseId is the only nullable field; addToCartV1 supplies null explicitly rather than relying on a default. Its unique concrete foreign key enforces at most one Cart per nonnull Purchase association and gives the reverse relation its one-to-one meaning. It **does not enforce one Cart per user Aggregate**; multiple null associations are not a singleton constraint. The reference uses ordinary NO ACTION deletion/update behavior, not a cascade. [Primitive mapping](../../../packages/shapes/src/primitiveMaps.ts#L178-L255) and [foreign-key compilation](../../../packages/core/src/drizzle/definition/compileSqliteTableDefinition.ts#L43-L53) retain those semantics.

There are no JSON or other structured column members. `items`, `checkoutPurchase` and `checkoutCart` are derived relations, not extra stored columns. No second lock/state column, copied Purchase outcome, latest-command ID, expiry or item count is justified.

## Lifecycle, coupled state and deletion

1. **First addition creates the Cart; later additions reuse it.** [addToCartV1](../../../examples/shopping/src/zerospin/aggregates/user/contracts/addToCartV1.ts#L39-L86) reads the existing Cart and items, checks the linked Purchase state and quantity, and creates Cart only when absent. The authoritative AggregateVersionRepo transaction serializes this read/create, so another normal first-add command sees the committed Cart. Removing all items leaves the Cart. No authored deleteCart path was found in the reviewed release.
2. **One Cart is an authored invariant, not a SQL singleton.** addToCartV1 is the sole Cart creator and no reviewed command creates another Cart while one exists. ProductCard, ShoppingCartSidebar and CheckoutButton use unfiltered findFirst accordingly. If a future writer or unsupported imported state creates several Carts, that selection becomes ambiguous; this is a boundary to preserve, not evidence of a reachable current duplicate-Cart defect. No new singleton column or schema framework is recommended.
3. **The Purchase supplies locking.** [addToCartV1](../../../examples/shopping/src/zerospin/aggregates/user/contracts/addToCartV1.ts#L44-L52), [removeFromCartV1](../../../examples/shopping/src/zerospin/aggregates/user/contracts/removeFromCartV1.ts#L26-L47), [updateCartItemQuantityV1](../../../examples/shopping/src/zerospin/aggregates/user/contracts/updateCartItemQuantityV1.ts#L32-L60) and [checkoutV1](../../../examples/shopping/src/zerospin/aggregates/user/contracts/checkoutV1.ts#L44-L79) refuse edits/new checkout while the associated Purchase is preparing, pending or needs_reconciliation. Paid, declined and refused allow reuse. Pending external-request membership cannot replace this rule: admission/dispatch progress and Purchase settlement are different facts.
4. **Checkout atomically selects a fresh attempt.** [checkoutV1](../../../examples/shopping/src/zerospin/aggregates/user/contracts/checkoutV1.ts#L44-L118) selects the requested Cart, rejects a missing/locked/empty/invalid one and a reused Purchase ID, creates Purchase and its frozen lines, then sets checkoutPurchaseId. [checkoutServerV1](../../../examples/shopping/src/zerospin/aggregates/user/contracts/checkoutServerV1.ts#L21-L44) records those operations and the frozen quotation request together. The pointer is explicit current selection among retained Purchases; timestamps are not a unique replacement association.
5. **Quotation/payment preserve exact continuation identity.** [getExternalPurchaseQuoteV1](../../../examples/shopping/src/zerospin/aggregates/user/contracts/getExternalPurchaseQuoteV1.ts#L84-L164) requires the exact Cart, matching checkoutPurchaseId and a preparing Purchase. A refused quote changes Purchase to refused, unlocking edits without erasing the result association. A valid quote advances Purchase to pending and records payment. [processExternalPaymentV1](../../../examples/shopping/src/zerospin/aggregates/user/contracts/processExternalPaymentV1.ts#L49-L105) finds the Cart by its unique checkoutPurchaseId and requires pending state, exact amount/key and frozen item correspondence. An uncertain external result changes Purchase to needs_reconciliation; paid changes Purchase and deletes CartItems only. Old observations fail link/state checks before they can clear items belonging to a newer attempt.
6. **The terminal link has a current reader.** [CheckoutButton](../../../examples/shopping/src/components/CheckoutButton.tsx#L14-L33) queries the associated Purchase and renders both unresolved and terminal statuses. [ProductCard](../../../examples/shopping/src/components/ProductCard.tsx#L31-L38) and [ShoppingCartSidebar](../../../examples/shopping/src/components/ShoppingCartSidebar.tsx#L17-L25) query Cart with its items and checkout association. Later item edits do not clear checkoutPurchaseId: it continues identifying the latest checkout attempt until replaced. Its paid status does not prove newly added items were purchased. A pending-only pointer would discard the selected terminal result or require replacement state; no such redesign is warranted here.
7. **Materialization and recovery retain their boundaries.** [materializeCommandTx](../../../packages/system-worker/src/AggregateVersionRepo/materializeCommandTx.ts#L14-L43) owns the synchronous resource transaction; [executeAggregateCommandTx](../../../packages/system-worker/src/AggregateVersionRepo/utils/executeAggregateCommandTx.ts#L38-L66) supplies rollback around evaluation/application. Cart/link/item/Purchase mutations commit with [complete pending publication and materializationHead](../../../packages/system-worker/src/AggregateVersionRepo/utils/retainEvaluatedCommandTx.ts#L9-L40). The [resource application step](../../../packages/system-worker/src/AggregateVersionRepo/utils/applyAggregateOperationsTx.ts#L21-L48) preserves operationIndex/order and uses finalizedAt for model timestamps. Original retry [recovers committed output](../../../packages/system-worker/src/AggregateVersionRepo/finalizeCommand/finalizeCommand.ts#L56-L108); [replay preparation](../../../packages/system-worker/src/AggregateVersionRepo/utils/prepareAggregateOutput.ts#L25-L30) suppresses external re-emission. Publication acknowledgement removes pending messages, not Cart. No network request belongs inside the synchronous resource transaction.
8. **Retention follows the Cart resource.** The Cart remains after emptying, failed checkout and paid checkout. No current expiry, acknowledgement-based deletion or retirement policy exists. Retaining earlier Purchase resources does not turn Cart into command history: checkout replaces its single selected association, while those Purchases retain their own business state. A future deletion design must address CartItem and Purchase references explicitly; this review adds no cleanup mechanism.

## Reviewer reconciliation and limits

Both independent reviewers retain all four fields and the existing checkoutPurchaseId name. They agree that the terminal association is necessary for query-rendered result selection, the lock derives from Purchase state, and current single-Cart behavior comes from the sole authored creator rather than a SQL uniqueness claim. updatedAt is precisely the Cart-row timestamp. No ordinary supported-path lifecycle defect or additional implementation task was established. Existing machinery and ADRs supplied context rather than constraining this verdict.

Only this finding and Plan 151 change. Earlier uncommitted PurchaseItem review documentation is preserved. No implementation, tests, fixtures, runners, configuration, storage reset, migration, deployment or data deletion is authorized or performed.
