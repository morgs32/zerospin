# AggregateVersionRepo.materializationHead

**Updated:** 2026-10-15. The current table is materializationHead; the earlier checkpoint and hash simplification was implemented in [Plan 197](../../archive/plans/197-plan-materialization-checkpoint-and-disposition-chain-hash.md).

## Current result

AggregateVersionRepo's local table and schema property are `materializationHead`. The row contains exactly:

```ts
const head = { singletonId: 1, aggregateIndex, dispositionChainHash };
```

The unused checkpoint `commandId` is removed from storage, writes, selections and genesis. Complete execution packets and immutable admitted input continue to retain command identity and validate duplicate association. The absent-row helper returns `{ aggregateIndex: 0, dispositionChainHash: genesisDispositionChainHash() }`. The constant singleton key, local contiguous progress and synchronous resource/checkpoint/publication transaction remain intact. AggregateActorVersionRepo and AggregateAgentVersionRepo use that same row shape. ServiceVersionRepo and ServiceActorVersionRepo now use materializationHead with singletonId, serviceIndex and dispositionChainHash; no local head retains commandId. These names do not change historical Chain checkpoint APIs, which can read arbitrary retained positions.

The shared protocol now names the hash `dispositionChainHash`. Both server families and browser/standalone implementations use the same exact preimage:

```ts
[previousHash, index, commandId, commandOutcome._tag];
```

Only the outcome's Success/Failure tag contributes. Success values, failure codes/details, timestamps, payload and operation bodies do not. Matching hashes therefore do not prove complete output equality; release-local packet and retained-input comparisons remain required. Concurrent Aggregate-only simplification stores exact original `commandOutcome` on AggregateChain commands; AVC still compares complete packets, while ServiceChain retains full original packets. This checkpoint change does not alter those responsibilities. Changed fixed schemas and chain preimages require empty affected storage; no storage was reset or translated.

### Verdict

**Remove `commandId`; retain `singletonId`, `aggregateIndex` and `dispositionHash`.** Current production code writes the latest command ID and selects it in `readAggregateCheckpoint`, but no consumer uses that returned field. Original and replay duplicate recovery validate complete output against AggregateChain's immutable admitted input. The latest checkpoint ID supplies neither that proof nor the next hash input.

The checkpoint itself is necessary. It records what this AggregateVersionRepo has committed locally, independently of AggregateChain retaining original execution or AggregateVersionChain retaining publication. Complete output now has the Plan 195 ownership split; it does not replace local resource progress. No lifecycle correctness defect was found in the reviewed paths.

### Row meaning, physical scope and lifecycle

One physical database belongs to one AggregateVersionRepo identified by `systemId / aggregateId / aggregateName / aggregateVersion`. Its `executionCheckpoint` table has at most one row under current writers, keyed by `singletonId = 1`. It represents the greatest contiguous aggregate position whose occurrence this release has committed, including successful resource application, no-op success and retained public refusal. This is a **materialization checkpoint**, not retained execution history, a pending message, subscriber acknowledgement or delivery diagnostics. [Physical owner](../../../packages/system-worker/src/AggregateVersionRepo/aggregateVersionRepoName.ts#L6-L12), [table declaration](../../../packages/system-worker/src/AggregateVersionRepo/aggregateVersionRepoDbConfig.ts), [single upsert writer](../../../packages/system-worker/src/AggregateVersionRepo/utils/retainEvaluatedCommandTx.ts).

Before the first local occurrence, no checkpoint row exists. `readAggregateCheckpoint` synthesizes `{ aggregateIndex: 0, commandId: null, dispositionHash: genesisDispositionHash() }`; this null is a helper result, not a nullable stored ID. Each committed occurrence inserts or replaces the same singleton. No checkpoint deletion path exists. Acknowledging either pending output deletes only that delivery's row, leaving materialization progress intact. Deleting or resetting this checkpoint independently of its resource database would lose the resource/position association and is not a supported lifecycle. [Absent-row read](../../../packages/system-worker/src/AggregateVersionRepo/readAggregateMaterializationHead.ts), [pending-message acknowledgement](../../../packages/system-worker/src/makeOutboxQueue/makeOutboxQueue.ts#L213-L225).

The current table has exactly four primitive columns, all non-null. There are no structured subfields, model metadata columns, framework timestamps or additional domain row identifiers. Shape compilation maps the declared columns directly to SQLite; the integer primary key supplies the row key rather than a second generated ID. SQL does not constrain the primary-key value to `1`; current writes and reads establish that convention. This review found no additional writer or corruption evidence warranting a new constraint or status field. [Column compilation](../../../packages/shapes/src/primitiveMaps.ts#L40-L53), [table construction](../../../packages/shapes/src/primitiveMaps.ts#L302-L305).

### Recorded finding: `commandId` has no checkpoint responsibility

The complete production read chain was traced, rather than treating a selected field as a consumer:

1. `retainAggregateResultTx` writes `command.id`; `readAggregateCheckpoint` selects it with the index and hash.
2. `readAggregateOccurrenceTx`, `finalizeCommand` and the replay subscriber consume `aggregateIndex`. Finalization consumes `occurrence.checkpoint.dispositionHash` and the **current** admitted command's `id`. None consumes `checkpoint.commandId`.
3. A committed original recovers the complete `aggregateChainOutbox` packet, then AggregateChain's immutable original execution after pending deletion. `validateCommandIdentity` compares that packet and any delivered command against AggregateChain's authoritative admitted input.
4. A duplicate replay recovers pending AVC publication or permanent AVC history and uses the same input-association checks. No checkpoint ID participates. An unavailable or missing packet fails explicitly; keeping the latest ID would not recover its outcome, operations, authority or older command identity.

[Complete original recovery](../../../packages/system-worker/src/AggregateVersionRepo/readEvaluatedCommand/readEvaluatedCommand.ts#L31-L68), [release-local result recovery](../../../packages/system-worker/src/AggregateVersionRepo/readEvaluatedCommand/readEvaluatedCommand.ts#L31-L68), [authoritative input comparison](../../../packages/system-worker/src/AggregateVersionRepo/validateCommandIdentity.ts).

Generic table inspection and existing verification assertions can display the stored ID. That proves visibility of the redundant copy, not a materialization or recovery requirement. Exact command IDs remain in admitted history and complete retained execution packets. The recommended stored row is therefore:

```ts
const checkpoint = { singletonId: 1, aggregateIndex, dispositionHash };
```

The absent-row result would become `{ aggregateIndex: 0, dispositionHash: genesisDispositionHash() }`. A later scoped implementation should remove the column, its write, its selection and its unused genesis field together, then update affected existing representation assertions. It should not move the ID into another checkpoint field, alias or local history. Changed fixed schemas require empty affected storage; this review authorizes neither that implementation nor a reset. Service's separately owned checkpoint is not reviewed or changed by analogy.

### Transactions, ordering and recovery

1. **One local commit owns progress.** `materializeCommandTx` reads/validates the occurrence, evaluates its release's program, finalizes the outcome/hash and retains output in one synchronous outer transaction. Original execution commits resources/refusal, the checkpoint and both complete pending output packets; replay commits local progress and AVC publication without an original-output message. An output encoding/insertion failure rolls back the whole transaction, including an earlier checkpoint upsert. [Outer transaction](../../../packages/system-worker/src/AggregateVersionRepo/materializeCommandTx.ts), [output/checkpoint retention](../../../packages/system-worker/src/AggregateVersionRepo/utils/retainEvaluatedCommandTx.ts).
2. **Refusal is processed progress.** Business execution uses a savepoint. A recognized public refusal rolls back resource effects before finalization advances the checkpoint with empty operation arrays. Infrastructure failures, unclassified defects and compound Causes propagate and commit no false checkpoint. Thus the greatest resource-row timestamp or greatest successful write cannot replace `aggregateIndex`. [Savepoint and failure handling](../../../packages/system-worker/src/AggregateVersionRepo/utils/executeAggregateCommandTx.ts#L38-L137), [empty refusal output](../../../packages/system-worker/src/AggregateVersionRepo/materializeCommandTx.ts), [synchronous rollback](../../../packages/core/src/drizzle/make/makeTx.ts#L69-L118).
3. **Execution order is local and contiguous.** Occurrence checks reject wrong owner/original release, pending replay and invalid positions. A fresh occurrence must be exactly checkpoint + 1; an earlier position is not evaluated again. Original finalization catches up through N−1 outside the permit, then rechecks progress under the permit before fresh declaration lookup and execution. Concurrent progress leaves the permit and recovers committed output. Identity/history RPCs remain outside SQL and execution permits. [Occurrence checks](../../../packages/system-worker/src/AggregateVersionRepo/utils/readAggregateCommandTx.ts#L28-L50), [original orchestration](../../../packages/system-worker/src/AggregateVersionRepo/finalizeCommand/finalizeCommand.ts#L56-L104), [replay duplicate handling](../../../packages/system-worker/src/AggregateVersionRepo/replayCommands/replayCommand.ts#L37-L54).
4. **Output delivery does not determine materialization.** AggregateChain can still lack original execution N when AggregateVersionRepo has already committed N and its checkpoint. Either publication destination can lag; acknowledging/deleting a pending packet never erases local progress. Original duplicate recovery uses complete original output; replay-result recovery uses that release's model output. Neither uses checkpoint `commandId` as a substitute for retained evidence. [Original recovery](../../../packages/system-worker/src/AggregateVersionRepo/readEvaluatedCommand/readEvaluatedCommand.ts#L31-L68), [replay recovery](../../../packages/system-worker/src/AggregateVersionRepo/readEvaluatedCommand/readEvaluatedCommand.ts#L31-L68).
5. **Activation preserves committed progress.** AggregateVersionRepo arms both output queues before fixed-prefix catch-up. The replay subscriber supplies the actual local index. Catch-up accepts a local checkpoint at or beyond the captured finalized prefix without rewinding resources or forcing a pending original reply. Checkpoint 10 with AggregateChain finalized prefix 9 is valid. Partial startup progress remains durable across interruption; later retry resumes from it. [Activation](../../../packages/system-worker/src/AggregateVersionRepo/AggregateVersionRepo.ts#L276-L282), [local subscriber index](../../../packages/system-worker/src/AggregateVersionRepo/replayCommandsFanoutSubscriber/replayCommandsFanoutSubscriber.ts#L66-L67), [fixed-prefix catch-up](../../../packages/system-worker/src/makeFanoutSubscriber/runFanoutCatchup.ts#L38-L68), [settled activation case](../../archive/plans/192-plan-activation-materialization-catchup.md#2-settled-semantics).
