## Physical owner and represented fact

One ServiceActorVersionRepo fixes `{ systemId, serviceName, serviceVersion, actorName, actorVersion, actorPath }`. Configuration resolves that exact Service release and actor view, then composes the release's resource graph with this projection infrastructure. Full resource composition supports relational selections and declared `where.RAW` dependencies; browser exposure remains selected and separately authorized.

One row in slot `1` means this exact actor projection has incorporated the contiguous source-command prefix through `serviceIndex` into its local resources, with the corresponding Service disposition prefix. This is **mutable checkpoint state committed with resources**, not admitted input, per-command history, pending delivery, subscriber acknowledgement or retained private completion. The head is overwritten as progress advances; it does not preserve prior rows.

Owner identity is fixed by the physical database and needs no repeated columns. Node/session/full historical claims, command ID, outcome and timestamps describe other responsibilities and do not define another materialized resource partition here.

### Absence and disposition-hash semantics

There is no eagerly seeded genesis row. Before the first committed source position, absent slot `1` means virtual `{ serviceIndex: 0, dispositionChainHash: genesisDispositionChainHash() }`. The subscriber reports zero, and snapshot/application use the same Service genesis: SHA-256 of `zerospin.service.disposition.v1`. This is initial empty-materialization semantics, not nullable columns, a SQL default or a compatibility repair after deleting a head while retaining resources. A later empty selected graph does not imply genesis.

The hash extends SHA-256 over `[previousHash, serviceIndex, commandId, outcome.result._tag]`. It identifies the Service release's source disposition prefix consumed by this projection. ServiceActorVersionRepo applies recorded output; it does not independently evaluate command programs or choose another result. The hash excludes Success/Failure contents, operation bodies, Origin and `outcome.finalizedAt`; it is not a resource checksum or complete-output digest.

For each new position the projection recomputes and compares the next hash before committing. Already committed positions are prepared/validated and then skipped using the local cursor; this head does not retain enough history to compare every old command body. Immutable complete ServiceVersionChain commands own that identity/equality responsibility. Do not add command history to the resource owner to duplicate it.

## Synchronous application, acknowledgement and recovery

1. Activation arms selected-publication recovery and awaits the source-bound subscriber's catch-up/enrollment before incoming requests run. Catch-up fixes one source prefix, rereads actual local progress after receiving pages/concurrent pushes and reports this head when enrolling. It does not report an advertised source tip as committed progress.
2. The application wrapper resolves the exact Service release before the transaction. `applyEvaluatedCommandsTx` resolves the actor identity and delegates to `applyServiceProjectionCommandsTx`, which reads head/resources and prepares each complete input against exact release/model/producer rules. It restores model command attribution from the parent and applies recorded `outcome.finalizedAt`; external descriptions do not execute here.
3. A position at or below the local cursor skips resource/outbox/head writes. A new position must equal `cursor + 1` and extend the retained hash correctly. Model mutations, selected graph/delta, complete pending selected publication and the updated head commit in the same synchronous page transaction.
4. Failure with no operations, no-op Success and unchanged selected graphs still produce one pending selected publication and advance the head. A later validation, mutation, encoding or SQL failure rolls back all new resource/outbox/head writes in that page. A partially applied page does not establish a new checkpoint.
5. Receiving application acquires publication recovery before the transaction and schedules selected delivery afterward. Its successful source receipt proves the ServiceActorVersionRepo resource/head/pending-publication commit. ServiceVersionChain then advances its separate `acknowledgedServiceIndex`; a lost reply can leave that acknowledgement behind this head. Redelivery skips already committed positions without reapplying resources or duplicating pending output.
6. ServiceActorVersionChain publication has its own acknowledgement. It deletes complete pending outbox rows after durable selected-history retention, never this head. Publication can lag local materialization independently of source acknowledgement. A socket failure cannot undo the local projection or the receiving Chain's retained output.

These boundaries require a local head even though permanent source commands and selected history exist remotely. Neither remote owner proves that this particular resource graph has incorporated the same prefix, and remote calls do not belong inside the local synchronous application transaction.

## Exact snapshot resources and checkpoint N

The concrete snapshot consumer is a separate reason to retain the paired position/hash locally:

1. `captureServiceSnapshot` validates the admitted ServiceSessionLock, exact actor/version/session, canonical actor identity claims and the full authored claims codec. The head contains no permission or private-resolution fields.
2. One synchronous local transaction reads this head `(N, hashN)` and selected resources, filtered by the admitted lock's models. They describe the same committed resource graph.
3. Outside SQL, `publishThrough(N)` drains pending selected publication through the captured position. The exact ServiceActorVersionChain checkpoint requested at `N` must match both captured `serviceIndex` and hash. A newer Chain tip or later acknowledgement cannot relabel the captured resources.
4. Private completion recovery uses the exact actor/version, Node, session, full claims and admitted models, bounded by `throughServiceIndex: N`. It supplies `resolvedThrough` separately; neither local materialization nor source acknowledgement implies that private completion prefix.

The head is not itself proof of authorization or Chain publication. It supplies the stable local boundary that those independent checks compare. Removing its hash would lose exact prefix comparison; removing its position would lose the resource/history/private-recovery bound.

## Retention and reconciled finding

Retain the head for the lifetime of this exact materialized resource view, including after source acknowledgement and pending publication drain. There is no supported delete, expiry or reset path. Deleting/rewinding it while retaining resources removes the atomic progress proof and can allow incorrect reapplication or break continuity/snapshots. No timestamp, admitted command ID, outcome, authority copy, publication cursor or retained history belongs here.

Both independent reviewers support retaining all three fields/current names and synchronous boundaries.
