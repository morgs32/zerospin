# AggregateAgentNodeRepo.materializationHead

**Reviewed:** 2026-10-21 against current uncommitted source, with independent lifecycle and column-design reviewers. This finding covers exactly AANR's physical occurrence. The earlier [SANR head finding](service-agent-node-repo-materialization-head.md) supplies shared-runtime context, not approval of this owner.

**Verdict: retain `aggregateVersion`, `aggregateIndex` and `dispositionChainHash`, with current guarded singleton handling.** They identify the applied release, actual local Aggregate progress and current disposition-prefix witness. An absent head is uninitialized; a present matching head at index zero is initialized. No supported-path lifecycle defect, redundant column or justified schema change was found.

**Review queue:** [Plan 151](../../plans/151-plan-storage-table-review.md). This is source review, not new runtime verification.

## Physical owner and represented fact

AggregateAgentNodeRepo is an unversioned MigratableDO identified by `(systemId, aggregateName, aggregateId, agentName)`. Its optional single head records the Aggregate release and contiguous public Aggregate position represented by that instance's selected materialization and reconciled wakes. It is a **materialization checkpoint**. Retained public history belongs to AggregateAgentVersionChain; this row is neither that history nor source delivery acknowledgement, automatic producer progress, command admission or execution completion.

Aggregate instance identity is already in the physical key. Adding `aggregateId`, `aggregateName`, `agentName` or `systemId` to the row would repeat it. The applied release is deliberately absent from the key and can differ from the currently desired Agent pin, so it must remain durable in the head.

## Every column and schema rule

The table has exactly three required columns, without defaults: two INTEGERs and one TEXT. There are no structured subfields, declared primary key, foreign key, unique constraint, secondary index, synthesized ID or timestamp. These primitive declarations supply NOT NULL, not SQL checks for positive releases, safe positions or hash format. Supported writers obtain domain values from the bound source protocol.

## Singleton, transaction and Aggregate source boundaries

1. **Guarded optional singleton:** `readHead` reads all rows from the actual DB/transaction. It returns absence or one row and rejects multiple rows with `agent-node-checkpoint-ambiguous`. The only writer deletes and inserts one complete replacement inside a synchronous transaction. Both callers read the existing head before mutation. No supported path exposes the intermediate deletion, creates duplicate heads or silently repairs ambiguous storage. No SQL key is required by the current access pattern.
2. **Coherent Aggregate baseline:** AANR adds its desired `aggregateVersion` to the full physical source key and calls that AggregateAgentVersionRepo. Snapshot capture validates bound Aggregate instance, Agent Origin and session; reads selected resources/checkpoint synchronously; publishes through the captured `aggregateIndex`; then requests that exact public Chain checkpoint. `getCheckpoint` enforces the requested index through zero-genesis handling or exact SQL lookup. Snapshot capture compares the returned hash. It does not explicitly compare the returned index again or read private Agent completion state.
3. **Installation and reconstruction:** With no head, AANR installs selected resources, head and reconciled wakes in one transaction. A present matching head at index zero is already initialized and survives reconstruction without resetting attempts. Missing metadata is not equivalent to a successfully installed position-zero resource set. No independent head deletion or TTL exists.
4. **Selected pages:** AANR fences the complete source tuple, including Aggregate instance and release. Receipt checks desired and applied release, validates the page, skips older positions, checks a repeated current position's hash and rejects gaps. Selected deletions/upserts, wake reconciliation and the resulting head commit together. Failed application rolls them all back. `lastIndex` does not advance local progress past the last processed row.
5. **Due commands and rebinding:** The alarm pass requires a present matching head before catch-up and due-command freezing. Attempt/outbox insertion does not itself advance `aggregateIndex`. Pending delivery blocks a changed pin before baseline capture or mutation; delivery drains under the old pin. A later installation replaces selected resources/head/wakes atomically and preserves matching attempted markers. Source progress is contiguous within one pin; replacement installs another source-bound baseline. Previous-source pages cannot update it.
6. **Independent acknowledgements:** For a matching pin, `getCurrentIndex` reports the actual durable `aggregateIndex`; absence or another pin reports zero without creating a head. Subscription catches up and rereads that cursor for enrollment. AggregateAgentVersionChain advances its acknowledgement after successful Node delivery and may lag when a reply is lost. Canonical command admission acknowledgement only permits deletion of its pending delivery row; neither acknowledgement advances or deletes this materialization head. Public Chain history remains retained.

The no-key representation has explicit reader/writer invariants. Adding a constant column merely to support another write shape is not justified by an observed lifecycle defect. The head must not be deleted independently of its selected materialization or reconstructed from a remote acknowledgement before a local transaction.

## Hash scope and reconciled disposition

Both independent reviewers recommend retaining the three fields and current singleton handling after checking AANR's actual Aggregate snapshot and instance-bound source paths. The hash claim remains narrow: AANR copies a source witness and compares only an overlapping row at the current position. Older hashes are ignored; new hashes are not recomputed. Catch-up/enrollment sends the index without this hash, and an empty catch-up does not compare remote/local checkpoint hashes.

The hash preimage covers previous hash, Aggregate position, command ID and `outcome.result._tag`. It does not cover resource deltas, payload, successful result values, failure details or timestamps. Matching hashes therefore do not establish equality of those contents. The stored witness preserves the existing current-position conflict refusal; it is not full materialization-integrity, enrollment or execution-completion proof. Obtaining it from remote history on every read would introduce another dependency into local checkpoint handling, without removing the local atomicity requirement.

No new key/index, hash protocol, historical checkpoint table, producer state or compatibility path is recommended. Other Agent table occurrences retain their own review status.
