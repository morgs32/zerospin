## Physical owner and represented fact

One ServiceChain fixes `{ systemId, serviceName }`; it is not bound to one Service release. It owns admitted commands, their first original `outcome` and complete pending external requests. ServiceVersionRepo owns release resources/evaluation and pending publication; ServiceVersionChain owns complete immutable release-local output. This table contains no materialized resource or retained operation history.

One row means: this original committed command emitted a frozen invocation whose external observation has not yet been admitted as its stable-ID Service command. It is **complete pending delivery/request state**, not immutable history, a subscriber cursor or a request-execution audit. Row existence itself supplies the pending fact; there is no separate status/attempt/acknowledgement column.

The name `externalOperationOutbox` remains appropriate. It does not promise FIFO execution or a second external-command delivery stage. Multiple pending invocations run independently; their admitted observations receive Service positions when their local settlement transactions commit.

## Original eight-column schema and constraints — before Plan 219

All eight fields in the reviewed pre-Plan-219 schema were required/non-null and have no SQL defaults. No primary key is declared. `externalCommandId` is unique through its descriptor; the explicit `initiating_command_operation` unique index covers `(initiatingCommandId, operationIndex)`. There is no generated ID, time, state, retry counter, acknowledgement or diagnostic column.

The formatted command-ID descriptor supplies required text and uniqueness. It does **not** establish SQL REFERENCES or require the future admitted command to exist before the request. The current declaration uses `primitives.id({ abbreviation: 'cmd', unique: true })`; it remains neither a foreign-key relation nor a primary key.

`recordOriginalCommandOutcomeTx` is the only insertion writer. No supported UPDATE exists. The shared queue scans/decodes the complete row; settlement re-reads and deletes by `externalCommandId`. Merely decoding an unused field does not establish a domain need to persist it.

## Every structured payload and Origin value

`payload` is `Schema.Json`: a JSON scalar, null, array or object with recursively contract-defined values. The fixed table defines no universal nested payload keys to remove or derive. Original preparation validates JSON encoding and exact authored external declaration; execution later validates that frozen value with the declaration's complete portable codec. Preserve every authored payload member.

`ServiceCommandOriginSchema` permits exactly these branches:

| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `kind: 'actor'`                   | Required discriminator for Actor authority. It cannot be inferred from payload or replaced with System authority.                                                                                                                                                          |
| Actor `actorName`, `actorVersion` | Required nonempty exact historical actor declaration identity used by later Service evaluation. The versionless ServiceChain does not fix them.                                                                                                                            |
| Actor `claims`                    | Required complete encoded `Record<string, unknown>`, including arbitrary authored claim keys/values. Its Origin preserves the original authority for later program/continuation evaluation. Full Actor claims are decoded through the exact historical Actor definition. Agent continuations do not repeat permission checks against the currently scheduled Agent definition; a claims-bearing execution contract still refuses Agent authority.

## Creation, original retries and retained operation order

Original Service evaluation enumerates authored operations before selecting model/external members. External preparation validates the exact authored contract object and encoded input, then allocates one external command ID in the original resource transaction. The complete output retains this identity for lost-reply recovery; stable does not mean deterministically calculated from the parent or index.

`recordOriginalCommandOutcomeTx` fully decodes one returned output, matches retained admitted identity/provenance and requires its finalized predecessor. On a first receipt, Failure cannot contain operations and positions must be safe/strictly increasing. One synchronous transaction sets `commands.outcome` and inserts every external invocation. It restores Origin and original Service release from the retained admitted command.

When `commands.outcome` already exists, an exactly equal outcome, including `finalizedAt`, returns before insertion; a conflicting outcome fails. This early guard applies even after requests settled and disappeared. It is intentionally not complete-output comparison: ServiceVersionChain separately retains and compares the immutable output, while ServiceChain does not keep operation history or a disposition hash. Do not replace this with a pending-row existence check, and do not reemit requests because an equal repeated receipt contains different schema-valid operation bodies.

Replay drops external emissions before preparing them or allocating their IDs. Remaining model positions are not renumbered. ServiceVersionChain's shared operations union retains sparse `operationIndex`; parent `commandId` and bound release supply history context. These history/preparation fields stay even if the pending schema drops its unused pair.

## Request execution, recovery and settlement

1. ServiceChain's original-outbox completion hook wakes replay delivery and external work after original receipt retention. Cold activation also wakes the external queue. The original-outbox durable alarm spans receipt and completion-hook work; an empty drain reruns the completion hook to repair commit-before-wake interruption. These hooks remain necessary recovery machinery.
2. `makeExternalOperationQueue.wake` restores its pending-work alarm before scanning. It decodes complete rows and reserves each external ID synchronously before scheduling independent background work. Repeated same-activation wakes cannot overlap that ID; the reservation lasts through request finalizers, local observation recording and alarm reconciliation. No pending order by parent/operation position exists.
3. ServiceChain resolves the retained `serviceVersion`, then exact external name/version. Missing/unsupported definitions or invalid frozen payload are infrastructure failures; they leave pending work for recovery rather than deleting it or selecting newer code. Authored request execution occurs outside SQL and original command permits.
4. Authored timeout/request/response-codec failure becomes an external Failure observation; a usable encoded response becomes external Success, including valid JSON null. Timeout waits for request finalizers. `externalOutcome.recordedAt` is sampled for that observation; it is separate from the parent's `outcome.finalizedAt` and needs no pending-row timestamp.
5. The settlement callback acquires `executeCommandOutbox.producerLease`, then `recordExternalOutcomeAndAdmitCommandTx` re-reads the pending row by stable external ID. Missing row returns without change. A present row constructs the external command from the retained invocation plus the observation, gives it the next `serviceIndex` and deletes the request in the same synchronous transaction. Storage/admission failure rolls deletion back.
6. Settlement explicitly runs `executeCommandOutbox.wake()` on producer exit while preserving its result or Cause; it does not await original execution of the newly admitted command. Later callbacks find no pending row and are no-ops. Alarm reconciliation holds recovery while any pending row exists and releases it when none remains.

**Exact deletion condition:** successful local admission of the first committed external observation and its stable-ID command, atomically with removal of the pending request. A remote response alone does not authorize deletion. Neither continuation execution nor retained continuation `outcome`, projection publication, browser receipt or subscriber acknowledgement is required for deletion. No other supported TTL/pruning/UPDATE lifecycle exists.

The external side effect is at least once across a loss before local observation admission. In-memory reservations protect a live activation, not a crashed process. `external.request` receives only `{ payload }`; stable local `externalCommandId` is not automatically a provider idempotency key. Preserve this existing responsibility rather than claiming exactly-once remote effects or adding unused durable in-flight/status/attempt fields.

Observation admission order is local transaction order after recovery hold, not an operation-index or remote-completion ordering guarantee. No second external-command outbox, allocator, reverse acknowledgement RPC or public observation ingress is needed.

## Approved six-column model and scope

Keep unique `externalCommandId`, exact external contract name/version, complete frozen `payload`, full `origin` and original `serviceVersion`. Remove only pending `initiatingCommandId`, pending `operationIndex` and `initiating_command_operation`. Retain all existing original-retry, operation-order, stable-ID, atomic settlement and recovery requirements. Add no column, alternate row state or new queue concept.

Origin and release are technically derivable by keeping the parent ID and joining same-owner retained `commands`. That is a real local alternative, not a remote-history dependency. It would retain an otherwise unused history pointer and introduce parent-query/codec/missing-parent assembly paths. Six complete invocation fields keep the pending row independently executable and remove unused lineage; parent inspection for diagnostics does not justify the extra pending responsibility.

Plan 219 explicitly selects the six fields at receipt instead of spreading an external operation minus only its discriminator. It updates the Service table-owned pending codec, writer, relevant existing assertions and governing ADR clauses/consumers. The shared queue already requires only invocation ID/name/version/payload; no new generic queue mode is justified. Preserve preparation and retained-history lineage/positions. Aggregate/Actor/Agent and other Service storage remain outside this proposal.
