# AggregateAgentNodeRepo.selectedResources

**Reviewed:** 2026-10-21 against current uncommitted source, with independent lifecycle and column-design reviewers. This finding covers exactly AANR's physical occurrence. The earlier [SANR finding](service-agent-node-repo-selected-resources.md) supplies related reasoning, not approval of this owner.

**Verdict: retain the three-column fixed selected materialization.** AANR needs complete local resource contents to reconcile wakes and freeze command input synchronously with its checkpoint. Its Aggregate-specific snapshot, source identity and pin-change paths support that responsibility. Envelope identity duplication is real; removing it does not justify new schema-transition or reconstruction machinery. No supported-path lifecycle defect or schema change was identified.

**Review queue:** [Plan 151](../../plans/151-plan-storage-table-review.md). Source review completion does not claim new runtime verification.

## Physical owner and represented fact

AggregateAgentNodeRepo is an unversioned MigratableDO identified by `(systemId, aggregateName, aggregateId, agentName)`. One row is one currently selected resource within that Aggregate instance under the applied Aggregate release. This is mutable scheduling resource state. AggregateAgentVersionRepo supplies selected materialization, while AggregateAgentVersionChain owns retained public selected history. AANR does not retain that history here.

The physical key supplies Aggregate instance and Agent identity. It supplies neither the selected Model name nor an individual resource ID: an Aggregate can contain multiple Models and many resources. Conversely, adding `aggregateId`, `aggregateName`, `agentName` or `systemId` to every selected row would duplicate the bound physical scope. The single materialization checkpoint identifies the applied release for the entire selected set; no per-row `aggregateVersion` is needed.

## Every stored field

All three SQL columns are required TEXT, without defaults; `resource` uses the JSON codec. There is one unique index on `(modelName, resourceId)`, no declared primary key or foreign key, and no synthesized timestamp column. SQLite's implicit rowid does not determine scheduling or source progress. Current readers justify the composite uniqueness and no additional index.

## Aggregate-specific source and transaction boundaries

1. **Coherent baseline:** AANR constructs an exact source key by adding the registered `aggregateVersion` to its immutable physical key. It calls that AggregateAgentVersionRepo with bound Aggregate name/ID, Agent Origin, session name and null `nodeId`. Snapshot capture validates the requested instance, Agent and session, synchronously reads resources/checkpoint, publishes through the captured `aggregateIndex` and checks that exact public Chain position's `dispositionChainHash`. It does not obtain private completion state.
2. **Installation and reconstruction:** Without a checkpoint, AANR synchronously installs selected resources, `materializationHead` and reconciled wakes. A present checkpoint, including index zero, establishes initialization. Same-pin reconstruction keeps the current rows and resumes catch-up rather than resetting attempts.
3. **Selected pages:** `nodeFanoutSubscriber` compares every source-key field, including Aggregate instance and release. The runtime also checks the applied release, validates Aggregate pages and requires contiguous `aggregateIndex` progress. Repeated prior positions are skipped; gaps/current-checkpoint conflicts refuse application. Deletions, complete upserts, wake reconciliation and final checkpoint advancement share the page transaction. Failed resource/behavior decoding rolls everything back.
4. **Due processing and selection exit:** The Agent pass catches up before reading local resources and freezing due commands. Attempt marking and frozen delivery insertion share a synchronous transaction. Failed synchronization skips new freezing while frozen invocations remain deliverable. Selection exit deletes resource/wake responsibility together, but leaves those frozen commands independent of selected contents. Their deletion requires exact durable admission acknowledgement, which does not establish execution commit or a retained `outcome`.
5. **Owner-pin change:** Pending delivery obstructs replacement before capture/installation. After old-pin delivery drains, a synchronous baseline replacement installs the new selected set/checkpoint and preserves matching attempted markers through reconciliation. Complete source-key fencing rejects previous-release pages. No per-resource progress, producer sequence, generation, historical copy or TTL is needed here.

Removing the local contents in favor of an alarm-time remote query would lose the synchronous boundary between selected state, checkpoint, wakes and frozen command input. The source can reconstruct the materialization, but reconstruction is not a substitute for the current local transaction. Rows disappear on authoritative selection exit or whole baseline replacement, not on command execution or admission acknowledgement.

## Representation challenge and reconciled disposition

Both independent reviewers recommend retention for this occurrence after checking the Aggregate-specific paths. The repeated SQL/envelope identity is justified by the current fixed scheduling container; it does not establish another independently variable business fact.

Ordinary per-Model tables would remove some envelope repetition, but AANR's physical identity is unversioned. `makeMigratableDORepo` initializes SQL before activation reaches the pending-pin guard. Binding the SQL schema to a replacement Aggregate release could therefore reject or change the old materialization before AANR reports its pending-delivery obstruction. The fixed container supports atomic baseline replacement after drain without introducing that schema-transition responsibility.

Aggregate Agent projection also explicitly sets `requireReferenceClosure: false`; Actor projection sets it true. Both Agent snapshot capture and projected-page generation honor the partial selection. Blindly copying canonical Model foreign keys could reject valid selected rows whose referenced resources were not selected. Per-Model composition is not a declaration-only simplification. A replacement generic attributes bag would instead require another reconstruction format and applied-Model binding, without an existing need to query individual attributes in SQL.

This is a fixed internal scheduling table, not a canonical `model.table` or authored row-query interface. [Plan 236](../../archive/plans/236-plan-model-rows-and-resource-envelopes.md#design) and the [Model-row lifecycle guidance](../../patterns/system-worker/repo-lifecycle.md) still govern Model-bound tables and their complete resource boundaries. Retaining this container does not restore Model identity columns on those tables or create a configurable storage policy.

The `resource` column supplies resource contents; AANR does not canonicalize or compare its bytes for identity, hashing or recovery. The [canonical-bytes prohibition](../../patterns/system-worker/no-canonical-bytes-in-sql.md) remains in force, including its explicit ban on enclosing command serialization. The five-field outbox conclusion does not imply that this resource JSON is the same responsibility. No column removal, rename, new index or ownership change is recommended.
